# 视觉检测设备故障诊断 Agent · 工程清单与技术选型

> 版本：v1（2026-11-14）
> 状态：方案定稿，待第 0 周可行性验证
> 项目代号：`fde-diagnosis-agent`

---

## 0. 一句话定义

操作员用一句话描述视觉检测设备的异常现象，Agent 自主判断该往算法侧还是硬件侧查，调 7 个工具取证，输出可执行的处置方案（结论 + 动作 + 出处 + 是否转人工）。

---

## 1. 业务场景

**产线现状**：CCD 相机 + 环形/条形光源 + 传送带 + 剔除机构，用于外观尺寸检测。日均检测量按产线节拍计。

**真实痛点**：误判率异常升高时，操作员的第一反应是"模型不准了"，把问题推给算法；算法工程师到现场一看，往往是光源衰减或镜头污染。反过来也成立——光源看着正常，实际是模型漂移。

**这个判断错误代价很高**：
- 判成算法问题 → 调阈值/重训模型，浪费 1-2 天，问题还在
- 判成硬件问题 → 停机拆机清洁，白停 2 小时，其实该调阈值

**所以这个场景的核心价值不是"查资料"，是"分流判断"。** 这也是它区别于项目一的地方。

## 2. 已定技术决策

| 项 | 决策 | 理由 |
|---|---|---|
| 设备类型 | 视觉检测设备 | 岔口跨域（AI + 光机电），路径天然发散 |
| 编排 | LangGraph + Checkpointer | 复用项目一的断点恢复经验 |
| 模型 | 先 qwen2.5:7b 验证，按失败率决定是否升 qwen3:8b / API | 6GB 显存是硬约束，14b 不可行 |
| Embedding | **固定 nomic-embed-text（768 维）** | 复用项目一 550 块库，换模型等于全库重建 |
| 数据存储 | PostgreSQL 单库，手册表复用 pgvector | 单库省事，可演示"数据不出门" |
| 手册检索 | 复用项目一 550 块知识库 | 零成本，两项目形成体系 |
| 工具协议 | Python 函数 + Pydantic schema | 最简，MCP 留作扩展 |
| 评测载体 | YAML 存 golden path + Python 跑分出 markdown 表 | 要出报告，不只是绿灯 |
| trace | 自建 JSONL 落盘 | 离线场景不能用 SaaS |
| Web | FastAPI + 单页诊断界面（显示工具调用链） | 演示资产 |
| 写工单 | 独立 FastAPI mock QMS | 复用项目一踩过的集成坑 |

## 3. 数据模型与构造清单

### 3.1 表设计

| 表 | 行数（目标） | 关键字段 |
|---|---|---|
| `devices` | 5 台 | 设备编号、产线、工位、相机型号、镜头型号、光源型号、装机日期、保养周期 |
| `defect_logs` | 800-1200 条 | 时间戳、设备、工位、缺陷类型、判定结果、置信度、物料批次、实际良品标记 |
| `alarms` | 40-60 条字典 + 若干发生记录 | 告警码、含义、常见原因、严重等级 |
| `calibrations` | 每台 5-8 次 | 标定时间、漂移量（px / mm）、结果、操作人 |
| `light_usage` | 每台 1 条累计 + 更换记录 | 光源型号、累计点亮小时、当前亮度设定、更换日期、衰减估算 |
| `manual_chunks` | 复用 550 块 | 手册片段 + 出处（来源文档、页码/章节） |
| `work_orders` | 运行时产生 | 工单号、设备、根因、动作、严重度、幂等键、状态 |

### 3.2 数据真实性要求

- **告警码、参数名、光源/相机型号必须可查**。视觉类参考基恩士（Keyence）、康耐视（Cognex）公开手册；伺服/传送参考汇川。**不得自编不存在的型号或参数值**，面试被追问会露。
- **故障现象描述必须是现场口吻**，例如"三号工位最近老是误判，白天好一点，夜班特别多"。这种句子造不出假的痕迹，是项目最值钱的部分。
- **手册里人工植入 8-10 处参数冲突**（同一参数在不同文档取值不同），供 `check_doc_conflict` 检测。

### 3.3 数据分布设计要求

20 条轨迹要能跑出来，数据必须让每类故障都有**可区分的证据特征**：

| 故障类型 | 关键证据特征（造数据时必须满足） |
|---|---|
| 光源衰减 | `light_usage.cumulative_hours` > 更换周期，且亮度设定被人为下调过 |
| 镜头污染 | 误判率随运行时间单调上升，无告警，标定漂移极小 |
| 标定漂移 | `calibrations.drift_mm` 超阈值，且发生时间与误判起点吻合 |
| 传送带速度 | 节拍参数被改过，误判集中在高速段 |
| 触发异常 | 漏拍比例偶发，与 PLC 触发日志时间吻合 |
| 新物料批次 | 误判集中在同一批次号，颜色/尺寸分布偏移 |
| 阈值过严 | 置信度分布整体下移但硬件指标全正常 |
| 模型漂移 | 长期缓慢上升，无任何硬件指标异常 |
| 训练数据缺失 | 新缺陷类型从未出现在训练集，被误判为已知类型 |

## 4. 七个工具 Schema

```python
# 1. 设备档案
query_device_profile(device_id: str) -> {
    device_id, line, station, camera_model, lens_model,
    light_model, install_date, maintenance_cycle_days
}

# 2. 误判日志（支持聚合，这是判断方向的主证据）
query_defect_log(
    device_id: str,
    time_from: datetime,
    time_to: datetime,
    group_by: Literal["hour", "station", "defect_type", "batch"] = "hour"
) -> {
    total: int,
    false_positive_rate: float,
    groups: [{key, count, rate}],       # 按 group_by 聚合
    samples: [{ts, station, defect_type, confidence, batch, is_actually_ok}]
}

# 3. 标定记录
query_calibration(device_id: str, limit: int = 5) -> {
    records: [{ts, drift_px, drift_mm, result, operator}],
    last_calibration_at, days_since_last, drift_trend
}

# 4. 光源使用
query_light_usage(device_id: str) -> {
    light_model, cumulative_hours, rated_life_hours,
    brightness_set, brightness_history: [{ts, value}],
    last_replaced_at, degradation_estimate
}

# 5. 手册检索（复用项目一 RAG）
search_manual(query: str, top_k: int = 3) -> {
    chunks: [{text, source_doc, page, score}]
}

# 6. 文档冲突检测
check_doc_conflict(param_name: str) -> {
    param_name,
    conflicts: [{doc_a, value_a, doc_b, value_b, likely_authoritative}],
    has_conflict: bool
}

# 7. 建单 / 转派（幂等）
create_work_order(
    device_id: str,
    root_cause: str,
    severity: Literal["low", "medium", "high"],
    actions: list[str],
    evidence_refs: list[str]
) -> {
    order_id, status, deduped: bool,
    assignee_group
}
```

**幂等键设计**：`hash(device_id + 故障时间窗(按天) + root_cause)`。重复调用返回已存在工单，`deduped=True`。

## 5. 动态岔口设计（三层）

这是整个项目的技术核心。**每一层都必须是模型自己判断，不能写成 if-else**。

### L1 信息补全岔口

现象描述缺时间窗 / 工位 / 缺陷类型时，Agent 自主决定"先查日志自己推断"还是"追问操作员"。

**判据（供模型参考，不硬编码）**：
- 有有效 `device_id` → 优先查日志（成本低、数据在库）
- 连设备都指不明 → 追问
- 日志查回来仍然无法定位 → 再追问

### L2 方向判断岔口（核心）

**这是"是不是 workflow"这道题的答案。**

| 证据形态 | 应指向 | 依据 |
|---|---|---|
| 误判集中在**固定工位** | 硬件侧 | 该工位的镜头/光源/标定独立于其他工位 |
| 误判**全工位随机分布** | 算法侧 | 模型和阈值是所有工位共用的 |
| 有明确告警码 | 先查告警含义 | 设备自诊断优先级最高 |
| 光源累计时长超寿命 + 亮度被调低 | 硬件侧（光源） | 衰减的典型特征 |
| 硬件指标全正常 + 置信度分布下移 | 算法侧（阈值） | 无硬件异常证据 |
| 误判集中在**同一物料批次** | 算法侧（数据漂移） | 新物料分布偏移 |

模型必须自己完成这个判断。**同一个现象，两次跑可能给出不同但都合理的路径**——这就是非固定路径的证明。

### L3 证据冲突岔口

查到手册参数冲突（如"光源亮度设定"两份文档分别写 80 和 65）时，**不得自行挑选一个继续用**，必须上报冲突并说明影响。

这条既是能力点（主动发现），也是面试的翻车素材（模型曾选错权威版本导致诊断跑偏）。

## 6. 20 条轨迹 Golden Path

每条轨迹允许**多条合法路径**（表内 `路径` 用 `|` 分隔表示可接受的变体）。

### H 组：硬件侧（5 条）

| ID | 输入现象 | 期望路径 | 正确终局 |
|---|---|---|---|
| H1 | "3 号线上周开始误判多，夜班特别严重" | defect_log(by station) → light_usage → 可能 check_doc_conflict | 光源衰减，累计时长超额定寿命 + 亮度被下调；建议更换光源 |
| H2 | "误判慢慢变多，没什么报警" | defect_log(by hour) → query_calibration → search_manual | 镜头污染；建议清洁镜头并复核标定 |
| H3 | "设备被人碰了一下之后就不对了" | calibration → defect_log | 标定漂移超阈值；建议重新标定 |
| H4 | "提速以后误判明显上升" | device_profile → defect_log → search_manual | 传送速度提升导致运动模糊；建议降速或缩短曝光 |
| H5 | "有时候整件产品没被拍" | alarm_code → defect_log → search_manual | 触发信号异常；建议检查 PLC 触发回路 |

### A 组：算法侧（5 条）

| ID | 输入现象 | 期望路径 | 正确终局 |
|---|---|---|---|
| A1 | "换了新供应商的料之后开始误判" | defect_log(by batch) → search_manual | 新物料外观分布偏移；建议补充样本或调整阈值 |
| A2 | "误判突然变多，硬件看着都正常" | defect_log → light_usage → calibration → search_manual | 阈值过严；建议下调阈值并复核 |
| A3 | "这三个月误判一直在缓慢上升" | defect_log(长窗口) → calibration → light_usage | 模型漂移；建议重训 |
| A4 | "出现了一种以前没见过的缺陷" | defect_log(by defect_type) → search_manual | 训练数据缺失该类；建议补充标注 |
| A5 | "只有某一种缺陷老被判错" | defect_log(by defect_type) → calibration → light_usage | 该缺陷类阈值/模型偏置；建议针对性复核 |

### I 组：信息不全，考追问（4 条）

| ID | 输入现象 | 期望行为 | 考点 |
|---|---|---|---|
| I1 | "误判率很高" | 追问设备编号（未给） | 不能编设备 |
| I2 | "3 号线 2 号工位误判多" | 自主查最近 24h，**不追问时间** | 合理默认优先于追问 |
| I3 | "系统说误判率正常，但客户投诉多" | 追问或转向查漏检率 | 现象矛盾，不能硬套模板 |
| I4 | "设备 CX-999 有问题"（库中不存在） | 明确报"设备不存在"，追问正确编号 | 不编数据 |

### W 组：需建单（3 条）

| ID | 输入现象 | 期望路径 | 考点 |
|---|---|---|---|
| W1 | 硬件故障需停机 | 取证 → create_work_order(high, 转设备科) | 严重度判断 |
| W2 | 算法问题 | 取证 → create_work_order(medium, 转质量/算法) | 分派正确 |
| W3 | 同一现象重复诊断 | 第二次 create_work_order 返回 deduped=True | 幂等 |

### T 组：陷阱（3 条）

| ID | 输入现象 | 期望行为 | 考点 |
|---|---|---|---|
| T1 | 诊断需查"光源亮度设定" | check_doc_conflict 发现冲突 → 上报，不硬选 | 不擅自裁决 |
| T2 | mock QMS 返回 500 | 明确说明接口不可用，不编造工单号 | 工具失败要诚实 |
| T3 | 查不到标定记录 | 回答"无标定记录"，不给推断结论 | 空数据不编 |

## 7. 评测指标

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 工具选对率 | 每步工具名在 golden 允许集合内的比例 | 逐条比对调用序列 |
| 步数偏差 | 实际步数 / 最短合法步数 | 自动统计 |
| 终局正确率 | 结论命中 golden 结论标签 | 人工标注一次，脚本比对关键词 |
| function calling 失败率 | JSON 解析失败 / 总调用次数 | 解析器埋点 |
| 归因分布 | 工具选错 / 参数错 / 判断错 / 环境错 | 跑分后人工归类，形成固定分类表 |

**归因四类定义**：
- **工具选错**：调了不该调的（如该查光源却查了工单）
- **参数错**：工具对但参数错（时间窗、group_by 写错）
- **判断错**：该停不停、该问不问、方向判反
- **环境错**：工具报错、数据缺失、模型输出格式崩

## 10. 风险与验证点

| 风险 | 影响 | 对策 |
|---|---|---|
| 7b function calling 太弱 | 项目跑不起来 | W0 先验证，失败率 >40% 换 qwen3:8b 或 API |
| 6GB 显存紧张 | 推理变慢或 OOM | num_ctx=4096，评测时关浏览器/IDE |
| 造数据不像真的 | 面试一问就露 | 按真实品牌手册仿，现象用现场口吻 |
| 岔口被写成 if-else | 退化成 workflow | L2 判断必须交给模型，代码里不出现基于数值的分支 |
| 评测变成只考"能不能跑通" | 出不了数字 | golden path 必须包含允许变体，跑分出表 |
