## 二、四个关键设计决策

### 1. 时间窗基准用"数据最新时间"，不用 `now()`

`query_defect_log` 不传时间时，取该设备的 `max(ts)` 倒推 7 天。

原因：演示数据是 2026-11-01 ~ 11-14 的历史区间，若用 `now()` 会在未来的演示时刻查空，
而且改数据日期就会让轨迹全部失效。数据驱动比时钟驱动稳。

### 2. 误判口径统一为过杀

`verdict='NG' AND is_actually_ok=TRUE`。这个口径不在每个工具里各自实现，
而是固定在三张表的语义上（`defect_logs.is_actually_ok` 由人工复判填写）。
若日后要区分"漏检"，加 `is_actually_ng` 字段即可，不改工具签名。

### 3. `check_doc_conflict` 不做正则抽数字

第一版想过：从片段文本里正则抽数字比对。实测会抽错——
"光源亮度由 85 下调至 80"里有两个数，正则会拿到 85，而该文档的取值应该是 80。

改为在 seed 时就给每块打 `params` 标签（JSONB），冲突检测直接按 key 精确比对。
代价是造数据时要人工标注，收益是不会误判。

### 4. 取证要求写进工具描述，不写进提示词

W0 实测：提示词里加"每个数字必须原样来自工具返回""至少核对两个维度"两条硬约束，
语义正确率从 40% 掉到 20%，参数准确率 100%→80%（指令过载导致注意力分散）。

所以这次把要求挪到 `query_defect_log` 的 description 里：
"判断硬件还是算法，必须看误判是否集中……只查一个维度就下结论属于取证不足"。
模型在选工具时就看到约束，不占用系统提示词的注意力预算。

## 三、一个值得记录的发现

`search_manual("光源亮度设定标准值")` 的首条命中是**厂内 SOP 的 65**，厂商手册的 80 排第二。

这暴露了纯 RAG 的风险：模型读第一条就照 65 继续推理，而 65 正是 CX-101 已经调到的问题值。

所以 `check_doc_conflict` 不是可选项——**检索命中冲突文档时，必须显式检查是否有冲突**，
否则模型会把"现场被调坏的值"当成"标准值"引用。这一点会写进 L3 岔口的触发条件。

## 四、已知缺口

1. **`create_work_order` 目前直接写库，未走 mock QMS 的 HTTP 接口。**
   清单要求走 HTTP 是为了复现项目一踩过的集成坑（HTTP 200 但业务码在响应体）。
   这一层还没搭，是下一步。
2. **`search_manual` 只查设备手册表，没查项目一的 `doc_chunks`。**
   若要回答"这个缺陷对应的检验标准是什么"，需要跨库检索，暂未实现。
3. **手册库只有 24 块**，冲突覆盖 10 个参数。参数再多时检索会变稀，需要补。
4. **工具没有单元测试**，目前只有冒烟脚本。轨迹评测（M4）会覆盖真实调用路径。
