## 一、图结构

```
START → intake ──(抽到设备号?)──┬─ 否 → ask_user → END
                                └─ 是 → plan ⇄ act
                                          ↓(无工具调用)
                                       verify → finalize → END
```

| 节点 | 职责 | 谁在做判断 |
|---|---|---|
| `intake` | 正则抽 `CX-\d{3}`，抽出设备号 | 程序（结构化抽取，不该让模型做） |
| **L1 岔口** | 没设备号 → 追问；有设备号 → 直接进 plan | 程序（信息完整性的硬规则） |
| `plan` | 调模型，决定下一步调哪个工具或收尾 | **模型** |
| `act` | 执行工具，把结果写回消息 | 程序 |
| **L2 岔口** | 有 tool_calls → 继续取证；无 → 进校验 | 模型输出决定，代码里没有数值判断 |
| `verify` | 结论里的百分比逐个比对工具返回 | 程序（模型做不好的事） |
| **L3 岔口** | 参数冲突时模型必须上报，不得自行选值 | 模型 + 工具返回值驱动 |

**L2 为什么必须是模型自己判断**：代码里没有任何"如果 1 号工位误判率高就查光源"的分支。
`route_after_plan` 只看模型有没有返回 tool_calls。方向判断全部发生在模型的推理里，
图只负责把它的决定执行下去。这是回应"你这算 Agent 还是 workflow"的关键——
固定路径的 workflow 在第二个岔口就会露馅。

## 二、H1 实测轨迹（10 次工具调用）

输入：`3号线 CX-101 夜班误判率飙升，白班还好一点，帮我查下原因`

| # | 工具 | 为什么调 |
|---|---|---|
| 1 | `query_device_profile` | 确认设备存在 |
| 2 | `query_defect_log(station)` | **主证据**：误判是否集中在一个工位 |
| 3 | `query_defect_log(hour)` | 用户说夜班重，验证时段规律 |
| 4 | `query_light_usage` | 工位集中 → 查该工位的独立部件 |
| 5 | `query_calibration` | 排除标定漂移 |
| 6 | `query_defect_log(batch)` | 反向排除物料批次 |
| 7 | `query_defect_log(defect_type)` | 反向排除缺陷类型 |
| 8 | `search_manual` | 查亮度标准值与更换要求 |
| 9 | `check_doc_conflict(光源亮度设定)` | 手册与 SOP 说法不一致 |
| 10 | `check_doc_conflict(标定周期(天))` | 顺带发现的第二处冲突 |

结论与证据（均来自工具返回）：

- 1 号工位 **58.82%**（20/34），3 号 10.64%，2 号 6.25% —— 差 5.5～9.4 倍
  → 模型和阈值是所有工位共用的，工位间差异只能来自该工位的独立部件
- 光源 **8620 h / 额定 8000 h**，超 620 h；亮度 **85 → 80 → 65** 两次下调
- 标定最近 10-30，漂移 0.079 mm 通过，趋势平稳 → 排除
- 批次误判率 12.5%~66.7% 分散在 10 个批次；缺陷类型 15.4%~31.0% 均匀 → 排除算法侧
- 两处冲突全上报：光源亮度 **80 vs 65**、标定周期 **90 vs 30**
- **明确拒绝建单**："亮度设定口径未确认，处置动作中的关键参数还没定"

对照 W0：qwen2.5:7b 平均 **0.9 步**就下结论（第一次猜对维度），DeepSeek 这里走了 10 步可溯源轨迹。
"取证充分"这个差异，在评测里会比"结论对不对"更值得作为指标。

## 三、这一轮踩的三个坑

### 坑 1：`check_doc_conflict` 在参数名不存在时崩了（真 bug）

第一版代码把"参数没命中"的分支写在了 `with connect() as conn, ... as cur:` 块**外面**：

```python
with connect() as conn, conn.cursor() as cur:
    cur.execute(...)
    rows = cur.fetchall()

if not rows:
    cur.execute("SELECT ...")   # ← 连接已关闭，OperationalError: the connection is closed
```

实测现象：模型查 `标定漂移阈值`（实际参数名是 `标定允许漂移(mm)`），直接报连接关闭，
模型只好在结论里写"该检查工具报错，未能完成"。

修法：把空分支挪进 `with` 内部，并且**返回 `available_params` 列表**，
让模型知道正确参数名是什么、能改名重查，而不是撞墙后放弃。
重跑后模型改查 `标定周期(天)`，命中了第二处冲突。

### 坑 2：校验器把正常换算判成编造

初版 `verify` 用字符串包含做比对：结论里出现 `6.3%`，就去工具返回的 JSON 里找 `"6.3"`。

但工具返回的是原始比率 `0.0625`，模型写 `6.3%` 是正常的四舍五入换算。
结果 3 个数字被误判成"无溯源"：`6.3%`（2 号工位）、`11.8%`、`66.7%`。

修法：改成数值容差比对——抽出工具返回里所有数字，允许 `|n - v| ≤ 0.15`（百分点口径）
或 `|n - v/100| ≤ 0.002`（比率口径）。重跑后校验通过。

**这个坑的教训**：校验层的假阳性比假阴性更伤——一旦它频繁误报，
人就会开始忽略告警，校验层等于失效。

### 坑 3：`steps` 算的是批次不是调用

第一版 `act` 里写 `steps + 1`，而一次 `act` 可能带 3 个 tool_calls。
结果 9 次调用只记了 3 步，熔断（`MAX_STEPS=8`）要到 24 次调用才触发。

改成 `steps + len(tool_calls)`，现在熔断语义是"最多 8 次工具调用"。

## 四、当前已知缺口

1. **没有 trace 落盘**：现在只在控制台打印。M5 要写 JSONL，字段含每步耗时、token、工具参数与返回。
2. **没有 20 条轨迹评测**：单条 H1 只能证明"能跑"。工具选对率、步数偏差、终局正确率、fc 失败率都还没统计。
3. **`verify` 只查百分比**：设备号、时间、参数值都没校验。W0 里最典型的失败是编设备号，这里还没防。
4. **没有断点恢复**：Checkpointer 未接，长轨迹中断等于重跑。
5. **冲突检测只覆盖 11 个参数**，模型遇到别的参数名还是会撞空。
