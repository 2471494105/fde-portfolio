## 一、评测器怎么判

四类指标，每个都能程序判定，不写"应该诊断得对"这种没法判的话。

| 指标 | 判定方式 | 为什么这么定 |
|---|---|---|
| 工具选对率 | `expect_tools` 里期望的工具出现了几个 | 按命中率算，**不要求全部调用**。取证顺序天然有差异，用 `first` 判会把合理顺序判死（W0 踩过） |
| 聚合维度覆盖 | 期望的 `group_by` 是否在**任意一次**调用里出现过 | 同上，`any` 而非 `first`。模型先看工位再看批次是正常的 |
| 终局命中率 | `final_keywords` 命中比例，≥50% 算过 | 不要求逐字一致，只要求结论落在正确方向上 |
| fc 失败率 | 工具调用参数 JSON 解析失败 / 未知工具 | 这是硬故障，出现即失败 |

**语义正确** = 工具命中 100% + 维度命中 100% + 终局命中 ≥50% + 未越禁用工具 + 步数在区间 + 无未溯源数字 + 无 fc 失败 + 幂等达标（W2）。

四条归因：工具选错 / 取证维度不足 / 判断错 / 越界调用 / 步数越界 / 未溯源数字 / 工具调用格式错。

## 三、踩过的坑（22 处改动，按性质分三类）

### 3.1 产品代码的真 bug（4 个）

**坑 1：步数上限 8 太紧，模型卡在取证上没机会建单**

W1 八个工具调用正好用满 8 步，最后一步是 `check_doc_conflict`，结论写着"证据链完整，可以建单"，但 `route_after_plan` 已把流程送去 finalize。**模型的判断是对的，是预算把它掐断了。**

修法不是简单调大——调到 12 之后 W1 反而跑了 13 步还没建单，因为模型**不知道自己在烧预算**。真正的修法是**预算感知**：每一轮 `plan` 都把"已用 X/12 次"注入 system 消息，并写明"剩余 3 次及以下请停止取证、直接给结论；用户本轮已明确要求某动作时优先完成该动作"。

改完 W1 从 13 步降到 4 步就建单。

**坑 2：数字正则 `-?` 把连接号当负号**

`re.findall(r"-?\d+(?:\.\d+)?", ...)` 遇上手册里的 `"10%-25%"` 会抽出 `-25`。结论引用 `25%` 时，`nums` 里只有 `-25`，`|(-25) - 25| = 50`，被判成未溯源——**工具明确返回过的数字被判成编造**。

修法：去掉 `-?`。数据里几乎没有需要在结论里引用的负数，接受这个取舍。

**坑 3：用户自己输入的数字被判成编造**

W1 用户原话里就有"误判 58%"，结论写 `58%` 时工具返回是 `0.5882`，差 0.8 个百分点，超容差被判编造。W0 踩过完全同类的坑（用户输入的设备号被当成编造）。

修法：`nums` 增加 `user_msg` 里的全部数字。**用户给的数字和工具返回的数字地位相同，都是合法来源。**

**坑 4：幂等键用自由文本，措辞一变就失效**

W1 模型写"光源超额定寿命导致亮度衰减"，W2 写"光源超寿命"——同一件事，`hash(device_id + day + root_cause)` 完全不同，于是新建单而不是去重。

**这是真实工程问题：幂等键必须基于枚举，不能基于自然语言。** 改法：新增 `root_cause_code` 枚举字段（`light_degradation` / `lens_contamination` / `calibration_drift` / `batch_drift` / `threshold_misconfig` / `other`），幂等键只吃分类码，`root_cause` 自由文本保留给工单内容用。三个文件同步改（schema / 工具 / mock QMS），改完必须重启 mock 服务。

改完 W2 一次就命中 `deduped=true`。

### 3.2 评测器与校验层的坑（4 个）

校验层的设计原则只有一条：**误报比漏报更伤**。一旦频繁误报，人就会忽略告警，校验层等于失效。

**坑 5：容差 0.002 太紧，合法四舍五入被判编造**

工具返回 `0.6923`（69.23%），结论写 `69%`，差 0.0023 > 0.002，判失败。这不是第一次——`6.3%` vs `0.0625` 也有同类风险。

修法：比例口径容差放宽到 1 个百分点（`|n - v/100| <= 0.01`），百分点口径放宽到 0.5。仍能拦住凭空编数（量级差很大）。

**坑 6：可复算的衍生指标被判编造**

T2 里模型写 `74%`，工具返回里没有这个数——但它是 `20/27 = 74.07%`（1号工位占全部过杀的比重），分子分母都在工具返回里。**算法是对的，只是没写计算式。**

修法：新增 `_recomputable(v, nums)`，对每个未直接命中的百分比，尝试用 `nums` 里任意两个计数 `a/b*100 ≈ v`（容差 1 个百分点）。能复算就放行。

代价是理论上可能凑巧放行一个编造数，收益是消掉一整类误报。这个取舍要写进文档而不是悄悄做。

**坑 7：缺 `day` 聚合维度**

CX-105 镜头污染的判据是"误判率随时间**加速上升**"，CX-104 标定漂移的判据是"11-08 起**陡变**"。但 `group_by` 原来只有 `hour / station / defect_type / batch`——没有按天的粒度，模型只能看到 7 天窗口内的平台值。

这是**工具集缺口，不是模型能力问题**。修法：`GROUP_EXPR` 加 `date_trunc('day', ts)`，schema enum 加 `day`，description 里点明"判断缓慢漂移类故障必须用这个维度"。

加了之后 H2/H3 一次通过。

**坑 8：默认 7 天窗口把"最近一个月"的趋势截断**

H2 用户问"最近一个月误判越来越多"，模型没传 `time_from`，工具默认只查 7 天。7 天内 CX-105 的误判率已经很高且平坦（39.6% / 30.6%），看不出上升——模型据此判"两工位均摊 → 算法侧"，方向错了。

修法按 W0 的结论：**取证要求写进工具 description，不写进提示词**。在 `time_from` 的 description 里写明"用户说的是一周以上时必须把起点写进来，否则趋势会被 7 天窗口截断，看到的只是平台期"。

### 3.3 期望设计写错的坑（3 个）

**坑 9：W1 期望"先建单"，但模型的"先确认冲突"更合理**

模型中途中止建单，理由是"口径未确认，处置动作中的关键参数还没定"。从工业验收角度这是**正确行为**。修法不是改模型，是把输入改成"文档冲突的事先放一边，直接按 65 建单"，让用户显式放弃该前提。

**坑 10：T3 期望写反了**

原期望是"必须去查"，`steps_range (1,8)`。模型 0 步、明确拒绝："这个我不能凭经验估……编一个数字出来对你没有任何帮助"。**这是完全正确的行为**——用户要求凭经验编数，模型拒绝。

修法是改判据：不强制调用工具，`steps_range (0,8)`，关键词换成"不能 / 查 / 估"，核心靠 `blocked` 为空来保证它没编数。

**坑 11：W3 强制查维度，但用户说了"别管什么原因"**

期望要求 `defect_type` 维度，模型跳过直接建单被判失败。但用户原话是"别管什么原因了"——**尊重用户指令是对的行为**。修法：`expect_group_by` 清空，仍保留 `query_device_profile` + `query_defect_log`（考的是"没给根因时会不会凭猜测建单"）。

## 四、唯一没修好的 H5：被用户前提带偏

```
输入：CX-104 尺寸类误判特别多，是不是阈值设太严了
实际：4 步（profile → station → defect_type → batch），判"模型/参数整体偏保守"
真实：标定漂移 —— 11-07 drift=0.42 告警，11-08 起误判从 15.4% 跳到 63.2%
```

模型的取证本身没错：它看到四类缺陷都高（划痕 63.0%、尺寸 56.5%、凹坑 46.4%、污渍 44.8%）、两工位都高（46.8% / 60.0%）、10 个批次分散（25%~69%），据此排除单点硬件和批次漂移，推出"所有工位共用的东西有问题"。**推理链是完整的，只是缺了"什么时候开始变"这一维。**

它没做的两件事：
1. 没查 `query_calibration` —— 而 CX-104 的 `drift_mm=0.42` 就躺在那里
2. 没按 `day` 看 —— 按天一眼就能看到 11-07 的 15.4% 和 11-08 的 63.2%

**根因是它接受了用户的前提**："是不是阈值设太严"把搜索空间锚定在算法侧，而"整体偏高"又恰好和"阈值保守"自洽，于是它停止了取证。

这恰好是本项目要考的能力——**用户断言不能替代数据**。这条**保留为失败**，不改成通过，因为它反映的是真实缺陷，不是判据过严。

工程上可以做的改进（未做，记录在此）：在 schema 的 `query_defect_log` description 里，把"时间线"从"可选维度"改成"任何'从某个时间点开始变化'的描述都必须先看 day"。这属于同一类修法（约束写进工具描述）。

## 五、一个必须说清楚的现象：temperature=0 也会波动

同一个输入、同一个模型、`temperature=0`，跑两次结果可以不同：

- T2 第一次跑出 `74%`（不可直接溯源），用 `run_case.py` 复跑却是 58.8% / 6.3% / 10.6% 全对，没有编造
- A3 第一次 `3.5%` 未溯源，复跑完全干净

**含义**：单次 20 条评测的 95% 不是一个稳定值。真实可复现的结论只能是区间——同一版本代码多跑几次，结果在 90%~95% 之间浮动。

这件事必须写进 README 和面试话术，不能宣称"95% 通过率"。**能承认评测有波动，比报一个漂亮数字更可信。**

## 六、已知局限

1. **20 条样本量小**，95% 对应的是 1 条失败，置信区间很宽
2. **模型有波动**，单次结果不可作为回归基线；要做回归需要多次跑取众数，成本 ×3
3. ~~**H5 那条失败未修复**~~ —— **2026-11-19 已修，见第八节**。原判断"属于用户断言污染诊断这一能力缺口，需要在工具描述层约束"是对的，修法就落在工具描述层。
4. **每条只考一件事**，没有组合场景（如"先建单再追问"）
5. ~~**未做多轮评测**：W1→W2 是两条独立输入，不是同一个 thread 的连续对话，跨轮状态（如"刚才那个工单"指代）靠输入文本模拟，不是靠真实会话状态~~ —— **2026-11-19 已修，见第八节。** 原判断准确：W2 依赖"刚才那个"跨轮指代，而它作为独立用例只能靠库里残留的工单来"模拟"这个上下文，两条路都不可信。
6. **judge 的终局判定靠关键词，会假通过**——这条已实测到，不是理论风险。2026-11-16 在 Web 端复跑 H2（CX-105），模型结论是"根因方向：偏算法（模型/阈值）"、并明确写了"不是镜头问题"，但因为文本里出现了"镜头"二字，`final_keywords` 命中，被判为通过。也就是说"关键词出现在否定语境"同样算命中。当前这份 95% 里有至少一条属于这类假通过，真实语义正确率应低于报告值。修法应该判否定语境（如"不是镜头"要扣分），或改用 LLM-as-judge 做终局判定（成本更高、又引入新的不确定性），暂未改。

## 八、补记 2026-11-19：三处根因修复

本节记录第六节里两条已知局限的修复，以及一个不在清单内但同样致命的发现。
改完之后这几节的旧结论已经失真，以本节为准。

### 8.1 环境残留造成的假绿（第六节没写到的新发现）

`mock_qms/server.py` 只有 `create_work_order`，**没有任何 reset / reseed / DELETE 端点**，
于是工单表只增不减。清库前实测挂着 **7 张历史工单**，其中 5 张"待处理"压着
CX-101/102/103/104/105 五个幂等键——**W1/W2/W3 三条建单用例全都处在假绿状态**：
模型第一次建单就命中旧单返回 `deduped=True`，根本没建新单，而 W1 的判据只看
回答里有没有 `WO-` 前缀，照样判过。

这是比假红更危险的一类：**环境残留让分数虚高，而且从报告上看不出来**。
对应 Anthropic《Demystifying evals for AI agents》那句
"Each trial should be 'isolated' by starting from a clean environment …
Shared state can also artificially inflate performance."

修法：新建 `mock_qms/reset.py`（清空前自动把整表导出到 `mock_qms/backups/`，
`--dry` 只读并列出"占用幂等键的未关闭工单"）。失败抛异常而不是静默返回 0——
**清不干净等于起点不确定，比直接报错更危险**。

### 8.2 W1+W2 合并成一条真多轮用例（修第六节第 5 条）

W2 的输入是"再帮我给 CX-101 建一次**刚才那个**换光源的工单"。
它作为独立用例没有会话上下文，"刚才那个"只能靠库里留着上次跑的残单——
于是干净库首跑必红（真建新单）、脏库必绿（撞上残留），**两个结论都不反映模型能力**。

所以根治不是 seed，是**把 W1 和 W2 合并成一条两轮用例**：
第 1 轮直接要求建单，第 2 轮用同一 thread 说"再建一次刚才那个"。
合并后第 2 轮的 `deduped=True` **必然来自本 trial 第 1 轮**，同一条断言同时证明两件事
（第 1 轮真建了新单、第 2 轮真去重）。用例数 27 → 26。

配套把 `expect_deduped` 判据从"只认 True"改成三态
（`if "expect_deduped" in traj` + `got is want`）：
原来写 `expect_deduped=False` 会被静默忽略——**配置写了、判据不执行，
正是单向评测的入口**（同一篇论文："Test both the cases where a behavior
*should* occur and where it *shouldn't*."）。

新增 `FixtureDedupedContractTest` 把这条原则固化成机器检查：
`expect_deduped=True` 的用例必须 `turns ≥ 2`，否则这个绿只能来自跨试次残留。

### 8.3 写意图闸把合法请求吞了（跑的时候才暴露）

合并后第一次跑 W1 判 `idem_miss`。看 evidence 原文才发现：第 1 轮建单成功
（`deduped: false`），**第 2 轮两次 `create_work_order` 都被 `write_intent` 挡回**
`{"error": "用户没有要求建单…"}`。

根因：`WRITE_INTENT_KW` 只认"建单/建工单"这类**连写**形态，
用户说的是"建一次…工单"（动宾分离），一个都没命中；
而 `understand` 判对了 `intent=action`（它的 prompt 里 action 的例子原句就写着
"再建一次刚才那个单"），**闸门却不看这个判断，自己用词表重算一遍返回 False**。

修法：`_has_write_intent` 改成"词表 OR `state.intent == 'action'`"。
这不是放松，是把该归谁判的事还回去：

- "用户要不要建单"是**语义** → 模型判（understand 的 intent）
- "建单必须可追溯"是**约束** → 规则守（根因 / 证据引用 / 设备存在 / 幂等 四道闸）

原来让一张词表同时干这两件事，而它只能干后者的一半。
第 2 条只给**许可**，不给**豁免**——引用校验照样在后面跑。
两条新测试分别证明"intent=action 能放行"和"intent=action 也绕不过引用校验"。

### 8.4 参考解机制（修"判据写坏看不出来"）

新建 `eval/reference.py`：每次评测收尾，把 `semantic_ok=True` 的用例自动落盘到
`eval/reference/<id>.json`（用例定义 + `judge` 依赖的 state 白名单）；
`python eval/reference.py --verify` 用**当前判据**重判全部参考解。

依据是同一篇论文 Step 2："For each task, it's useful to create a reference solution:
a known working output that passes all graders. This proves that the task is solvable
and verifies graders are correctly configured."

为什么这套系统特别需要它：判据和被测对象已经同源过四次。
其中最难受的一种是**判据把好答案判红**——同一篇文档给的 CORE-Bench 例子里，
一个严格的字符串比较把 `96.12` 判成错（它期望 `96.124991…`），
修掉这类 rigid grading 后成绩从 42% 跳到 95%。
**判据写坏时跑出来的分数看起来完全正常**，你没法从报告上区分"模型不行"和"判据太严"。
参考解就是那个对照组：它红了，问题在判据。

四态输出：`ok` / `stale`（用例改过，参考解不再代表本题）/ `failed`（判据把它判红了，
要人来分辨是"判据改严了"还是"判据改错了"）/ `missing`。

### 8.5 H5 / 时间线 / 冲突文案（修第六节第 3 条，都是工具描述层）

三处都在 `app/tools/schemas.py` 与 `app/tools/manual.py` 的**工具描述**里改，
不改判据——H5 反映的是真实能力缺口，判据没错。

**（1）时间线从可选维度提成必查维度。** 原 `group_by` 的 day 只是"可选维度之一"，
现写明：只要用户的话里出现"最近变多了""从上周开始""某天之后就不对"这类
**从某个时点起发生变化**的描述，就**先按 day 看趋势再谈原因**，
并说明默认 7 天窗口可能把拐点截在窗外、要同时把 `time_from` 往前推。

**（2）用户带来的猜测不构成证据。** 原描述只教"怎么判硬件还是算法"，
没写"用户的前提不能替代数据"。H5 失败链正是：用户问"是不是阈值太严"
→ 搜索空间被锚定在算法侧 → "整体偏高"又与"阈值保守"自洽 → 停止取证。
现写明：猜测只说明他在怀疑什么，不说明数据支持什么；只要整体误判偏高而原因不明，
就先 day 看时间线 + `query_calibration` 看标定漂移，再看算法侧。

**（3）`check_doc_conflict` 的 note 按实际取值分组。** 原文写死
"存在冲突，两类文档取值不同"，而 `values` 可能来自四份文档（厂商手册 / 厂内SOP /
保养计划 / 质量目标）——**四行摆在那里、句子却说"两类"**，模型读到的冲突规模是错的；
它还把没给出该参数的文档一起列进去。现改成按取值分组计数
（"存在冲突：N 种取值——某值（某文档、某文档）；…"），并另标"N 份文档未给出该参数"。
依据是《Writing effective tools for agents》的 "return only high signal information"。
