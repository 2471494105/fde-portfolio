# 意图层改造：把 L1 从关键词闸门改成模型判断

日期：2026-11-16
改动范围：`app/graph/state.py`、`app/graph/nodes.py`、`app/graph/build.py`、`eval/trajectories.py`、`eval/run_eval.py`

---

## 一、改之前是什么样

原来的 L1（第一层）只做一件事：正则从输入里抽 `CX-\d{3}`。

- 抽到了 → 当作诊断请求 → 进 plan
- 抽不到 → 当作信息不全 → 追问"请提供设备编号"

这是拿**代理指标**（句子里有没有设备号）当**真实需求**（用户是不是想诊断）。

三条实测证据：

| 输入 | 用户实际想要什么 | 系统干了什么 |
|---|---|---|
| `cx-104 数据` | 看数据 | 跑了 7 次工具，输出 1479 字、20 个百分比，直接给根因 |
| `E-101 这个告警是什么意思` | 查告警码含义 | 0 次工具，反问"请问是哪一台设备" |
| `帮我看看最近怎么样` | 还没说清 | 直接要设备号，不问他到底想看什么 |

第二条最能说明问题：**告警码含义根本不需要设备号**，系统却因为没抽到设备号而拒绝回答。

根因有两层：
1. 系统里没有"信息不足"这个出口。抽不到设备号就只有"追问设备号"一个动作。
2. 模型天然倾向补齐缺失的上下文，而不是承认不知道。这跟 W0 里它编设备号是同一个毛病——**让缺陷看起来像能力**。加上 5 台设备全都有病，问哪台都能"答对"，这个缺陷在演示里根本暴露不出来。

## 二、为什么不用规则表

我最初提的方案是加一张意图规则表：输入里出现"是什么意思/怎么设置"就判知识类，出现"建单/派工"就判动作类，等等。

这个方案被否掉了，理由是它和项目的核心论证冲突：

> 如果意图就要套一大堆检测，就谈不上智能，我认为应该让 agent 做第一层用户意图判断。

规则表做意图判断，等于把 L1 变成一串 if-else，整个项目就退回成 workflow 了——恰恰是第一个项目被质疑的那个点。而且规则表的问题是维护成本随输入形态线性增长，每来一种新问法就得补一条，补到二十条以后没人敢改。

所以边界重新划定：

| | 谁做 | 属于什么 |
|---|---|---|
| 用户想干什么 | **模型** | Agent 的判断 |
| 模型输出自不自洽 | 程序 | Guardrail（护栏） |

程序不替模型判断意图，只校验模型输出有没有硬矛盾。这是 B+C 双轨的分工：B 负责判断，C 负责守住明显不成立的组合。

## 三、设计

### 3.1 五类意图

| intent | 定义 | 路由 |
|---|---|---|
| `diagnose` | 描述异常、问原因、要求排查 | plan ⇄ act → verify |
| `lookup` | 要看数据/档案，不要求给原因 | lookup（模板出表） |
| `knowledge` | 问规则、标准、含义、操作步骤 | knowledge（检索手册） |
| `action` | 要求执行动作（建单、派工、登记） | plan ⇄ act → verify |
| `clarify` | 信息不足以判断以上任何一类 | ask_user |

understand 节点让 DeepSeek 输出一个固定 JSON：

```json
{
  "intent": "diagnose|lookup|knowledge|action|clarify",
  "device_ids": ["CX-104"],
  "alarm_codes": ["E-101"],
  "param_names": ["光源亮度设定"],
  "phenomenon": "用户描述的异常现象（概括原话），没有就填空字符串",
  "missing": ["还缺什么信息才能继续"],
  "reason": "一句话说明凭什么这么判"
}
```

`response_format={"type":"json_object"}`，timeout 20 秒。失败时退回旧逻辑（有设备号判 diagnose，没有判 clarify），保证接口不因模型抖动而中断。

`param_names` 不是给答复用的，是给 knowledge 分支用的：用户问"亮度该设多少"时，这个字段决定要不要去查文档冲突。

### 3.2 程序只校验硬矛盾

| 模型判成 | 缺什么 | 程序动作 | 为什么这是硬矛盾 |
|---|---|---|---|
| `diagnose` | 无设备号 | 降级 clarify | 没有诊断对象，没法查 |
| `lookup` | 无设备号 | 降级 clarify | 不知道查哪台 |
| `action` | 无设备号 | 降级 clarify | 不知道给谁建单 |

**这里我一开始写错了一条，值得记下来。**

我把"`diagnose` 但没有 `phenomenon`"也加进了降级条件。结果 I2 `CX-101 有点问题，你查一下` 被判成 clarify、0 步工具——用户明明说了"你查一下"，系统却反问他要什么。

教训：

- **没有对象是硬矛盾**：不知道哪台设备，真的没法诊断。
- **没描述现象不是硬矛盾**：可以先取基础数据（档案 + 各维度分布）再判断，这也是合格的诊断第一步。

判据只保留前者。这句话也写进了 UNDERSTAND_PROMPT：用户明确要求查看/排查时，即使没描述现象也应判 diagnose。

### 3.3 四条分支

```
START → intake（只抽候选设备号，不判意图）
      → understand（模型判意图）
          ├─ diagnose / action → plan ⇄ act → verify → finalize → END
          ├─ lookup            → lookup ──────────────┘
          ├─ knowledge         → knowledge ───────────┘
          └─ clarify           → ask_user → END
```

- `lookup`：不调模型，直接用模板拼设备档案 + 各维度误判表，结尾固定写"没有做根因判断"。数据查询不该让模型自由发挥。
- `knowledge`：检索手册 → 如果 `param_names` 非空，**自动**再查一次 `check_doc_conflict` → 有冲突就在上下文里塞一段"必须指出冲突"的指令。这是把 L3（证据冲突）接进知识分支，避免重蹈"读检索第一条就照抄"的坑（`search_manual` 首条命中的恰好是已经被调坏的 65）。
- `clarify`：追问文案按已知信息生成三种版本（有设备无现象 / 有现象无设备 / 都没有），不再硬编码"请提供设备编号"。
- `verify`：取结论时先看 `state["final"]`（lookup/knowledge 直接产出），再看 messages 末尾的 assistant 消息（诊断路径）。**这一步改错了会让 verify 把用户的输入当成结论去校验**，因为 lookup 不往 messages 写。

## 四、三个 regression 与修法

改完第一版直接跑全量，从 95% 掉到 **66.7%**（16/24）。三个都是我自己造的：

| 现象 | 根因 | 修法 |
|---|---|---|
| I1 `我们线体误判率突然飙升了`、I4 `3号线那台机器误判又高了` 直接跑诊断，越界调了 profile/defect_log/light_usage | 漏了"diagnose 必须有设备号"这条校验，无设备号也进了 plan，模型自己挑设备 | 补降级分支 |
| W2 `再帮我给 CX-101 建一次工单`、W3 `你先给我建个工单` 被判 clarify，0 步 | "phenomenon 为空就降级"误伤了动作类请求——建单本来就不需要描述现象 | 增加 `action` 类别，action 无设备号才降级 |
| T1 `亮度到底该设多少` 只调了 search_manual，没调 check_doc_conflict | knowledge 分支没接 L3 | understand 输出 `param_names`，knowledge 里按参数名查冲突 |

还有一个不算产品 bug 的：I6 第一版 FAIL，原因是我在 lookup 的文案里写了"**没有做根因判断**"，"根因"两个字命中了禁用词。这是判据设计错误，把 `forbid_words` 收紧成 `["根因：","根因是","故障原因：","故障原因应是"]` 就正常了。

## 五、评测：24 条，8 轮

改造前 20 条，加了 I5–I8 四条意图用例：

| id | 输入 | 考什么 | 期望 |
|---|---|---|---|
| I5 | `E-101 这个告警是什么意思` | 纯知识问题不该要设备号 | intent=knowledge，禁"请问是哪一台" |
| I6 | `cx-104 数据` | 要数据时不该给根因 | intent=lookup，禁"根因：" |
| I7 | `帮我看看最近怎么样` | 什么都没说只能追问 | intent=clarify，0 步 |
| I8 | `CX-102 应该是镜头脏了，帮我确认下` | 用户带错误假设（真因是批次 B20261105） | 必须按 batch 取证并指出批次 |

8 轮结果：

| 轮 | 结果 | 失败项 |
|---|---|---|
| 1 | 22/24 | H5, I2 |
| 2 | 22/24 | W1, T3 |
| 3 | 22/24 | H5, T3 |
| 4 | 21/24 | H5, T1, T3 |
| 5 | 22/24 | H5, T2 |
| 6 | 20/24 | H5, W1, T1, T2 |
| 7 | 22/24 | H5, T1 |
| 8 | 22/24 | H5, W3 |

读法：

- **稳定失败只有 H5**（8 轮全失败），是设计缺口，故意保留。
- **T2 前 6 轮失败 3 次**，加上"用户陈述与工具返回冲突必须指出"这条提示词后，连续 5 次通过。这是"用户带错前提、系统顺着说"的实例，属于上一轮定的 P0②。
- **T3 前 4 轮失败 3 次**，查下来是我的判据写错了：它走 knowledge 分支回答"手册没有给出，无法估计"，这本身正确，但要求它必须出现"不能""查"两个字。改成 `["无法","没有","不能"]` 后正常。
- **91.7% 不是稳定值**：它是 8 轮里出现 4 次的那个值，区间是 83.3%–91.7%，平均 90.0%。改造前报的 95% 是单次快照，同理也不能当稳定值用。

## 六、改造前后的数字不能直接比

95%（20 条）→ 91.7%（24 条）看起来是能力下降，其实不是：

1. 用例从 20 条变 24 条，新增的 4 条是专门挑模型软肋的（纯知识、只说"数据"、什么都不说、带错误假设），比原有 20 条更刁。
2. 原有 20 条里除了 H5 之外全通过，说明诊断能力没退化。
3. 意图判错在 8 轮里是 **0/192**——五类意图分类一次没判错，这是这次改造最直接的收益。

要比较的话应该比同一批 20 条：改造后那 20 条通过 19–20 条，与改造前持平。

## 七、已知缺口

1. **告警码没有进向量库**。`E-101` 等 8 条告警码只在 `alarms` 表，`device_manual_chunks` 那 24 块里没有词条定义。所以 I5 只能回答"手册未收录"，虽然答得诚实，但没真的解决问题。项目清单里写了"告警码必须可查"，数据层没落实。
2. **H5 仍然失败**：用户问"是不是阈值太严"，模型只在算法侧取证，没查 `query_calibration`，也没按 day 聚合，缺"什么时候开始变"这一维。这是它接不住错误前提的另一种形态——顺着前提只查了前提对应的那一侧。
3. **校验层仍是 0% 拦截**。上一轮 `scripts/audit_verify.py` 实测：随机编造 300 个百分比，直接命中 177 个、靠 `_recomputable` 放行 123 个、正确拦下 0 个。所以报告里的"未溯源数字 0/24"不是模型干净，是尺太松。
4. **绝对数字根本不校验**：`PCT_RE` 只匹配带 `%` 的数，"累计 9200 小时""0.88mm" 这类完全不过校验。
