# 模型接入与 token 成本优化

日期：2026-11-16
背景：用户提出"token 消耗太大、没有免费模型"，要求先切本地，随后提供了第三方中转站的 key。
本文记录实测结论，不是推测。

---

## 一、结论先行

1. **本地 qwen2.5:7b 不能当主力**，三重降级：质量 25%、慢 8.7 倍、token 反而多 91%。
2. **真正的省钱杠杆是前缀缓存，不是换模型**。修一个拼 prompt 的错误后，缓存命中率从 **0% 升到 82.7%**，输入成本降约 64%，完全无损。
3. 新接入的中转站（minekuai / `deepseek-v4.1-flash-1017`）**质量合格甚至更好**（把历史遗留的 H5 失败修好了），但**慢约 20 倍**（125–136 s/条），因为步数从 4–7 膨胀到 6–12。

---

## 二、三个 provider 的实测对照

| 指标 | 官方 DeepSeek | 中转站 v4.1-flash | 本地 qwen2.5:7b |
|---|---|---|---|
| 语义正确率 | 95.8%（23/24） | 抽样 7/7 OK（H5 修复） | **25%（1/4）** |
| 单条耗时 | 5.9 s | **125–136 s** | 35.6 s |
| 单条步数 | 4–7 | 6–12 | 2（提前停手） |
| 单条 token | 21853 | 36117 | 9739 |
| 前缀缓存 | 修复后 82.7% | 82.7% | 不适用 |
| 真实价值 | 开发迭代最快 | 单价最低 | 单价 0 元、可断网 |

**为什么本地的 token 反而多 91%：** 它写得啰嗦（大段"我们接下来调用…"），又多一次 plan 退回重试，而且 `num_ctx` 必须开到 8192 才不丢证据，整段 prompt 每次重算。

**为什么本地"省 55% token"是假象：** 同一条 H3，DeepSeek 21853 token 走完 7 步，本地 9739 token 只走 2 步就停手。省下的是没干的活。

## 三、最有价值的一条：前缀缓存为什么一直是 0

### 现象
接入后加了缓存统计，实测一条 8 步用例：

```
plan 1  prompt=2265  命中 0     未命中 2265
plan 2  prompt=3203  命中 0     未命中 3203
plan 3  prompt=4591  命中 0     未命中 4591
plan 4  prompt=5265  命中 0     未命中 5265
plan 5  prompt=5513  命中 0     未命中 5513
```

五轮全未命中。缓存完全没用上。

### 根因
`plan()` 把工具预算拼在 **system prompt 开头**：

```python
budget = f"\n\n[工具预算] 已用 {used}/{MAX_STEPS} 次。"
sys_prompt = SYSTEM_PROMPT + budget
```

`used` 每步都变，所以 **system prompt 的第一个字符就开始变**。前缀缓存按"从头逐字匹配"工作，开头一变，后面 2000+ token 全部作废。

这不是模型不支持缓存，是调用方式让缓存永远无法成立。

### 修复
让 system prompt 逐字恒定，把会变的内容（预算、跨轮摘要、重试提醒）**追加到 messages 末尾**：

```python
sys_prompt = SYSTEM_PROMPT          # 恒定
notes = [f"[工具预算] 已用 {used}/{MAX_STEPS} 次…",
         "[前几轮发生了什么]…",
         "[系统提醒]…"]
msgs = [{"role": "system", "content": sys_prompt}] + _context_messages(state)
msgs.append({"role": "user", "content": "\n\n".join(notes)})
```

### 修复后
```
plan 1  prompt=2266  命中 0     未命中 2266   0%
plan 2  prompt=3523  命中 2176  未命中 1347   62%
plan 3  prompt=5042  命中 3456  未命中 1586   69%
plan 4  prompt=5941  命中 4736  未命中 1205   80%
plan 5  prompt=6976  命中 5632  未命中 1344   81%
plan 6  prompt=7580  命中 6912  未命中 668    91%
```

累计 prompt 31328，命中 25912 → **82.7%**。按缓存约 1/10 计价，等效输入从 31328 降到约 1.1 万。

**这个修复对所有 provider 都有效**，包括官方 DeepSeek。

## 四、接入第三方中转站的必要前置

`probe_provider.py` 的价值：**接入任何新端点前，先证明它真的返回 tool_calls**。

中转站最常见的两种降级：
1. 不透传 `tools` 字段，模型只能用自然语言描述"我要调用…"；
2. 返回的 tool_calls 结构被改坏，`function.arguments` 不是合法 JSON。

这两种都会让图里所有分支失效，而且**不会报错**，只会表现为"模型不肯调工具"。

本次实测通过：

```
content: 我同时查一下光源时长和缺陷日志。
tool_calls: [('query_light_usage', '{"device_id": "CX-101"}'),
             ('query_defect_log', '{"device_id": "CX-101", "group_by": "station"}')]
usage: prompt=502 completion=188
缓存字段: 128 / 374
```

两个并行调用，参数正确，且缓存字段可用。

## 五、换模型带来的一个新回归（已修）

**I2：** 用户说"CX-101 有点问题，你查一下"，模型跑了 12 步后**自己建了单**，被判越界调用。

这不是模型变笨，是第 6 条规则太松：`根因明确、处置动作明确时才调 create_work_order` —— "查一下"被理解成也包含派工。

修复后 I2 通过（10 步，不建单），W1 仍能正常建单（4 步）：

```
6. 根因明确、处置动作明确时才调 create_work_order。
   用户只说"查一下""看看怎么回事""有点问题"时不要建单——那是诊断请求，不是派工请求。
```

**教训：** 建单是唯一的副作用动作，它的触发条件必须写死边界，不能靠"根因明确"这种软判断兜。

## 六、本地模型的完整证据链

### 上下文必须先修，否则一切结论无效
Ollama 超长 prompt **静默截断**，不报错：

| 设置 | 实际 prompt_eval_count | 耗时 |
|---|---|---|
| 默认（改前） | 2050（截断） | 2.5 s |
| num_ctx=4096 | 2050（**参数无效**） | 2.1 s |
| num_ctx=8192 | 6629（不截断） | 14.2 s |
| 设备级 `OLLAMA_CONTEXT_LENGTH=8192` | **6629** | 13.2 s |

`OpenAI /v1` 端点用 `extra_body={"options":{"num_ctx":8192}}` **透传无效**（实测仍 2050）。
唯一可行：设用户级环境变量 `OLLAMA_CONTEXT_LENGTH=8192` 并重启 Ollama（本机版本 0.40.16）。

### 修好上下文之后，质量仍然不行
| 用例 | 结果 |
|---|---|
| H1 夜班误判 | FAIL（缺 station 维度） |
| H3 11-08 陡变 | FAIL（缺 day 维度） |
| H4 镜头污染 | OK |
| W1 建单 | FAIL（1 步就停，没建单） |

工具选对了（命中率 1.000），但**取证维度不全**——是取证能力问题，不是 tool calling 格式问题。

### 中途停手是它的固有行为
两类典型输出，tool_calls 都是空的：
```
"接下来，我们调用 query_light_usage 查看 2 号工位的光源累计点亮时长…"
"调用 query_calibration 工具查询1号工位的标定记录。"
```

为此加了 `_pending_call` 判据（结尾 160 字同时出现真实工具名 + 动作意向词）和一次 `plan_retry` 退回。但放宽判据后 3 条仍只有 1 条通过——**说明判据不是主因，模型取证能力才是**。

## 八、已知代价与未完成项

1. **步数膨胀**：中转站模型 6–12 步，官方 4–7 步。token 从 21853 涨到 36117（+65%），吃掉了缓存收益的一半。缓存省 64% × 步数涨 1.65 倍 ≈ 净省约 40%。
2. **单条 125–136 s**，24 条全量评测需要 50 分钟以上，本轮未跑完（只跑了 7 条抽样，全 OK）。
3. **缓存有效窗口未知**：DeepSeek 官方缓存要求前缀一致且短时间内重复请求，中转站是否遵守这一点、过期时间多长，均未测。
4. **中转站的价格未知**：没有计价文档，无法核算"每轮评测多少钱"，只能算 token 量。
5. 工具返回压缩（`_slim_result` / `_payload`）上线了，但**实测证明它不是瓶颈**——工具返回本来就不长，token 大头是 system prompt + 7 个工具 schema（每次约 2100）。

## 十、换 provider 对代码的影响面与必做操作（实测）

这一节回答"用中转站会动到哪些代码、还要额外做什么"，全部经过实测，不是推断。

### 10.1 已经做的改造（不需要你再动手）

| 位置 | 改动 | 为什么必须改 |
|---|---|---|
| `app/graph/llm.py` | 三 provider 抽象（`deepseek` / `ollama` / `openai`），`BASE_URL`、`MODEL`、key 全部走环境变量 | 换端点不该改调用方 |
| `app/graph/llm.py` | 新增 `CALL_TIMEOUT`（`FDE_TIMEOUT`，默认 120s，本地 180s） | 见 10.2 第 1 条 |
| `app/graph/nodes.py` | `understand` 的 `timeout=20`、`knowledge` 的 `timeout=30` 改为 `CALL_TIMEOUT` | 同上 |
| `scripts/start.ps1` | key 检查同时认根 `.env` 的 `FDE_API_KEY` 和 `w0\.env` 的 `DEEPSEEK_API_KEY`，并打印 provider/model/base_url | 原来只认 `w0\.env`，切中转站后一键启动会误报"诊断会失败" |
| `app/trace.py`、`build.py` | `run_start` 增加 `provider`、`base_url` | 同一模型名可能挂在多个中转站，只记 `model` 事后分不清这批是谁跑的 |
| `scripts/smoke_web*.py` | 请求超时 120s → 300s | 中转站单条 125–136s，会被自己的测试判成失败 |

### 10.2 换 provider 才暴露出来的三个坑

**坑 1：硬编码超时绕开了 client 配置**

`nodes.py` 里 `understand` 写死 `timeout=20`、`knowledge` 写死 `timeout=30`。`OpenAI(timeout=120)` 是客户端默认，**单次调用传了 timeout 就以单次为准**，所以这两处一直在用 20s/30s。

实测同参同 prompt 连发三次，耗时是 **3.0s / 54.7s / 11.2s**，波动 18 倍。20s 的超时会被偶发击穿，后果是 `understand` 走 fallback——而意图判断是这个项目最核心的指标（此前 192 次 0 错）。它的失败方式很阴：不报错，只在"意图偶尔判错"上体现。

**坑 2：缓存不是全线生效，按 2048 token 块对齐**

| prompt 规模 | 命中 |
|---|---|
| 672 token（understand 类短请求） | 两次都是 **0** |
| 2277 token（真实 plan：system 917 字符 + 7 个工具 schema） | 第 2 次起 **2048 / 90%** |

结论：**只有 plan 能吃到缓存，understand / knowledge 这类短请求永远命中不了。** 上一轮那个 82.7% 是 plan 循环内的命中，方向没错，但别指望把短节点也算进去。

**坑 3：无现象描述时取证会偏**

同一条 `CX-101 误判率有点高，你看看怎么回事`（没有现象描述）：

- 冒烟测试那次：12 步，结论"光源问题基本可以排除"，最终指向镜头污染/模型漂移
- 带现象的 H1（"夜班误判率飙升，白班还好一点"）：9 步，语义正确

不是模型坏，是"现象为空"时它自由发挥。所以 `clarify` 追问现象这一步不能省，否则会拿到一个自信但方向错的结论。

### 10.3 三项兼容性实测（都通过）

| 项 | 结果 | 意义 |
|---|---|---|
| `response_format={"type":"json_object"}` | 原生支持，返回纯 JSON 可直接 `json.loads` | `understand` 不会走 fallback |
| tool_calls | 并行返回 2 个、参数正确 | 图的分支逻辑完全不用改 |
| 连发 12 次 | **12/12 成功** | 一条 12 步的诊断不会触发限流 |

### 10.4 每次换 provider / 改代码后必须做的操作

1. **改 `app/**` 后必须重启 8020**。uvicorn 没开 `--reload`，进程内存里还是旧代码。本轮已重启（新 PID 30648，首页 200）。
2. **评测前确认 8010 mock QMS 在跑**。它宕过一次，导致 W2 失败，模型会写出"连接被拒绝"。
3. **Ollama 只需为 `search_manual` 保持运行**（`nomic-embed-text` 768 维）。诊断主链路不依赖它。
4. 换端点后**先跑 `probe_provider.py`，再跑 `probe_compat.py`**，两个都过再接入，不要直接上评测。

### 10.5 成本与延迟的净账

| | 官方 DeepSeek | 中转站 |
|---|---|---|
| 语义正确率 | 95.8%（23/24） | 抽样 7/7 OK（H5 反而修复） |
| 单条耗时 | 5.9 s | 38–136 s（CPU/网络波动） |
| 步数 | 4–7 | 6–12 |
| 单条 token | 21853 | 36117 |
| plan 缓存命中 | 82.7% | 82.7% |
| 净成本 | 基准 | 缓存省 64% × 步数涨 1.65 ≈ **省约 40%** |

**结论：省钱成立，省时间不成立。** 调 prompt、改代码用官方（5.9s 等得起），批量评测/离线演示用中转站，本地只在断网兜底且接受 25% 正确率。
