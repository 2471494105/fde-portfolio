# P0：补上两个"结构上没有答案"的缺口

日期：2026-11-16
背景：前一轮核对过"用户真实会问什么 × 系统能不能答"，发现两处**不是模型不聪明、而是系统根本没给路径**的缺口。这轮补掉。

---

## 一、缺口 1：工单只能写，不能读

### 1.1 缺口的表现

`app/tools/schemas.py` 原有 7 个工具，其中只有 `create_work_order`（写）。
`work_orders` 表里有 5 条真实工单，但**没有任何工具能读它**。

用户问「CX-101 上次那个工单处理了吗」，模型只有两条路：
1. 编一个 WO 号（最坏）
2. 说"查不到"——但工单明明在库里，这叫**系统的表达缺陷**

这不是提示词能修的，必须补工具。

### 1.2 改法

新增 `query_work_order(device_id="", status="", limit=10)`，在 `app/tools/workorder.py`。

**关键设计：三态，不混成一个"没查到"**（沿用项目一"查不到要拆三态"的教训）：

| state | 含义 | 返回 |
|---|---|---|
| `device_not_found` | 设备编号不在台账 | 明确说"设备不在台账，请确认编号" |
| `no_order` | 设备存在，但没有任何工单 | 明确说"没有工单记录，这是查询结果，不是记录缺失" |
| `found` | 查到 | 按建单时间倒序返回列表 |

**其他细节**：
- `device_id` 自动 `.strip().upper()`，`cx-105` 与 `CX-105` 等价
- `limit` 强制收敛到 `[1, 50]`，防止模型传 1000 把整表拖出来
- `status` 精确匹配；当前库里只有"待处理"一种取值，但接口不写死
- 只读：不写库、不改状态、不建单

### 1.3 实测

| 场景 | state | count | 结果 |
|---|---|---|---|
| CX-101（有 2 单） | found | 2 | WO-20261116-002 / WO-20261115-001 |
| CX-102（无单） | no_order | 0 | "设备 CX-102没有任何工单记录" |
| CX-106（不存在） | device_not_found | 0 | "不在设备台账里，请确认编号" |
| 全厂 | found | 5 | 5 条按时间倒序 |
| `cx-105` 小写 | found | 1 | 归一化生效 |
| `limit=999` | found | 5 | 实际最多 50 |

### 1.4 端到端

输入「CX-101 上次那个工单处理了吗」→ **第 1 步就调 `query_work_order`**，2 步完成。
模型还主动发现了两件我们没让它找的事：
- 两张单疑似重复（同设备同根因，11-15 和 11-16 各一张，只有误判率精度不同）
- 设备档案最新日志是 11-14，早于 11-16 建单时间，"11-15 之后数据没进系统"

### 1.5 Web 端暴露的第二个缺口：lookup 分支只实现了一半

CLI 跑通之后去 Web 端（8020）用真实问法复测，结果**根本没调工单工具**：

```
intent=lookup  steps=2  tools=query_device_profile, query_defect_log
```

回答的是设备档案 + 误判率，一个字都没提工单——等于又退回到"查不到"。

**根因**：`nodes.py` 的 `lookup` 节点是**完全写死的模板**，固定调
`query_device_profile` + `query_defect_log`，结构上没有调用其他工具的位置。
这个设计本身是对的（源码注释写明：刻意不让模型组织文字，防止它替用户补意图，
`cx-104 数据` 就靠这个避免模型自作主张给根因），但代价是 **lookup 只覆盖了"设备数据"这一类查询**。

**修法选择**：不新增意图子类、不加关键词表（已明确否决用规则表判意图），
而是"只要查设备数据，就把该设备的工单一并列出来"。
理由：工单也是这台设备的数据，不需要猜用户是不是想问工单，也就不需要语义判断。

两个细节：
- 工单块**不渲染 `root_cause` 全文**，只给 order_id / 状态 / 严重度 / 派工组 / 建单时间。
  因为 lookup 的合同是"不做根因判断"，把根因描述摆进给用户的文本等于变相给结论，
  也会撞 I6 的 `forbid_words`（"根因："）。
- 设备不存在时直接 `continue`，不再查工单（档案错误已经把问题说清了）。

修后 Web 端：

```
intent=lookup  steps=3  tools=query_device_profile, query_defect_log, query_work_order

### CX-101 历史工单（2 张）
- WO-20261116-002 | 待处理 | 严重度 high | 设备科 | 建单 2026-11-16 10:20:44
- WO-20261115-001 | 待处理 | 严重度 high | 设备科 | 建单 2026-11-15 04:30:00
```

I6 同步复测：含"误判率" ✓、不含"根因：" ✓，未退化。

**教训**：CLI 跑通不等于功能可用。写死模板的分支只有在真实入口用真实问法跑一遍才会暴露。

### 1.6 成本

`query_work_order` 的 schema 占 **543 字符 ≈ 236 token**，作为固定成本出现在每一步的 prompt 里。
8 步用例因此多约 1888 token。这是"补一个工具"的真实代价，不能只说好处。

## 二、缺口 2：8 条告警码在表里，手册里没有

### 2.1 缺口的表现

`alarms` 表存着 8 条真实告警码定义（E-101/E-102/E-201/E-202/E-301/E-401/W-501/W-502），
但 `device_manual_chunks` 的 24 块手册里**一个词条都没有**。

用户问「E-101 是什么意思」→ `search_manual` 检索不到 → 只能答"手册未收录"。
而数据明明在库里，只是没进检索路径。

### 2.2 改法

在 `data/manual_seed.py` 的 `DOCS` 里新增一份文档「告警码对照表 ALM-2026」，9 块：

1. **1.1 告警码编码规则**——解释 E/W 首字母、数字首位对应子系统（1 采集/2 光源/3 标定/4 图像质量/5 判定）、三个严重等级
2. **E-101 ~ W-502 各一块**——含义、等级、常见原因、处置

**为什么 params 一律留空**：`check_doc_conflict` 是按 `params` 的 key 精确比对参数的。
告警码不是"参数冲突"对象，若给它们塞 params，会污染冲突检测的比对集。留空即天然隔离。

**为什么拆 9 块而不是 1 块**：embedding 检索是按块打分的。合成一块会让"E-101"这个词条被 W-502 的内容稀释，命中分数下降；拆开后单块语义纯粹，排序更靠前。

**处置建议里刻意不写具体数字**：避免与手册里已植入的 10 处冲突（亮度 80/65、寿命 8000/6000 等）产生新的冲突源。E-202 的处置只写"按保养计划的光源更换周期"，不写小时数。

### 2.3 实测检索

| 查询 | 首位命中 | 来源 |
|---|---|---|
| E-101 这个告警是什么意思 | **E-101 相机未连接或通讯中断** | score 0.7789 |
| W-502 误判率超阈值 | **W-502 误判率超过设定阈值** | — |
| E-201 光源亮度低于设定值 | **E-201 光源亮度低于设定值** | — |

冲突检测未受影响：`check_doc_conflict("光源亮度设定")` 仍 `has_conflict=True`。

### 2.4 端到端

输入「E-101 这个告警是什么意思」→ intent 判为 `knowledge`，**1 步**完成，
回答包含含义、编码规则（引用块 2）、等级处置、常见原因、影响，并主动补一句
"手册未收录 E-101 的具体复位方式或历史发生频次"——**知道自己不知道的边界**。

## 四、这轮暴露的两个问题（未修，留档）

### 4.1 意图判断的 JSON 解析没有重试（已修 · 2026-11-16）

第一次跑「CX-101 上次那个工单处理了吗」时，`understand` 报：
`意图判断调用失败（JSONDecodeError），退回按设备号判断`
→ intent 被判成 `diagnose`（应为 `lookup`）。

连发同一条 prompt 10 次复测：**10/10 正常**，说明是偶发（中转站偶发返回非 JSON），不是稳定缺陷。

但代码问题是真实的：原来 `json.loads` 与 LLM 调用在**同一个 try 里**，
"解析失败"被当成"调用失败"，整体退回 fallback，**没有重试**。
一次偶发就丢掉整层意图判断，而这个项目最强的指标恰恰是"意图判对"。

**改法**：
1. 新增 `_parse_json_loose()`：① 直接解析 → ② 剥掉 ```json 围栏 → ③ 取第一个 `{` 到最后一个 `}` 兜底
2. `understand` 把"调用"和"解析"拆成两段：
   **调用失败不重试**（避免把延迟叠成两倍），**解析失败重试一次**
3. 仍失败才 fallback，理由分别写明"调用失败"还是"不是合法 JSON"，不再是笼统的同一句
4. trace 记 `intent_parse_retry`，附原文头部 80 字符，便于以后判断是中转站裹壳还是模型跑偏

**验证脚本**：`scripts/test_intent_parse.py`，全程 mock 不联网，可随时复跑。

| 场景 | 旧写法 | 新写法 |
|---|---|---|
| ```json 包裹 | JSONDecodeError | 第 1 次调用即救回（不浪费重试） |
| 前导说明文字 | JSONDecodeError | 救回 |
| 截断的 JSON | fail | fail（该失败就失败，不硬凑） |
| 完全非 JSON | fallback | 重试 1 次后 fallback，理由"不是合法 JSON" |
| 调用超时 | fallback | **不重试**，仍 fallback，理由"调用失败" |
| 正常 JSON | 正常 | 正常（未破坏） |

`_parse_json_loose` 单元层 6 种输入：A/B/C 救回，D/E/F 预期放弃。

**端到端回归**：I2 / I5 / I6 / I9 = **4/4 = 100%**，意图判错 0/4，总耗时 295 s（平均 73.8 s/条）。

### 4.2 工单数据本身有重复

WO-20261115-001 与 WO-20261116-002 是同设备、同根因、内容几乎一致的两张单。
幂等键是"设备+根因分类+日期"，**跨天不生效**，所以第二天重跑就会再建一张。
这是设计上的已知边界，但这轮被模型自己发现并指出，说明它会暴露给客户。
后续要么在 PowerBI 式的"工单看板"上合并显示，要么把幂等窗口从"天"改成"未闭环则不再新建"。

## 五、P0-3：现象为空时的取证规范

### 5.1 原始记录与实际表现对不上

原问题：「CX-101 误判率有点高，你看看怎么回事」（用户没给现象）→ 12 步，结论「光源问题基本可以排除」；
带现象的 H1（"夜班飙升、白班还好"）→ 9 步答对。

按这个记录，问题是"无现象时端到端取证会偏"。

**实测 7 次，0 次复现**：

| 轮次 | 跑法 | 步数 | 终局命中 | 结论落点 |
|---|---|---|---|---|
| 1 | run_eval | 9 | **0.500** | 只命中一个关键词 |
| 2 | run_eval | 8 | 1.000 | 1号工位 + 光源 |
| 3 | run_eval | 9 | 1.000 | 1号工位 + 光源 |
| 4 | run_case | 8 | — | "问题出在1号工位的光源部分，属于硬件侧" |
| 5 | run_case | 7 | — | "根因：1号工位光源超额定寿命（8620h/8000h）" |
| 6 | run_eval（改后） | 8 | 1.000 | 1号工位 + 光源 |
| 7 | run_eval（改后） | 8 | 1.000 | 1号工位 + 光源 |

第 4、5 两次的完整轨迹显示：**第一步就按 station 聚合**，随后主动查了
`query_light_usage`、`query_calibration`、`search_manual`、`check_doc_conflict`。
第 4 次还自己指出三处档案不一致（亮度标准冲突、光源数据是设备级不能按工位拆、
光源更换时间 2024-09-20 早于设备安装 2025-03-12）。

**结论**：原记录里的"排除光源"在当前代码下不复现。
最可能的解释是它发生在**缓存修复之前**——那轮 `plan` 的 system prompt 被截断，
模型只看到半套取证要求。修完之后这批行为已经变了。

### 5.2 真实残留：约 12% 的结论波动

7 次里有 1 次终局命中 0.500：方向对（1号工位），落点不全（没落到光源）。
这比"排除光源"轻，但对现场来说仍算"没说到点上"。

### 5.3 只改一处：`group_by` 加一句起步指引

改 `app/tools/schemas.py` 里 `query_defect_log` 的 `group_by` 描述，追加：

> 不知道选哪个时先查 station——误判最常见的形态是集中在单个工位，而整体误判率看不出这一点。

**为什么只加这一句，不加一整套规则**：

1. `description` 里原本已有「只查一个维度就下结论属于取证不足，硬件类排查至少应再看工位分布」——
   **强度已经够，缺的只是"起步选哪个维度"**，不是"要不要多查"
2. schema 是每一步 prompt 的固定成本。`query_work_order` 一条就 236 token，
   这里每加一句都会按步数放大，7 步用例就是 7 倍
3. 项目既定原则是"取证要求写进工具 description、不写提示词"，
   这句正好落在 description 层，不破原则

改后终局命中 2/2 = 1.000。

### 5.4 顺着测出来更该修的：判定器本身不可信

3 次 eval 里，**语义正确率都是 100%，但终局命中率有一次是 0.500**。
两个数矛盾，说明判定器判"语义正确"时**不要求终局关键词全中**。

顺着这条线往下查，判定器实际有**两个方向相反的缺陷**，一个太松、一个太严，
合起来让"结论对不对"这个最关键的数字完全不可信。

#### 缺陷一：阈值太松（`kw_rate >= 0.5`）

`final_keywords` 命中率只要 ≥50% 就判通过。
H4 的期望词是 `["1号工位", "光源"]`，只说了工位、没落到光源，命中率 0.5，照样判 OK。

**改法**：新增可选字段 `final_required`（必须全部出现的词），语义与 `final_keywords` 分开——

| 字段 | 语义 | 现有用例 |
|---|---|---|
| `final_keywords` | 同义任选，命中过半即可 | `["不存在", "未查到", "CX-101"]` 这类同义表述 |
| `final_required` | 结论必须落在这些点上，缺一即失败 | 目前只有 H4 |

不直接把 0.5 改成 1.0，是因为 25 条用例里有大量"同义词组"
（`["哪一台", "设备编号"]`、`["无法", "没有", "不能"]`、`["3号", "三个工位", "1-3"]`），
一刀切会把它们全判失败。只给真正需要严格判的用例加字段，老用例行为不变（已用 H5 对照验证）。

#### 缺陷二：阈值太严——被一个空格打败

改完阈值后跑 4 次，结果 2 OK / 2 FAIL，失败原因**全部是"缺1号工位"**。
看着像模型系统性漏掉了工位，于是把 `final` 正文拉出来看，发现：

> **根因方向：1 号工位光源已超额定寿命、亮度两次下调……**

结论写得完全正确，只是模型输出的是「1 **空格** 号工位」，而判定器按字面查 `"1号工位" in final`。
**一个空格，把正确结论判成了失败。**

**改法**：比较前先做 `_norm()` —— 去掉所有空白（含全角空格）再匹配，
关键词、`final_required`、`forbid_words` 三处统一。

#### 用已有结论离线重判（零 token，不重跑模型）

`history.jsonl` 里已存了 4 条 H4 的结论全文，直接重判：

| 时间 | 旧判定 | 新判定 | 说明 |
|---|---|---|---|
| 15:55:51 | OK | OK | 一致 |
| 16:00:30 | OK | OK | 一致 |
| 16:05:17 | **FAIL（缺1号工位）** | **OK** | 只因「1 号工位」带空格 |
| 16:09:55 | **FAIL（缺1号工位）** | **OK** | 同上 |

**归一化前通过 2/4，归一化后通过 4/4。**

#### 这条链条的教训

1. "终局命中 0.500"这个信号本身是对的，但**它指的方向是错的**——
   不是模型漏了结论，是测量工具坏了。
2. 如果只修阈值（太松那个），会得到"失败率 50%"的假结论，然后去改模型——
   **改一个本来没问题的东西，越改越乱**。
3. 必须先让测量可信，再谈优化。判定器的两个缺陷方向相反，
   任何只修一边的做法都会把结论推向另一个错误方向。

#### 顺带补的：`run_eval` 现在逐次落盘 `eval/history.jsonl`

`report_eval.json` 只保留最后一次，每次覆盖。上一轮就是因为这个，
"12 步排除光源"那次的具体结论永远查不到了。
现在每次评测都 append 一条 `{ts, id, ok, kw_rate, req_miss, steps, tools, reasons, final 全文}`，
落盘失败不阻断评测。

有了它，才能做上面那种"不花一分钱重判历史结论"的诊断。

### 5.5 诚实的边界

归一化后，目前可查的 6 次 H4 结论**全部正确**（4 条离线重判 + 2 条此前已通过的）。

但这仍不足以说明"稳定"：

1. 6 次全对，若真实失败率是 12%，概率约 0.88^6 ≈ **46%**——有一半可能是运气
2. 更要紧的是：**此前所有被判失败的记录都需要用新判定器重新核对**。
   已知的两次"缺1号工位"全是空格问题，那么更早那些"终局命中 0.500"的记录里，
   有多少同样是空格造成的？现在没法回溯——`report_round1..6.json` 只存了聚合数，没有结论正文。
3. 这也是为什么要补 `history.jsonl`：从这一轮起，每一次的结论正文都留档，
   以后任何"失败率上升"都能在零 token 成本下先做一次离线复核，确认是真失败还是测量问题。

结论：**判定器已修，但"模型在无现象输入下是否稳定"这个问题，现在还答不了**。
要回答它，需要在新判定器下再积累 15–20 次同输入实测。

### 5.6 评测并发化（`--workers`）

25 条串行要 1 小时（实测 142 s/条，每步 15.5 s），太贵。加了 `--workers=N`。

**两个必须处理的坑**：

1. **不能直接并发**：`get_saver()` 是进程内单例，且 `from_conn_string` 只开**一条** psycopg 连接。
   多线程同时写会报 `another command is already in progress`。
   → 并发时给 `run()` 传 `use_checkpoint=False`，每条用独立、无持久化的图（评测本来就单轮）。
2. **建单类必须串行**：`W2` 考的是"再建一次应返回已存在"（幂等），
   与 `W1` 并发会交叉，幂等结果就不可信。
   → 按 `type == "建单"` 分流，W1/W2/W3 强制串行，**且排在并发批之后**，避免与并发批共享 mock QMS 状态。

**实测**：`--only=I5,T1 --workers=2` → 2 条 **11 s**（平均 5.6 s/条），无连接冲突，均判 OK。

**代价**：并发会让中转站排队更久，单条可能从 5 s 排队涨到 15 s，
实际加速比低于 workers 数。

**加速比目前没有可信数字，不写倍数。** 手上这两个数不可比：`--only=I5,T1 --workers=2` 的
5.6 s/条是谷时测的，而 142 s/条是峰时测的，两者之差主要是排队，不是并发收益。
要回答"并发到底快几倍"，必须做受控实验：同 2 条用例、同一时间段、串行与 `--workers=2` 各跑一次。
实验排在谷时和 18 条基线一起做，跑完回填；在此之前任何倍数都是猜的。

**分批校验**：并发批 22 条（H/A/I/T 全部），串行批 3 条（W1-W3），已断言 `set(serial) == {W1,W2,W3}`。
