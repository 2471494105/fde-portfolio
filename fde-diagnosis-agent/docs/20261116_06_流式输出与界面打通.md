# 流式输出与界面打通

日期：2026-11-16
项目：fde-diagnosis-agent（视觉检测设备故障诊断 Agent）
本轮目标：把「等 32 秒白屏」改成「每秒都看得见在干什么」

## 一句话结论

首帧 **0.12 秒**到达，首个节点事件 **0.13 秒**到达。用户不再面对一片空白的等待界面，从第一秒起就知道系统接住了这句话、正在做哪一步、这一步已经跑了多少秒。

---

## 一、为什么必须做：时间到底花在哪

用 `scripts/probe_stream.py`（`astream_events` 探针）实测一条 8 步诊断的节点级耗时：

| 环节 | 累计耗时 | 占比 |
|---|---|---|
| understand（理解问题） | 5.5 s | 15% |
| **plan × 5 次 LLM 调用** | **30.2 s** | **83%** |
| act × 5 次工具执行 | 0.73 s | **2%** |
| verify + finalize | 0 s | 0% |

**结论：98% 的时间在等模型返回，工具本身是毫秒级。**

这条数据直接决定了实现范围——只要把 plan 期间那十几秒的等待可视化就够了，**不需要做 token 级流式**。token 级流式会把复杂度抬到「解析增量 JSON」，而收益只是把一句话拆成几十个字慢慢冒出来，对「我是不是卡死了」这个问题没有任何回答能力。

## 二、两条技术路线的实测取舍

### 路线 A：`astream_events`（弃用）

`scripts/probe_stream_ckpt.py` 验证：async 图执行 + 同步 `PostgresSaver` → 抛 `NotImplementedError`。
LangGraph 要求异步执行必须配 `AsyncPostgresSaver`，而这会重构整个持久化层。多轮会话会直接崩，所以排除。

### 路线 B：同步 `g.stream(stream_mode="debug")`（采用）

`scripts/probe_stream_debug.py` 验证成功，加 `--ckpt`（真 PostgresSaver）也无报错：

- `task` 事件在节点**开始**时即发出：understand task 在 0.03 s，result 5.18 s 后才到
- `task_result` 的 `payload["result"]` 就是 state delta
- 与 `StreamingResponse` 天然兼容（Starlette 会把同步生成器丢进线程池迭代）

**为什么不用 `stream_mode="updates"`**：它只在节点**结束后**才给结果。模型跑的那十几秒里前端依然一片空白，等于没做流式。

## 三、后端实现（`app/web/server.py`）

新增接口 `POST /api/diagnose/stream`，body 与同步接口一致（`{msg, session_id}`），响应 `text/event-stream`。

帧类型：

| 帧 | 字段 | 用途 |
|---|---|---|
| `open` | `thread` | 连接建立，会话落地 |
| `node_start` | `node, label, t` | 某节点开始，前端起计时 |
| `node_end` | `node, label, ms, detail, t` | 某节点结束，前端追加一行 |
| `done` | `final, blocked, steps, tools, evidence, trace_id, thread_id, turn, intent, total_ms` | 全量结论 |
| `error` | `message` | 异常 |

关键设计：

**1. 节点名翻译成人话**
`plan` 对现场人员毫无意义，映射成「判断下一步查什么」；`act` → 「执行查询」；`knowledge` → 「检索设备手册」。内部术语不暴露给用户。

**2. 状态增量翻译成一句话**
`_node_detail(name, delta)` 把 state 增量变成可读描述：plan → 「决定调用 query_device_profile、query_defect_log」或「准备收尾」；act → 「…已返回」；verify → 「数字全部可溯源」；finalize → 「结论 1375 字」。

**3. trace 不能偷懒用 `with`**
`trace.Tracer(...)` 手动创建、手动 `close(error=err)`。原因是 `with` 依赖 contextvar，而流式生成器跑在线程池里，contextvar 跨线程会丢。

**4. token 记不了，如实写在 note 里**
模型 usage 在节点内部产生，`debug` 事件不携带。所以流式运行的 `tokens_total` 恒为 0，`run_start` 的 `note` 写明「stream 模式：只记节点节奏，token 未记录」。

**5. `_validate()` 抽出来共用**
空消息 / 超 2000 字 / session_id 格式，两个接口用同一份校验，避免流式版漏校验。

**6. `_as_obj()` 归一化工具返回类型**
工具返回类型不统一：多数是 dict，`query_device_profile` 这类返回的是已经序列化好的 JSON 字符串。若统一 `json.dumps`，字符串会被套上第二层引号，前端 `JSON.parse` 得到 str 而不是 dict，摘要逻辑全线失效。`_as_obj()` 识别 `{`/`[` 开头的字符串并 `json.loads` 回对象，`_summarize()` 与 `head` 都先过它。验收口径：`json.loads(head)` 的类型必须是 `dict`，不是 `str`。

## 四、前端实现（`app/web/static/index.html`）

新增「实时执行」面板：脉冲点 + 当前动作 + 递增计时 + 已完成步骤逐条追加。

**1. 本地计时器（最关键的一处）**

后端只在节点开始和结束时各发一帧，中间那十几秒（模型正在生成）**没有任何事件**。
如果不做本地计时，数字会一直停在 0.0，「正在判断下一步查什么」看上去就跟卡死一模一样——流式白做了。

所以用 `setInterval(100ms)` 本地刷新计时，与后端事件解耦。实测截图里能看到数字在真实递增：1.5 → 3.5 → 5.5 → … → 129.9。

**2. SSE 帧边界处理**

帧以空行 `\n\n` 分隔。只处理**已经完整**的帧，剩下的半帧留在 `buf` 等下一个 chunk：

```js
while ((idx = buf.indexOf('\n\n')) >= 0) {
  const blk = buf.slice(0, idx);
  buf = buf.slice(idx + 2);
  ...
}
```

如果把每个 chunk 直接当整帧解析，1300+ 字的长结论必然被截断。

**3. `seenDone` 标志**

防止「连接提前结束但界面永远停在正在…」，收不到 `done` 帧时明确报「连接提前结束，没有收到结论」。

  31.94s  [done] steps=10 tools=10 total=31836ms trace=20261116_180611_5bae

### 5.2 界面层：`scripts/watch_stream_ui.py`（CDP 驱动 headless Edge）

这个脚本用 `websockets` 直连 Edge 的 CDP，每 1 秒采样一次 DOM，抓「用户实际看到的界面」。

**跑法 A：knowledge 型（快）**

```
1.0s  正在：理解你的问题
4.3s  正在：检索设备手册       已完成 1 步
11.6s *** 完成 ***  总耗时 11.4 秒
步骤行：
   4.7s | 理解你的问题 | 耗时 4.7s | 意图：knowledge
  11.4s | 检索设备手册 | 耗时 6.7s | 引用 1 条数据
  11.4s | 核对结论依据 | 耗时 0.0s | 数字全部可溯源
  11.4s | 整理结论     | 耗时 0.0s | 结论 512 字
```

**跑法 B：diagnose 型（中转站排队时）**

```
   1.1s  正在：理解你的问题
   5.4s  正在：判断下一步查什么   已完成 1 步
 135.1s  该节点耗时 130.2s
 160.9s *** 完成 ***  共 7 次工具调用，总耗时 160.3 秒
```

**这一次排队恰好是最有力的证据**：单节点卡了 130 秒。没有流式时，用户会盯着白屏 130 秒并认定系统挂了；有流式时，第一秒就有反馈，计时数字一路涨到 129.9，用户清楚知道「它在算，不是死了」。

同一个问题在谷时跑是 24.9 秒，在峰时是 160.3 秒——**差 6.4 倍，全部来自排队**。

## 六、踩过的坑

| 坑 | 表现 | 处理 |
|---|---|---|
| `--virtual-time-budget` 冒充等待 | `--dump-dom` 只快进虚拟时钟、不等真实网络，流式响应还没回来就 dump，DOM 长度 25998→26018，几乎没变 | 必须走 CDP 真等 |
| 列宽 66px 挤爆 | 「理解你的问题」被折成两行 | 改成 `86px 132px 1fr` |
| 完成态文案错 | 显示「正在 完成 160.3 秒」 | 前缀单独成 `#livePrefix`，完成态置空，标签改「总耗时」 |
| 0 token 被误读 | 历史列表显示「0 token」，像在说没花钱 | `/api/runs` 加 `note` 字段，前端对 `tokens==0 && note 含 stream` 显示「流式·未记 token」 |
| 轨迹显示转义 JSON | `{\"device_id\": \"CX-104\"...}` 现场人员读不懂 | 前端加 `shortVal/fmtArgs/fmtHead`，`.tl-v` 改普通字体 |
| 前端解析被截断的 JSON 必然失败 | 后端给的 `head` 是 `json.dumps(res)[:600]`，600 字一截就不是合法 JSON，前端每条都只能显示「太长」 | 后端加 `_summarize()` 在对象仍完整时算摘要，新增 `summary` 字段 |
| 摘要报英文字段名没用 | `字段 key、count、false_positive、rate` | 改成「条数 + 首条关键值」，如 `groups 12 条　首条 key=2026-11-08` |
| 首条值过长 | `search_manual` 首条 `text` 是整段手册正文 | `s0 = v0[:24] + "…"` 截断 |
| 多轮证据不分层会误导 | 界面显示「工具调用 1 次」而结论里有 10 个数字，用户以为都是刚查的 | `_brief(evidence, steps)` 按 `steps` 切本轮、每条打 `current`；前端加灰色「上轮」徽标 |
| 观察脚本浏览器缓存 | 固定 `user-data-dir` 导致改了前端仍看到旧界面 | 每次用 `edge-cdp-stream-<pid>` 全新 profile |
| 重启竞态 | `Stop-Process` 后立即 `Start-Process`，新进程 bind 失败、旧进程继续服务 | 先轮询端口真正释放，再用 `/api/runs` 轮询确认就绪 |
| **工具返回类型不统一** | `query_device_profile` 返回的是已序列化的 JSON **字符串**，`search_manual` 返回 dict；后端对两者都 `json.dumps`，字符串被套上第二层引号 | 加 `_as_obj()` 归一化：识别 `{`/`[` 开头的字符串先 `json.loads` 回来，`_summarize`/`_head` 都走它 |
| **双重编码伪装成前端 bug** | `head` 被套两层引号后，前端 `JSON.parse` 得到的是 str 而不是 dict，落入 `shortVal` 截断分支，界面上看就是「原始 JSON 片段」，看起来像前端没生效 | 定位靠打印 `traceBody.innerHTML` 看 `<pre>` 里的首字符是 `"` 而不是 `{`——多一个引号就是多一层编码 |

## 七、已知未修

1. **流式运行无法记录 token**。要给流式也记 token，得让节点把 usage 写进返回值，属于跨模块改动，本轮未做。
2. ~~**knowledge 结论里的 `[1]` `[2]` 是裸文本**~~ 已修：`inline()` 里加引用角标规则，只匹配 1-2 位纯数字，
   并先把行内代码抽成占位符，避免改坏 `[2026-11-08]` 这类日期和代码里的方括号。四组输入实测通过。
3. ~~**工具调用轨迹显示原始 JSON 转义串**。~~ 已修：后端在对象完整时算 `summary`，前端「参数 k=v + 返回摘要 + `<details>` 折叠原始」，多轮历史证据加灰色「上轮」徽标。
4. **流式轨迹缺业务细节**。`_sse` 里手动 `Tracer` 只写 `node_start`/`node_end`，不写 `plan`/`tool`/`verify` 事件，`runs\*.jsonl` 里只剩 run_start 与 run_end，`steps`/`final_head` 为空——违背「每条运行留完整轨迹」这个卖点。
5. ~~**观察脚本的超时阈值与截图时机**~~ 已修：不再按总时长猜，改成「无进展超时」——`label` 或已完成步数发生变化就重置计时，240 秒毫无变化才判卡死，另外留 900 秒硬上限。根因是排队让总时长不可预测（同一条问题谷时 24.9 秒、峰时 160.3 秒），任何固定阈值都必然在某些时段截到中间态。
6. **客户端断开后服务端继续跑**。脚本超时会留下一条 0.0s 的不完整轨迹记录。断线续跑正是 checkpointer 的价值所在，但需要前端支持「重新接上同一 thread」。
