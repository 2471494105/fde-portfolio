# 校验层引用式溯源与流式轨迹

> 2026-11-16 · 第二个作品项目 `fde-diagnosis-agent` · A 档三项收尾
> 对应 Obsidian：[[双重编码伪装成前端 bug：数引号层数]] 的姊妹篇，本篇讲"指标本身在撒谎"

## 一、三个问题其实是同一类

A1（溯源是假指标）、A2（流式轨迹缺业务细节）、A3（流式不计 token）看着是三件事，
共同点是**界面显示的指标与真实情况无关**：

| 界面写的 | 实际情况 |
|---|---|
| 未溯源数字 **0** | 一个数字都没被检查 |
| 每条运行留完整轨迹 | jsonl 里只有 `node_start` / `node_end` 两行 |
| token 显示 **0** | 根本没记录，不是没花 |

功能缺失用户能发现；仪表盘撒谎用户发现不了，而且会**据此做出错误判断**——
这正是 FDE 现场最不能出的问题。

## 二、A2 + A3：同一个根因，只改一处

### 症状

流式跑一次，`runs\*.jsonl` 里只有：

```
run_start → node_start(understand) → node_end → … → result → run_end(tokens_total: 0)
```

而 `runs\*.jsonl` 的注释写着"记录粒度刻意细到单次 LLM 调用和单次工具调用"。

### 根因

`app\web\server.py` 的 `_sse()` 里创建了 `Tracer`，但**从未把它设为 current**。
节点内部所有可观测代码都走 `trace.current()`：

- `nodes.py` L416 `trace.current().add_tokens(pt + ct)`（plan）
- `nodes.py` L194（understand）、L785（knowledge）
- 各处 `trace.emit("plan"/"verify"/"tool"/"intake"…)`

`trace.current()` 返回 None 时，`emit()` 静默跳过（这是刻意设计，评测时不落盘），
`add_tokens` 直接不执行。于是**所有节点级事件和 token 计数都被无声丢弃**。

对比：CLI 路径 `build.py` 的 `run()` 用了 `with trace.Tracer(...)`，所以一直是对的。
**两条路径只有一条接了观测，问题只在 Web 端。**

### 第一次尝试失败：只激活一次不够

给 `Tracer` 加 `activate()` / `deactivate()`，在 `_sse` 开头调一次。
重跑依然只有 `node_start` / `node_end`。

原因：`_sse` 是同步生成器，Starlette 的 `StreamingResponse` 每次 `next()`
都把它丢进线程池执行，而**每个 threadpool 调用带的是调用方 context 的副本**。
生成器第一句 `yield _frame({"type": "open"})` 之后，本次调用的 context 就被丢弃，
`activate()` 的效果随第一个 yield 一起消失。

### 第二次尝试成功：每轮 next 之前重新激活

改成手动迭代：

```python
it = g.stream({"user_msg": msg}, cfg, stream_mode="debug")
while True:
    t.activate()          # 在本次 next 的 context 里重新设
    try:
        chunk = next(it)
    except StopIteration:
        break
```

`next(it)` 与 `activate()` 在同一次调用内、同一 context，
所以节点执行时 `trace.current()` 有值。`yield` 出去的帧也在同一 context。

### 验收

| 项 | 修复前 | 修复后 |
|---|---|---|
| jsonl 事件 | `node_start`/`node_end`/`result` | 加上 `intake`/`understand`/`knowledge`/`verify`/`plan`/`tool` |
| `tokens_total` | 0 | **1913**（E-101，1 次工具） |
| `result.steps` / `final_head` | 空 | 有值 |

顺带删掉了 `run_start` 里那句 `note="stream 模式：只记节点节奏，token 未记录"`
——致歉式的注释换不来正确的数据，根因修了就该删掉。

## 三、A1：从"能不能查到"改到"有没有引用"

### 旧逻辑的两个洞

```python
# 只校验百分比
for pct in PCT_RE.findall(final):
    if any(abs(n - v) <= 0.5 or abs(n - v/100) <= 0.01 for n in nums): continue
    if _recomputable(v, nums): continue      # nums = 全部证据的数字混池
    blocked.append(f"{pct}%")
```

洞一：**复算用了全部证据混池**。`a/b*100 ≈ v` 在几百个数字里两两相除，
任意编造值都能"凑"出来。

洞二：**只认 `%`，绝对量根本不进校验**。
一条 420 字的告警解释结论 `pct_count=0`，等于一个数都没看，界面照样写"数字全部可溯源"。

### 实测这两个洞有多深

用真实 evidence（8 条工具返回、441 个数字）跑 300 个随机编造的百分比：

| 口径 | 放行 | 拦截率 | 说明 |
|---|---|---|---|
| A 旧口径（全池命中 + 全池复算） | 300/300 | **0%** | 441 个数字两两相除，**必中** |
| B 弱溯源（单条命中 + 单条复算） | 228/300 | 24% | 单条证据 135 个数字时，76% 仍能凑 |
| C 强溯源（直接命中，或算式成立） | 0/300 | **100%** | 随机值不可能凑出成立的算式 |

编造的绝对量（"9200 小时"这类）：

| 逻辑 | 放行 |
|---|---|
| 旧（只校验 `%`） | 200/200，**100%**（根本不进校验） |
| 新（只认直接命中） | 0/200，**0%** |

所以"未溯源数字 0"在旧逻辑下等价于"什么都没检查"，在新逻辑下才是真的 0。

### 新设计：角标 + 四层判定

模型在结论里给每个数量标 `[k]`，k 指向第 k 条工具返回。判定分四层：

| 分支 | 条件 | 处理 |
|---|---|---|
| `cited_ok` | 标了 `[k]`，且该条证据里直接有这个数；或写了算式 `74%（=20/27）` 且分子分母都在该条证据里 | 通过，计入引用率 |
| `cited_bad` | 标了 `[k]`，但该条证据里找不到 | **硬拦**，进 `blocked` |
| `cite_oob` | `[k]` 越界（多为上下文裁剪所致） | 记为未引用，**不判死** |
| `uncited` | 没标角，退回全证据宽口径 | 通过但记为未引用 |
| `recomputed` | 靠两数相除凑出来（弱溯源） | 放行，但**不计入引用率** |

三条设计取舍：

1. **不收窄判定就永远是假指标。** 把"凑出来"也算引用，引用率就永远接近 100%，
   和旧逻辑没有区别。所以弱溯源单独计数、不计入 `cited`。
2. **但也不能一上来把"漏标"判成编造。** prompt 遵从率会波动，大面积误报比漏报更伤——
   人一旦习惯忽略告警，校验层就彻底失效。`uncited` 与 `cited_bad` 必须分开。
3. **`cite_oob` 不判死。** 上下文裁剪会挤掉早期证据，角标越界不等于编造。

### 覆盖面也扩了

```python
_QTY_UNIT = "天|小时|分钟|秒|mm|条|台|次|个|块|倍|工位"
QTY_RE = re.compile(rf"(\d+(?:\.\d+)?)\s*(%|{_QTY_UNIT})")
```

刻意的排除：设备号 `CX-105`、告警码 `E-101`、日期 `2024-08-15`、编号"第 1 号"
——它们是**标识符**，不是论据。加进来只会制造噪声。

单测 11 组全过，其中第 10 组抓出一个真缺陷：`5mm` 被 `105/2024*100 ≈ 5.19` 复算放行。
绝对量靠两数相除凑毫无业务意义，所以**复算只对 `%` 开放**，其它单位只认直接命中。

### prompt 约束

第 10 条（新增）：

```
结论里每个数字后面要标引用编号 [k]。k 表示这个数出自第 k 条工具返回，
按你实际看到的顺序从 1 开始数。
- 单个数字：标定周期 90 天[1]
- 一句话里多个数字同源：标定周期 90 天、允许漂移 0.3mm[1]
- 你自己算出来的比值必须写出算式：74%（=20/27）[1]，分子分母都要在引用的那条证据里。
  校验层会复算，凑不出算式的数字按编造处理。
```

## 四、界面：把假指标换掉

| 位置 | 旧 | 新 |
|---|---|---|
| 结论头部 meta | 未溯源数字 **0** | `引用 3/5`，另有 `未标角 N`、`未溯源 N`（仅在有拦截时显示） |
| 轨迹「校验」行 | 数字全部可溯源（N 个百分比） | `数量 N 个 · 带引用 N · 未标角 N` |
| verify 节点详情 | 数字全部可溯源 | `数量 N 个 · 带引用 N · 未标角 N · 全部可溯源`；若 `qty=0` 则显示「结论里没有需要溯源的数字」 |

第三种文案是刻意加的：`qty=0` 时不能显示"全部可溯源"——那是"没检查"，
不是"检查通过"。实测 E-101 那条 342 字结论就是这种情况（没有带单位的量）。

## 五、坑

1. **观测代码在两条路径上只接了一条。** CLI 走 `with Tracer`，Web 走手写生成器，
   后者漏了激活。凡是"两套入口一套观测"的地方都值得单独查一遍。
2. **同步生成器 + threadpool = contextvar 失效。** 只激活一次必然失败，
   必须每轮 `next()` 之前重新设。这个坑没有报错、没有日志，只能靠实测事件数量发现。
3. **收紧校验口径会改变判定标准。** 从"百分比"扩到"带单位的量"，
   25 条用例的 `blocked` 预期值都要重算——已跑过的 7 条基线结论要重判。
4. **绝对值不能靠复算兜底。** `105/2024*100≈5.19` 能把一个证据里根本没有的 `5mm` 放行，
   这类"看起来合理"的放行是最危险的。
5. **`cite_oob` 必须豁免。** 上下文裁剪导致角标越界，如果判成编造，
   长会话里会突然大量误报。
6. **token 计数依赖 context 而非返回值。** 只要 `trace.current()` 为空就静默归零，
   而无需修改任何调用点——所以这类问题永远不会报错。
7. **文案会把两件事读成一件事。** 第一次跑出来写的是
   "数量 28 个 · 带引用 25 · 未标角 3 · 全部可溯源"——"未标角 3"和"全部可溯源"
   并列，读起来是自相矛盾。`未标角`是漏标，`可溯源`是没有编造，两件事都得说，
   但要分开说：有未标角时改成"未标角 3（全证据里能查到）"。

## 六、验证记录

| 项 | 结果 |
|---|---|
| verify 离线单测 | 11/11 通过 |
| 审计：编造百分比拦截率 | 0% → 24% → **100%**（三档口径） |
| 审计：编造绝对量拦截率 | 100% 放行（旧）→ **0%** 放行（新） |
| 审计：真实值误报 | **0/300** |
| 审计：标错角拦截 | **152/152 = 100%** |
| 流式轨迹事件 | 修复前 3 类 → 修复后 7 类 |
| 流式 token | 0 → 1913（E-101，1 次工具） |
| 端到端·知识型（E-101，142.9s） | `qty=0`（342 字结论里没有带单位的量，模型照样标了 `[1][2]`）→ 界面显示"结论里没有需要溯源的数字" |
| 端到端·诊断型（CX-101，256.8s） | 1485 字 / 9 步 9 工具 / **数量 28 个、带引用 25、未标角 3、拦截 0** / 其中 17 个是百分比 / tokens 23364 |

诊断型这条的关键：28 个数量里 **0 个靠凑**（`recomputed=0`），
说明模型在真实诊断里本来就引用工具原文的数，不需要自己算——
"要求写算式"这条约束在最需要它的场景（复算）反而是兜底而不是主路径。
反过来也说明：如果不要求算式，靠凑的通道一旦打开就再也关不上。

## 七、尚未做的

- **25 条用例的 `blocked` 预期值未重算。** 覆盖面扩大后，之前"0 拦截"的用例可能变成有拦截，
  已跑的 7 条基线结论需要重判一次。这件事和 18 条基线补跑同批做。
- **`cite_oob` 的判定阈值没调。** 目前只要越界就豁免，理论上可以靠"全标大号角标"绕过，
  但被豁免的数字仍会进 `uncited` 统计，能看出来。是否加"越界比例超过 X% 就报错"待定。
- **写算式的通道还没被真正触发过。** 两条端到端（知识型 `qty=0`、诊断型 `recomputed=0`）
  里模型都是直接引用工具原文，没走到"自己算"这条路径，所以算式解析与验证只有单测覆盖，
  没有生产样本。要等一个"必须现场计算"的用例（如"算一下这台设备的误判率涨了多少"）才验得出来。
- **token 仍只统计 LLM 节点，不含工具耗时。** `tokens_total` 是准确的，但"这次贵在哪"还要结合 `tool` 事件的 `ms` 才能回答。
