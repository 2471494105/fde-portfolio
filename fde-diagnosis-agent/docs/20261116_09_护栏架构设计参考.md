# 护栏架构设计参考：六段·三态·四处置

> 2026-11-16 · 跨项目参考档案（不属于某一个作品，可搬到任意 Agent 项目）
> 护栏不是"教模型别出错"，是"模型错了也做不成坏事、说不出假话、烧不掉预算"。
> 本文的结构、判据、处置三部分固定，只有阈值和文案随业务变。
> 实证数字来自本项目（fde-diagnosis-agent）与第一个项目（检验单 RAG）的实测。
> 个人知识库主档：Obsidian `20_技能\生产护栏架构：六段·三态·四处置.md`。

## 一、定位：护栏不是什么

三个边界必须先划清，否则护栏会变成什么都想管、什么都不敢拦的软柿子。

| 不算护栏 | 为什么不算 | 归谁 |
|---|---|---|
| 结论对不对（推理质量） | 数字全对、因果错，护栏一个字都拦不了 | 评测 + 人工复核 |
| 模型答得好不好（质量） | 那是能力，不是约束 | 评测 |
| 业务规则（什么算合格） | 会随客户变，且需要人工确认 | 配置 + 人工 |

护栏只管一件事：**模型自主产生的、系统能独立验证的东西**。凡是系统没有独立对照源的，都不是护栏能管的。

## 二、主公式

护栏只有一种结构：

```
判定(模型给的候选值, 系统独立的对照源) → 三态 → 处置
```

**三态是硬要求，不是优化项**：

| 态 | 含义 | 缺了它会怎样 |
|---|---|---|
| 通过 | 对得上 | —— |
| 拒绝 | 明确对不上 | —— |
| **不确定** | 判不了（越界、模糊、上下文裁剪） | 只能二选一：误拦掉真实值，或者整段跳过 |

二态护栏必然滑向一边。实测：数字溯源只用"能查到 / 查不到"两态时，为了不误伤真实的四舍五入，容差被迫放到 0.5，结果编造值 100% 能通过；收紧到 0.05 不误伤了，但"角标越界"这种真实情况会被当成编造打死。**三态一开，两个方向同时收紧才可能成立。**

## 三、六类检查点

模型的自由度是有限的六种，所以骨架天然六段，顺序也固定（由它们在流程里的位置决定，不由重要性决定）：

| # | 自由度 | 对照源 | 判定性质 | 处置 |
|---|---|---|---|---|
| 1 | 调哪个工具 | 工具注册表 | 确定 | 硬拦 |
| 2 | 参数填什么 | schema + 枚举白名单 | 确定 | 硬拦 + 重试 |
| 3 | 引用哪个实体 | 台账 / 库 | 确定 | 硬拦 + 给候选 |
| 4 | 说的数字哪来的 | 工具返回原文 | **概率** | 标注 + 比例超阈中断 |
| 5 | 声称做了什么 | 系统回读 | 确定 | 硬拦 + 改写措辞 |
| 6 | 用多少资源 | 预算 | 确定 | 截断 + 进收尾 |

### 3.1 工具名：白名单 + 固定回错

```python
impl = TOOL_IMPLS.get(name)
if not impl:
    res = {"error": f"未知工具 {name}"}      # 不抛异常，让模型能自己改
```

要点：**未知工具回结构化 error，不抛异常**。抛异常会让整轮 run 挂掉，而模型其实有能力换成正确工具。

### 3.2 参数：三段兜底 + 运行时不信任 schema

```python
try:
    args = json.loads(tc["function"]["arguments"] or "{}")
except json.JSONDecodeError:
    res = {"error": "参数 JSON 解析失败", "raw": ...}
else:
    try:
        res = impl(**args)
    except TypeError as exc:
        res = {"error": f"参数不匹配：{exc}"}
    except Exception as exc:
        res = {"error": f"{type(exc).__name__}: {exc}"}
```

最容易漏的一条：**JSON Schema 里的 `enum` 只是给模型看的，运行时不会强制**。传一个不在枚举里的 `group_by` 会一路走到 SQL。必须在工具实现里再校验一次：

```python
if group_by not in GROUP_EXPR:
    return {"error": f"group_by 只支持 {sorted(GROUP_EXPR)}"}
```

### 3.3 实体：存在性 ≠ 归属

这是最常被合并、也最常出事的两件事：

| 检查 | 问的问题 | 对照源 | 失败后果 |
|---|---|---|---|
| 存在性 | 这个设备/工单在库里吗 | 台账 | 编造一个不存在的对象 |
| **归属** | 这个对象是**用户提过**的吗 | 用户原话 / 会话 | **拿库里任意对象冒充用户意图** |

存在性校验很便宜，大家都做；归属校验常被忽略，因为它要求把"模型抽出来的实体"和"用户原话里的实体"比对一遍。

本项目现状：`act` 把 `args.device_id` 直接丢给工具，**不比对 `state.device_ids`**——模型可以拿库里任意存在的号去查。存在性有，归属没有。

### 3.4 数字：引用式溯源（概率判定，只能标注）

核心不是"能不能复算出来"，是"你说这个数出自第几条，我去那一条看一眼"。

前者是**开放验证**（池子越大越容易通过，永远不会失败），后者是**封闭验证**（能证伪）。

四层判定：

| 分支 | 条件 | 处置 |
|---|---|---|
| `cited_ok` | 该条证据里直接有；或写了算式 `74%（=20/27）` 且分子分母都在该条里 | 计入引用率 |
| `cited_bad` | 标了 `[k]`，但该条里找不到 | 标注为未溯源 |
| `cite_oob` | `[k]` 越界 | 豁免（多为上下文裁剪） |
| `uncited` | 没标角，退回全证据宽口径 | 通过但单列 |
| `recomputed` | 靠单条内两数相除凑出来 | 标"推断值"，不算引用 |

**一条不变量**：没写出处 ≠ 写了错出处。前者放行但记账，后者硬拦。三者合并成一档，要么大面积误报（人一旦习惯忽略告警，护栏就废了），要么把编造一起放过。

### 3.5 动作：系统回读，不信任模型的自述

`prompt` 里写"不得声称已完成"是**治不了编造的**——被拦后模型照样说"已写入台账"。必须在作答之后做代码层纠正。

同时，外部系统的 HTTP 200 也不等于成功：

```python
if body.get("code") != 0:
    return {"error": "业务失败，工单未创建", "biz_code": body.get("code")}
if not data.get("order_id"):
    return {"error": "返回成功但缺少 order_id"}
```

### 3.6 资源：预算到顶要进收尾，不是报错

```python
if state.get("steps", 0) >= MAX_STEPS:
    return "finalize"      # 收尾出一版缺信息的结论，而不是继续烧
```

要点：**到顶是正常路径，报错是异常路径**。把预算用尽当成异常，用户会看到失败而不是"基于现有信息给了一版结论"。

## 四、处置语义表

不要按"重要不重要"决定拦不拦，按**确定性 × 可逆性**：

| 判定性质 | 后果可逆性 | 处置 | 例 |
|---|---|---|---|
| 确定 | 不可逆 | **硬拦 + 中断** | 越权、删除、重复建单 |
| 确定 | 可逆 | **硬拦 + 让模型重试** | 参数越界、未知工具 |
| 概率 | 结论可信度 | **标注 + 比例超阈才中断** | 数字溯源、语义匹配 |
| 系统不可用 | 阻塞 | **降级但不给结论** | 凭证失效、下游挂 |

这张表能直接解释两个容易吵起来的问题：

- 为什么数字溯源**只标注不中断**——它是概率判定，硬拦会误伤真实值
- 为什么归属校验**必须中断**——它是确定的，且越权后果不可逆

## 五、硬软分层与联动

护栏分两类，**失败语义不同，不能共用一套代码**：

| | 硬护栏 | 软护栏 |
|---|---|---|
| 典型 | 权限、存在性、归属、写动作 | 数字溯源、语义一致性 |
| 判定 | 确定 | 概率 |
| 单次失败 | 立即拦死 | 只记账 |
| 累计失败 | —— | **超阈值才熔断** |

联动条件要具体。本项目建议：`blocked / qty > 20%` 时中断一轮转追问。理由：单个四舍五入对不上是容差问题，大面积对不上就是模型在编——只有后者值得中断。

## 六、八个标准件（可直接搬）

| # | 标准件 | 关键约束 |
|---|---|---|
| 1 | 工具名白名单 | 未知工具回结构化 error，不抛异常 |
| 2 | 参数三段兜底 | JSON 坏 / 未知工具 / TypeError 各一句人话 |
| 3 | 实体不存在时回 `error + known_xxx` | 让模型能改成追问，而不是瞎猜 |
| 4 | 预算到顶进收尾 | 到顶是正常路径 |
| 5 | 输入长度 + 格式校验 | 在路由层做，别等进模型 |
| 6 | **观测设施 try/except 隔离** | 写日志失败不能影响业务 |
| 7 | 引用编号 + 溯源四层 | `[k]` 体系，封闭验证 |
| 8 | 三态错误码 | 凭证失效 / 系统不可用 / 真没有，绝不合并 |

第 3 件和真正的价值：把"查不到"拆成三态，是因为**只有第三态可以考虑给默认值**，前两态给默认值就是拿旧数据冒充实时。

第 6 件本项目**还没做**：`Tracer.write` 的 `_fh.write` 没有 try/except，磁盘满或权限错会抛异常，整轮 run 挂掉。辅助设施不该影响主流程。

## 七、阈值必须实测标定，不能拍

容差是护栏里唯一必须跑数据的参数。本项目的标定过程（8 条真实证据、441 个数字、2000 个随机样本）：

| 容差 | 21 个数字的证据 | 135 个数字的证据 | 平均命中率 |
|---|---|---|---|
| 0.5 | 12.4% | **27.8%** | 18.4% |
| 0.05 | 0.8% | **2.8%** | 1.9% |
| 0.01 | 0.8% | 2.8% | 1.9% |

结论：**0.5 在数字密集型证据里等于没有护栏**。收到 0.05 才勉强可用。

还有一个更隐蔽的通道：比率口径 `v/100` 的容差。原来 0.01 时，`91.7%` 的 `v/100=0.917` 会撞上证据里的 `0.92` 就算"命中"——数字一密，任何百分比都能找到"一半的邻居"。收到 0.001 才干净。

**方法**：写一个脚本，随机生成样本，统计在真实证据上的命中率，命中率超过 5% 就说明容差太宽。这一步不做，后面所有"拦截率 100%"都是自欺。

## 八、七种假护栏

都是本项目或项目一真实踩过的，共同特征是**界面显示绿、实际没测**。

| 假护栏 | 表现 | 怎么识破 |
|---|---|---|
| 分母为 0 的绿灯 | "未溯源 0"，其实 `qty=0` 一个数都没检查 | 凡能输出"0 错误"的指标，必须同时输出"检查了多少" |
| 只认一种单位 | 只校验 `%`，绝对量全部放行 | 断言覆盖面，别信"已校验"四个字 |
| 混池复算 | 拿全部证据的数字两两相除 | 池子越大越"通过"，本身就是问题 |
| 宽容差 | 容差 0.5，密集证据里谁都能命中 | 跑命中率实验，超过 5% 就别信 |
| 观测没接上 | 有 tracer，但从没 activate | 数**事件类型个数**，不数"有没有文件" |
| 未知当放行 | 未知角色静默归最低权限 | 未知必须显式拒绝 + 记录 |
| 折叠承载权限 | 用 `<details>` 折叠敏感内容 | 折叠 ≠ 不传，数据已经在客户端了 |

第七种特别要记：**折叠、置灰、隐藏都不是权限控制**。数据只要下发到客户端，就等同于公开。

## 九、新项目开工检查表

开第三个项目时，对着这张表逐格填，填不满就是有缺口：

| 检查点 | 要填的东西 | 填不出的后果 |
|---|---|---|
| 工具名 | 白名单在哪、未知怎么回 | 模型会瞎调 |
| 参数 | 每个 enum 在运行时校验了吗 | 越界值直达 SQL/文件 |
| 实体 | 存在性 + **归属**分别怎么查 | 拿任意对象冒充用户意图 |
| 事实 | 什么算"必须溯源的事实"、标识符怎么排除 | 误报淹没真问题 |
| 动作 | 系统怎么回读、HTTP 200 之后还看什么 | 模型说"已写入"而实际没写 |
| 资源 | 步数 / token / 时长上限，到顶去哪 | 无限烧钱 |
| 观测 | 写失败会不会影响主流程 | 日志设施拖垮主流程 |
| 处置 | 每条判定的确定性 × 可逆性 | 概率判定被硬拦，或确定判定被放过 |
| 阈值 | 用什么真实数据标定的、命中率多少 | 所有拦截率数字都是自欺 |

## 十、本项目（fde-diagnosis-agent）盘点

**已接进主流程 17 项**：输入长度上限（2000 字）/ session_id 正则 / runs 路径白名单 / 意图判失败兜底 / 无设备号降级追问 / `ask_user` 节点 / 工具调用异常兜底 / `group_by` 白名单 / 设备存在性 + `known_devices` / 工单三态（业务码 + `order_id`）/ 步数熔断（`MAX_STEPS=12`）/ 上下文裁剪（`MAX_CTX_TURNS=2`）/ 结论溯源四层 / LLM 超时（`CALL_TIMEOUT=120`）；2026-11-16 晚补的三项：`act` 归属校验（`device_id` 必须落在 `state.device_ids`，空号放行以支持全厂查询）/ `create_work_order` 六项入参校验 + 设备存在性三态（`device_not_found` 与 `system_unavailable` 分开）/ `Tracer` 全链路 try/except 隔离（写失败即置空，不再逐条重抛）。

## 十一、一句话判据

**每个护栏格都问一句：这个判定，系统有没有独立的对照源？**

- 有 → 它是护栏，按"确定性 × 可逆性"定处置
- 没有 → 它不是护栏，别放进护栏层，否则会得到一个看起来很严、实际全靠模型自述的假防线
