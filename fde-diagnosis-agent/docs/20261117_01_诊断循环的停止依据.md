# 诊断循环的停止依据：把"为什么停"做成一个字段

日期：2026-11-17
状态：有效

## 一、改之前是什么样

`understand → plan ⇄ act` 这个循环，**结束有三条来路**，全部汇进同一个出口：

| 来路 | 触发条件 | 代码位置（改前） |
|---|---|---|
| 步数耗尽 | `steps >= MAX_STEPS(12)` 且模型还发 tool_calls | `route_after_plan` 直接 `return "finalize"` |
| 模型自己收手 | 这一轮不给 tool_calls | `route_after_plan` 落到 `return "verify"` |
| 计划写了但没执行 | 正文写了"接下来调用 X"、无 tool_calls | `plan_retry==0` 时退回 plan 一次 |

三条路径在报告里长得一模一样：一次 **12 步仍没结论、被预算掐断**的运行，和一次 **3 步数据够了、干净收工**的运行，都是 `OK / 步数 12 / 语义 1/1`。

但这两件事的可信度差着量级：前者是半成品，后者是可交付结论。**事后拿不到任何归因线索。**

## 二、还有一处只写不读

`UNDERSTAND_PROMPT` 要求模型输出 `missing: ["还缺什么信息才能继续"]`。Grep 全文件后确认，这个字段只出现在三处：

1. `understand` 的返回值
2. `ask_user` 拼追问文案
3. `trace.emit("understand", missing=...)` 的日志

**`plan` 完全没有读它。**

于是模型每轮做决策时，只看得到 `[工具预算] 已用 {used}/12 次`——这句只有**上限语义**（还剩几次），没有**够用语义**（已有什么、还缺什么）。中间 3–9 步这段最贵的区间里，模型没有任何判断依据。

这是"同一份事实存两份"的第 6 个实例：模型第一轮写下"还缺什么"，之后每轮却看不到自己写的东西，写了一份、没人读、不报错。

## 三、一手依据（Anthropic）

### 1. `stop_reason` 是 7 个值的枚举

```
StopReason = "end_turn" | "max_tokens" | "stop_sequence" | "tool_use"
           | "pause_turn" | "refusal" | "model_context_window_exceeded"
```

来源 `https://platform.claude.com/docs/en/api/messages`

关键在最后两个：`max_tokens` 和 `model_context_window_exceeded`。**预算耗尽被单独列为一种停止原因**，不和 `end_turn`（正常完成）混在一起。

### 2. 完成与预算是两件事

> "During execution, it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) **to assess its progress**. Agents can then pause for human feedback at checkpoints or when encountering blockers. **The task often terminates upon completion, but it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control.**"

来源 `https://www.anthropic.com/engineering/building-effective-agents`（2024-12-19）

这句话用了两个并列的"但"：`terminates upon completion` 是**任务完成**；`maximum iterations` 是**维持控制**。前者是结束条件，后者是安全阀。混成一个，就再也分不出"做完了"和"被掐断了"。

### 3. verify 在循环里，不在循环外

Claude Agent SDK 的官方 loop 形状：

```
gather context -> take action -> verify work -> repeat
```

来源 `https://claude.com/resources/articles/building-agents-with-the-claude-agent-sdk`（2025-09-29）

本项目原先把 `verify` 放在循环**外**（只在出结论后校验引用），循环过程中完全不验证"已拿到的数据够不够"，因此只能靠"步数快用完"来停止。

## 四、决定

### 4.1 三个停止原因，对齐 Anthropic 语义

| 本项目取值 | 对应 Anthropic | 含义 | 路由去向 |
|---|---|---|---|
| `need_more` | `tool_use` | 模型还要调工具，循环继续 | `act` |
| `enough` | `end_turn` | 模型不再调工具，正常收工 | `verify` |
| `budget_exhausted` | `max_tokens` | 还想继续但额度已尽，结论是半成品 | `finalize` |

定义（`nodes.py`）：

```python
def _classify_stop(has_tool_calls, steps, max_steps=MAX_STEPS):
    if has_tool_calls:
        return STOP_BUDGET_EXHAUSTED if steps >= max_steps else STOP_NEED_MORE
    return STOP_ENOUGH
```

**关键一条：`budget_exhausted` 只在「还想继续 + 额度已尽」时成立，不是「步数满 12」就成立。**
步数满了但模型自己说够了，仍然是 `enough`——这正是 Anthropic 要把 `end_turn` 和 `max_tokens` 分成两个值的理由：一个是被截断，一个是被完成。

### 4.2 `missing` 每轮送进 plan 的 notes

`_plan_notes(state, used)` 里新增一段：把 `understand` 抽出的缺口原文列给模型，并给出对照要求——

```
[你一开始判断还缺的信息]
- 该工位的历史标定记录
- 光源已用时长
对照上面这些：已经补齐就停止取证、直接给结论；没补齐就只查还缺的那一条。
```

同时把预算提示的措辞从**只讲上限**改成**讲够不够**：

> 判断标准不是「还剩几次」，而是「够不够」：能给出根因和处置就停，不够才继续。

### 4.3 `stop_reason` 进三个出口

- `trace.emit("plan", ..., stop_reason=..., gaps=...)`：本轮为什么停、这一轮送进去的是哪几条缺口
- `result_event`：`result` 事件加 `stop_reason` 字段（CLI 与 Web 共用同一份定义）
- `finalize` 的跨轮摘要：`结束=enough` / `结束=budget_exhausted`，下一轮模型能看出上轮是否被掐断

## 五、取舍

### 为什么从响应结构推导，而不是让模型输出一个停止字段

三个理由：

1. **Anthropic 服务端的 `stop_reason` 本身就是从响应结构推导的**：有没有 `tool_use` 块决定 `tool_use` / `end_turn`，输出是否被截断决定 `max_tokens`。不是模型自己写一句"我要停了"。
2. **零成本**：不额外调模型、不多读 token。`plan` 本来每轮就要发一次请求，`has_tool_calls` 和 `steps` 都是现成的。
3. **不会漏写**：如果让模型在正文里声明停止原因，它会在发 tool_calls 时正文为空、或者干脆不写。那样就从"确定的信号"退化成一个"可能缺失的字段"——正是这次要消灭的毛病。

### 为什么不做程序硬判定（"调过某几个工具就强制 finalize"）

Anthropic 给的是一条判断准则（assess its progress），执行者仍是模型。把业务判断写死在代码里，等于用规则替代诊断能力，遇到规则没覆盖的故障就完全失灵。

### 为什么 `missing` 是"初始缺口清单"而不是"每轮更新的坑位状态机"

模型每轮都能看到 tool result，它自己知道填没填上。给它一份第一轮写下的清单作为锚点，比让它维护一个需要每轮重写的状态字段更可靠——后者多一个可能不遵从的格式要求，且没有回归手段。

## 六、验证

### 单测：44/44（0.04 s，不连库不发 HTTP）

新增 8 条，其中三条有区分力：

| 断言 | 区分什么 |
|---|---|
| `test_budget_exhausted_only_when_still_wanting_more` | 同一个 `_classify_stop(False, 12)` 必须返回 `enough`。**把两者写成同一个值的实现会正好挂在这一行。** |
| `test_missing_reaches_plan_notes` | 缺口原文必须真的出现在 notes 里——不是"代码里看起来接了线" |
| `test_empty_missing_adds_no_blank_section` | 没缺口时不塞空标题：「缺口是空的」和「这一轮没判断出缺口」不是一回事 |

`_plan_notes` 从 `plan` 里抽成纯函数，就是为了这一类断言。原来内联在 `plan` 里，写错或漏传只有真跑一次模型才看得出来，而模型不遵从是静默的。

### 真实用例探针：三句原话各判一次

| 输入 | intent | missing |
|---|---|---|
| `3号线 CX-101 夜班误判率飙升，白班还好一点，帮我查下原因` | diagnose | 3 条 |
| `cx-104 数据` | **lookup** | 2 条 |
| `CX-104 最近误判有点多，是不是光源问题？` | diagnose | 3 条 |

结论：`missing` 在真实用例上**确实非空**，接线不是"代码里接了、数据上空的"。

附带发现：`cx-104 数据` 现在判成 `lookup`，**不再走诊断循环**。这解释了 11-16 那张截图里输入"cx-104 数据"却跑满 7 次工具调用的现象——当时它被判成了 diagnose。

### H1 实测（`report_20261117_1113_cc9fbf5.json`，`code_hash=0e435040d921`）

| 指标 | 值 |
|---|---|
| 语义 | 1/1 |
| 明确出处率 | 16/17 = 94.1% |
| 步数 | 8 |
| 预算耗尽 | **0/1** |
| 判断够了收工 | 1/1 |
| 耗时 | 155 s |

步数从改前的 10 降到 8，`stop_reason` 确实采到了 `enough`。

**注意样本量**：这是单条、单次，"步数从 10 降到 8"不能当成普遍结论——模型本身有随机性，中转站排队也会影响耗时。要判断这次改动是否普遍减少步数，得跑全量。

## 七、遗留

| 项 | 状态 |
|---|---|
| 全量 25 条未在本次改动后重跑 | 未做。当前只有 H1 一条的单次数据 |
| `budget_exhausted` 从未被真实触发过 | 未观察到。真触发时结论是半成品，需要单独看它的质量 |
| `missing` 只由 `understand` 判一次 | 循环中不更新。模型能不能凭"初始清单 + 工具返回"自己收敛，需要更多样本 |
| verify 仍在循环外 | 本次只补了"停止依据"，没动 verify 的位置。Anthropic 把 `verify work` 放在循环里，这是下一步可考虑的点 |
| `trace_ok` / `trace_rate` 字段名与语义不符 | 语义已改为 `not misquoted`，字段名仍是旧的，未改 |

## 八、这份文档能回答什么

- 想知道"这次运行为什么停了、是不是被预算掐断的" → 看 `stop_reason`，不要看 `steps`
- 想判断某份报告能不能引用 → `budget_exhausted` 不为 0 的那几条，结论是半成品
- 想知道"为什么不让模型自己声明停止原因" → 第五节第一条
