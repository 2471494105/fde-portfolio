# 区间值：引用单位决定表达力

日期：2026-11-17
状态：有效

## 一、改之前：上界根本不参与校验

结论里有大量区间：`误判率 10%~25%`、`需要 2–4 条证据`。claim 结构里只有一个 `value`：

```json
{"text": "复位后预计降到 6%~99%", "value": 6, "unit": "%", "ref": "1#rate"}
```

`_verify_claims` 只拿 `value` 和字段比。`6` 对上了就放行，`99` 从来没被检查过。

这不是"漏了一条规则"，是**位置只有一个，模型只能把下界塞进去，上界无处可写**。

## 二、一手依据：引用单位是"片段"，不是"数字"

Anthropic Citations 的结构里，一条引用是这样：

```json
{"type": "char_location",
 "cited_text": "The exact text being cited",
 "document_index": 0,
 "start_char_index": 0, "end_char_index": 20}
```

字段分工是整套设计里最要紧的一点：

| 字段 | 谁产生 |
|---|---|
| `cited_text`（原文） | **API 从文档里抽出来** |
| `start/end_char_index`（位置） | 模型给 |

官方原话：「the API parses citations into the response formats described in the following sections and **extracts `cited_text` directly**, citations are guaranteed to contain valid pointers to the provided documents.」

`cited_text` 不计输出 token，回传也不计输入 token——因为它不是生成的，是回填的。

**这条依据的意义不在"Anthropic 怎么实现"，在于"引用单位是什么形状"这个判断：**

> 一个引用位置能担保的，只有**落在那个位置上的东西**。
> 数值字段里的 `0.1541` 只担保 `15.41%` 这一个数。它担保不了 `10%~25%`。

所以区间不是"字段不够用"，是**位置选错了**——拿一个精确位置去担保一个不精确断言。

## 三、规则：三种情形，各自归属不同

| 情形 | `ref` | 结构 | 校验 |
|---|---|---|---|
| 数从**数值字段**抄来 | 指向该字段 | `value` 单点 | 必须精确等于字段值 |
| 数从**文本字段**抄来 | 指向该字段 | `value` + `value_max` | 两端都必须出现在那段原文里 |
| 数**不是抄的**（区间归纳、预测、算式） | `null` | `value` + `value_max` | 标灰放行，不计失败 |

**核心约束只有一条：`ref` 指向数值字段时，不许写 `value_max`。**

工程上的理由：`ref` 指着一个精确位置，却用它担保一个不精确的断言，这是**引用写错**，不是**表达力不够**。
两者性质不同：前者该判失败，后者该标灰放行。混在一起处置，等于要么放过伪引用，要么逼模型把有依据的区间也写成单点。

## 四、实现

`SYSTEM_PROMPT`（claims 规则段）：

```
- 结论里出现区间（「6%~11%」「2–4 条」）时写成 value + value_max 两个数，
  value 是下界、value_max 是上界。
  ref 指着某个具体数值字段时禁止写 value_max：那个位置只担保一个精确值，
  你要说区间就说明这个区间不是它给的，ref 必须写 null。
  ref 指着整段文字字段（原文里本来就写着「上升 10%-25%」）时可以写，
  但两个端点都必须能在那段原文里找到。
```

示例第三条同时改成 `{"value": 6, "value_max": 11, ...}`——原来那条示例自己就只写了下界，是个活标本。

`_verify_claims` 在单点判定**之前**插一段区间分支，顺序固定：

| 步 | 判断 | 处置 |
|---|---|---|
| 1 | `lo` / `hi` 转 float 失败 | `ref_bad`，`（区间端点不是数字:…）` |
| 2 | `hi < lo` | `range_bad`，`（区间上下界写反:…）` |
| 3 | `got` 不是字符串（ref 指数值字段） | `range_bad`，`（ref 指向数值字段 …，撑不住区间 …）` |
| 4 | 文本字段但只有一端匹配 | `range_bad`，`（区间 … 与该字段原文对不上）` |
| 5 | 两端都匹配 | `path_ok` / `cited_path` / `cited_ok` / `range_ok` 各 +1 |

第 3 步是关键：它是"精确位置不能担保不精确断言"这条设计在代码里唯一的落点。

`stats` 新增 `range_ok` / `range_bad`，`eval/run_eval.py` 汇总与 `summary` 同步加这两个字段，并单独打印一行：

```
区间引用      {range_ok} 成 / {range_bad} 败
```

**两个数必须成对出现**：只报成立数会让人以为"区间没问题"，只报失败数又看不出模型到底用没用区间。

## 五、验证

### 单测：49/49

新增 `RangeClaimTest` 五条，其中一条是**反向断言**——

> `ref: "1#rate"`（字段值 0.1541）配 `value_max: 25`，必须判失败。

只要实现里少了"数值字段禁 value_max"这条，这一条就会挂。只用"能放行"做合同，会被宽泛实现骗过去。

另外四条分别覆盖：文本字段两端都在（成立）、缺一端（判失败）、`ref: null`（标灰不计失败）、上下界写反（判失败）。

### H1 真跑：三次，两轮同一代码

| 报告 | `code_hash` | 语义 | 出处率 | 步数 | 引用写错 | 区间 |
|---|---|---|---|---|---|---|
| `1113` | `0e435040` | OK | 16/17 = 94.1% | 8 | 0 | 无（该版本无区间校验） |
| `1130` | `a0cdb9e9` | **FAIL** | 14/17 = 82.4% | 8 | 1（2/3 号工位 rate 对调） | **1 成 / 0 败** |
| `1134` | `a0cdb9e9` | OK | 15/15 = 100% | 7 | 0 | **1 成 / 0 败** |

**`1130` 的失败与区间无关**。那两条 `path_bad` 都是单点 claim，没有 `value_max`，压根没进区间分支——
模型把 2 号工位的 11.39% 和 3 号工位的 4.84% 抄反了，校验器拦住了"抄串"。

同 `code_hash`、同用例，`1130` FAIL 而 `1134` OK，说明是**模型抽样波动**，不是改动引入退化。

**这次真跑回答了之前悬着的一个问题**：模型会不会把本该单点的值写成立区间（比如 `15%~15%`）？
两轮 H1 的答案是——各出现一次合法使用（两端都在原文里），**零次滥用**。

## 六、取舍

**为什么数值字段 + `value_max` 必须判失败，而不是标灰放行。**
标灰的语义是"程序无从判断"。这里程序完全能判断：字段里只有 `0.1541`，上界不是它给的，模型自己编的。
把它标灰放行，等于承认"精确位置可以为任意断言背书"，那所有精确性都没了。

**为什么 `ref: null` 允许写区间。**
区间归纳（"从 11-07 到 11-08 涨了约 4 倍"）、预测（"复位后预计降到 6%~11%"）、算式结果，
本来就不属于任何单一字段。判死会逼模型乱填 `ref`，那比标灰更糟。

**为什么没选"把校验放宽到全证据池"。**
全池意味着"只要某条证据里有这个数就算有出处"。区间上界最容易在全池里凑巧命中——
那就变成"搜得到就算引对了"，与引用是"指向某个位置"的定义相悖。

**为什么不给 `value_max` 加第三种校验口径（比如要求两端在同一句里）。**
同一句是文本层面的约束，`_value_match` 只做数值比对，加"同句"要引入分句逻辑。
当前先保证"两端都在该字段原文里"，粒度够用；真出现跨段落拼接的伪引用，再收紧。

## 七、踩到的坑

**断言串少了一个字，看起来像实现错了。**

`test_range_missing_one_endpoint_is_misquoted` 一直 FAIL，但单独复现该用例时输出完全正确：

```
misquoted: ['上升 10%~40%（区间 10.0~40.0 与该字段原文对不上）']
```

断言写的是：

```python
any("与字段原文对不上" in m ...)
```

**实现输出的是「与该字段原文对不上」，断言里少了"该"字。**

排查路径值得记：先怀疑实现（打印实际输出）→ 输出正确 → 怀疑测试环境（单独跑、同模块内跑）→ 都对 →
打印两边的字符码点（`hex(ord(c))`）→ 字符串看着一样但不匹配 → 逐字比对发现差一个字。

`repr` 不通用的地方就在这：两个中文串在 `repr` 里都"看起来正常"，只有数长度或数码点才暴露。
**以后凡是"字符串看着一样但 `in` 不成立"，直接数长度，不要靠眼睛。**

## 八、遗留

- **全量 25 条未在区间版本上重跑**。当前只有一条 H1 的 OK 锚点（`1134`），n=1 不能算通过率。
- **`verify` 仍在循环外**。Anthropic 把 `verify work` 放在 agent loop 内部（`gather → act → verify → repeat`），
  本项目只补了"停止依据"，没动 verify 的位置。是否搬进循环，尚未讨论。
- **`RangeClaimTest._verify` 与 `ClaimContractTest._verify` 是两份复制**。改了 `trace` 的构造方式要改两处，可能漂移。
  暂不抽公共构造器：两个类的 payload 不同，抽出来要加参数，收益不明显。
- **模型是否会把 `2–4 条` 这类"计数区间"也写成 `value_max`，未经观察**。H1 里出现的唯一一次区间是百分比区间。
