# 验证进循环：判完就终局，等于没验证

日期：2026-11-17
状态：有效

## 一、改之前：verify 是终点，不是检查点

图长这样：

```
plan ⇄ act ──(模型判断够了)──→ verify → finalize
```

`verify` 判完就出结论，**失败没有回头路**。`misquoted` 只进两个地方：报告的 `reasons`、`trace.emit` 的日志。**一个字都没回喂给模型。**

所以本项目原先做的是"评审"，不是"验证循环"——两者差在有没有反馈。

有实测样本说明代价。11-17 那次 H1（`report_20261117_1130`）：模型把 2 号工位的 `11.39%` 和 3 号工位的 `4.84%` 抄反了。`_verify_claims` 准确抓到：

```
2 号工位误判率仅 4.84%（字段值 0.1139 ≠ 4.84%）
3 号工位误判率 11.39%（字段值 0.0484 ≠ 11.39%）
```

**但抓到的时候已经在 finalize，只能判 FAIL。** 同一句话如果当时回喂过去，模型自己能改——它只是抄串了，不是不知道。

## 二、一手依据

`https://claude.com/resources/articles/building-agents-with-the-claude-agent-sdk`

三处原文：

| 原文 | 它给出的结论 |
|---|---|
| 「In Claude Code, Claude often operates in a specific feedback loop: **gather context -> take action -> verify work -> repeat**.」 | verify 是**环内**的一跳，后面还有 `repeat`。配图里的回流箭头从 `Verify work` 指回 `Gather context` |
| 「The Claude Code SDK **finishes the agentic loop by evaluating its work**. Agents that can check and improve their own output are fundamentally more reliable—they **catch mistakes before they compound, self-correct when they drift**」 | 验证的价值在"**在错误累积之前**抓住"。等到终点才判，错误已经累积完了 |
| 「The best form of feedback is providing **clearly defined rules** for an output, then **explaining which rules failed and why**」 | verify 的产出不是布尔，是**失败原因**。三种方式（定义规则 / 视觉反馈 / LLM as judge）里排第一，也是唯一不用额外调模型的 |

第三句是可执行的那句。它把 verify 的输出格式定死了：**要说清哪条规则、为什么失败**，否则模型只能猜。

## 三、改法：加一个 check 闸口

```
plan ⇄ act
  │
  (enough)
  ↓
check ──(通过)──→ verify → finalize
  │
  (不通过，且还没回环过)
  ↓
plan（messages 末尾追加"哪条规则、为什么失败"）
```

要点：

- **复用 `_verify_claims`**，不另写一套判定。统计用 `_new_stats()` 造的临时壳，判完丢弃——正式统计仍归 `verify`，两边都落一份会让汇总翻倍。
- **回环上限 `MAX_CHECK_RETRY = 1`**。一次机会够用：抄串这类错误一次就能改，改不了说明它确实不知道。
- **`budget_exhausted` 不经过 check**，仍直接 `finalize`。预算已尽，回环等于拿半成品再赌一次。
- **不在 check 里重试"没按契约输出"**。上一轮就没写出合法 JSON，重跑一次大概率还是写不出，白花一轮。

### 回喂文案

```
[引用未通过]
- 2 号工位误判率 4.84%（字段值 0.1139 ≠ 4.84%）
请重新输出完整的 claims JSON：把数字改成字段里的实际值；如果这个数确实是
算出来的、数出来的或预测值，就把 ref 改成 null 并在 text 里保留算式；
如果判断是证据不够，就继续调工具补齐，不要硬写结论。
把指错的 ref 直接改成 null 不算修正。
```

三句必须都在：

1. **具体值**（`0.1139` 和 `4.84` 都出现）——只说"引用有误"，模型只能猜该改哪个数
2. **两条出路**（改值 / 改 null 并说明）——不给出路，它可能硬改成一个同样错的数
3. **堵死绕过**（"把指错的 ref 直接改成 null 不算修正"）——见下节

## 四、新开的作弊面：拿 `ref: null` 换通过

这是这次改动唯一真正的新风险。

`null` 的语义是"这个数没有直接出处"，标灰放行、不计失败。所以模型有一条零成本过关的路：

```
指错了 3 个 ref → 全改成 null → misquoted 清零 → 通过
```

那些数从"**指错了**"变成"**没指**"。后者不报错，却比前者更差——前者至少暴露了它想指哪里。

对策不是把 `null` 也判死（那会逼模型乱填 ref，比放行更糟），是**比较回环前后的 `unsourced` 数量**：

```
回环后未溯源数字从 0 条涨到 2 条：把指错的 ref 改成 null 不是修正，是把引用问题换成了没引用
```

这条记进 `check_notes`，由 `verify` 并入最终 `misquoted` → 判失败。

**要防的是"改完还不如不改"，不是"不许用 null"。** 本来就有 3 个 null 的结论，回环后还是 3 个，不算绕；从 0 涨到 2 才是。

## 五、实现清单

| 位置 | 改动 |
|---|---|
| `app/graph/nodes.py` | `MAX_CHECK_RETRY=1`；`check()`；`route_after_check()`；`_new_stats()` 抽出；`route_after_plan` 的 `enough` 出口从 `verify` 改成 `check` |
| `app/graph/nodes.py` `verify` | `misquoted` 初值改为 `list(state.get("check_notes") or [])`，让 check 抓到的问题能进最终判定 |
| `app/graph/state.py` | 加 `check_retry` / `check_action` / `check_notes` / `check_unsourced0` |
| `app/graph/build.py` | 加 `check` 节点 + 条件边 `{"plan": "plan", "verify": "verify"}`；`result_event` 加 `check_rounds` |
| `eval/run_eval.py` | `judge` 记 `check_rounds`；汇总与 `summary` 加 `check_rounds_n`；单独打印"引用自查回环"一行 |

`result_event` 必须单列 `check_rounds`：只报 `misquoted` 为空，会把"一次就干净"和"被拦下改过才对"混成同一个"没问题"，而后者本身就是模型稳定性的指标。

## 六、验证

### 单测 56/56

新增 `CheckLoopTest` 七条：

| 测什么 | 关键断言 |
|---|---|
| 干净结论不回环 | `check_action == "pass"`，且返回里没有 `messages` |
| 伪引用回环一次 | `retry`，且回喂文案同时含 `0.1139`、`4.84`、`null` |
| 已回环过不再回环 | `retry=1` 输入 → 仍 `pass` |
| **拿 null 换通过被记下** | `retry=1, unsourced0=0`、结论全 null → `check_notes` 含"不是修正" |
| 非 JSON 不重试 | `pass`，交给 verify 判 |
| 路由读 `check_action` | `retry→plan`、`pass→verify` |
| **check_notes 能进最终判定** | 直接调 `verify`，`misquoted` 里出现"不是修正" |

最后一条是这一批里最容易被漏的：`check_notes` 如果只写在 state 里、`verify` 不读，它就是个写了没人读的字段，绕法照样静默通过。

## 七、取舍

**为什么最多回环一次。**
两次以上收益递减：抄串一次能改，改两次还错说明它根本找不到那个字段。而每多一次回环就是一次完整的 LLM 调用（H1 单条约 20–40 s、几千 token），成本敏感。

**为什么 check 不落正式统计。**
`check` 里跑了一遍 `_verify_claims`，`verify` 又跑一遍。如果两处都写 `stats`，汇总是把同一批 claim 算两次，`qty` 直接翻倍。所以 check 用 `_new_stats()` 造个临时壳，判完丢弃。

**为什么路由靠 `check_action` 而不是"看 messages 变长没有"。**
后者在模型恰好在 messages 里留了一条空 content 时会失效。而路由失效的表现是"本该回环的没回环"——静默，不报错，只在纠错次数上少一次。

**为什么 `budget_exhausted` 不经过 check。**
预算耗尽意味着 12 步额度已经用完。回环要再跑一轮 plan，没有额度了；而且那条结论本来就是半成品，回喂只会让它在"半成品"基础上再猜一次。

## 八、遗留

- **回环路径没有真实样本**。`check_rounds=1` 至今 0 条，只有 `CheckLoopTest` 的函数级覆盖。要拿到真样本得等模型再抄错一次，或者人为构造——后者要 mock 一次完整的图运行，成本高于收益。
- **回环后 `plan` 读到 messages 末尾是 user 消息，没在真实 provider 上验证过**。OpenAI 兼容格式通常允许连续 user，但没实测；当前回环 0 次，所以这条路径也没走到。
- **`verify` 现在仍只有一个出口**。这次是"在 verify 前面加闸"，不是"把 verify 本身搬进循环"。真正的形态应该是在每次 `act` 之后都验一次，但那会让每一轮都多一次判定与潜在的额外调用——成本不允许，且中间轮没有 claims 可验。
- **`check_rounds` 会不会长期是 0**。如果一直是 0，有两种可能：模型确实不抄错，或者闸口根本没生效。单靠这个数分不出来，需要配一条"人为注入错误的样本"才能自证。这条属于 `假绿灯` 那类问题。
