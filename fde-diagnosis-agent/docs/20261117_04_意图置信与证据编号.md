# 意图自报置信与证据编号：两处"让模型做它做不好的事"

日期：2026-11-17
状态：有效·多轮端到端未验证

这一篇记两件事，它们表面无关，根因是同一个：**把一个纯机械的判断交给模型，然后怪它判错。**

- 第一件：五选一的意图分类，靠示例而不是靠规则。
- 第二件：让模型自己数"这是第几条工具返回"，再拿它当引用编号。

## 一、意图误判：示例覆盖了规则

9 句实探（`t_probe_intent.py`，import 真实 `nodes.understand`，包 `trace.Tracer`，`RUNS_DIR` 改临时目录），第一轮 7 对 2 边界，其中 1 句真错：

| # | 原话 | 改前判定 | 问题 |
|---|---|---|---|
| 3 | `cx-104 的标定周期是多少` | **knowledge** | 错。knowledge 会去 `search_manual` 答"规程要求每 90 天标定一次"，而用户要的是这台设备的 `maintenance_cycle_days` |
| 9 | `就是那个工位，夜班更差` | clarify | 单轮合理，但多轮会丢已确认设备（`clarify` 不在继承白名单里） |
| 6 | `光源亮度该设多少` | knowledge | 判对，但耗时 25.8 s |

第 3 句的错因不在模型不知道：它自己把参数名填进了 `param_names: ['标定周期']`，**说明它认得这是参数**。错在 `UNDERSTAND_PROMPT` 的 knowledge 示例里就写着「标定周期多久」——示例覆盖了规则。模型优先跟示例，不跟规则，这是 prompt 的常见失效形态。

## 二、一手判据：Anthropic 的 routing 门槛，两个前提都不满足

`https://www.anthropic.com/engineering/building-effective-agents`

| 原文 | 含义 |
|---|---|
| 「Routing ... classification can be handled accurately by an LLM or a more traditional classification algorithm」 | 前提一：**分类能做准** |
| 「Workflows ... predefined code paths」/「Agents ... LLMs dynamically direct their own processes」 | workflows 是写死的路径，agents 是模型自己指挥 |
| 「we actually spent **more time optimizing our tools than the overall prompt** ... we changed the tool to always require absolute filepaths—and we found that the model used this method **flawlessly**」 | 改工具比改 prompt 便宜 |
| 「consider adding complexity *only* when it demonstrably improves outcomes」 | 不加不能证明收益的东西 |

两条前提**都不满足**：五类之间本来就有重叠（知识 vs 数据），而且实测就判错过一次。按 Anthropic 自己的判据，这里不该用 routing。

但我们也不是纯 workflows——`plan ⇄ act` 是模型自己决定查什么，接近 agents 形状。所以做法不是"换架构"，而是**把判错的成本降下来**。

代价那条原文也要记：「higher costs, and the potential for compounding errors」。判错之后一路往下跑，错的理解会被后面的每一步继续使用，这就是 compounding。

**据此否掉的方案**：把 `scope` 拆成两维（"问的是设备还是规程" × "问的是规则还是取值"）。拆完还是 routing，只是切得更细，前提仍然不成立。

## 三、Jev 能帮什么，不能帮什么

TypeSafe AI 的 System One，2026-09-15 开源。三种判定类型 `choice` / `noul` / `score`，返回概率不生成文本，70–500 ms。

| 原文 | 它说明什么 |
|---|---|
| 「**out-of-set label is impossible**」（`https://interfaze.ai/blog/jev-now-open-source-lev`） | 只在你给的选项里选，不会冒出第六类 |
| 「**Calibrated**. Gate on the probability: act above 0.9, send the rest to a person」 | 概率是可用的，并且**要拿它改变行为**，不是拿它装饰日志 |
| 「不能生成自由文本；类型正确的答案也可能判断错误」（`https://jevai.dev/zh-Hans/`） | 它不抽取字段 |
| 「Jev showed measurable **overconfidence, averaging 88% reported confidence against roughly 80% actual accuracy** on Banking77」（`https://www.mindstudio.ai/blog/jev-vs-classic-classifiers-benchmark`） | 自报置信本身也会偏高 |

结论：Jev 帮延迟、格式、成本、置信度四样，**不帮"类别重叠"**。只拿它替换五选一，第 3 句那种错会变得**更隐蔽**——带高置信度答错，反而不会被追问拦住。

接入代价也够呛：`POST .../v1/systemone` 不走 OpenAI 兼容，`get_client()` 走不通；多一个 2026-09 的新服务依赖；而且它只判选项，不做 `phenomenon` / `param_names` / `missing` 抽取，而现在一次调用干六件事。

**不采纳。** 取的是它的思想，不是它的服务。

## 四、融合的是两句话，不是那个服务

1. **模型自报一个概率。** `UNDERSTAND_PROMPT` 加 `"confidence": 0.85` 字段，规则第 5 条写明"两类都解释得通时给 0.5~0.7，不要凑 0.9；你虚报高分会让它跳过追问，带着错的理解往下跑到底"。
2. **这个概率必须改变行为。** `CONF_ASK=0.6` / `CONF_OK=0.75`：
   - `< 0.6` → 直接降成 `clarify`，先问清楚
   - `0.6~0.75` → 照判断走，但结论带"按「X」理解，若不对请直接纠正"
   - `>= 0.75` → 不提

阈值不跟 Jev 的 0.9。他们的 0.9 是"不可逆决策转人工"，我们判错只是多问一句，**代价可逆**，所以线可以低得多。

## 五、闸的位置：必须在硬矛盾校验之后

这是实测暴露的两个新问题之一。

**第一版把闸放在硬矛盾之前**，第二轮探针（阈值 0.9）的结果：

- 9 句里 6 句落在 0.6–0.9 → 全部挂备注 → **噪声化**。每句都"我不太确定"等于每句都不确定，用户会免疫。
- 第 9 句出现 `判定: clarify` + `备注: 按「diagnose」理解` 的**自相矛盾**。

自相矛盾的根因是顺序：硬矛盾校验会把 `diagnose` 改写成 `clarify`，闸若在前，note 是按旧的 `diagnose` 写的，最终 intent 却已经是 `clarify`。用户读到的是"你说按诊断理解，那你为什么还问我"。

**改法**：闸移到硬矛盾三连之后；`intent == "clarify"` 时不再叠 note——追问本身就是不确定性最好的表达。

**第三轮**（阈值 0.75、闸在后）：9 句全对，**只有 1 句带备注**，置信 0.65，理由：

> 「问题带有具体设备号，并询问某个参数当前取值，倾向是在查这台设备的配置数据；但『标定周期』也可能是规程标准，因此按两类都可能来解释，置信度给中等。」

这才是校准该有的样子：它知道自己在边界上，主动降分，并且把两种解释都说出来了。

同时修的另外两处：

- `fallback_intent` 从 `"diagnose"` 改成 `"lookup"`。原来是 `"diagnose" if hint else "clarify"`——LLM 挂掉时只要句中有设备号就走**最贵**的那条路。兜底不能挑最贵的。
- `ask_user` 按「现象有没有 × 设备确不确认」四分。有现象、没设备时说"你提到「误判率偏高」，还缺一个设备编号"，而不是"需要两个信息"——后者会让用户重说一遍他已经说过的话。

## 六、另一件事：证据编号不该让模型数

### 实测：同一份代码，25% 与 100%

| 报告 | `code_hash` | 语义 | 出处率 | 步数/工具 | 耗时 |
|---|---|---|---|---|---|
| `report_20261117_1227_df94a36.json` | `22839652dc84` | **FAIL** | 5/20 = 25% | 9 / 9 | 111 s |
| `report_20261117_1230_df94a36.json` | `949db020636b` | OK | 22/22 = 100% | 9 / 9 | 33 s |

两份唯一的差别是 `_verify_claims` 里 `path_miss` 的报错文案（多印了编号和工具名），**判定逻辑一个字没动**。

15 条失败的字段名逐条核过：

| 模型写的 ref | 实际在哪个工具 |
|---|---|
| `cumulative_hours` / `rated_life_hours` / `over_life_hours` / `brightness_set` / `brightness_history[1].value` / `degradation_estimate` | `query_light_usage` 全都有 |
| `records[0].drift_px` / `days_since_last` | `query_calibration` 有 |
| `conflicts[0].value` / `conflicts[1].value` | `check_doc_conflict` 有 |
| `chunks[1].text` / `chunks[2].text` | `search_manual` 有 |

`_slim_result` 只截数组、不改键名，`_payload` 保证模型看到的与 evidence 存的是同一份。

**所以不是字段名错，是证据序号 `k` 错位。** 它记住了"calibration 里有 records"，记不住"calibration 是第几条"。

### 根因

`_verify_claims` 原来用 `ev[k-1]` 按下标取。模型数的"第几条"和 `ev` 列表下标，在**单轮**里恰好相等，**多轮**里不等——`_ctx_window` 裁掉前几轮后，`ev[0]` 可能是证据 7。

按下标算，等于要求模型同时记住"看到的是第几条"和"裁完以后算第几条"。这就是它会错的地方。

### 改法（Anthropic 那条"改工具不改 prompt"）

- `_payload(res, ev_no=N)` 在每条 tool 返回最前面印 `[证据 N] `，模型**抄**，不用数。
- `_load_obj` 剥掉前缀再 `json.loads`。
- `_verify_claims` 按证据自带的 `ev_no` 查，`by_no` 里没有的直接判"不在可见范围"。
- `act` 的编号从 `state` 已有条数续。**原来按本轮增量列表算，第二轮会从 1 重数**，`by_no` 后写覆盖先写，引用旧号会静默命中一条完全不相干的证据。这条有单独测试。

用文本前缀而不是往 JSON 里加 `_ev` 字段，是因为工具返回可能是 list 或标量：加字段要么改结构（模型引用的路径全变），要么加不进去。前缀对所有类型都成立，且不影响 JSON 内部的字段路径。

### 反向验证

把校验临时改回 `ev[k-1]`，`EvidenceNumberingTest` 立刻红两条：

```
标定周期 90 天（证据 1 是 query_calibration，其中没有字段 chunks[0].text）
```

这条信息和 `report_20261117_1227` 里那 15 条的形状**完全一样**——所以那次 FAIL 的机制在单测里可以复现，不必靠生产事故来解释。

## 七、被连带改到的地方

**tool content 不再是纯 JSON。** 任何下游解析都要过 `_load_obj`。`OwnershipGuardTest` 原来直接 `json.loads(out["messages"][0]["content"])`，改后必须走 `_load_obj`——否则会出现"测试解析方式比生产宽松"的假绿。

## 八、验证与未验证

已验证：

- 单测 73/73（0.066 s）。新增 `IntentConfidenceTest` 8 条、`AskUserWordingTest` 4 条、`EvidenceNumberingTest` 6 条。
- 9 句意图探针三轮，最后一轮 9/9，仅 1 句带备注。
- H1 端到端两次：17/17、22/22，`path_miss=0`、`ref_bad=0`。`ref_bad` 归零本身是证据——不剥前缀的话 `json.loads` 会全线失败，所有引用都会判"不是结构化返回"。

**未验证**：

- **多轮端到端。** 单轮里证据编号恰好等于列表位置，所以两次通过只能证明改造没引入破坏，**证明不了模型真在抄编号**。第二轮编号从 10 开始，才是唯一有区分力的场景。
- `CONF_ASK` / `CONF_OK` 是拿 9 个样本定的，样本量严重不足，阈值可能随全量数据回调。
- 工具 description 加长后是否挤压 prompt token，未量化。

还有一条方法论上的：

**单条 OK 也是假绿灯。** `1227` 与 `1230` 已经说明：同一机制下一次 25%、一次 100%。要判断某片区域稳不稳，只能连跑多次或跑全量。
