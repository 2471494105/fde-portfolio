# 多轮用例进 eval：让"跨轮还准不准"变成能回归的指标

> 一句话：三轮探针跑通不等于修好了。它只证明"这一次没漂"，
> 下一次改校验规则时没有人会自动重跑它。

- 日期：2026-11-17
- 前置：`docs/20261117_05_档C引用换工具名.md`、`docs/20261117_06_参数指纹定住哪一次调用.md`
- 代码：`eval/trajectories.py`、`eval/run_eval.py`

## 一、为什么必须进 eval

前面所有多轮结论（档 C 的 17/18、指纹的 14/17）都来自临时脚本 `t_probe_three_c.py`。
它有三个问题：

| 问题 | 后果 |
|---|---|
| 不在 `eval/trajectories.py` 里 | 不在 `cases_hash` 里，改了什么无从对比 |
| 不产报告文件 | 不进 `history.jsonl`，没有历史 |
| 没人会主动跑 | **下一轮改动改坏跨轮引用，没人知道** |

第三条最要命。这一整天改的都是"引用能不能指对"，而跨轮正是最容易出问题的地方——
结果它偏偏是唯一没有自动化保障的那一块。

## 二、两条用例

### M1：第 3 轮裁剪下的引用

```python
"turns": ["cx-104 数据",
          "cx-104 标定漂移是什么意思",
          "cx-104 最近误判率高得离谱，帮我查一下成因"]
```

`CTX_VISIBLE_TURNS = 2`，所以第 3 轮 `lo=2`，**第 1 轮的证据被真正裁出视野**。
模型这时若还按"我第几个查的"去写引用，就会落空。

期望：`query_defect_log` / `query_calibration`，维度 `station`，关键词「标定」「漂移」，
`intent=diagnose`，步数 4–14。

### M2：槽位继承

```python
"turns": ["CX-101 数据", "误判率怎么这么高"]
```

第 2 轮**不带设备号**。真实用户不会每次重复报设备号——"刚才那个"是人话的默认。

**判错的样子很隐蔽**：模型自己补一个设备号去查，查得到数据、报告全绿。
所以这条的关键词写的是「1号工位」——CX-101 的过杀集中在 1 号工位（光源衰减）。
只有真的查了 CX-101 才写得出这个位置。

另外它还防"追问到死"：如果每轮都问"哪台设备"，用户会觉得这机器不会聊天。

## 三、跑法上的三个约束

### 1. 多轮必须共用 checkpointer

`run(use_checkpoint=False)` 时 `build_graph` **每轮新建一张图**，
上一轮的 `messages` / `device_ids` 全丢，第 2 轮等于从零开始——
那样"多轮用例"测的还是单轮，正是它要防的那个假绿灯。

因此多轮分支固定：

```python
tid = f"eval-{traj['id']}-{int(time.time() * 1000)}"
for t in turns:
    state = run(t, thread_id=tid, trace_run=False, use_checkpoint=True)
```

### 2. 多轮必须串行

checkpointer 是进程内单例、只有一条 psycopg 连接，并发写会报
`another command is already in progress`。所以 `serial` 批从
`type == "建单"` 扩成 `type == "建单" or t.get("turns")`。

注意这两个"串行"的原因完全不同：建单类串行是因为**共享外部 mock QMS 状态**，
多轮类串行是因为**共用同一个 checkpointer 连接**。原因不同但结论相同，放在同一批。

### 3. 多轮要有自己的判据

只跑单轮那套（工具/维度/关键词/步数），看不出"跨轮还准不准"。

新增 `round_ok`：

```python
dead = cite_oob + path_miss + ref_bad
round_ok = dead == 0
```

三者都是"引的出处落空"，成因不同：

| 计数器 | 含义 |
|---|---|
| `cite_oob` | 该工具的返回已不在本轮视野（被裁了） |
| `path_miss` | 字段路径在返回里取不到（编了路径） |
| `ref_bad` | 格式就不是 `工具名#路径`（把编号写回来了） |

**都是多轮才暴露的病**，所以这条判据只对多轮用例生效，已并入 `semantic_ok`。

```
[M1] OK 步数11 工具11
[M2] OK 步数8  工具8
```

| 指标 | 值 |
|---|---|
| 语义正确率 | 2/2 |
| 明确出处率 | 35/36 = 97.2% |
| **多轮引用成立** | **2/2** |
| `cite_oob` / `path_miss` / `ref_bad` | 全 0 |
| 引用写错 | 0/2 |
| 有未溯源数字 | 1/2（`ref: null`，标灰放行） |
| 预算耗尽 | 0/2 |
| 总耗时 | 310 s（154.9 s/条，多轮本来就慢） |

`cases_hash` 从 `b125ea215ed5` 变成 **`cf15938f3ea0`**——加了两条用例，旧报告的该字段不再可比。

### 核实"真继承"而不是"看起来对"

M2 的关键词命中只能说明结论提到了 1 号工位。真正的证据在 evidence 前缀里：

```
query_defect_log{device_id=CX-101,group_by=station,time_from=2024-01-01}
query_calibration{device_id=CX-101,limit=6}
query_light_usage{device_id=CX-101}
```

**全部 `device_id=CX-101`**，没有一个是模型自己补的别的设备。

M1 同样全部 `device_id=CX-104`，而且一轮里用了三种分组：

```
query_defect_log{device_id=CX-104,group_by=station}
query_defect_log{device_id=CX-104,group_by=defect_type}
query_defect_log{device_id=CX-104,group_by=day}
query_defect_log{device_id=CX-104,group_by=day,time_from=2026-10-08,time_to=2026-11-14}
```

最后一条同时带时间范围和分组——指纹把"查的是什么"完整描述住了。

## 五、报告里新增的一行（以及为什么分母为 0 也要打印）

```
多轮引用成立  2/2   （最后一轮所有 ref 在本轮可见证据里成立）
```

没跑多轮时会打印：

```
多轮引用成立  未运行   （本次没有多轮用例）
```

**这一行不能省略**。如果只打印 `0/0` 或者干脆不打印，"没跑"和"全绿"在报告上长得一样——
这正是"假绿灯"那条经验：指标说没问题之前，先自证它到底跑没跑。

## 六、留下的问题

| 问题 | 现状 |
|---|---|
| 多轮很慢 | 154.9 s/条，M1 三趟。全量 27 条里带上 M1/M2 会更慢，适合谷时跑 |
| 只覆盖两条路径 | 都是"查数据→问原因"。没有覆盖"建单后追一句"「改一个参数重查」这类 |
| `round_ok` 不判"结论对不对" | 它只判引用成不成立。结论错误仍靠 `kw_rate`，两者口径不同 |
| `CTX_VISIBLE_TURNS = 2` | 仍是经验值，没有按 token 预算算过。它直接决定第几轮开始裁剪 |

## 七、一句话总结

多轮的病只在多轮里发作，那就必须有多轮的用例在跑，并且有专门的计数器看着它。
临时脚本跑通一次，只能算"见过这个病"，不能算"防住这个病"。
