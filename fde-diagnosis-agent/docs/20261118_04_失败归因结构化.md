# 失败归因：从一句话变成可核对的四元组

`effb7f4` · 2026-11-18

## 一句话

失败的原因不是"判据不够聪明"，是**判据的输出停在了布尔 + 一句字符串**。

## 现象

T3（"不用查了，你凭经验估一下"）在 `history.jsonl` 里有三次实测，`reasons` 全是同一句 `判断错/结论未命中`：

| commit | 模型实际做了什么 | tools | kw_rate |
|---|---|---|---|
| `ae28aa2` | 追问"CX-101 你想先看哪一方面" + 两个选项 | `[]` | 0.0 |
| `a553cc6` | 追问，且把"意图置信度 0.55 低于 0.6"这段内部字段直接打在答案里 | `[]` | 0.0 |
| `32704d4` | 真去查了 `query_device_profile`/`query_defect_log`/`query_work_order`，输出 15 条 claim 全 `path_ok` | 3 个 | 0.333 |

三件事的修法完全不同：前两条改话术或改"该不该追问"的判定，第三条本该是**抗令**（用户明说不用查）却查了。一个字符串盖住三种病，等于把诊断推给看报告的人。

## 根因：反馈不对称

`_verify_claims` 有 20 多个判定分支，每遇到一个新问题就在**输入侧加一个分支**；`reasons` 从头到尾是硬编码字符串。

- 改输入侧 → 红变绿，**立刻有反馈**
- 改归因侧 → 红还是红，**没有任何反馈**

任何系统在这种反馈机制下都会长成"判定越做越细、归因一直粗糙"。这解释了为什么同一个模式在四处复发（判据分类 / 单值贴数组 / 定性 claim / T3）。

## 改了什么

`judge()` 里 `reasons` 与新增的 `failure` **同源产出**——同一个 helper 写两处，不是写两遍（分开写迟早漂移）。

```json
{"code": "conclusion_off",
 "owner": "model",
 "basis": {"kw_rate": 0.333, "tools": [...], "kw_hit": ["没有"]},
 "note": "这条用例没要求任何工具，判据看不出这些调用是多余还是有用"}
```

| 字段 | 作用 |
|---|---|
| `code` | 病名，可直接 grep / 统计 |
| `owner` | `model` / `case` / `uncertain` / `env`，谁该负责 |
| `basis` | 依据哪几个指标判出来的，看报告的人不用自己再组合一遍 |
| `note` | 判据**判不出来**的边界，明说"看不出" |

**`owner` 里没有 `evaluator`**：判据不该给自己的错开脱。运行异常归 `env`（超时不代表模型做错），步数越界归 `uncertain`（判据手上只有这一个数，分不出是用例区间写窄还是模型绕远路）。

### `kw_rate < 0.5` 拆三支

这是最核心的一处：

| 条件 | code | 含义 |
|---|---|---|
| `intent=clarify` 且用例要求直接答 | `asked_instead` | **原来完全没有信号** |
| 调了工具仍没命中 | `conclusion_off` | 答偏 |
| 什么都没有 | `conclusion_miss` | 没答也没查 |

第一行补的是一个一直存在的洞：`ask_ok` 只在 `if ask_expect:` 内部才判，`expect_ask=False` 时追问**根本不被判违规**，只能由关键词笼统抓到。T3 前两条记录正是这种情况。

### 汇总里也要看得见

`summary.failure_kinds`（如 `{"conclusion_off": 1}`）+ 控制台一行 `失败归因`。不加的话 `failure` 只躺在逐条明细里，看总览时还是得一条条点开——那样等于没有。

## 明确没做的

1. **判据的 20 多个分支：不动。** 工作正常；重构的收益是好看，代价是 8 份历史报告的可比性。
2. **意图层：不动。** T3 的 `intent` 落成 `lookup`，说明"用户要求估个数"可能根本没有对应意图，只能掉进"查数据"。这是另一件事，需要单独证据。
3. **`final_keywords` 不放宽。** 放宽等于承认答非所问可以过。

## 验证

- 单测 **131/131**（原 126 + `JudgeAttributionTest` 5 条）。5 条先跑红（`KeyError: 'failure'`）再改绿。
- `--only=T3` 端到端跑通：`intent=lookup`、3 工具、`kw_rate=0.333` → `conclusion_off`，与 `32704d4` 那轮行为一致。报告里 `failure` 与 `failure_kinds` 都落盘。
- **全量未跑**（27 条约 53 分钟，留谷时）。

## 已知边界

- **判不出"抗令"**：T3 的 `expect_tools: []` 语义是"不强制"，不是"禁止"；`forbid_tools` 只禁了 `create_work_order`。判据不知道"用户说了不用查"，只能把这条边界写进 `note`。要真判它，得给用例加"期望零工具"的字段——那是改用例，不是改判据。
- **历史数据重放不了**：`history.jsonl` 只存判完的结果，**没存 `intent`**，所以三次 T3 只有最后一次能从 `report_eval.json` 重放。
- **`reasons` 文案变长了**（多了"调了 N 个工具"这类后缀）。跨版本逐字对比不再成立——但历史报告的 `reasons` 本来就是旧代码产生的，清晰 ＞ 逐字可比。

## 下一步

- 全量重跑，拿 `failure_kinds` 分布看真实瓶颈在哪类。
- 若 `conclusion_off` 占比高，再决定是给用例加"期望零工具"字段，还是动意图层。
