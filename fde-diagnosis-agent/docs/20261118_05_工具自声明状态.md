# 工具自声明状态：unknown 的写入口绑在走不到的节点上

> 记录日期：2026-11-18　提交：`6978e21`　本期主题：三档"没有"里的 `unknown` 为什么恒空，以及由此暴露的预算语义与 `cite_stats` 膨胀

## 一、问题：三个"没有"只有两个能写

State 里"没有"分三档：

| 字段 | 含义 | 谁来给 |
|---|---|---|
| `missing` | 用户能补的信息（设备号、时间窗） | `understand`，走 `ask_user` |
| `unknown` | 工具正常返回，但结果为空 | 原本只在 `lookup` / `knowledge` 节点里写 |
| `svc_fail` | 工具或模型调用挂了 | 各节点兜底 |

**`unknown` 的三个写入口全在 `lookup`（`device_not_found`、`no_work_order`）和 `knowledge`（`manual_empty`）。**

而路由是这样的：

```python
route_after_understand:
    diagnose | action → "plan"
    lookup            → "lookup"
    knowledge         → "knowledge"
```

诊断意图（本项目的主场景）走 `plan → act`，**根本不进 `lookup` 和 `knowledge`**。所以 `unknown` 在主路径上恒为空——不是"工具没返回空"，是"这些分支压根没执行"。

这和此前 `conflicts` 的病一模一样：**留痕绑在节点上，只覆盖走那个节点的路径，而主路径恰恰不走。**

## 二、第一版修法失败：想从证据里回收，但判据靠猜

第一版写了 `_unknown_from_evidence(ev)`，从 `evidence` 里反向判"这条返回是不是查无"：

- `query_work_order` 的 `state == "no_order"` / `"device_not_found"`
- `query_calibration` 的 `records == []`
- `search_manual` 的空 `chunks`

前两个能用，因为 `query_work_order` 本来就返回结构化 `state`。但真实跑 CX-999（设备不存在）时**没验证到**——模型只调了 `query_device_profile`，而这个工具用 `error` 字符串表示查无：

```python
return {"error": f"设备 {device_id} 不存在", "known_devices": known}
```

当时我刻意没收它，理由是"文案匹配太脆"。这个判断是对的，但结果就是 `unknown` 依然漏了最常见的一类实质查无。

## 三、真因：`error` 字符串承担了两种互斥语义

看 `query_defect_log`：

```python
if group_by not in GROUP_EXPR:
    return {"error": f"group_by 只支持 {sorted(GROUP_EXPR)}"}      # A. 模型参数写错
...
if cur.fetchone()["n"] == 0:
    return {"error": f"设备 {device_id} 没有误判日志"}              # B. 库里确实没有
```

**同一个 `error` 字段，A 是"该改参数再查"，B 是"该拒答"。** 上游只看字符串，要么靠文案猜（脆，且中文改动就崩），要么干脆不收（`unknown` 恒空）。

**靠文案猜错的后果不是漏报，是造一个假的拒答依据**：模型把 `group_by` 拼错了，系统记成"这台设备没有日志"，然后理直气壮地告诉用户"查不到"——用户拿到的是一个从未被验证过的结论。

这是本轮最值得记住的一条：**判定依据本身是假的，比没有判定依据更危险。**

## 四、修法：让工具自己声明状态

给四个工具加 `state` 字段，把"我这类没查到"和"你参数写错了"分开：

| 工具 | state 取值 |
|---|---|
| `query_device_profile` | `found` / `device_not_found` |
| `query_defect_log` | `found` / `no_defect_log` / **`bad_args`** |
| `query_calibration` | `found` / `no_calibration` |
| `query_light_usage` | `found` / `no_light_record` |

`_unknown_from_evidence` 改成**查表**，只认 `state`，不碰文案：

```python
STATE_KIND = {
    ("query_work_order",     "no_order"):         ("no_work_order", ...),
    ("query_work_order",     "device_not_found"): ("device_not_found", ...),
    ("query_device_profile", "device_not_found"): ("device_not_found", ...),
    ("query_defect_log",     "no_defect_log"):    ("no_defect_log", ...),
    ("query_calibration",    "no_calibration"):   ("no_calibration", ...),
    ("query_light_usage",    "no_light_record"):  ("no_light_record", ...),
}
```

**`bad_args` 不在表里，这是设计而非遗漏。** 参数写错不是查无，记进 `unknown` 就等于给了模型一个假的拒答理由。

配套 `_merge_unknown(*lists)` 按 `(kind, what)` 去重：同一台设备被查两次，只算一条缺口。

`verify` 里两行接上（两个 `return` 都要带）：

```python
unknown = _merge_unknown(state.get("unknown"), _unknown_from_evidence(ev))
```

## 五、实测

**1. CX-999（设备不存在）**

```
=== 工具调用轨迹 ===
1. query_device_profile({"device_id": "CX-999"})
   -> {... "state": "device_not_found", "known_devices": ["CX-101".."CX-105"]}

=== 查无（工具正常返回，但结果为空） ===
- [device_not_found] CX-999：设备编号不在台账里
```

同时该结论里的 `台账共 5 台可用设备` 被判 `blocked`（`ref=null` 标灰）——"数出来的值"边界再次生效，`known_devices` 是数组、撑不住"5 台"这句话。

**2. `budget_exhausted` 首次真实触发**

`FDE_MAX_STEPS=1`，跑正常诊断：

```
stop_reason: "budget_exhausted", steps: 5, check_rounds: 0
```

**跑了 5 步，与预算 1 不符。** 查轨迹确认环境变量生效（`MAX_STEPS = 1`）后，真因是：

> 预算判断发生在 `plan` **之后**，而一次 `plan` 可以发多个 `tool_calls`。

- 第一次 plan：`steps=0`，有调用 → `0 >= 1` 为假 → `need_more`；该次 plan 发了 **5 个**调用，act 全部执行 → `steps=5`
- 第二次 plan：`steps=5`，有调用 → `5 >= 1` → `budget_exhausted` → 路由 finalize；该次 plan 又发了 **2 个**调用（`query_defect_log`、`search_manual`），**被丢弃**

所以「预算 1」不等于「只允许 1 步」，它掐的是**"还想继续就停"**。那 2 个被丢弃的调用，就是 `_classify_stop` 里 `budget_exhausted` 的真实含义——**半成品**。

这也验证了兜底文案是对的：没形成完整结论时，`verify` 明确写"已达取证步数上限，未能形成完整结论"，而不是把半成品当结论交付。

**3. 回归与单测**

- 180 tests OK（本轮新增 5 条：4 条 `unknown` 判据 + 1 条 key 上限）
- CX-101 正常路径 6 步、13 条 claims 全部带 `ref`、校验通过
- `state: "found"` 出现在正常返回里，不影响任何引用路径

## 六、顺手补的债：`cite_stats` 定 key 上限

`_new_stats()` 当前 **26 个 key**，`_verify_claims` 运行时另补 `cited` / `ev`，报告里实际 **28 个**。

生产代码只读其中 12 个（`app/web/server.py`、`eval/run_eval.py`、`eval/check_criteria.py`），其余约 15 个只在单测里被读。

这不是"字段多"，是**第二个 state 的雏形**：每加一类失败就加一个 key，加完没人回头改 eval / 报告 / UI 的读数。

处理方式是**定上限而非拆 key**：

```python
LIMIT = 30   # 当前 26，留 4 个余量
```

超了就必须先回答"谁读它"；答不出来就走 `cite_fail`（明细，无上限）而不是继续塞 key。不删已有 key，保证新旧报告可比。

**守护测试的区分力是实测过的**：把 `LIMIT` 临时改成 25，报 `26 not less than or equal to 25` 变红，改回 30 转绿。不加这一步，守护测试就只是占位。

另一条测试 `test_runtime_only_keys_are_still_written` 钉住 `cited` / `ev` 是运行时补的。**第一版写错在这里**：断言查 `nodes.verify` 的源码，但这两个 key 实际写在 `_verify_claims` 末尾，测试当场红，说明断言本身有区分力。

## 七、未决

1. **预算语义要不要改。** 现在"预算 1 跑 5 步"是因为一次 plan 发多个调用。若要真按步数限流，得像 Anthropic 的 `tool_use` 那样对**单个 tool_use 批次**计数，而不是对 plan 轮计数。本轮只记录事实，未改。
2. **`run_case.py` 的两处措辞/缺口。** 一是把 `blocked` 打印成「以下数字未在工具返回中出现」，容易被读成失败（实际是标灰放行）；二是不打印 `stop_reason`，查预算只能翻 `runs/*.jsonl`。
3. **`unknown` 进摘要后的跨轮效果未验证。** `unknown` 会进 finalize 的摘要，理论上下一轮会知道"库里没有"。本轮只验证了单轮内回收，多轮没跑。
4. **`cite_stats` 是否彻底拆。** 现方案是只定上限。若将来真需要拆，方向是 `cite_stats`（判定用，有上限）+ `cite_detail`（明细，无上限）。

## 八、可迁移的一条

**"同一字段承担两种互斥语义"是留痕系统最常见的崩坏方式。**

`error` 字符串同时表示"查无"和"参数错"，`error` 就失去了可判性；上游只能猜，猜错就造出假依据。修法不是让上游猜得准，而是让下游**把语义放进结构**（这里是一个 `state` 字段）。

判断一个新字段该不该加，问一句：**有没有读方，读方会不会因为它的缺失而做出错误判断。** 两个答案都是"是"，就该加；第二个是"是"而第一个不是（比如 `cite_stats` 里那 15 个没人读的 key），说明位置放错了，该进明细表而不是计数表。
