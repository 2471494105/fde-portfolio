# 查无响应要可行动：把"事实"变成"下一步"

> 记录日期：2026-11-18　提交：`3e8b85c`　本期主题：`unknown` 进摘要后仍不生效，读一手文档后把修法从"改 prompt"换成"改工具响应"

## 一、起点：一个被验证为不生效的字段

上一轮（DOC-28）把 `unknown` 从证据里回收，并拼进 `finalize` 的摘要：

```python
gap = f"；查无 {what}"
```

写进去是一回事，被当成约束是另一回事。本项目历史上已经栽过两次「字段写了没人读」，所以写了 `scripts/probe_unknown_multiturn.py` 实测。

**第一次结果：摘要确实含「查无 CX-999」，第 2 轮模型照旧去查了一次。**

## 二、探针判据错了两次（比结论更值得记）

**错误一：`evidence` 跨轮累积，我没按 `turn` 过滤。**

第一版直接遍历 `state["evidence"]` 统计"第 2 轮以 CX-999 为参数的调用"，报出 **4 次**。真实是 **1 次**——另外 3 次来自第 1 轮，checkpointer 把上一轮的 evidence 一起带过来了。

> 判据错一次，结论就差一个量级。而且它错得很安静：数字变大了，看起来像"更严重的问题"，不会有人怀疑它。

**错误二：把程序节点的调用算成"模型重复查"。**

修好 `turn` 过滤后仍有 1 次。但看 `intent=lookup`——那一轮走的是 `lookup` 节点，它**无条件**执行 `query_device_profile(d)`，这是程序代码，不是模型的工具决策。把它算成"模型不听话"，等于拿代码的行为去评判模型。

**修正后的判据：只在 `intent` 不属于 `lookup`/`knowledge` 的轮次里判，因为那两种意图的取证是节点里的程序实现。**

## 三、读一手文档，改掉了自己的修法

原本判断：摘要不生效，那就把摘要写得更有约束力（方案 A），再加一条 `act` 层对相同 `(tool, args)` 去重（方案 B）。

按用户要求去读 Anthropic 原文，两篇（是 engineering 文章，不是学术论文）：

**《Writing effective tools for agents》(2025-09-11)**

> Lots of **redundant tool calls** might suggest some **rightsizing** of pagination or token limit parameters is warranted；lots of tool errors for invalid parameters might suggest tools could use clearer descriptions or better examples.

> Too many tools or **overlapping tools** can also distract agents from pursuing efficient strategies.

> When tools overlap in function or have a vague purpose, **agents can get confused about which ones to use**.

> if a tool call raises an error … you can **prompt-engineer your error responses to clearly communicate specific and actionable improvements**, rather than opaque error codes or tracebacks.

**《Effective context engineering for AI agents》(2025-09-29)**

> **Without proper guidance, an agent can waste context by misusing tools, chasing dead-ends, or failing to identify key information.**

> Compaction … The model preserves architectural decisions, unresolved bugs, and implementation details while **discarding redundant tool outputs or messages**.

**读完之后的三个决定：**

1. **方案 B 砍掉。** Anthropic 处理冗余调用是从上游三个地方（工具合并、错误响应、上下文清理）下手，**没有**在循环里对相同参数去重。那个做法既无依据，又会掩盖"模型想重试"的真实意图，还会让 `evidence` 变少、引用路径变窄。
2. **方案 A 降级。** 它只管"下一轮还记得"，不管"这一轮该干什么"。
3. **新增方案 D。** 真问题是错误响应**只陈述了事实，没给动作**：

```json
{"error": "设备 CX-999 不存在", "state": "device_not_found",
 "known_devices": ["CX-101".."CX-105"]}
```

模型读完只能自己猜下一步——于是又查一次，而且查的是 `query_device_profile` 而不是 `query_work_order`，因为这两个工具在"设备不存在"这个情形下边界本身是模糊的（正是 Anthropic 说的 *vague purpose*）。

## 四、改动

### D：查无响应补 `hint`

新建 `app/tools/hints.py`，把 7 类文案集中成一张表：

| state | hint 指向的动作 |
|---|---|
| `device_not_found` | 别再改查它的工单/标定/光源，请用户核对编号 |
| `no_order` | 工单确实没有，别重复查、别编工单号 |
| `no_defect_log` | 日志确实没有，别按别的设备推算 |
| `no_calibration` | 标定确实没有，别重复查 |
| `no_light_record` | 光源记录确实没有，别重复查 |
| `bad_args` | 这是参数写错，不是库里没有，改参数重试 |

**为什么集中成表而不是就地写文案**：文案原来散在 7 个返回点上，改一处漏一处不会有测试报错。成表之后可以和 `STATE_KIND` 交叉校验。

**注意 `hint` 不是新发明的约定**：`create_work_order` 里早就有 `hint` 字段，只是没覆盖到查询路径。这次是沿用它，不是另开一列。

### C：`lookup` 的结论不许自相矛盾

实测看到过这一条：

```json
{"conclusion": "按设备档案与最近 7 天的误判统计列出如下，不做根根判断。",
 "claims": [], "advice": []}
```

**承诺"列出如下"，`claims` 是空的。** 结构化消费端（eval / UI / 下一轮摘要）读的是这两个字段，一个说有、一个是空数组，这条结论自己打自己。

改成分支：`claims` 非空才说"列出如下"；为空时明说"在设备台账里查不到，没有档案、误判统计或工单可列"，并给一条核对编号的建议。

### A：摘要从"事实"改成"排除项 + 动作"

```
改前：；查无 CX-999
改后：；已排除：CX-999（设备不在台账，别再查它）
```

按 `kind` 分文案（`KIND_HINT` 表），因为"设备不存在"和"这本手册里没这个参数"能给的下一步不一样。

代价：摘要每轮长约 12 个字符。风险：模型可能过度遵守，换了角度该查也不查。

## 五、验证

**单测**：183 全绿。新增 `HelpfulErrorResponseTest` 三条：
- `STATE_KIND` 里每个 state 在 `HINT` 里都有对应（交叉校验两张表）
- 每条 hint 必须有动作词（`不要`/`别再`/`请`），只陈述事实的不合格
- 两个工具模块都必须引用共享表 `HINT[`

**改措辞时旧测试立刻报红**：`test_finalize_summary_mentions_gap_and_clash` 断言含「查无」，改成「已排除」后变红。顺势把断言加严成"同时验事实与动作"，否则把动作删掉、只留事实，测试仍然绿。

**探针双场景**（`scripts/probe_unknown_multiturn.py`）：

| 场景 | 意图路径 | 结果 |
|---|---|---|
| A diagnose → lookup | 第 2 轮由节点程序执行 | 通过：摘要含排除项；结论不再"列出如下"，改成"查不到，无可列" |
| B diagnose → diagnose | 第 2 轮走 plan→act，**模型有决策权** | 通过：`步数=0 工具=[]` |

B 场景的第 2 轮结论原文：

> CX-999 不在设备台账中；编号本身无法对应到任何真实设备，因此白班与夜班误判率高低都无从核实，也无法归因
> advice: 上一轮已经确认：在 CX-999 中查不到任何设备记录；**如果再查 CX-999 的标定、光源或工单，也会得到同样的查无结果，所以不再重复查询**

**模型不只没查，还把 hint 的逻辑复述出来了。** 这是"响应里的动作真的被用上了"的直接证据。

**B 场景第一次没测到**：第 2 轮问"白班误判率也一样高吗"，意图被判成 `lookup`（只要有设备号 + 数据诉求就归 lookup），又回到程序路径。换成"白班误判率也偏高，**是什么原因**"才进 `diagnose`。

## 六、未决

1. **`citation` 里 `hint` 会不会被模型当 claim 引用**。`hint` 里刻意不写数字，但"7 天""三次"这类词仍可能被抄进结论——本轮没观测到，也没有判据拦它。
2. **`hint` 的过度约束效应**。B 场景通过了，但只跑了一次。要确认它不是"这一跑恰好听话"，需要 3–5 条同结构的多轮样本。
3. **`lookup` 节点对不存在的设备仍会查 `query_device_profile`**。这是程序实现，改不了也不该改（它就是"查一下告诉我没有"的语义）；C 修的是它之后产出的结论。
4. **`run_case.py` 仍不打印 `stop_reason`**，查预算语义只能翻 `runs/*.jsonl`。

## 七、可迁移的两条

**第一条：判据的盲区比结论的盲区更贵。**

这一轮探针连错两次——一次漏了 `turn` 过滤，一次把程序行为算成模型行为。两次都不报错，只是给出一个看起来合理的错数字。**凡是"统计某个行为发生了几次"的判据，先问清"这几条记录是谁产生的"。**

**第二条：读一手文档的价值不在"学到新方法"，而在"否掉自己的方案"。**

方案 B（act 层去重）是我想当然的产物，读完之后砍掉了。如果只读二手总结（"Agent 要避免重复调用"），我会更确信 B 是对的方向——因为二手总结不写"我们从哪三个地方解决"，只写结论。
