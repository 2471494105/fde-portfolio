# 动作层校验：写意图闸与驳回码

> 记录日期：2026-11-18　提交：`470b557`（代码）、`7dd866d`（探针）　本期主题：`act` 只有"工具存在"与"设备归属"两道校验，写动作缺"该不该做"这一层

## 一、起点：一条诊断问题能变成一张工单

`act`（`app/graph/nodes.py`）原有两道校验：

| 校验 | 拦什么 | 不拦什么 |
|---|---|---|
| `TOOL_IMPLS.get(name)` | 模型编一个不存在的工具名 | 存在的工具在什么条件下可以调 |
| `_owned_device_ids` | 拿别的设备号去查 | 对合法设备做写操作 |

两道都成立，但都回答"能不能碰这个对象"，没有一道回答"该不该做这个动作"。

结果是：用户问「CX-101 的夜班误判率为什么一直偏高」，模型只要想调 `create_work_order`，`act` 就会执行它。参数校验（`_check_order_args`）此时才生效，而它只校验格式——枚举合法、字段非空，`evidence_refs` 甚至只判"列表不空"。

**所以这条路径是通的：不用证明任何结论，直接建一张单。**

而这条防线在本项目的旧实现里是有的：`fde-rag-demo/02_进阶/langgraph_agent.py:241`

```python
if name in WRITE_TOOLS and not has_intent:
    blocked[name] = f"用户没有要求写/上报，禁止调用 {name}"
```

同一个作者做对过，正式图里丢了。

## 二、一手依据：执行权在宿主，不在模型

Anthropic《Tool use with Claude》对 client tools 的定义：

> Claude decides when to call a tool based on the user's request and the tool's description, then returns a structured call that **your application executes (client tools)**.

这句话把两件事分开了：**决定调不调**是模型基于"用户请求 + 工具描述"做的判断；**执行不执行**是宿主应用的事。工具描述只是"告诉模型"，运行时不强制——所以只要宿主的执行层不设闸，"模型觉得不该"就成了唯一防线。

Anthropic《Writing effective tools for AI agents》里另一句，说的是同一件事的另一面：

> if you're writing tools for an MCP server, tool annotations help **disclose which tools require open-world access or make destructive changes**.

即：破坏性应当被**显式登记**，而不是靠模型每次自己识别。本项目的落地就是 `WRITE_TOOLS` 这个集合。

## 三、三个非对称的取舍

### 3.1 关键词，不是分类器

`WRITE_INTENT_KW` 只认"动词+单据"连写的形态：

```python
("建单", "开单", "开工单", "建工单", "创建工单", "提交工单", "新建工单",
 "报修", "上报", "登记")
```

**"工单"单独出现不算。** 因为「CX-101 之前那张工单后来处理得怎么样了」里有"工单"，但那是在读。

这个方案会漏（用户说"这得处理一下"）也会误（用户说"上次建的那张单呢"）。之所以仍然选它，是因为**两个方向的代价不对称**：

| 方向 | 后果 | 补偿 |
|---|---|---|
| 漏拦 | 模型被拒一次，收到 hint 后回头问用户 | 多一轮对话 |
| 误放 | 用户只是提问，却被建了一张脏工单 | 撤单 + QMS 里留一条不存在的记录 |

误放的代价由别人承担（设备科要处理一张来路不明的单），所以宁可收紧。

### 3.2 拿不到用户原话时，失败关闭

`_current_question` 在 `messages` 里倒序找最后一条 `role=user`，找不到就返回空串——空串意味着"没有写意图"。

这是有意的 **fail-closed**。反过来的写法（拿不到就放行）会把"上下文缺失"变成"可以建单"，而上下文缺失恰恰是最容易被构造出来的状态。

### 3.3 意图闸排在归属闸之前

顺序是：`工具存在` → `写意图` → `设备归属` → 执行。

理由是这两问的层级不同：写意图问"该不该做这件事"，归属问"能不能对这台设备做"。**前者不成立时，后者没有意义**——先判归属会得到一个更啰嗦的拒绝理由（"这设备不是你提过的"），而真实原因是"你压根不该建单"。

## 四、驳回理由为什么要两份

`_check_order_args` 现在返回三元组：`(归一字段, problems, problem_codes)`。

```python
problems      = ["evidence_refs 为空，没有证据的工单事后无法复核"]          # 人读
problem_codes = [{"code": "empty_list", "field": "evidence_refs", ...}]  # 机读
```

**结论层早就是结构化的**：`verify` 的 `cite_fail` 是 `[{code, note}]`，`cite_stats` 有 28 个可聚合的键。而动作层只有自由文案，同一个项目里同一个失败信号两种承载形态。

`problems` 原样保留，不改成 dict，理由是：现有消费方（`test_guardrails.py:137/143` 的 `"evidence_refs" in p`、`smoke_qms.py` 的真值判断）都按文案工作，改成 dict 会让它们全红——**那是制造假红，不是修问题**。

这和 State 里 `final` / `final_text` 的分工是同一个模式：一份给人读，一份给程序读。

## 五、验证

**单测**（`tests/test_guardrails.py`，183 → 188）：

| 用例 | 断言 |
|---|---|
| 诊断问题不可建单 | `blocked_by=write_intent`，工具未被调用 |
| 显式建单放行 | 工具被调用一次 |
| "查工单"不算写意图 | 被拦 |
| 无 user 消息 | fail-closed，被拦 |
| `problem_codes` | 与人读文案逐条一一对应 |

**真实路径探针**（`scripts/probe_write_intent.py`）——单测替换了整个工具实现，只能证明"act 没调那个假函数"。探针保留真实 `create_work_order`（参数校验、设备存在性查询照走），只替换 `httpx.post`：

```
[A] 无写意图  blocked_by='write_intent'  到达HTTP=0  → 通过
[B] 有写意图  error=None  到达HTTP=1  → 通过
[C] 参数非法  codes=[('empty_list','actions'), ('empty_list','evidence_refs')]  → 通过
```

**端到端**（`run_case.py "CX-101 的夜班误判率为什么一直偏高，帮我查下"`）：intent=diagnose，8 步，引用校验全绿，模型自己给出「本轮只做诊断，未创建工单」。闸没有误伤正常流程。

## 六、局限与下一步

**已解决**：该不该调这个写工具。

**没解决**：`evidence_refs` 里那些 ref 是否真实存在。现在仍然只判非空——模型可以写一个不存在的引用建单通过。

这正是海致 Atlas 里"裁决器校动作"的核心，也是本项目 `verify` 已经具备但没用上的能力：`_verify_claims` 里那套 ref 解析器（工具名 + 参数指纹 + 字段路径）可以直接复用来校验 `evidence_refs`。

**这是下一个改动（P0-b），不是这一轮做了的事。**
