# 意图判据从"置信"改成"代价"：规则前置 + 按代价分档 + 假设声明

- 上一份：`docs/20261118_07_写意图闸与驳回码.md`
- 日期：2026-11-19

## 一、要解决的不是"判得准不准"，是"判据选错了维度"

P1 之后 L1 的判据只有一条：`confidence < 0.6` 就追问。这条判据只看"模型多信自己"，不看"猜到错的代价"，于是两个方向相反的错同时存在：

| 现象 | 本质 | 后果 |
|---|---|---|
| A5「换了新供应商的料之后误判变多了」——spec 完整，只是模型没判对 | 被一句追问糊过去 | **假绿**：报表上看不出它判错，只看到"它谨慎地多问了一句" |
| lookup「cx-104 数据」——一步就能给答案 | 白白多问一轮 | 成本落在用户身上，答两遍 |

**共同点：把一个"要不要问"的决策，交给了一个只衡量"模型自信度"的标量。**

## 二、一手依据（不拿博客二手总结当依据）

| 来源 | 关键原文 | 用来支持什么 |
|---|---|---|
| **clarify-or-commit**，arXiv 2601.06407 | `every question carries both the potential to reduce uncertainty and **the cost of additional user effort**` | 每轮真正要决策的是 CLARIFY vs COMMIT，判据是"问的收益 vs 成本" |
| **Structured Uncertainty guided Clarification**，ACL 2026 findings（另见 arXiv 2511.08798） | specification uncertainty（用户没说清）vs model uncertainty（模型没把握）；用 EVPI 选问题可达**覆盖率 +7~39%、问题数减少 1.5~2.7 倍** | A5 属于后者——**不该问，该判错**；用 EVPI 选问题比"全问"更省更准 |
| **Active Task Disambiguation**，ICLR 2025 | `the question with the largest information gain is the one that splits the space of compatible solutions into equal partitions` | 本项目 `ask_user` 的"要排查原因 / 只想看数据"正好是二分，不用改 |
| **REVOIR**（Rational Enquiry via Value-of-Information Reasoning） | `when the assistant can receive cheap user corrections after acting, REVOIR naturally infers that asking questions is not always efficient`；比微调策略少问 5 倍 | lookup / knowledge 先做更划算 |
| **vLLM FAQ** / Reproducibility / Batch Invariance | `the same requests might be batched differently ... Once a different token is sampled, further divergence is likely` | 为什么意图这种"短且离散"的输出最容易在并发下翻（判据越短越贴 argmax 边界） |
| **Anthropic《Quantifying infrastructure noise》** | 基础设施能摆动 agentic benchmark 好几个百分点，且**看起来像模型变差了** | `--workers>1` 的数字不能当能力基线 |

## 三、改法（四处改动 + 一处确认不必改）

### ① 规则前置：确定性优先于概率

`route_by_rule(msg)` 只在**罕见组合**上下手：

| 规则 | 正则要点 | 27 条夹具精度 | 命中用例 |
|---|---|---|---|
| `guess` | 不用查 / 凭经验 / 估一下 / 随便给 | 100% | T3 |
| `act_verb` | **（建\|派\|登记）+ ≤6 字 +（单\|工单\|派工）**，必须是动宾 | 100% | W1、W3 |
| `change+dev` | 变化词 + **同时**命中 `CX-\d{3}` | 100% | H1、H3、A1、A3、A5 |

**不进前置的三条**（有精度实测支撑，不是猜的）：

| 规则 | 精度 | 误伤样本 |
|---|---|---|
| `why+dev` | 86% | W3「别管什么原因」 |
| `look_only` | 50% | H2「标定记录」 |
| `param_only` | 33% | H5、W1 |

**取舍：弱规则依赖常见词（记录、阈值、原因），真实表达一丰富就误伤；误伤会把本来正确的判断改错，而那种错在报表上像"模型退化"。所以规则不追求覆盖率，追求"出手必对"——漏掉的会落到追问，那是安全路径。**

规则命中后**仍然调模型**（要 `phenomenon` / `param_names`），但 **intent 不听模型的**。这样并发抖动只影响抽取，不影响路由。

**实测覆盖**：27 条命中 8 条（29.6%），**8/8 与期望一致**。之前并发全量里漂过的 A4/A5/I3/I8/T1 五条，**A5 已被这层接管**，剩下四条仍走模型。

**W2 刻意不命中**：从"建"到"工单"隔了 10 个字，超过 6 字窗口。距离越远，两个词越可能是两件事。W2 走模型判 action 本来就是稳的（它历史上的失败是幂等未命中，不是意图错）。

### ② 代价分档闸

```python
BRANCH_COST = {"action": 3, "diagnose": 2, "lookup": 0, "knowledge": 0, "refuse": 0}
```

| 条件 | 动作 |
|---|---|
| `conf < 0.6` 且 `cost ≥ 2` | 追问（`action` 有外部副作用要回滚；`diagnose` 跑十几步且答偏了不像"答非所问"） |
| `conf < 0.6` 且 `cost < 2` | **照做**，把假设写在结论最前面 |
| `0.6 ≤ conf < 0.75` | 照做 + 提示"按 X 理解" |
| 规则命中 | **跳过整道闸**（规则确定，模型 confidence 对它是噪音） |

### ③ 假设声明放 `finalize`

```python
if note and isinstance(final, dict) and final.get("conclusion"):
    final = dict(final)
    final["conclusion"] = f"（{note}）\n\n{final['conclusion']}"
```

**安全前提**：`verify` 已在 `finalize` 之前跑完，这里只加前缀、不动 `claims`，不会凭空造出一个可引用的事实。且只在 `intent_note` 非空时加——置信足够时不出现"我不太确定"，否则每句话都在免责，用户会免疫。

### ④ 来源 tag

`trace.emit("understand", ..., route_by=route_by, model_intent=...)`：

- `route_by` 取值 `rule:<名字>` 或 `model`
- `model_intent` 留一份模型自己的判断 → **规则覆盖它时，两个值的分歧本身就是最有价值的样本**（规则对而模型错，或反过来）

**注意：这两个字段目前在评测链里拿不到。** 设计意图是"算每条规则的真实误伤率"，但 `run_eval` 传 `trace_run=False`，不落 `runs/`——**渠道是断的**，见下面"代价"第 1 条。别照这一段的字面去找数据。

### ⑤ `ask_user` 一个字没改（这是结论，不是遗漏）

原本打算新增 `ask_kind` 字段来区分"缺 spec"和"判不准"。查了现有实现，**两件事本来就分开了**：

| 情况 | 由谁表达 | 用户看到的话 |
|---|---|---|
| 缺设备 | 四分支文案（`phen and not known_dev`） | 「你提到「误判率有点高」，还缺一个设备编号」 |
| 缺现象 | 四分支文案（`known_dev and not phen`） | 「CX-104 你想先看哪一方面？」 |
| 两样都缺 | 四分支文案（`else`） | 「需要两个信息才能开始」 |
| **判不准**（信息齐、分支不定） | `intent_note` 前缀 | 「你这句话两种理解都通，先确认一句再往下走」+ 后面的二分选项 |

**前三种是"缺什么"的差异，第四种是"不确定"的差异——两套机制表达两件事，比塞进一个枚举字段更省。** 加 `ask_kind` 唯一的好处是"可统计"，但统计通道本来就没有（见下"代价"第 1 条）。**为可统计而加字段，而字段本身不可统计，就不该加。**

## 四、代价（明说，不藏）

1. **`route_by` 只进 trace、没进 state，而 eval 不写 trace。** `eval/run_eval.py` 第 507/510 行传的是 `trace_run=False`——**评测链根本不落 `runs/` 文件**。所以这个字段目前在真实评测里**没有任何出口**，只有手动 `trace_run=True` 跑单条时才看得见。**这是我写这轮代码时的一个实际失误：字段记了，但记完没人能拿到。**
   两种补法都记在这里，下一轮选一条：
   - **进 state**：`understand` 返回 `route_by`，`run_eval` 直接读 → 代价是 State 从 35 涨到 36 个字段、报告表与 `RESET` 表都要跟着改
   - **让 `run_eval` 收集事件**：`trace_run=True` 或给 `Tracer` 加内存 sink → 代价是磁盘与耗时（27 条 × 十几步）
   **在没补之前，"误伤率统计"这件事只是设计，不是能力。**
2. **`ask_user` 没加 `ask_kind`。** "缺 spec"和"判不准"靠现有四分支文案 + `intent_note` 覆盖，没有独立可统计的标识。
3. **规则会漏。** 8/27 是覆盖率，不是"都能判"。剩下 19 条仍可能漂——收益是**把这部分方差砍掉 29.6%**，不是消灭它。
4. **假设声明会让结论变长。** 只在低置信时出现，代价可接受；但它出现在 `final["conclusion"]` 里，所以 `session_summary` 的 `final_head` 也会带上它（跨轮摘要里模型会看到"上一轮我按 lookup 理解的"）。

## 五、验证

- **单测 209 条全绿**（原 196 + 新增 13：`BranchCostGateTest` 7、`RouteByRuleTest` 6）
- 两条旧断言按新语义改写：
  - `test_low_confidence_falls_back_to_ask` → 断言"两种理解"（不再写"低于 0.6"，用户不关心阈值是几）
  - `test_string_confidence_is_parsed` → 从断言 `clarify` 改成**保持 lookup + 带 0.40 假设**（低置信的 lookup 现在刻意不再追问）
- **关键 5 条串行**（`report_20261119_0123_f30b8b3.json`，n=5）：`T3`→refuse、`A5`→diagnose、`W1`→action、`I6`/`I9`→lookup。**I9「上次那个工单处理了吗」没被"工单"两字拐成 action**——动宾正则是被这条误伤打出来才补的。
- `A5` 仍挂 `cite_wrong`（`0.5062` 写成 `50.62%`）。**这是小数↔百分比换算的引用老问题，与路由无关。**
- **全量 27 条串行：本轮没跑完（跑到 H1/H2 即叫停，无报告文件）。** 所以"有没有把别的用例打挂"**暂无证据**——单跑证明不了没影响别人，并发掉分也证明不了改坏。**明天第一件事：`--workers=1` 全量。**
