> 用途：十分钟答辩 demo 的现场逐条脚本 + 翻车时的备份。
> 本文数字全部来自 2026-11-20 12:05–12:10 的实跑，不是估算。

## 一、开场前 3 分钟（缺一步就会翻车）

| 检查 | 命令 | 期望 |
|---|---|---|
| 服务 | `powershell -ExecutionPolicy Bypass -File scripts\start.ps1` | 输出 4 个 `[ok]`，QMS 8010 / Web 8020 都在 |
| 工单初态 | `psql -c "select count(*) from work_orders"` | **必须 = 1**（只剩 `WO-20261105-001`） |
| 若不是 1 | `psql -f data\seed\002_data.sql` | 重导后仍是 1 |

彩排本身也会留下单，所以**彩排完必须复位**。

## 二、三幕脚本（总耗时约 46 秒模型时间）

### 第一幕：完整诊断（22.5 s，5 步）

- 输入：`CX-101 误判率有点高，你看看怎么回事`
- 工具序列：`query_device_profile → query_defect_log → query_light_usage → query_calibration → check_doc_conflict`
- 可讲的三句：
  - 误判率 23.89%（27/113），1 号工位 58.82%（20/34），3 号工位仅 10.64%（5/47）——同一个厂里差异这么大，指向局部硬件而不是模型阈值；
  - 光源累计 8620 h、额定 8000 h，超寿命 620 h，亮度从 85 → 80 → 65 被两次下调；
  - 标定 2026-10-30 漂移 0.467px、结果通过，可排除标定漂移。
- 加分点：结论里主动写了"光源亮度设定存在文档冲突（手册 80 / 厂内 SOP 65），请质量确认以哪份为准，我不替你选"——这是 `check_doc_conflict` 的价值，也是"不确定就不编"的实证。

### 第二幕：设备不存在（7.5 s，2 步）

- 输入：`CX-106 这台设备最近误判有点多，帮我看看`
- 工具序列：`query_device_profile → query_defect_log`
- 可讲：台账只有 CX-101…CX-105，模型拒答并列出可选项，**不对不存在的设备做任何推断**。
- 注意有个坑：`query_defect_log` 对 CX-106 返回的是 `no_defect_log`（"设备确实没有误判日志，属于结论而非故障"），
  这句话本身容易误导——模型没有跟着它走，仍然以台账为准。这一条正好用来讲"工具会撒谎，结论要交叉验证"。

### 第三幕：带着模糊诉求建单（15.9 s，2 步）

- 输入：`3号线 CX-103 反正就是有问题，你先给我建个工单`
- 工具序列：`query_device_profile → create_work_order` → 库内出现 `WO-20261120-002`（待处理）
- 可讲：结论第一句就写明"CX-103 根因尚未确认，按用户要求先行派工"——**不拿建单冒充诊断结论**。
- 库侧佐证：`select order_id, device_id, status from work_orders` 会看到多出这张单。

## 三、翻车时怎么接

| 现场症状 | 应急动作 | 话术 |
|---|---|---|
| API 超时 / 503 | 切到本文第一幕、第二幕的结论截图或录屏 | "网络抖动，我先放刚才跑通的实录，随后现场再跑一遍" |
| 建单 500 / 连接被拒 | 先 `Invoke-WebRequest http://127.0.0.1:8010/health`，不通就重跑 `start.ps1` | 照实说"工单服务是我本地的 mock，刚掉了，重启就好" |
| 模型答歪（少见） | 不要现场 debug，直接跑第二幕（最稳的一条，7.5 s） | "这条它跑偏了，正好说明为什么我要有 26 条回归集来判断它什么时候可信" |
| 时间不够 | 只跑第一幕 + 第三幕 | — |

## 四、口径纪律（别说过头）

- 能说：**26/26 全量通过（333 s，`code_hash=cd9a0a36bce3`）**，四道闸（解析三态 / 终态词核对 / 种子覆盖 / 四轴校验）已落地并有 287 条单测。
- 不能说：**"四道闸修好了所有问题"**——G1/G2 在这一轮一次都没触发，它们的价值目前只有单测的正反证据。
- 不能说：**"稳定 100%"**——满分只出现过两轮，且中间隔了一次判据改造。
- 被追问"怎么证明判据本身可信"时，答：判据失败与模型失败分账记（`owner=model/env/uncertain`），
  并有"判据自检 10/10 + 参考解 3/3 + 种子覆盖自检"三道启动检查。
