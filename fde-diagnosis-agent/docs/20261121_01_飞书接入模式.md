# 飞书接入模式

日期：2026-11-21
项目：fde-diagnosis-agent（视觉检测设备故障诊断 Agent）
本轮目标：在 Web 单页之外**增开** IM 入口（Web 保留，启动命令与三幕演示都不动，见第十三节），同时保证"平台换代时接入手艺贬值、判定手艺不贬值"
状态：设计完成，未落地代码，未做真机联调

## 一句话结论

诊断图的逻辑（12 步预算、8 个工具、289 条护栏单测、98.4% 出处率、三层键），一行都不用改；新增的全部落在一个薄适配器里。飞书明天出原生 agent、或者客户要换钉钉，删掉这个文件就能换掉——**改两个文件以上，就说明架构错了。**（Web 单页不撤，两入口并存；装配形态、抽事件流的判据、thread_id 命名空间见第十三节。）

## 〇、先回答"这活会不会白做"

飞书正在把"agent 能接进来"做成基础设施：飞书 aily 已有人拿它搭"设备大师"（东风奕派把 10 年老师傅经验变成 200 名维修工的标配，紧急故障响应 10 分钟→4 分钟），飞书在中国 IM 环境里的 Agent 接入率报 65.2%，北汽福田把 ERP/MPS 直接喂进飞书的 agent。这不是"以后会"，是"已经在"。

所以先把四层拆开，看哪层会贬值：

| 层 | 具体是活 | 平台会不会做 | 本轮投入 |
|---|---|---|---|
| 传输 | 长连接、事件订阅、验签解密、限流、回执 | **会全包** | 不做自研，直接用官方 SDK |
| 渲染 | 卡片 JSON、进度更新、按钮、折叠、模板 | 会包，且会做得比我好 | 用官方卡片 JSON，不搭模板工具 |
| **判定** | 什么算对、什么算同一件事、哪一步不能自动做 | **不会** | 这是资产 |
| **口径** | 台账、手册、告警码、根因分类、谁能建单、区域范围 | **拿不到，也不该拿** | 这是资产 |

结论：**失效的是"接入"这门手艺，不失效的是"判定与口径"这门手艺。**

### 判据（写进验收，不是口号）

明天飞书出原生 agent、或客户要换钉钉，问一句：**要改几个文件？**

| 答案 | 说明 |
|---|---|
| 改 1 个（`entry_feishu.py` → `entry_dingtalk.py`） | 架构成立 |
| 要动 `state.py` / `nodes.py` / 工具层 | 飞书的数据结构渗进了业务层，这才叫真失效 |

落地时用 `grep -rn "open_id\|chat_id\|message_id\|card\|feishu\|lark" app/graph app/tools` 做机械检查，**命中即违规**（唯一豁免见第五节那条 `operator_id`）。

## 一、七个决策（已定，不再变动）

| # | 决策 | 定案 | 理由 |
|---|---|---|---|
| 1 | 接入方式 | **长连接**（WebSocket，飞书 SDK 内能力） | 只要服务器能**出网**，不需要公网 IP、域名、内网穿透，也不需要解密验签；工厂典型"能出不能入" |
| 2 | 事件入口 | 群聊 @ 机器人（主）+ 单聊（可选） | 群聊 @ 只需 `im:message.group_at_msg`；**不申请** `im:message.group_msg`（群内全消息是敏感权限，审批与合规成本都不该背） |
| 3 | 会话粒度 | `thread = chat_id + open_id + 30 分钟活跃窗` | 见第二节：群共享一个 thread 会打穿 `_owned_device_ids` |
| 4 | 异步形态 | **一张卡全程更新** | 先 S0 处理中，完成后 PATCH 成 S1 结论 |
| 5 | 写操作确认 | **卡片按钮**（不靠文本里说"确认"） | 护栏的"人工确认"第一次有了 UI 载体 |
| 6 | 实例模型 | **单实例** | 演示与单厂都够；多实例的前提是先有 thread 级锁（见第九节） |
| 7 | 与 Web 入口 | **并存**，共用同一个图与同一个线程存储，会话命名空间隔离 | Web 的 `session_id` 与飞的 thread 不许重名，否则同一 thread 被两种入口同时跑 |

### 为什么不选话题群

话题群把每条消息变成一个独立"话题"，回复挂在话题下，飞书直接返回 `thread_id`（`omt_xxx`）。它天然解决"张三问的和李四问的不串"，技术上只要 `reply_in_thread: true`。

演示不用它，三条：

1. 话题群的客户端界面是"话题列表"，面试官不熟，要多解释一层；
2. 依赖客户群已开启话题，没开就整套不通；
3. 自造租约可以额外把"班次/设备"塞进会话维度，`omt_xxx` 塞不进。

**留兼容开关**：消息体里若带 `thread_id`，优先用它；否则走自造租约。

## 二、一个必须先说的坑：群共享会话会打穿归属校验

`_owned_device_ids`（`app/graph/nodes.py:1409`）的语义是**本轮允许工具访问的设备集合**，来源是 `understand` 合并后的 `device_ids`；写操作靠它拦"建单引用本轮没查过的设备"（`nodes.py:1523`）。

如果**一个群 = 一个 thread**：张三 @ 问 CX-101、李四问 CX-102，两人的 `owned_device_ids` 混进同一份 state，归属闸直接失效——李四能引用张三查的证据建单。

所以 thread 至少按人切。定案：

```
thread_id = "fs-" + sha256(chat_id + "|" + open_id)[:16]     # 稳定部分
活跃窗     = 同一 (chat_id, open_id) 内，间隔 ≤ 30 分钟则续同一 thread
断链       = 超 30 分钟，或用户显式说"新会话"，开新 thread（旧的不删）
```

为什么是 30 分钟而不是"一次一毁"：现场最高频的是**同一人连续追问**（"那 11-08 那天呢"）。一次一毁会让他重复报设备号，而这正是 01 层记过的真实问法。

为什么不是"一个班次"：演示不需要，且班次租约要读考勤数据，属于交付层能力。

## 三、飞书这层的硬约束（不是选择题，是地雷）

| 约束 | 数值 | 对本项目的影响 |
|---|---|---|
| 事件必须 3 秒内回执 | 超时按 15s / 5min / 1h / 6h 重推，最多 **4 次**，窗口约 **7.1 小时** | 单条诊断实测 7.5–22.5 s（`DOC-35` 三幕），远超 3 s → **必须异步**；去重记录至少留 24 h |
| 成功也会重推 | 链路是"至少一次"语义 | 幂等不是优化，是必需品 |
| 接收消息事件的去重字段 | 该事件页明确写"**请使用 `message_id` 去重，不要依赖 `event_id`**"，而同站的事件概述页说用 `event_id` | 以更具体的事件页为准：**收用 `message_id`** |
| 长连接是集群模式、**不广播** | 同一应用多 client 时只有一个随机收到 | 不能把会话状态放进程内存；`PostgresSaver` 正好兜住 |
| 每个应用最多 50 个连接 | 每初始化一个 client 算一个 | 多实例部署前先算连接数 |
| 长连接仅支持企业自建应用 | 商店应用只能用 webhook | 客户若坚持商店应用，走 webhook |
| 长连接仍需**能访问公网** | 只出不入 | 完全断网的车间走不通，只能退回 kiosk/内网 IM |
| 群聊默认只收 @ 的消息 | 收全群要 `im:message.group_msg`（敏感） | 不申请，见决策 2 |
| 发消息限频 | 同一群 **5 QPS**（群内机器人共享）、接口 1000/min 与 50/s | 故障爆发时 10 人同时 @ 必须排队，不能一人一张卡狂推 |
| 消息体大小 | 文本 150 KB、卡片 **30 KB** | 1375 字结论没问题；**20 条 claims 全列大概率超** → 必须折叠 |
| 更新已发卡片 | 仅 **14 天**内、单条 **5 QPS**、前后都需 `config.update_multi: true`、更新身份与发送身份一致 | 结论卡与建单结果卡都走这条 |
| 卡片回调 | 3 秒内响应；延时更新 token **30 分钟**有效、**同 token 最多 2 次** | 建单完成后**不能再**延时更新 |
| 旧版卡片回传交互 | **不支持**长连接 | 只用新版卡片（`card.action.trigger`） |

### 三条更新通道，别用错

| 通道 | 时限 | 次数 | 本项目的用途 |
|---|---|---|---|
| 回调响应体里直接带 card | 3 秒内 | 一次 | 点按钮 → 立刻换成 S2 表单 |
| `POST /interactive/v1/card/update`（延时更新，用回调 token） | 30 分钟 | **2 次** | 备用；建单完成不能用（token 次数已用） |
| `PATCH /im/v1/messages/{message_id}`（无条件更新） | **14 天**、5 QPS | 无次数限制 | **S0→S1、S2→S3 全部走这条** |

一句话：**凡是"发完之后还想改"的，都用 PATCH。**

## 四、薄适配器：只做五件事

接口（示意，实现时按项目实际命名）：

```python
@dataclass
class InboundMessage:
    channel: str        # "feishu" / "web"
    user_key: str       # 入口内唯一的用户标识（飞书：open_id；web：浏览器指纹）
    room_key: str       # 会话容器（飞书：chat_id；web：session_id）
    text: str
    event_id: str       # 判重用（飞书：message_id）
    thread_hint: str | None
    raw: dict           # 只给日志，业务层不许读
```

五个职责，别的都不许：

1. **收**：事件 → `InboundMessage`（归一化，业务层永远只见这六个字段）
2. **判重**：`event_id` 查 PG 去重表，命中就丢弃，**不回执失败**
3. **回执**：3 秒内 200，业务丢后台
4. **渲染**：把统一的事件流（`node_start` / `node_end` / `done`）翻成卡片元素
5. **发送/更新**：`send_card` / `patch_card`

反向禁令（落地后用 grep 查）：

- 业务层（`app/graph/**`、`app/tools/**`）**不许出现** `open_id`、`chat_id`、`message_id`、`card`、`feishu`、`lark`
- 适配器**不许**直接调图内部节点、不许判断根因、不许读台账
- 渲染器里"内部术语→人话"的映射复用已有的 `_node_detail`，并挪进共用层（Web 也用它），**不要为飞书重写一份**

### 唯一一处必须动业务层：`operator_id`

C 段式身份（读用飞书账号、写才要工号）意味着建单要带"谁提交的"。但 `create_work_order` 现在没有这个参数。

边界这样划：

- `operator_id` 是**业务概念**（谁提交的、属于哪个角色、给多大范围），可以进 state，合法；
- `open_id` 是**平台概念**，只在适配器里出现，转成 `operator_id` 后进入业务层。

所以改法：`create_work_order` 加可选参数 `operator_id`；state 加字段 `operator_id`（由入口写入）；写工具调用时从 state 取。这是"加一个字段"，不是"接一套平台"。

**注意 worker 的连带影响**：`schemas.py` 的工具定义、`BEHAVIOR_FILES` 指纹、`code_hash`、四轴校验都会变，一次改动会作废当前基线，重跑一次全量才能重新引用数字。

## 五、三层键，作用域别混

入口层一接，键就从一层变三层。三把键作用域完全不同，混了就出鬼故事：

| 层 | 键 | 谁生成 | 窗口 / 保留 | 防什么 |
|---|---|---|---|---|
| 入口 | `message.message_id` | 飞书 | 至少保留 **24 小时**（官方重推窗口 7.1 h） | 事件重推导致同一句话跑两遍 |
| 会话 | `fs-` + sha256(chat_id\|open_id) | 我方 | 30 分钟活跃窗 | 串台、上下文污染 |
| 业务 | `sha256(device_id\|root_cause_code)[:32]` | 服务端 | 跟"未关闭"走，无固定窗 | 重复建单 |

关键纪律：**入口键不参与业务判定，业务键不看入口**。入口重推被入口键挡掉；入口没挡住（换了 message_id 但内容一样）还有业务键兜底——两层不是冗余，是不同故障模式。

发送侧还有一把：`im/v1/messages` 的 `uuid` 参数，同 uuid **1 小时内至多成功一条**。重试发"处理中"卡片时带上它，避免同一张卡发两次。

## 六、一条消息的完整旅程

| 步 | 谁做 | 做什么 | 时限 |
|---|---|---|---|
| 1 | 飞书 → 适配器 | 群里 @ "CX-101 又误报了" 到达 | — |
| 2 | 适配器 | 用 `message_id` 判重；命中则丢弃 | < 5 ms |
| 3 | 适配器 | 立即回执 200，业务丢后台线程池 | **< 3 s** |
| 4 | 适配器 | 算 `thread_id`，发 S0"处理中"卡片（带 `uuid` 去重） | 1 次 API |
| 5 | 图 | `understand → plan → act → verify → finalize`，事件流推出 | 7.5–22.5 s |
| 6 | 适配器 | `node_*` 事件 → PATCH 卡片进度行（限 5 QPS，节流到每步一次） | 每步 1 次 PATCH |
| 7 | 适配器 | `done` → PATCH 成 S1：摘要在前、依据折叠、`确认建单` 按钮 | 1 次 PATCH |
| 8 | 点按钮 | 回调 3 s 内回 `{}` → 后台 PATCH 成 S2（工号下拉） | — |
| 9 | 提交 | 回调回 `{}` → 校验工号 → 建单 → PATCH 成 S3（单号 + 审计行） | — |

trace 每轮多记四列：`channel` / `room_key` / `user_key` / `event_id`。**这四列是入口层唯一允许进 trace 的平台字段**（trace 是日志，不是业务状态）。

## 七、卡片四态（含"再点一次"的完整细节）

| 状态 | 内容 | 按钮 |
|---|---|---|
| **S0 处理中** | 逐行进度（"正在查设备台账…已用时 4 s"），无结论 | 无 |
| **S1 结论** | 摘要 3 行 + 依据折叠（claims 藏里面）+ 单号区空 | `确认建单` |
| **S2 待确认** | "即将为 CX-101 创建工单 · 镜头污染 · medium" + 工号下拉 | `提交` / `取消` |
| **S3 已建单** | 单号区 `WO-20261121-003 · 待处理 · 1001 · 14:32` + 审计行 | `再提交一次`（小字灰） |

### S3 的按钮不是隐藏，是故意留着

两个理由都真实：现场真会重复点（以为没成功、交接班的人又点一次、断网重试）；演示需要它。

### 按钮值：只表达意图，参数用签名快照

```json
{
  "action": "create",
  "thread_id": "fs-xxxxxxxx",
  "snapshot": "base64(建单参数 JSON)",
  "sig": "HMAC-SHA256(snapshot, 服务端密钥)"
}
```

为什么不能只放 `thread_id`：建单参数（`root_cause_code` / `evidence_refs` / `severity` / `actions`）在 `RESET_EACH_TURN` 里，用户隔两轮再回来点按钮时 state 已滚掉。

服务端收口三步：

1. 验 `sig`，不过直接拒（防卡片被转发、被别人点、被改参数）
2. 用 `snapshot` 建单
3. **回查 state 交叉验证**：state 里还有同设备同根因，就以 state 为准

一句话：**快照负责"参数还在"，签名负责"参数没被改"，state 负责"以谁为准"。**

### 第一次点与第二次点

| | 路径 | 屏幕 |
|---|---|---|
| 第一次 | 校验 → 建单 → 返回 `deduped:false` + 新单号 | PATCH 成 S3，单号区出现单号 |
| 第二次 | **同一条路径**，但三件事不许做：①不重跑诊断 ②不往群里发新消息 ③不在入口层再查一遍 | QMS 返回 `deduped:true` + 原单号 → toast + 卡片追加审计行 |

三个"不许做"的理由：重跑 20 秒会冷场且可能得出不同根因；发新消息会刷屏；入口层再查一遍等于把业务键的第二份定义搬到入口，迟早两边不一致。

### 第二次点，屏幕上要看到两个反馈

| 位置 | 文案 | 为什么两个都要 |
|---|---|---|
| Toast（回调响应体） | `已存在未关闭工单，本次未新建` | 即时反馈，点下去立刻有反应 |
| 卡片审计行 | `14:35 · 1001 再次提交 · 已去重，沿用 WO-20261121-003` | 留得住；toast 三秒就消失，回看截图只有这一行 |

**单号区一个字不动**——两次点一个单号，比任何文案都有说服力。

### 演示用下拉，不用输入框

| 方式 | 表现 | 决定 |
|---|---|---|
| 输入框填 4 位 | 要打字、可能打错、观众干等 | 不用 |
| 下拉：1001 / 1002 / 1003 / 9999 | 一点即选，还能顺带演"9999 无效被拒" | **用** |

工号语义（演示夹具）：`1001` 操作工 A 线、`1002` 维修工全厂、`1003` 班组长 A 线、`9999` 无效。

### 失败三分支

| 情况 | Toast | 卡片 |
|---|---|---|
| 工号无效（9999） | `工号 9999 不在可用范围内` | 停在 S2，不掉状态 |
| QMS 不可用 | `建单系统暂时不可用，单未创建` | 回 **S1**（不能显示单号） |
| 原单已关闭后再点 | 无 toast，正常建单 | S3 新单号 + `上一张 WO-xxx 已关闭，本次新建` |

第三条要记住：**关闭的单不占幂等键**，所以"再提交一次"不是永远去重。演示前必须确认那张原单是"待处理"，否则第四幕会演成"新建成功"，看不出幂等。

### 一个必须先说清的缺口：没有 operator 字段

想写"14:32 由 1001 提交"，但 `work_orders` 表没有 `operator_id`（`data/schema.sql:100-112`）。

| 选项 | 成本 | 提示能写成 |
|---|---|---|
| A 演示降级 | 0 | `已存在未关闭工单 WO-xxx（待处理）` |
| B 加 `operator_id` + `channel` 两列 | 一次迁移 | `14:32 由 1001 通过群入口提交` |

演示用 A，**但面试主动讲 B**——"我知道这个提示缺谁提交的字段，加两列就能补成三段式"，比硬演出来值钱。

## 八、演示脚本（四幕，90 秒内）

| 幕 | 输入 | 屏幕预期 | 解说词 |
|---|---|---|---|
| 1 | 群里 @「CX-101 最近误判率怎么这么高」 | S0 逐行进进度 → S1 结论，每个数字带出处 | "它查了台账、缺陷日志、手册，每个数字都能指回哪一行" |
| 2 | 追问「那 11-08 那天呢」 | 不重报设备号，直接给那天 | "我没再报设备号，它接着上一轮" |
| 3 | @「CX-106 有问题」 | 拒答 + 列出现有 CX-101～105 | "台账里没有的设备，它不编" |
| 4 | 点 `确认建单` → 选 1001 → 再点 `再提交一次` | S2 → S3 单号 → 再点后 toast + 审计行，单号不变 | "现场一定有人点两次。单号没变，多了一行 14:35 已去重。去重靠的不是界面禁点，是数据库里那个键" |

第 4 幕最后那句是重点：**面试官会问"你是不是只把按钮禁用了"，先把答案堵了。**

这四幕是飞书入口内的脚本。它怎么和已定型的 Web 三幕并排演（三幕留 Web、飞书加演 30 秒），见第十三节。

## 九、失败面与兜底

| 故障 | 表现 | 兜底 |
|---|---|---|
| 事件重推（7.1 h 内） | 同一句话跑两遍 | `message_id` 去重表，保留 24 h |
| 群禁言 / 机器人被屏蔽 | 发送返回 `230035` | 记 trace，**不重试轰炸**；不刷群 |
| 内容超限 | 卡片 > 30 KB 返回 `230025` | claims 折叠；超限时降级为"摘要 + 单号 + 打印链接" |
| 限频 | `230020` | 单群 5 QPS，节流；故障爆发排队并回"已排队，前面还有 N 条" |
| 工号无效 | — | 停在 S2，不写库 |
| QMS 不可用 | — | 回 S1，禁止显示单号（否则就是"告诉用户建了其实没建"） |
| 完全断网 | 长连接连不上 | 这个入口不成立；退回 kiosk/内网 IM。**必须提前跟客户说清** |
| 多实例 | 事件随机落到某实例 | 演示不用；真上线先加 PG advisory lock（按 `thread_id`），否则同一 thread 会被两实例同时跑 |

## 十、明确不做（演示版边界）

| 不做 | 理由 |
|---|---|
| 多实例与广播 | 单实例够；多实例要先做 thread 级锁，属于真上线 |

| 自研流式打字效果 | 平台会做得更好；进度用节点级，不做 token 级 |

## 十三、双入口与切换（Web 保留）

**一句话：飞书是加法，Web 一行不改。** 依据是代码里早就把"跑一轮"抽象出来了——`app/graph/build.py` 的 `run(msg, thread_id=...)` 是唯一入口函数，`app/web/server.py:405` 直接调它。飞书不需要重写诊断，它只是第二个外壳。

### 13.1 装配形态：两进程（定案）

| 入口 | 启动 | 变不变 |
|---|---|---|
| Web | `uvicorn app.web.server:app` | **原命令，不变**；DOC-35 三幕与录屏 SOP 全部照旧 |
| 飞书 | `python -m app.entry.feishu`（独立进程） | 新增 |

- 共用 `FDE_PG_DSN`：同一 checkpoint 表、同一 `work_orders`、同一 QMS
- **不做同进程 `both`**：SDK 依赖装不上、事件循环冲突、凭据缺失，任何一个都会把 Web 演示一起拖死。答辩现场不拿稳定性做实验
- 飞书进程启动自检：长连接已连 + DB 可写，才打印 ready；任一失败就退出并打印原因——**不静默降级**，否则现场表现是"机器人在线但一句话不回"

### 13.2 唯一必须动 Web 侧的一处：抽事件流

`_sse`（`app/web/server.py:526-603`）把三件事揉在一起：图事件 → 帧、帧 → SSE 字符串、以及为 Starlette 线程池写的 `t.activate()` 每轮补偿。

```
app/entry/stream.py   iter_events(msg, thread_id) → yield dict 帧
  ├─ web/server.py 的 _sse    帧 → SSE 字符串（对外字节不变）
  └─ entry/feishu             帧 → 卡片 PATCH（S0 的四行进度靠它）
```

- **验收判据（已修正）**：原写"帧序列逐字节 `diff` 一致"，**实测不可能**——LLM 采样会让 plan 轮数变化（同一句话改造前 4 轮 / 22 帧，改造后 5 轮 / 24 帧；历史 trace 里同一句的 plan 轮数分布是 0×1、2×2、3×4、4×10、5×4，本来就抖）。改成三件可机械核对的：①**帧骨架**（`type`+`node` 序列）同构；②`done` 帧**键集合逐项相同**（实测 26 个全等）；③`_frame` 序列化函数一行未动。判据 ②③ 已全过，① 的差异落在既有抖动范围内。抽层最典型的翻车是"能跑但少一帧"——前端不报错，只是进度条缺一截
- **必须一起搬走**：每轮 `next()` 之前重新 `t.activate()`。不搬，`add_tokens` 与 `trace.emit` 全部静默丢弃，jsonl 里 token 恒为 0。飞书的回调线程和 Starlette 线程池是同一类问题
- **只复用 `run()` 不够**：单轮要结论用 `run()`；**分阶段进度必须走 `g.stream`**，S0 的逐行推进就是从流里来的

### 13.3 thread_id 命名空间：只给飞书加前缀

| 入口 | thread_id 形状 | 为什么 |
|---|---|---|
| Web | 裸 uuid（前端 localStorage） | 不动 → 演示机里存的旧会话不失效；`server.py:30` 的 `_ID_RE` 只允许 `[A-Za-z0-9_-]{1,80}` |
| 飞书 | `fs:<chat_id前8>:<open_id前8>:<YYYYMMDD>:<序号>` | 自带命名空间，事后审计能看出入口、人和天 |

前缀只影响**会话隔离**，不影响权限：归属校验读的是 state 里合并后的 `device_ids`（`app/graph/nodes.py:1523`），与 thread_id 无关。

### 13.4 跨入口幂等：能演，但演不全

- 业务键 `sha256(f"{device_id}|{root_cause_code}")[:32]` 与入口无关 → **Web 建的单，飞书再点一次会命中同一 `idempotency_key`**，这条是真能演的
- 但 `work_orders`（`data/schema.sql:100-112`）没有 `channel`、没有 `operator_id` → 结果对，却说不出"这张单是哪个入口、谁提交的"
- 演示口径：单号不变照讲；"谁提交的"降级为台词，不写库
- 要补就加这两列，代价与第十一节第 6 条同一笔账（`code_hash` / 四轴要重跑）

### 13.5 演示编排：三幕在 Web，飞书加演

- Web 三幕沿用 DOC-35（22.5 / 7.5 / 15.9 s），录屏 SOP 一个字不动
- 飞书只加演 30 秒，取第四幕里最短的一段：群里 @ → S0 → S1 → 点确认 → S3
- 台词一句："同一句提问，两个入口，同一判定层。"
- **现场网络不归你控**：长连接连不上就切录屏，绝不临场装 SDK

### 13.6 切换成不成立的机械判据

- `grep -rn "feishu\|lark\|open_id\|chat_id" app/graph app/tools` → 归零
- 关掉飞书进程，Web 三幕照常跑完 → 成立
- 想在 state 里塞一个 `entry` 字段来"支持切换" → **失败**。入口是装配概念，不是业务概念；一旦进 state，它会跟着 checkpoint 落地、跟着评测用例被断言，然后每加一个入口就要改一次判据

### 13.7 本节新增的未验证

- 抽 `iter_events` 后的帧序列 `diff` 还没做（现在只是设计的验收判据）
- `lark-oapi` 能否在这台机器装上、能否连出 public 网，未验证（要联网 pip，演示机建议提前打进 requirements）
- 两进程同库的连接数翻倍，`PostgresSaver` 默认池大小未核
