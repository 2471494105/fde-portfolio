## 一句话

先做"能一天内失败的"（依赖能不能装、凭据建不建得出来），再做唯一必须动 Web 的那一刀（抽事件流，有逐字节 diff 兜着），最后才动基线（`operator_id` 进工具会改 `code_hash`）。

## 一、现成方案盘点：用什么、不用什么

| 候选 | 结论 | 依据 / 理由 |
|---|---|---|
| `lark-oapi` 1.8.0（官方 SDK） | **采用** | PyPI 最新稳定版，`requires_python>=3.8`，依赖 `requests` `requests_toolbelt` `pycryptodome` `websockets>=11,<16` `httpx>=0.24,<1.0`；长连接与卡片回调都在一个 `ws.Client` 里 |

| 卡片搭建工具（cardkit） | 不用它做运行时 | 但**可以借它导出 JSON 当骨架**，省掉手搭四个态的排版 |

| `sse-starlette` | 不采用 | 现有 `StreamingResponse` + 手写帧已跑通（SSE 帧类型 open/node_start/node_end/done/error），换库等于换帧格式，还得重做前端 |
| `feishu-sdk`（第三方 PyPI） | 不采用 | 只包了发卡片，事件、更新、签名都不管，且绕开官方 SDK |
| `openbird`（npm，逆向网页版 WebSocket + 浏览器 cookie） | 不采用 | 非官方、借用个人身份，违反平台条款且随时失效 |
| `larkline` / `lark-agent-bridge` / `feishu-bridge`（把 agent 接进飞书的现成桥） | **不采用其代码，抄它的失败清单** | 见 §2 的三条新约束；它们的可靠性设计比本设计更实操：**卡片更新失败降级发 markdown**、**失败/超时卡片留 retry 按钮**、**快速连发消息合并成一次请求**、**新消息打断正在跑的 run**、**idle watchdog（N 分钟无输出即杀并注明）**、日志按天写 + `/doctor` 读时间线 |

## 二、联网实测到的三条硬约束（比设计文档更准，补进 DOC-36 缺的部分）

| 约束 | 具体 | 对本项目 |
|---|---|---|
| **流式卡片约 10 分钟被服务端强制收尾**，之后的更新**静默丢弃** | `larkline` 记录：飞书在约 10 分钟时强制 finalize 流式卡片，客户端与手机端一致；它自己在 ~8.5 分钟暂停并显式提示，最终答案改发新消息；阈值 `LARKLINE_STREAM_CARD_SAFE_MS` | 本项目一轮 7–23 秒，**碰不到**。但真上线遇到长任务必须写兜底，否则"卡永远停在正在调用工具" |
| 卡片 JSON 2.0 的体积与元素双限 | 30 KB（发送接口）+ **200 元素**（2.0 结构） | 20 条 claims 折叠方案要按"元素数"也数一遍，不能只数字节 |
| `lark-oapi` 与现有 venv 的 `websockets` 冲突 | 现有 **17.4**，SDK 要求 `<16`，dry-run 结论：`Would install lark-oapi-1.8.0 pycryptodome-4.5.0 websockets-15.0.1` | 会**降级** websockets。本项目不用 uvicorn 的 ws、也不走 langgraph-sdk 的 ws transport，已实测无影响——降完后 CX-101 端到端 18.2 s / 6 步 / 出处齐全（见 W0） |

### 判据修正：W1 的"逐字节 diff"不成立

原判据写的是"抽层前后同一问题的帧序列逐字节 `diff` 一致"。做完发现**这条判据本身是错的**——LLM 采样会让 `plan` 轮数变化：

| 采样 | plan 轮数 | 帧数 |
|---|---|---|
| 改造前（18:23） | 4 | 22 |
| 改造后（18:30） | 5 | 24 |
| 历史同一句/近义句（12 次） | 0×1、2×2、3×4、**4×10、5×4** | — |

第三行是关键：5 轮本来就出现过 4 次，所以"多一轮"是既有抖动，不是抽层引入的。因此判据换成三件能机械核对的事：

1. **帧骨架同构**：`type` + `node` 序列（`open → (node_start, node_end)*n → done`），允许 plan/act 重复段数抖动
2. **`done` 帧键集合逐项相同**：实测 26 个键完全一致，字段顺序也一致
3. **`_frame` 序列化函数一行未动**：帧 → SSE 的编码没换过

另外抽层带出 3 条单测引用了被搬走的私有符号（`cite_text` × 2、`_done_event` × 1），已改成指向新归属（`app.entry.labels` / `app.entry.stream`）——**这是抽层的正常代价，不是缺陷**：测试断言私有函数时就绑定了它的位置。

### W2 实测：骨架通了，三条判据过了两条半

文件与职责（六个）：

| 文件 | 职责 | 关键取舍 |
|---|---|---|
| `inbound.py` | 事件 → `InboundMessage`（7 字段） | 只接 `text`；`post`/`image`/`file` 明确 skip 并给原因；`raw` 只留 3 个日志字段，防人顺手拿去判业务 |
| `dedupe.py` | `entry_dedupe(channel, event_key)` + TTL 24 h | 一条 SQL 完成"查+占位"（`ON CONFLICT DO NOTHING … RETURNING`），不给并发留窗口；短连接，不维护池 |
| `render.py` | 帧 → 卡片 2.0（进度行 + 结论 + 依据） | 同 node 多轮不去重（4 轮 act 就是 4 行）；只做到"看得出进展"，四态留给 W5 |
| `client.py` | `send_card` / `patch_card` / `send_text` | 发送侧 `uuid` 幂等（1 小时同 uuid 至多一条） |
| `ready.py` | `ReadyOnConnected`（日志钩子） | 单独摘出来，就为了不把 lark 拖进单测 |
| `__main__.py` | 装配 + 退出码 | 回调只做归一/判重/丢线程池，判重**必须**留在回调里同步做 |

实测（本机 2026-11-21 18:45）：

| 判据 | 结果 |
|---|---|
| 缺凭据 → 退出码 2 | ✅ `exit=2`，stderr 一行 `missing env: FEISHU_APP_ID, FEISHU_APP_SECRET` |
| 假凭据 → 不伪造 ready | ✅ `db: ok` / `ws: connecting...` 之后飞书回 `1000040346 app_id is invalid`，`exit=1`，**全程没有 ready 行** |
| 业务层平台字段 grep 归零 | ✅ `app/graph/**`、`app/tools/**` 对 `open_id\|chat_id\|message_id\|feishu\|lark` **0 命中** |
| 判重语义 | ✅ 同键第一次 `False`、第二次 `True`；换 channel 不互相误杀 |
| 单测 | ✅ **310/310**（289 护栏 + 21 新增），耗时 0.53 s |

三条实现细节，都是踩出来的：

1. **SDK 没有"连接成功"回调**。`ws.Client.start()` 把 `_connect()` 和随后阻塞的 `_select()` 串在一次调用里，中间没有缝。它唯一给的正面信号是 logger 里那行 `connected to …`，所以 ready 判断挂在 logging handler 上——不轮询它私有的 `_conn`（字段名会随版本变）。
2. **`app_id` 错时 `start()` 抛 `ClientException`，默认会打出二十几行 traceback**，真正的错误码埋在最底下。已改成捕一行 `ws failed: …` + 一行 hint，退出码 1。
3. **`import lark_oapi` 要 15.5 秒**（本机实测）。这就是 `ready.py` 被单独摘出来的原因：单元测试从 5 s 涨到 22 s，只为了覆盖一个 `if "connected to"` 的判断，不划算。

边界（**故意没做**，避免"骨架"和"能用"混成一个症状）：

- `_handle()` 现在是**只回执不跑图**：发一张卡片写着"骨架版本：只回执不诊断"。接 `iter_events` 是 W5 的事。
- 卡片回调 `card.action.trigger` 尚未注册（W5/W7）。
- `entry_dedupe` 表由 `Dedupe.setup()` 建，**还没进 `data/schema.sql`**（W4）。
- `ready: ws connected, db ok` 已真机验过（2026-11-21 19:03:28，打码后 19:35 复验）。

## 四、三条排序理由

1. **W0 先做**：装不上或装坏了，后面九项全是空谈。它一天内就能给出"能/不能"。
2. **W1 排第二**：它唯一会动已跑通的 Web 代码，所以要在手上还有充足回滚空间时做，而且它的判据（帧 diff）越早越干净——等 W5 的卡片层接上来，再改帧就分不清是谁的锅。
3. **W6 排最后**：它改 `BEHAVIOR_FILES` → `code_hash` → 四轴，一旦动，之前所有引用的评测数字都要重跑。凡是"还没到必须动"的，一律押后。
