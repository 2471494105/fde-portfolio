# 连接层：字段映射与四形态跨源实测

> 2026-11-25 | 代码 `app/ds/mapping.py`、`scripts/check_ds_matrix.py`；配置 `data/mapping/client_a.json`；样本 `data/sandbox/from_client/`

## 一、要解决的不是「没数据」，是「数据长得不一样」

接第二家客户时最先撞的往往不是连不上，是这些：

| 客户那边 | 我们这边 |
|---|---|
| `equip_no` | `device_id` |
| `prod_line` / `work_station` | `line` / `station` |
| `install_dt = 2025/03/12` | `install_date = DATE` |
| `conf_pct = 91`（百分制） | `confidence = 0.91` |
| `is_ok = Y` | `is_actually_ok = true` |

八列没有一个字一样。没有翻译层，每接一家客户都要改一次 loader 代码。

## 二、取舍一：映射是显式承诺，不做自动探测

一个 JSON 写清楚「客户的哪个字段，对应我的哪个字段，什么类型，什么格式，要不要缩放」。

**为什么不自动猜。** 按列名相似度做模糊匹配，在客户只有 8 列时看着很聪明；到 30 列、两家客户都有 `id` 和 `status` 时就开始错配，而且错得没有声音——数据照样入库，只是入错了列。

**代价是每接一家要写一个 JSON。** 这是刻意保留的成本：写配置的人必须真的看过客户的字段清单。这一步省掉了，省掉的就是「你确认过吗」这件事本身。

**多余列一律忽略，不做保留。** 客户文件下次多出来一列「备注」，不代表系统承诺认识它。

## 三、取舍二：缺列要报，空值要放——这次最值钱的一条

两种「没有」必须分开处理，混在一起就会两头都错：

- **源里根本没有 `equip_no` 这一列** → 配置过时，或者文件换了 → **报错**，错误信息带行号和实际列名
- **列在，值是空** → 数据脏 → **原样放行成 `""`**，交给断言层

反过来会怎样：

- 空值也报错 → 客户文件里第一条设备号没填，整个导入就卡死。运维唯一能做的是删掉那行再导入——脏数据从「看得见」变成「被藏起来」，之后所有报表都是干净的假象
- 缺列也放行 → 字段名改了没人知道，静默变成一整列 NULL，比崩溃难查一百倍

所以映射层只负责翻译，不负责判对错。判对错是断言层的职责：`B1 设备号空串` 就是专门为第二种情况准备的，它现在能在 staging 表上真的抓到。

## 四、实测：四种进入形态，同一套断言

| 形态 | 设备 | 日志 | B 类红 | A 类红 |
|---|---|---|---|---|
| pg 直连真表 | 5 | 9 | B1–B6 | 无 |
| csv 文件导出导入 | 5 | 10 | B1–B6 | A1 |
| http 分页接口 | 5 | 10 | B1–B6 | A1 |
| **client 客户格式（过映射）** | 5 | 10 | B1–B6 | A1 |

`client` 这一行是本次的重点：字段名全换、日期是斜杠、置信度是百分制（91 → 0.91），过完映射之后，**结果与原名 CSV 形态逐条一致**。

反面证据（不配映射直接灌）：

```
UndefinedColumn: 关系 "stg_devices" 的 "equip_no" 字段不存在
```

一条都进不去，但报的是「列不存在」，一眼能定位到没配映射。

## 五、pg 为什么少一条

源数据里有一条 `CX-999`（设备号写错）的日志。

- pg 形态走真表，外键把它挡在门外，**从未进入落地表**，所以 A1 无从报
- csv / http / client 走无约束落地表，原样搬进来，A1 立刻红

这说明 pg 的结构约束不是断言的替代品，是**叠加**在它上面的额外保护。客户给你的源大多没有外键，换源之后 A 类断言才是唯一防线。

## 六、这一步证明了什么，没证明什么

**证明了**：换一家客户，改的是一个 JSON，不是代码。loader、断言、单测都不动；`app/ds/*` 不在 `BEHAVIOR_FILES` 内，`code_hash` 不变。

**没证明**：这只是「字段名 / 格式 / 单位」这一层。真实对接还有鉴权、分页游标、增量水位、部分字段缺失、两家客户口径打架——一个 JSON 解决不了这些。
