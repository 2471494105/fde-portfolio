**这一批留下的方法论（写在这里免得下次重犯）**：

1. **只证此刻的判据，发现不了「昨天还在、今天没了」**。十条判据里只有第 6、7 条证「一段时间里没发生的事」，其余八条都只证「此刻对不对」。任何「历史/累积/不被销毁」的承诺，必须有一条跨轮判据落地在**只增不减的文件**上——`data_health.json` 每轮覆盖，它自己证不了自己。
2. **新判据的第一个反例必须是「它说有问题、实际没问题」**。跨租户判据第一版 SQL 少 `AND tenant <> ?`，把本租户历史自引用算成跨租户，每轮固定假报「2 条」而库里 0 条。永假报警会训练人把报警当背景噪声，比没有判据更坏。
3. **同一件事不能有两个结论**。判据只加在子脚本、没上移到 `facts_issues` 时，一度出现「`check_facts` exit 1、`data_health` 报 OK」——这比一个错结论更糟。
4. **每条新判据都要问一句「它进不进 `semantic_ok`」**。`semantic_ok` 是手写的 `and` 链，漏加一项，判据照红、正确率照样 100%，读报告的人只会看数字（`N-17`）。只写日志等于没写。

**这一批留下的方法论（接在九之二后面，第 5 条）**：

5. **假绿和假红是同一个错，不是两个方向**。假绿让人把错当成对，假红让人把对当成错；后者更隐蔽，因为它长得像"判据在工作"。判断一条新判据有没有真在工作，不问"它红了没",问两件事：**它在几个不同的输入形状上被走过？红了的时候，被指着的那个人是不是真的错了？** `N-18` 就是反例：判据只在一个字段（`maintenance_cycle_days`）上被验证过，却对另外六个字段给出同一个结论。
6. **凡"环境故障"，必须先看它有没有自己的归因通道**。`deduped_env` 存在，所以幂等挂了会被标灰；建单本身没有，所以 `W3` 被冤枉了三批，`env_n` 一直报 0。**一个 `env_n=0` 只有在"每个会造成环境失败的工具都有自己的通道"时才可信**。
