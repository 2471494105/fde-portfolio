# 数据契约 v1

> 2026-11-25 | 依据 `data/schema.sql` 与 `scripts/check_data_contract.py` 实际内容编写，不是设计稿。
> 一句话原则：**契约不是文档，是可执行的东西。** 每条条款要么有断言编号，要么在第六节明确标"未覆盖"。

## 零、这份文档给谁看

| 读者 | 用它干什么 |
|---|---|
| 接新客户的人 | 照这张表问客户要字段、问口径、问枚举 |
| 写断言的人 | 每条契约对应一条断言，改契约必须改断言 |
| 客户 IT | 这就是验收清单：「这些不满足，数据就不该进主表」 |
| 未来的我 | 三个月后忘了「station 为什么有两套格式」时有地方查 |

## 一、五条元规则（跨表通用，比任何单表条款都重要）

**R1 时间字段是「发生时刻」，不是「入库时刻」。**
`defect_logs.ts` 是设备做判定的时刻，`work_orders.created_at` 是建单时刻。两者混用就没法区分「这条是补录的」还是「实时的」，而补录数据不能用来算响应时间。

**R2 空串、缺失、0 是三件不同的事。**

| 情况 | 含义 | 谁来管 |
|---|---|---|
| 空串 `''` | 填了但没内容，数据脏 | 放行入库，断言抓（B1、B6） |
| 缺失（列不存在） | 配置过时 / 客户文件换了 | 映射层直接报错，带行号和列名 |
| `0` | 真实值 | 正常入库 |

**R3 设备身份只有一个来源：`device_id`，它必须在 `devices` 里存在。**
六张表引用 `device_id`，其中五张有外键，`work_orders` 没有——见第六节。

**R4 枚举是闭集。** 新增一个 `severity` 值等于改契约，要登记版本；不是"数据里多了一个值"。

**R5 数值带单位，单位写在列名或注释里，不写在业务代码里。**
`drift_px` / `drift_mm` / `cumulative_hours` / `rated_life_hours` 全部如此。

## 二、逐表契约

### 2.1 `devices` — 设备档案（5 台）

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `device_id` | TEXT PK | 否 | 非空串；去空格转小写后必须唯一 | B1、B2 |
| `line` | TEXT | 否 | 产线名，如 `3号线` | — |
| `station` | TEXT | 否 | **区间**格式 `1-3号工位`，不是单点 | B5（区间基准） |
| `camera_model` | TEXT | 否 | 相机型号，如 `In-Sight 2801` | — |
| `lens_model` | TEXT | 否 | 镜头焦距，如 `16mm` | — |
| `light_model` | TEXT | 否 | 光源型号，如 `CA-DC21E` | — |
| `install_date` | DATE | 否 | 安装日期 | — |
| `maintenance_cycle_days` | INT | 否 | 保养周期（天），应为正数 | **未覆盖** |

### 2.2 `defect_logs` — 误判日志（主证据表）

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `id` | BIGSERIAL PK | 否 | — | — |
| `ts` | TIMESTAMP | 否 | 判定发生时刻，不得在未来 | B4 |
| `device_id` | TEXT FK | 否 | 必须存在于 `devices` | A1（pg 由 FK 保证） |
| `station` | TEXT | 否 | **点**格式 `2号工位`，且必须落在档案区间内 | B5 |
| `defect_type` | TEXT | 否 | 缺陷类型，自由文本 | — |
| `confidence` | REAL | 否 | 模型置信度 **0–1** | B3 |
| `batch` | TEXT | 否 | 批次号，**≥4 字符** | B6 |
| `verdict` | TEXT | 否 | 模型判定，闭集 `OK` / `NG` | A4（pg 由 CHECK 保证） |
| `is_actually_ok` | BOOLEAN | 否 | 人工复判结果，与 `verdict` 独立 | — |

### 2.3 `alarms` — 告警码字典

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `code` | TEXT PK | 否 | 告警码，如 `E-101` | — |
| `meaning` | TEXT | 否 | 中文含义 | — |
| `common_cause` | TEXT | 否 | 常见成因 | — |
| `severity` | TEXT | 否 | 闭集 `info` / `warning` / `critical` | **由 CHECK 保证，无显式断言** |

### 2.4 `alarm_events` — 告警发生记录

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `id` | BIGSERIAL PK | 否 | — | — |
| `ts` | TIMESTAMP | 否 | 发生时刻，不得在未来 | B10 |
| `device_id` | TEXT FK | 否 | 必须存在于 `devices` | 由 FK 保证，**无显式断言** |
| `code` | TEXT FK | 否 | 必须存在于 `alarms` | 由 FK 保证，**无显式断言** |

### 2.5 `calibrations` — 标定记录

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `id` | BIGSERIAL PK | 否 | — | — |
| `device_id` | TEXT FK | 否 | 必须存在于 `devices` | 由 FK 保证 |
| `ts` | TIMESTAMP | 否 | 标定时刻 | — |
| `drift_px` | REAL | 否 | 像素级漂移 | B7（符号一致性） |
| `drift_mm` | REAL | 否 | 换算到物方的漂移（mm） | B7 |
| `result` | TEXT | 否 | 闭集 `通过` / `告警` / `失败` | A2（pg 由 CHECK 保证） |
| `operator` | TEXT | 否 | 标定人 | — |

**B7 判据**：`drift_px` 与 `drift_mm` 都非 0 且异号 → 红。异号说明换算公式或坐标方向错了，不是数据脏。

### 2.6 `light_usage` — 光源使用

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `device_id` | TEXT PK FK | 否 | 一台设备一行 | — |
| `light_model` | TEXT | 否 | 光源型号 | — |
| `cumulative_hours` | INT | 否 | 累计点亮小时 | B8 |
| `rated_life_hours` | INT | 否 | 厂商标称寿命（小时） | B8 |
| `brightness_set` | INT | 否 | 当前亮度设定 | — |
| `last_replaced_at` | DATE | **是** | 上次更换日期，从未更换为 NULL | — |

**B8 判据**：`rated_life_hours <= 0`，或 `cumulative_hours > rated_life_hours * 3` → 红。超过 3 倍大概率是单位写错（小时当分钟填）。

### 2.7 `light_brightness_history` — 亮度变更历史

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `id` | BIGSERIAL PK | 否 | — | — |
| `device_id` | TEXT FK | 否 | 必须存在于 `devices` | 由 FK 保证 |
| `ts` | TIMESTAMP | 否 | 变更时刻 | — |
| `value` | INT | 否 | 变更后的亮度值 | — |

**这张表允许没有历史记录**（新设备没调过亮度），但它不该在「有设备却没一行记录」时假装正常——B11 只要求它非空，空表视为"没有异常"是假象。

### 2.8 `work_orders` — 工单（mock QMS 读写）

| 列 | 类型 | 可空 | 口径 | 断言 |
|---|---|---|---|---|
| `order_id` | TEXT PK | 否 | 工单号 | — |
| `device_id` | TEXT | 否 | **没有外键**，靠 B9 手工兜 | B9 |
| `root_cause` | TEXT | 否 | 根因描述 | — |
| `root_cause_code` | TEXT | 否 | 根因码，默认 `other` | 进幂等键 |
| `severity` | TEXT | 否 | 闭集 `low` / `medium` / `high` | 由 CHECK 保证 |
| `actions` | TEXT | 否 | 处置动作 | — |
| `evidence_refs` | TEXT | 否 | 证据引用 | — |
| `idempotency_key` | TEXT | 否 | `hash(device_id + root_cause_code)`，**不含日期** | A3 |
| `status` | TEXT | 否 | 自由文本，但幂等条件依赖它 | A3 |
| `assignee_group` | TEXT | 否 | 派工组 | — |
| `created_at` | TIMESTAMP | 否 | 建单时刻（不是故障时刻） | — |

**A3 判据**：`status NOT IN ('已完成','已合并','已取消')` 的工单里，同一 `idempotency_key` 只能有一条。
条件用**黑名单**而不是白名单：将来新增任何状态，默认仍算"还挂着"、仍参与去重，宁可多挡不会漏挡。

## 三、四条跨表不变量

| # | 不变量 | 满足情况 | 断言 |
|---|---|---|---|
| INV-1 | 所有引用 `device_id` 的表，值必须存在于 `devices` | 6 张引用，5 张有 FK，`work_orders` 没有 | A1、B9 |
| INV-2 | 枚举列只能取闭集内的值 | `verdict` / `calibrations.result` / `alarms.severity` / `work_orders.severity` | A2、A4 |
| INV-3 | 档案的 `station` 是区间，日志的 `station` 是点，两者不是同一个词 | 需要区间展开后比较 | B5 |
| INV-4 | 同一设备 + 同一根因码，同时只能有一张未关闭工单 | 部分唯一索引（黑名单条件） | A3 |

## 四、契约 → 断言映射

| 断言 | 契约条款 | 检查内容 |
|---|---|---|
| A1 | INV-1（defect_logs 部分） | 日志设备号必须存在于档案 |
| A2 | INV-2（标定） | `result` 只能是 通过/告警/失败 |
| A3 | INV-4 | 开单幂等键唯一 |
| A4 | INV-2（日志） | `verdict` 只能是 OK/NG |
| B1 | 2.1 `device_id` | 非空串 |
| B2 | 2.1 `device_id` | 归一后唯一 |
| B3 | 2.2 `confidence` | 0–1 |
| B4 | 2.2 `ts` + R1 | 不得在未来 |
| B5 | INV-3 | 日志工位落在档案区间内 |
| B6 | 2.2 `batch` | ≥4 字符 |
| B7 | 2.5 符号一致性 | 漂移异号 |
| B8 | 2.6 寿命倍数 | 累计 ≤ 标称 ×3 |
| B9 | INV-1（work_orders 部分） | 工单设备号存在 |
| B10 | 2.4 `ts` | 告警不得在未来 |
| B11 | 全表 | 业务表不得为空（空表冒充"没有异常"） |
| B12 | 2.9 `params` | 正文提到参数名却没填 params（忘填即永久退出冲突检测） |
| 隔离区 | 增量装载 | `stg_quarantine` 非空即红 |

跑法：

```powershell
# 主库结构（pg 源）
python scripts\check_data_contract.py --expect=clean

# 沙箱脏数据（测试场景，隔离区有故意造的脏行）
python scripts\check_data_contract.py --expect=dirty --allow-quarantine

# staging 落地表（换源之后）
python scripts\check_data_contract.py --prefix=stg_ --dsn=... 
```

## 五、变更登记规则

三件事必须一起做，缺一件就是"改了没登记"：

1. 改本文档对应条款
2. 加/改断言（`scripts/check_data_contract.py`）
3. 跑一次跨源矩阵（`scripts/check_ds_matrix.py`），确认 B 类在各形态仍一致

只改 `schema.sql` 不加断言 = 数据库会挡，但换源之后没人挡。
只加断言不改文档 = 三个月后没人知道这条断言在防什么。
