# 数据契约 v1

> 2026-11-25 | 依据 `data/schema.sql` 与 `scripts/check_data_contract.py` 实际内容编写，不是设计稿。
> 一句话原则：**契约不是文档，是可执行的东西。** 每条条款要么有断言编号，要么在第六节明确标"未覆盖"。

## 零、这份文档给谁看

| 读者 | 用它干什么 |
|---|---|
| 接新客户的人 | 照这张表问客户要字段、问口径、问枚举 |
| 写断言的人 | 每条契约对应一条断言，改契约必须改断言 |

## 一、五条元规则（跨表通用，比任何单表条款都重要）

**R1 时间字段是「发生时刻」，不是「入库时刻」。**
`defect_logs.ts` 是设备做判定的时刻，`work_orders.created_at` 是建单时刻。两者混用就没法区分「这条是补录的」还是「实时的」，而补录数据不能用来算响应时间。

**R2 空串、缺失、0 是三件不同的事。**

| 情况 | 含义 | 谁来管 |
|---|---|---|
| 空串 `''` | 填了但没内容，数据脏 | 放行入库，断言抓（B1、B6） |
| 缺失（列不存在） | 配置过时 / 客户文件换了 | 映射层直接报错，带行号和列名 |
| `0` | 真实值 | 正常入库 |

**R3 设备身份只有一个来源：`device_id`，它必须在 `devices` 里存在。**
六张表引用 `device_id`，其中五张有外键，`work_orders` 没有——见第六节。

**R4 枚举是闭集。** 新增一个 `severity` 值等于改契约，要登记版本；不是"数据里多了一个值"。

**R5 数值带单位，单位写在列名或注释里，不写在业务代码里。**
`drift_px` / `drift_mm` / `cumulative_hours` / `rated_life_hours` 全部如此。

## 五、变更登记规则

三件事必须一起做，缺一件就是"改了没登记"：

1. 改本文档对应条款
2. 加/改断言（`scripts/check_data_contract.py`）
3. 跑一次跨源矩阵（`scripts/check_ds_matrix.py`），确认 B 类在各形态仍一致
4. **改了 `stg_devices` 的业务列，同步 `check_ds_delete.CONTENT_COLS`**（见第八节）。漏这一步不会报错，只会让那一列改了也不重灌

只改 `schema.sql` 不加断言 = 数据库会挡，但换源之后没人挡。
只加断言不改文档 = 三个月后没人知道这条断言在防什么。

## 七、长期怎么看：谁在什么时候验证它合法

前面六节回答「什么是合法数据」。这一节回答另一半——**谁、在什么时候、用什么去验证**。

契约只写这一半，等于只有写代码的人知道该看什么；写全了，接手的人才知道出了事该翻哪一张表。

| 时机 | 谁跑 | 跑什么 | 失败意味着 | 落地了吗 |
|---|---|---|---|---|
| 写入时 | 数据库 | 类型 / 非空 / 外键 / 部分唯一索引 | 脏行根本进不来 | ✅ `data/schema.sql` |
| 装载时 | 每轮同步 | 结构断言 16 条 + 隔离区 | 行被挡在隔离区，主表仍干净 | ✅ `check_data_contract.py` |
| 换源后 | 接新源那一次 | 跨源矩阵（四形态同一套断言） | B 类不一致 = 搬运过程丢了信息 | ✅ `check_ds_matrix.py` |
| 发版前 | 跑评测之前 | `data_health.py` 四块汇总 | 报告 `meta` 里写着 `status=fail` | ✅ 已接进 `meta["data_health"]` |
| 每天 | 计划任务 | 同上四块 + 隔离区涨跌 | 日志里留一行 FAIL | ✅ 已注册（每日 09:00，**仅在登录时运行**）；⚠️ 无值班人 |
| 出事之后 | 人 | 隔离区 + 审计表 | 能回答「什么时候开始脏的」 | ✅ `stg_quarantine` / `stg_delete_log` |

三条口径：

1. **检查结果必须带时间戳**。`data_health.json` 的 `checked_at` 与 `stale_minutes`，超过 24 小时只提醒、不当判据——数据没变的话三天前的检查照样成立，变没变只有人知道。
2. **失败不自动重试、不自动修**。巡检的价值是留下证据，不是把问题抹平；自动重试会把「第一次就失败了」这件事藏起来。
3. **周期巡检最大的风险是「跑了没人看」**。所以它的产物必须是下一次检查能读到的文件（`eval/data_health.json` + 日志），而不是一段控制台输出。

现在还缺的：

- ~~隔离区的周期巡检与健康汇总不是同一件事~~ —— 已并入每日四块，隔离区只判**涨跌**（绝对值被固定夹具定死，看不出来）。但当前沙箱里这个数恒为 0：增量检查每轮清空隔离区，**检查脚本重置了它自己要检查的对象**（详见 `DOC-44` 第九节）。
- 红了谁处理——没有值班人。**代码能保证「痕迹在」，不能保证「有人看」。**

## 八、内容指纹的口径

「内容变了」是同步里唯一一处**由我方定义**的判断：数据库挡不住（值列都合法）、上游也不声明（它只说"这是当前的"）。定义不写下来，换个人接手就会按自己的理解重写一遍，然后静默不更新。

| 项 | 口径 | 为什么这么定 |
|---|---|---|
| 参与列 | `device_id` / `line` / `station` / `camera_model` / `lens_model` / `light_model` / `install_date` / `maintenance_cycle_days`（`check_ds_delete.CONTENT_COLS`） | 这 8 列任一变了都影响下游回答——型号换了我们还在拿旧型号答，比不更新更糟 |
| 排除列 | `_src` / `_loaded_at` / `_ingested_at` / `created_at` / `updated_at` | 天然会变，进了指纹每轮都判"变了"，增量退化成全量重灌 |
| 算法 | `md5(值1|值2|…)`，空值按空串 | 我方自算，不让上游给。让上游给 hash 等于把"什么算变了"的定义交出去，客户换个源口径就跟着换 |
| 回灌范围 | 只覆盖**快照真的给了的列**（按 key 是否存在判断，不看值） | 把"快照没给"当成"值为空"会一次清掉本地数据——这比漏更新危险得多，而且是不可逆的 |
| 漂移检测 | 每次跑拿 `information_schema` 对一遍表结构，漏列写进 `content_hash_cols.missing`，由 `data_health.py` 判红 | 漏列没有任何症状：不报错、不变红、报表照出，只是那一列永远不改。只能靠机器每次对，不能靠人记 |
| 历史 | `content_hash` 是单值 | 答不了"这条设备上个月是什么版本"。要答这个必须另存版本表，当前刻意没做 |

这条检查是自证的：第一次跑就报出 **8 个业务列只纳了 2 个**，`station`、`camera_model`、`lens_model`、`light_model`、`install_date`、`maintenance_cycle_days` 六列改了都不会重灌。补全后 8/8、未纳入 0 个。如果只把它写成文档而不写检查，这六个列现在还是漏的。

**为什么排除列要显式列出来，而不是"只写业务列"**：因为判漏的规则是"表里每一列要么在指纹里、要么在排除表里，两边都不在就是漏了"。没有排除表，系统列会被当成漏列天天喊，喊久了就没人看。

## 九、判定参数的口径：删除与增量

「这条还在不在」「这条算不算新」在数据上都不可判定，判断靠下面几个参数。它们都是我方定义，不是上游声明的：

| 参数 | 现值 | 它定义什么 | 改大/改小会怎样 | 依据 |
|---|---|---|---|---|
| `ABSENT_CONFIRM` | 2 | 连续缺席几次才判删 | 改成 1：一次分页超时就删一批；改成 5：真删的设备多活几轮，继续被检索到并参与回答 | **没有运营依据，当前是拍的** |
| `MIN_SNAPSHOT_RATIO` | 0.5 | 快照条数低于本地的这个比例，整轮拒绝 | 调高更安全但容易停滞；调低则上游半挂时仍会照规则删 | **没有运营依据** |
| `OPEN_STATUS_EXCLUDE` | 已完成 / 已合并 / 已取消 | 工单这三种状态算已闭环，不再保护设备 | 漏一个状态：保护集误收，设备永远删不掉；多一个：有活工单的设备被删 | 复用 `mock_qms/reset.py` 的幂等口径，两处不能各写一套 |
| `OVERLAP_WINDOW` | 1 天 | 水位往回退多久取候选，用来捞回「主键比水位小」的补录单 | 调大：每次多读一段、更能补上迟到很久的补录；调到 0：主键更小的补录**永远漏，且不报错** | **没有运营依据**，1 天只为把机制测出来 |
| 水位比较方式 | `(ts, pk)` 复合、严格大于 | 同时间戳里主键更大的算新数据 | 退回单一 `ts`：同一秒进来的多条被整段漏掉（这是主路径，不是边角）；主键缺失时退化为「同秒全看一遍」，靠落库幂等兜 | 前提是主键在源表内单调递增 |
| 时间轴三字段 | 源端过滤 `ts` / 本地水位 `ts` / 业务时间 `ts` | 增量到底按哪个「钟」筛数据 | 任一处换成入库时刻（`_loaded_at`/`created_at`）：晚到的补录单被判「已灌过」，**整批静默丢**；换错还会把水位推到到货时间，之后更进不来 | K-3 一手样本（2026-11-26）：GitHub `commits?since` 按 committer 过滤，返回里 author 可早到 2025-12-15。本项目三处同为 `ts` 是**当前假设**，接真源必须重核 |

六条约束：

1. **参数随产物走**。两个检查的 JSON 都带 `policy`，值从常量取；删除那边 `guards` 文案由同一常量拼出来；`data_health` 检查「护栏文案里的阈值 == `policy`」，不等就红（已验：手写「阈值 9」立刻 FAIL，改回即恢复）。报告里的数字必须是代码真在用的那个，不能是人抄的。
2. **判据不写死期望值**。「正常模式应为 4 台」「`"overlap": "1 day"`」这类写法，夹具或常量一动就错。骤降轮改成不变量（整轮拒绝后活跃台数应等于上一步）；窗口改成由常量生成，再加一条**实跑证据**（见下）。
3. **开没开必须由实跑证明，不能由声明证明**。增量的 `overlap_evidence` 记两个数：不带窗口漏了几条（`[8]`）、带窗口补回几条（`[9]`）。两个数相等就红——把窗口置 0 验过：`[9] 开 0 天重叠窗口重跑` 补 0 条、累计从 15 掉到 14，巡检立刻 FAIL。**声称开着却不起作用，比明说不开更糟。**
4. **改这些值算契约变更**，按第五节走一遍，并同步改本节的「现值」。
5. **护栏必须有反例证明它活着**。判据写在代码里不算数：隔离区那条「比上次多就红」在本项目里每轮都被 `TRUNCATE` 重置成恰好 1 条，`delta` 恒为 0，等于从未被触发。2026-11-26 补第 `[11]` 步：每轮造一次 +1 再收回，`quarantine_probe` 的 `before/after/restored` 三个数全部真查库，`data_health` 只复核这三个数、不看脚本自评。**涨不上去、收不回来、证据缺失，三种都红**（已验：把探针时间改成过去 → `1 → 1`、状态 fail、「隔离区上涨已经不可观测」）。原先是靠人手工把旧 JSON 的 rows 改小验一次——那只证明人懂判据，不证明判据每轮活着。
6. **时间轴三字段必须显式登记，且互相说得通**。源端过滤字段、本地水位字段、业务时间字段登记在 `app/ds/time_axis.py`，`plan()` 的 `ts_key` 从这个登记取，不许在调用点另写字面值。判据七条：三个字段非空；**水位必须等于业务时间**；三个都不许落入库时钟黑名单（`_loaded_at` / `created_at` / `ingested_at` …）；`filter_clock` 只能是三枚举之一；名字不同却声称同钟即红；钟不同必须在 `drop_scenario` 写清丢了什么；给了表列清单时登记的两个本地字段必须真存在。落地两处：第 `[12]` 步核对登记与 `information_schema`，第 `[13]` 步造一条「业务时间早于水位、入库时间晚于水位」的探针，**它必须被判已灌过（新增 0 条）**——若代码读成别的钟，这条会被灌进主表。反例验过三种：探针时间改晚 → 新增 1 条、status fail 且跑完自清理；登记写成表里没有的列 → 两条红；把同一探针按 `_loaded_at` 过滤 → 灌进 1 条且水位被推到 2026-11-26（多灌一行之外还堵死后续补录）。**K-3 的教训不是「名字要一样」，是「钟要一样」——名字一样、语义不同的两个 `ts` 更危险，机器查不出，所以必须靠这条探针每轮作证。**

诚实清单：

| 问题 | 后果 |
|---|---|
| 阈值 2 和比例 0.5 没有运营依据 | 客户问「为什么是 2 不是 3」答不了。要答得先有「上游快照完整率」的历史数据，现在没有 |
| 重叠窗口 1 天同样是拍的 | 窗口太小补不回迟到很久的补录，太大每轮多读一大段；两头都是猜的，没有迟到分布数据支撑 |
| 复合水位依赖主键单调递增 | 客户重传更小主键时只能靠窗口兜；不给窗口就静默漏，`[8]` 步就是把这处残留测出来而不是假装没有 |
| 软删保留期与真删（物理删）未定 | 谁删、多久删、删之前通知谁，三项都空；代码刻意不做物理删 |

## 十、事实层的时间口径（2026-11-26 补）

前九节写的是**客户数据**。`facts.device_fact` 是我方派生表（从 `stg_devices` 的当前值
摊平出来的版本历史），不属于客户给的那几张，单列一节。

| 列 | 类型 | 可空 | 口径 |
|---|---|---|---|
| `tenant` | text | 否 | 客户标识，单客户时 `client_a` |
| `entity_id` | text | 否 | 设备号 |
| `fact_key` | text | 否 | 属性名（= `stg_devices` 的列名，7 个） |
| `value` | jsonb | 否 | 值本体；清空写 JSON null，不写 SQL NULL |
| `value_hash` | text | 否 | 值指纹，判等不比 JSON |
| `valid_from` | timestamptz | 否 | 这条事实从何时成立；口径见 `valid_from_basis` |
| `valid_to` | timestamptz | 是 | 非空 = 已作废；**只作废，永不 DELETE** |
| `valid_from_basis` | text | 否 | 只允许 `ingested` / `effective` |
| `ingested_at` | timestamptz | 否 | 写进这张表的时刻 |
| `supersedes` | bigint | 是 | 自引用，指向被取代的那一行 |
| `source` | text | 否 | 哪个作业写的 |

约束：`valid_window = CHECK (valid_to IS NULL OR valid_to >= valid_from)`（区间是**半开**的
`[valid_from, valid_to)`，同一事务内改值时两者相等属正常）；部分唯一索引
`device_fact_unique_current ON (tenant, entity_id, fact_key) WHERE valid_to IS NULL`。

两条新约束（编号接第九节）：

7. **派生的时间也只能记到货，且必须显式登记口径**。上游没有「这个值从什么时候开始
   成立」，所以 `valid_from` 只能取同步时刻，`valid_from_basis` 登记成 `ingested`。
   声称 `effective` 就必须真的有上游给的生效字段——`data_health` 判这一条，写成
   `effective` 即红。**这是 K-3 在事实层的重演**：把到货时刻当发生时刻，表里看起来有
   历史，实际是到货历史。代价三条，写在此处便于被追问：两次快照之间的中间状态不可见；
   精度等于同步频率；补录被记成「刚到货」而不是「发生在过去」。
8. **「没给」与「给了空」必须在落地表之外区分**。`stg_devices` 是无约束落地表，上游
   少给一列就是 `NULL`，而 `SELECT *` 永远给出所有列——**NULL 同时表示两种意思，这一层
   分不出来**。事实层的选择是把 NULL 当作「没给」（保持旧值不动，绝不关），代价是
   「上游真的清空一个属性」这条路径没有表达方式。要支持它必须改源端协议（空串、
   显式 tombstone），不能靠把 NULL 塞进这张表。**这是已知限制，不是待修项。**
