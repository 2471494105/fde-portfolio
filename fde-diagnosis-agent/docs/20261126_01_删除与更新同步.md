# 删除与更新同步

> 2026-11-26 | 决策 `app/ds/delete_sync.py`、落库实测 `scripts/check_ds_delete.py`、建表 `data/sandbox/delete_sync.sql`

## 一、为什么删除比增量更难

增量做错了是「少」：某张工单查不到，人会来问，能被发现。
删除做错了是「静默」：库里少一台设备，报表照常出，数字变小了，而**变小究竟是应该的还是错的，事后从结果里看不出来**。

三个方向里有两个是静默的：

| 失效 | 表现 | 能被发现吗 |
|---|---|---|
| 少灌（增量） | 查询缺数据 | 能，有人会问 |
| 多删 | 报表变小，一切正常 | **不能**，没有参照 |
| 该删未删 | 幽灵设备一直出现在报表里 | 很难，要人记得"这台早该下线了" |

所以这块的重点不是把删除写对，是**让它在不确定的时候删不掉**。

## 二、三条口径（都可逆，不需要拍板）

1. **一律软删**：记 `deleted_at` + `deleted_reason`，不物理删。evidence 可能引用它，审计要能回答"当时为什么判它没了"。
2. **没有删除信号时，靠连续缺席判定**：阈值 2 次。
3. **快照骤降整轮拒绝**：本轮快照不足库内的 50%，一条也不删。
4. **保护与矛盾信号都不删**：删除事件是最强证据，但它不能删掉有未闭环引用的设备（工单会悬空），也不能删掉这一次仍出现在快照里的设备（两个信号自相矛盾）。

## 三、五种动作

| 信号 | 动作 | 为什么这么定 |
|---|---|---|
| 源端下发删除事件 | 立刻 `soft_delete` | 明确的删除意图，不用等缺席累积 |
| 源端下发删除事件，但**有未闭环引用** | `protect`，转人工 | 事件只说明上游那边没了，不说明本地工单已闭环 |
| 源端下发删除事件，但**仍在快照里** | `noop`（本轮不删） | 两个信号自相矛盾，删除不可逆，等下一次快照消除 |
| 连续缺席 1 次 | `mark_absent`（只记账） | 单次缺席是采集中断的常态，不是删除 |
| 连续缺席 ≥ 2 次 | `soft_delete` | 两次都没出现，才认为是真没了 |
| 有未闭环引用（保护集） | `protect`，转人工 | 工单挂在这台设备上，删了 evidence 就断链 |
| 快照不足库内一半 | `aborted`，整轮不执行 | 上游故障时差额等于全库 |
| 曾软删、现在又出现 | `revive` | 删除必须可撤销 |

## 四、为什么阈值不是 1

阈值取 1，等于把每一次网络抖动、每一次采集器重启都变成一次"删除 + 复活"。审计表会被这类噪音刷满，**真正的一次删除埋在里面看不见**。

阈值取 2 的代价是：设备下线后第一天报表多一台幽灵。这个代价比误删便宜得多——幽灵会被人认出来（"这台不是早卖了吗"），误删不会。

阈值取几是运营口径，代码里默认 2，**没有依据**，见第十一节。

## 五、为什么第一次缺席要落库

`absent_count` 必须存下来，不能靠"上次快照"推——我们只保存当前快照，没有上一轮快照可比。

所以 `stg_device_state` 不是缓存，是必需的元数据表。它和客户数据表不同：**它由我们写、只由我们读，所以可以有主键。**

## 六、骤降护栏：唯一一个「拒绝执行」的分支

上游故障有三种形态，在数据上长得完全一样：

- 接口超时，返回空列表
- 客户的库被清空 / 换库了
- 权限过期，查询返回 0 行

**没有这道护栏，代码会非常正确地执行一次灾难**：每台设备缺席 1 次 → 全部 `mark_absent` → 下一轮全部 `soft_delete` → 报表从 500 台变成 0 台，每一步都合规、不报错、日志干净。

这是「逻辑正确、结果灾难」的典型，也是这类同步最该防的一处。

`MIN_SNAPSHOT_RATIO = 0.5` 是对半留余量：真实业务一次下线一半设备几乎不可能，真发生了（工厂关停）也该人工介入，而不是脚本自己删。

**它不是摆设，反向探针验过**：把阈值调到 0.1 再跑，第 [7] 步立刻从 `aborted` 变成 `soft_delete×1`，活跃 4 → 3、软删 1 → 2。

## 七、软删与物理删的边界

代码里**没有一条 `DELETE` 语句**，这是刻意的：

1. **evidence 引用**——工单和诊断证据可能指向这台设备的历史记录，物理删会让引用悬空
2. **审计**——删错了要能恢复，恢复需要原始行
3. **责任**——物理删不可逆，应由人执行，不由定时任务执行

保留期多久、谁来真删：**没定**。代码只提供 `deleted_at`，删不删是运营决定，不是代码决定。

## 八、一个单测抓出的真错

`content_changed(None, "h2")` 返回了 `True`。

语义上，「旧哈希未知、新哈希有值」不能判定内容变了——读不到旧值不等于旧值不同。修成 `if new_hash is None or not old_hash: return False`。

**为什么这条重要**：这个函数决定内容更新要不要重灌。判 `True` 会让每轮都重灌这台设备，增量静默退化成全量——又是一类「不报错但白干」。

## 九、实测十一步

| 步骤 | 决策 | 活跃设备 | 为什么这么设计这一步 |
|---|---|---|---|
| [1] 首轮全量 5 台 | 无 | 5 | 初次见到全部设备，无缺席可比 |
| [2] CX-105 第一次缺席 | `mark_absent×1` | 5 | 只记账，不删 |
| [3] CX-105 第二次缺席 | `soft_delete×1` | 4 | 阈值到了 |
| [4] CX-105 回补 | `revive×1` | 5 | 删除可撤销 |
| [5] CX-104 下发删除事件 | `soft_delete×1` | 4 | 明确信号，不等第二次缺席 |
| [6a] CX-103 缺席 1 次（保护集） | `protect×1` + `noop×1` | 4 | 有工单挂着，转人工 |
| [6b] CX-103 缺席 2 次 | `protect×1` + `noop×1` | 4 | 保护不因缺席次数失效 |
| [6c] CX-103 缺席 3 次 | `protect×1` + `noop×1` | 4 | 同上 |
| [6d] CX-105 缺席 1 次 + CX-103 复活 | `mark_absent×1` + `noop×1` + `revive×1` | 4 | 给骤降轮准备"已缺席 1 次"的设备 |
| [7] 快照骤降到 1 台 | `aborted` | 4 | 整轮拒绝，一条不删 |
| [8] CX-101 仍在快照，却收到删除事件 | `noop×2` + `revive×1` | 4 | 信号矛盾，不删；同轮 105 回补复活 |
| [9] CX-103 收到删除事件，但它有未闭环工单 | `protect×1` + `noop×1` | 4 | 事件不越过保护，转人工 |

最终 **活跃 4 台 / 软删 1 台 / 审计 18 条 / 护栏 6 条**。

探针（`--min-ratio=0.1`）：[7] 变成真删一台，**[7] 当时活跃 3 台**（正常应为 4）。注意别拿最终台数判断护栏——[8] 会把快照补回来、被删的设备复活，最终又回到 4；所以脚本现在把 `[7] 当时的活跃台数` 单独打一行，这就是**加步骤会冲掉旧探针可见性**的实例。

## 十、补记：三个「有名无实」

写完之后把决策层和执行层逐行对照读了一遍，找出三处**声明的东西比做到的多**，都在同一块：

1. **删除事件越过了保护集**。`events` 分支排在 `protected` 前面，上游一句 `purge` 就能把有未闭环工单的设备删掉——工单随之悬空，正好违反本节自己写的「有未闭环引用不删」。补两步实测（`[8]` `[9]`）与三条单测钉住。
2. **`stg_device_state.protected` 列从没被写过**。保护只活在脚本常量 `PROTECTED` 里，查库永远是空的。改成 `protect` 时落 `protected=true`，并让决策层的保护集 = 夹具 ∪ 库里标了保护的 id——**保护跟着设备走，而不是跟着某个脚本的常量走**。
3. **`content_changed()` 没有生产调用点**。只有定义和单测，"更新同步"只到一个函数为止。这一条没有硬接：夹具里没有内容指纹字段，真实上游会不会给 hash 也不知道（见第十三节）。

三条的共同点：**字段在、函数在、常量在，语义不在。** 这类东西不会让任何测试变红，只会让读代码的人以为它已经做了。

关于 `protected` 还有一条口径要记：**没有任何代码自动清它**。理由和保护本身一样——保护的理由是「有未写完的工单」，设备重新出现在快照里不代表工单闭环了。清除需要「工单闭环」这个外部信号，本路径不提供，也不该自己猜。

## 十一、三个自己修的问题（写下来防复犯）

1. **`live_count` 只在末尾算一次**，导致整张表每一行显示同一个数。改成每步当场算并返回。
2. **最初用 `TRUNCATE + 重写` 装载快照**，会把被删设备的状态行一起抹掉——**软删变硬删**。改成 `INSERT ... WHERE NOT EXISTS`。
   这条最有教益：脚本本身是用来验证"软删"的，而它的装载方式偷偷做了硬删，跑出来的绿是假绿。
3. **[6] 步快照把已软删的 CX-104 放回去**，逻辑上该判 `revive`，于是 `noop` 分支一次都没被测到。后续快照固定排除 103 / 104。
   另有 **[6d]**：骤降轮如果所有设备都是满额缺席，第一道护栏（阈值）先拦住，第二道（骤降）永远不触发——必须专门准备一台"已缺席 1 次"的设备，骤降护栏才真的被测到。

## 十二、还没做

- **阈值 2 与 `min_ratio=0.5` 没有运营依据**，是拍的默认值，也没写进数据契约
- **保护集来源**：真实环境应从 `work_orders` 反查未闭环引用；沙箱里是硬编码夹具 `PROTECTED = {"CX-103"}`。现在已落进 `stg_device_state.protected`，但**谁来清这个标记**还没有入口——需要「工单闭环」信号，本路径刻意不做猜测
