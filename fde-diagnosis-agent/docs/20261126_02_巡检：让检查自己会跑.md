# 巡检：让检查自己会跑

> 2026-11-26 | 包装 `scripts/health_daily.ps1`、调度 `scripts/register_health_task.ps1`（默认只预览）；被巡检的是 `scripts/data_health.py` 的四块检查

## 一、问题不在检查，在「谁跑」

`data_health.py` 已经有非零退出码，四块检查也能落盘。但那要求有人开一个终端、cd 到目录、敲一行命令。

**一个只在人想起来时才跑的检查，等于「我以为有人看」。** 这正是本项目一直在分的那一类：不是质量不够好，是不报错。

## 二、三层，每层只做一件事

| 层 | 是谁 | 只负责 |
|---|---|---|
| 检查 | `scripts/data_health.py` | 判断四块过没过，落 `eval/data_health.json` |
| 包装 | `scripts/health_daily.ps1` | 跑一次、写一行摘要、透传退出码 |
| 调度 | `scripts/register_health_task.ps1` | 每天一个时间点触发（**默认只预览**） |

不放一起的理由：检查脚本要能在任何地方跑（手动、CI、评测前），日志是这台机器上的事。混在一起，换一台机器就得改检查代码。

`scripts/*` 不在 `BEHAVIOR_FILES`，这三条都不动 `code_hash`。

## 三、摘要从 JSON 读，不解析控制台输出

包装层不抓 stdout 里的字段，只读 `eval/data_health.json`。输出格式随打印改，JSON 结构不会——**人写的文字会漂，机器写的数据不会**。

失败时另说：那时的 stdout 会整段落进日志，因为要看清是哪一块崩的。

## 四、刻意不做的三件

1. **不自动重试**。重试会把「第一次就失败了」藏起来，而"第一次失败"往往才是要看的信号。
2. **不自动清隔离区**。脏行是证据，不是垃圾。
3. **不自动修数据**。巡检只记事实。

## 五、三种失败必须分开（本节是这次最有用的一条）

同样是退出码 1，有三种完全不同的处境：

| 形态 | 发生了什么 | 日志那一行 |
|---|---|---|
| 跑完，全绿 | 四块都过 | `OK 契约 16/16 矩阵B一致 True 增量 15行/15id 删除 活跃4/软删1 隔离 1条` |
| 跑完，有红 | 检查跑通了，断言真红 | `FAIL 退出码 1：契约断言红 2 条：B3, B7` |
| **崩在内部** | 检查根本没跑完，JSON 还是上一轮的 | `FAIL 退出码 1：见本行上方完整输出（本轮没写新 json，可能崩在检查内部）` |

第三种最危险：**JSON 是旧的成功结果，`issues` 是空的**。如果直接拿它当本轮结论，就会把「没跑成」写成「跑完了没发现问题」——一次完美的假绿。

判据用**文件修改时间**，不用 JSON 里的 `checked_at`：

> 前者是客观事实，后者是内容自己声明的。内容写错了也能骗过按内容做的判断。

这条是探针第一次跑出来的：最初用 `checked_at` 比时间，探针造的那份「刚写好的 fail」被误标成「没写新 json」；换成 `LastWriteTime` 之后，只有「文件确实没被这一轮写过」才会被标。

## 六、实测三条探针

| 探针 | 构造方式 | 期望 | 实际 |
|---|---|---|---|
| A 崩溃 | 假检查 `exit 1`，不写 JSON | FAIL + 「没写新 json」标注 | ✅ 一致 |
| B 正常 | 真跑四块 | `OK` 一行，退出 0 | ✅ 契约 16/16 等全绿 |
| C2 真失败 | 假检查写完 `status=fail` 的 JSON 再 `exit 1` | FAIL + 列出 issues，**不带标注** | ✅ `契约断言红 2 条：B3, B7` |

探针 C 的第一次尝试失败过一次（用 `checked_at` 做判据），见第五节——**这里记下来，是因为它证明「判据本身也要被探针测」**。

探针用的假检查是临时文件，跑完已删；真 `eval/data_health.json` 在探针前后都是 `status=ok`、`issues=0`。

## 七、最大的剩余风险：跑了没人看

日志落在 `eval/health_daily.log`，被 `.gitignore` 的 `*.log` 挡住——刻意：日志是现场产物，不进版本库，也不该跟着代码走。

**"有人看"这一步代码解决不了。** 能做的只有两件：

- 让痕迹便宜可查：一行摘要 + `data_health.json` 里的 `stale_minutes`
- 在没人看的时候，不要假装有监控

**巡检脚本存在 ≠ 有监控。** 这句话必须写下来，因为它是这类工作最容易自我欺骗的地方。

三段各答一个问题，**刻意不合并成一个绿灯**：

| 段 | 回答什么 | 来源 |
|---|---|---|
| 数据健康 | 最近一次检查好不好、多久之前 | `eval/data_health.json` |
| 巡检 | 最近一次「巡检」是 OK 还是 FAIL | `eval/health_daily.log` |
| 计划任务 | 有没有东西会自己再跑一次 | `Get-ScheduledTask` |

**为什么不合并**：手动跑成功、巡检失败时两个数会打架。合并成一个绿灯，就把「谁跑的、跑了几次」这层信息抹掉了——和前一次 `--only` 覆盖全量造成的假绿灯是同一类错误。

四条判据，任一不满足退出 1：检查超 `-MaxAgeHours`（默认 24）／结果不是 `ok`／巡检最后一行非 `OK`／任务不存在、被禁用、或上次执行失败。`LastTaskResult=267011`（`0x41303`「从未运行」）单独豁免，不算失败。

四条探针验过：陈旧 74.5 小时、巡检 FAIL、任务不存在 → 都退出 1 并精确指出是哪一条；正常路径退出 0。过程中抓到一个真错：`contract` 在 JSON 里是**对象**不是字符串，第一版直接按 `$dh.contract` 取，打出一串哈希表内容——**摘要要逐字段取，不能靠对格式的印象**。

## 九、隔离区：只能看涨跌，而这个「涨」现在每轮由探针造一次

隔离区的口径和别的块不一样。它**本来就该是空的**，所以「非空即红」在主库成立；但沙箱里那 1 条是增量检查的固定夹具（`id=4`、`ts=2027-01-01`），绝对值恒为 1，红不了也不该红。于是这里能用的唯一判据是**趋势**：

- `quarantine.rows` 本次条数
- `quarantine.prev_rows` 上一次记录的条数，从 `eval/data_health.json` 读，**必须在覆盖之前读**——顺序错了就是自己跟自己比
- `quarantine.delta` 两者之差；`> 0` 即红：`隔离区比上次多了 N 条（有新行被挡在主表外）`
- `quarantine.readable`：`quarantine_report()` 在「表不存在」和「连不上库」两种情况下都返回 `None`，**读不到不等于 0 条**，所以单独记一个布尔

第一版验这条判据的办法是**人手工改**：把旧 JSON 里的 rows 改成 0 再跑，`delta=+1`、状态 fail、退出 1；再跑一次自愈回 0。`health_status.ps1` 只报涨（`隔离 1 条（较上次 +1）`），0 涨不显示——不是信息。问题在方法上：它验的是「我懂这条判据怎么触犯」，不是「这条判据每轮都活着」。判据在代码里、输入永远为 0，和没写一样。

2026-11-26 补 `check_ds_incremental.py` 第 [11] 步：每轮末尾**造一次 +1 再收回**。三个数全部真查库，一个都不是算出来的：

| 数 | 怎么来的 | 期望 |
|---|---|---|
| `quarantine_probe.before` | 探针前 `SELECT count(*) FROM stg_quarantine` | 1 |
| `quarantine_probe.after` | 插一条未来脏行（`id=9030`、`ts=2030-01-01`）后再查 | 2 |
| `quarantine_probe.restored` | `DELETE ... WHERE row_id=9030` 后再查 | 1 |

插的是未来时间：只有未来行**必然**进隔离区、必然不进主表、必然不动水位——不依赖上一轮跑到哪一步。`data_health` 侧只复核这三个数（`quarantine_probe_issues()`），不看脚本自己写的 `ok` 字段：**证据缺失 = 红**（等于回到「delta 恒 0」那种没验过的状态）、**涨不上去 = 红**、**收不回来 = 红**。

两头验过：正常跑 `1→2→1`、`delta=1`、状态 ok；把探针时间改成过去（`2026-11-10`，于是它被当正常数据进主表、隔离区纹丝不动）→ `before=1 / after=1`、状态 **fail**、提示「探针没让隔离区涨 1 条（1 → 1）：隔离区上涨已经不可观测」；改回后恢复 ok。探针那一步主表新增 0、水位不动，跑完终态与跑之前一致。

仍需诚实标注边界：增量检查每轮都 `TRUNCATE stg_quarantine` 再插 1 条夹具，也就是**检查脚本重置了它自己要检查的对象**。所以 `delta` 在这台机器上仍然恒为 0——探针证明的是「隔离区涨了会被看见」，不是「生产库真的有新脏行」。真实环境里隔离区不会被装载脚本复位，那个 `delta` 才是真信号。这是本项目里唯一一块「判据活着、真信号要等生产环境」的证据。

顺带一条更值得记：**同一张表，测试环境和生产环境的口径本来不同**。测试环境允许清空（要重复跑），生产环境绝不允许清空（脏行是证据）。脚本能 `TRUNCATE`，是因为它跑在沙箱；把这段搬到生产就是销毁证据。

## 十、时间轴：三个字段必须说同一个「钟」

增量到底按哪个时间筛，在代码里本来是**三处各写一个**：源端查询的 `since`、`plan(ts_key=...)` 读哪个字段、`stg_watermark.mark` 记什么。三处只要有一处不同，增量就**整批静默丢**——不报错，只是有些行永远进不来。

K-3 的外部样本把这件事说死了（`07_外部样本/github-commits-since.json`）：请求 `since=2026-11-20`，返回 5 条，`author.date` 是 11-09 / **2025-12-15** / 11-06 / 07-24 / 11-13，而 `committer.date` 全在 11-25/26 —— **`since` 按 committer 过滤**。本地水位如果记 author 时间，下一轮用同一条 `since` 拉回来这批「author 早于水位」的提交，会被判「已灌过」→ 整条丢弃。

所以判据不是「三个名字一样」，而是「三个钟一样」。名字一样、语义不同的两个 `ts` 更危险：机器查不出，人也不会怀疑。

落地分两步：

- **第 [12] 步，静态核对**：`app/ds/time_axis.py` 里登记 `source_filter_field` / `local_watermark_field` / `business_time_field`，七条规则逐条判——三字段非空；**水位必须等于业务时间**；三字段不许落入库时钟黑名单（`_loaded_at` / `created_at` / `ingested_at` …）；`filter_clock` 只能三枚举之一；名字不同却声称同钟即红；钟不同必须在 `drop_scenario` 写清丢了什么；给了表列清单时登记的本地字段必须真在 `information_schema` 里。`plan()` 的 `ts_key` 从这个登记取，登记与行为同源。
- **第 [13] 步，实跑探针**：造一条 `ts=2026-01-01`（远早于水位）、`_loaded_at=2026-11-26`（晚于水位）的假记录。按登记的钟判，它**必然**被判「已灌过」，新增 0 条；如果代码读成了那个入库时刻，它就会被灌进主表。跑完不论结果都 `DELETE` 自己那一行。

三种反例都真跑过：

| 反例 | 实测现象 |
|---|---|
| 探针业务时间改晚（`2026-11-26`） | 新增 1、`landed=True`、`status=fail`；清理后仍是 15 行，没有留下脏行 |
| 登记写成表里没有的列（`event_ts`） | 两条红：「水位不是发生时刻」+「在表里不存在」，`static_ok=False` |
| 同一探针按 `_loaded_at` 过滤（不跑脚本，直接调 `plan`） | `good=1`，**且新水位被推到 2026-11-26 #9029**——多灌一行之外，还把后续补录全堵死 |

`data_health` 侧同样拆开判：`time_axis_issues()` 只看登记内容与 `rows_added` / `left_behind` / `plan_ts_key`，不看脚本自评。顺带修了一处旧问题——原来 `status != "ok"` 被当成「重复 id」的同义词，现在 status 同时承载重复、隔离区探针、时间轴三种失败，继续这么判会把「时间轴红了」报成「幂等失效」。改成各自按数字判。

诚实标注两条边界：① 本项目源端过滤与业务时间**恰是同一列 `ts`**，这是当前假设，接真源必须重核一次；② 本地夹具没有 `_loaded_at` 列时，把 `ts_key` 错写成 `_loaded_at` 会当场 `KeyError`（吵闹地崩），而真实源有这一列时是**安静地多灌**——两种形态都在这一节记下了，别以为崩了才叫错。
