## 一、要解决的问题：三个答不了的问题

`stg_devices` 每轮同步被覆盖，一张表只有一个「现在」。这带来三个问题，**都不报错**：

1. **三个月后问「当时 CX-101 在哪条线」**。库里只剩新值，只能答「现在是 1号线B」。
   没有任何数据能证明当时是 1号线。Git 日志是版本控制，不是数据证据——它记的是
   「我们改过哪行代码」，不是「设备当时是什么状态」。
2. **客户拿一条投诉来复现**。我们只能拿今天的设备状态去跑昨天的判定，跑出来的结果
   是假的，而且看起来完全正常。
3. **一台设备一个月换三次线，想算「换线后 NG 率变化」**。算不了——没有换线时刻，
   也没有「换线前是什么」。

这三件事的共同点：**答案里少了一个版本，而不是多了一个错误**。所以判据不是
「有没有历史表」，而是「改了一个值之后，旧值还在不在，且说得清它什么时候结束」。

## 二、它在六层里的位置

L1 事实层。三条边界：

- **只由确定性作业写**，Agent 不许写。诊断模型可以读事实，不能往事实表里写自己的推断。
- **只作废（`valid_to`），永不 `DELETE`**。没有删除路径，就没有「删错了」这种故障。
- **不做衰减**。衰减是 L2/L3 的事；事实只有「有效 / 作废」两态。

与相邻两层的关系：L0 证据（原始载荷）是事实的来源；L4 装配（结论里的设备事实
有没有 id 可回指）是它的消费者——L4 现在还没接，属于押后项。

## 三、表结构与三条硬规则

```sql
CREATE SCHEMA IF NOT EXISTS facts;

CREATE TABLE facts.device_fact (
    id               BIGSERIAL PRIMARY KEY,
    tenant           TEXT NOT NULL,
    entity_id        TEXT NOT NULL,
    fact_key         TEXT NOT NULL,
    value            JSONB NOT NULL,
    value_hash       TEXT NOT NULL,
    valid_from       TIMESTAMPTZ NOT NULL,
    valid_to         TIMESTAMPTZ,
    valid_from_basis TEXT NOT NULL DEFAULT 'ingested'
                     CHECK (valid_from_basis IN ('ingested', 'effective')),
    ingested_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    supersedes       BIGINT REFERENCES facts.device_fact(id),
    source           TEXT NOT NULL,
    CONSTRAINT valid_window CHECK (valid_to IS NULL OR valid_to >= valid_from)
);

CREATE UNIQUE INDEX device_fact_unique_current
    ON facts.device_fact (tenant, entity_id, fact_key)
    WHERE valid_to IS NULL;
```

三条硬规则，每条都有一道「不靠人记得」的机制：

1. **一个键同时只能有一条当前值**。由部分唯一索引保证，代码不是唯一防线。
   注意索引名不能叫 `device_fact_current`——索引和视图在 PG 里共用同一个 schema
   命名空间，同名会直接报「不是一个视图」。
2. **值没变就不产生新行**。判 `value_hash`，不逐字段比。逐字段比的后果是：
   表加一个属性，比较逻辑就漏一处，漏一处就「永远不更新」且没有症状。
3. **快照没给 ≠ 值为空**。`incoming` 里缺的键保持当前值不动，绝不关掉。
   这一条踩了坑，见第六节。

## 四、时间只能记到货时刻（K-3 在事实层的原样重演）

上游没有「这个值从什么时候开始成立」这件事。我们只知道「这一轮同步跑到了它」。
所以：

- `valid_from` 只能填同步时刻；
- `ingested_at` 与它相同；
- `valid_from_basis` 登记成 `ingested`（到货），不是 `effective`（生效）。

代价写清楚，不绕过：

- 两次快照之间的中间状态不可见（改了又改回，我们只看到「没变」）；
- `valid_from` 的精度等于同步频率，每天一次就是天级；
- 补录数据晚到时会被记成「刚到货」，而不是「发生在过去」。

`valid_from_basis` 这一列不是为了将来能填 `effective` 才留的——它让**现在这批数据的
时间口径可以被查询识别**，而不是被下游当成发生时刻直接拿去算。这和 K-3 是同一个错法：
把到货时刻当发生时刻，表里看起来有历史，实际是到货历史。

区间是**半开**的 `[valid_from, valid_to)`。同一事务内改值，`valid_to` 与新行的
`valid_from` 相等——旧版本「在同一个瞬间被观测到就被换掉了」。批量回灌时会出现，
不是 bug。

## 五、存储位置与容量

| 内容 | 位置 | 生命周期 |
|---|---|---|
| 当前值（源端口径） | `fde_sandbox.stg_devices` | 每轮覆盖 |
| 历史事实（我方口径） | `fde_rag.facts.device_fact` | 只作废，不删 |
| 当前事实视图 | `fde_rag.facts.device_fact_current` | 派生 |
| 原始快照 | `data/snapshots/<批次>/*.json`（未建） | 永久 |

**为什么不放沙箱**：沙箱表每轮被检查脚本 `TRUNCATE`，那是为了「重复跑同一套断言」。
历史要留到三个月后，扔进沙箱就等于让「验证正确性」这个动作销毁证据。第 [7] 步
就是真的清一次沙箱再查一次——讲道理不算证据。

**为什么放主库不放第三个库**：诊断结论要同时回答「设备现在什么状态」和「手册怎么说」，
两边必须能 join。

**为什么用独立 schema**：多客户上线第一刀切在 schema（`tenant_a.facts` / `tenant_b.facts`），
表结构不用动。表里已经带 `tenant` 列。

容量（按 5 台 × 7 属性 × 每天 1 次 × 10% 变更率）：

| 规模 | 年新增行 | 逻辑量 | 含膨胀稳态（×3） |
|---|---|---|---|
| 5 台 | 1,300 | 320 KB | 不到 1 MB |
| 200 台 | 52,000 | 12.4 MB | 37 MB |
| 500 台 | 130,000 | 31 MB | 93 MB |

（此前口算用「8 属性」得 160 MB/年，偏高三成：`device_id` 是实体键不是属性，
实际参与版本化的是 7 列。）真正会长的是原始快照文件，不是这张表——**唯一需要定策略的
是快照采样频率**。

## 六、踩到的坑：NULL 是语义黑洞

第一次跑，第 [4] 步「只给 CX-104 的两列」得到 **6 关 6 开**、总数从 36 涨到 42、
一致性检查报 6 项不符。

原因：`stg_devices` 没有约束，上游少给一列的落地结果就是 `NULL`；而 `SELECT *`
永远给出所有列，所以「列存在但值为 NULL」。第一版 `rows_to_facts` 判断 `if k in r`
就当成「给了」，把 NULL 当成了新值——一次只给两列的上游，就让其余 6 个属性被判成
「清空」并关掉旧值。

修法是 `if k in r and r.get(k) is not None`，并承认一条边界：

> **在 pg 源里，NULL 同时表示「没给」和「给了空值」，落地表这一层分不出来。**
> 要表达「真的清空」，必须改源端协议（空串、显式 tombstone），不能靠把 NULL 塞进这张表。

这条边界不是缺陷，是必须写在文档里的已知限制：不写，下一个人会以为「清空属性」
这条路径是好的。

## 七、双端验收：七步与两个反例

`python scripts/check_facts.py`（已并入 `data_health.py` 第 [5/5] 块）

| 步骤 | 期望 | 实测 |
|---|---|---|
| [1] 首轮同步 5 台 × 7 属性 | 35 行，全新增 | 0 关 / 35 开 / 0 不变，35 行 |
| [2] 同一份值再同步 | 0 关 0 开 | 0 / 0 / 35，仍 35 行 |
| [3] CX-101 line → 1号线B | 1 关 1 开 | 1 / 1 / 34，36 行 |
| [4] 只给 CX-104 两列 | 0 关 0 开，34 键进 `uncovered` | 0 / 0 / 1，36 行，34 键没给 |
| [5] 手插同键第二条当前值 | 被唯一索引拒绝 | 拒绝（`device_fact_unique_current`） |
| [6] `facts_current` vs `stg_devices` | 逐键一致 | 35 项比对，不符 0 |
| [7] `TRUNCATE stg_devices` 后查 facts | 历史不变 | 36 → 36 行，沙箱 0 行，已恢复 |

版本链实测（CX-101.line）：

```
id=5   value='3号线'  2026-11-26 13:51:15 -> 2026-11-26 13:51:15  supersedes=None
id=36  value='1号线B' 2026-11-26 13:51:15 -> （当前）              supersedes=5
```

**两个反例，都真跑过，改回后复跑确认绿：**

1. **把 NULL 当成值**（去掉 `and r.get(k) is not None`）：
   `[4]` 变成 6 关 6 开，总数 36 → 42，一致性报 6 项不符，退出码 1。
2. **删掉唯一索引**（注释掉 SQL 里的 `CREATE UNIQUE INDEX` 并 `DROP INDEX`）：
   `[5]` 报「没拒绝」，`uniqueness.rejected=false`，退出码 1。恢复后重建索引，复跑绿。

这两条的分工：反例 1 证明「决策判据活着」，反例 2 证明「约束活着」。只看代码
永远测不出第二种——约束是否存在只能靠真的插一条。

## 八、一条设计判断：两套真相并存，但只在历史维度

`stg_devices` 是**源端口径的当前值**，`facts` 是**我方口径的历史**。两套并存是刻意的，
因为它们回答不同问题（「上游现在说什么」 vs 「我们认定当时是什么」）。

但**在当前维度上两者必须一致**，不一致就是 bug 而不是设计。所以第 [6] 步每轮逐键比对，
`data_health` 里也判。这一条是从根上防「两套真相打架」——只靠人记得核对，迟早会漏。

## 九、诚实边界（不解决什么）

- **不解决「没有生效时间」**。只记到货时刻，见第四节。
- **不解决「上游清空一个属性」**。NULL 分不出「没给」和「空值」，见第六节。
- **不解决并发下的正确性**，只把并发串行化。同步路径用事务 + advisory lock，
  唯一索引是第二道防线；真正的多实例并发部署没测过。
- **不解决保留期与真删**。`facts` 只作废不删，行数只会涨。500 台一年 13 万行，
  暂时不需要归档，但「三年后怎么办」没答案。
- **不改变任何诊断结论**。L4 还没接，结论里的设备事实仍然没有 id 可回指。
  `code_hash` 仍 `0909a28fbc1c`——`app/ds/facts.py` 和 `scripts/*` 都不在
  `BEHAVIOR_FILES`，落地成本是 0 指纹。
