# 事实层的三个假绿

> 2026-11-26 夜 | 承接 DOC-45。L1 落地当天全绿（427 单测、五块巡检 `status=ok`），
> 当晚对着库和代码重查了一遍，捞出三条 P0——每一条都让「L1 已落地」这句话当场不成立，
> 而三条全都不报错。判据仍是那句：**是否让结论静默不可信**。

## 一、为什么会有这份文档

DOC-45 的结论是「历史能查、能证、能解释」。这个结论建立在七步验收上：首轮 35 行、
重复同步 0 关 0 开、改值 1 关 1 开、NULL 不关旧值、唯一索引拒绝、35 项一致、沙箱重置后 36→36。

七步全过。然后我去库上问了一个更笨的问题：**这 36 行是哪来的？**

```sql
SELECT source, count(*), min(valid_from), max(valid_from) FROM facts.device_fact GROUP BY source;
```

```
 source      | n  |        min         |        max
-------------+----+--------------------+--------------------
 facts_check | 36 | 2026-11-26 13:54:05 | 2026-11-26 13:54:05
```

36 行全部来自验收脚本，`valid_from` 全部落在同一秒。也就是说：**这张表里一行真实历史都没有，每次巡检都把上一次的删掉、再重建一份**。而第 `[7]` 步正在同一个进程里报告「沙箱重置后历史 36 → 36 存活 ✅」。

## 二、P0-1：巡检每天清空生产事实层，然后宣布历史存活

**现象**。`scripts/check_facts.py` 的 `main()` 开头是 `reset_facts(prod)`，`prod` 是 `fde_rag` 主库，执行的是 `TRUNCATE facts.device_fact RESTART IDENTITY CASCADE`。`scripts/data_health.py:209` 每天调 `factschk.main`。

**为什么静默**。所有判据都在「重建之后」的状态上成立：行数 36、改值成对、索引拒绝、一致 35 项。没有一条判据问「这些行是不是刚被这一轮造出来的」。更荒诞的是 `survives_reset`（第 `[7]` 步）：它先取 `before = count_rows()`，再 `TRUNCATE` 沙箱，再取 `after`，两者相等就宣布存活。而主库的 `before` 已经是**三条语句之前被这个脚本自己清空之后**的数。

这是「检查者与被检查者共用一个重建权」。同一个动作既是肇事者，又是唯一的证人。

**修法**。把验收租户和生产租户分开：

- `PROD_TENANT = "client_a"`：巡检只读、只计数，一个字都不写。
- `SELFTEST_TENANT = "fcheck"`：七步在这里跑，允许每轮清掉自己的起点。
- `reset_tenant(prod, tenant)` 用 **DELETE** 不用 TRUNCATE：`TRUNCATE ... RESTART IDENTITY` 会把全表 id 序列重置回 1，别的租户还在的行在巡检后 id 会与新建的行撞号，`supersedes` 指错行、报告里引用的 id 指向另一条事实。
- 主流程前后各数一次生产租户行数，相等才叫「没动」，写进 `isolation`。

**证据**。

```
生产租户     client_a 35 → 35 行（未动）；验收只清 fcheck（本轮起点清掉 36 行）
```

反例一（把 `reset_tenant` 的目标改成生产租户，模拟原 bug）：

```
生产租户     client_a 36 → 0 行（被验收动了）；验收只清 fcheck（本轮起点清掉 36 行）
问题：
  - 验收动到了生产租户（client_a 36 → 0 行）：验收只能写自己的租户
```

反例二（跨轮）：手工清掉生产租户，再跑巡检，**下一轮自己发现**：

```
数据健康      FAIL
问题：
  - 生产事实层从 35 行降到 0 行、最早一条 2026-11-26 14:15:02 → 空（跨轮）：历史被清过，不是正常删除
```

第二条判据的关键在于它必须跨轮：本轮「0 → 0 未动」照样是绿的——只用单轮证据，清空和没清空长得一模一样。所以另开一份只增不减的台账 `eval/facts_ledger.json`，每轮追加 `prod_rows / prod_first_valid_from`，巡检与上一轮比：**行数下降且最早一条变新，只有一种解释**。台账里现在还留着那次反例的记录（`35 → 0 → 35`），它是这条判断的原始样本。

## 三、P0-3：删除完全不传导到 L1

**现象**。`stg_device_state` 里 CX-105 记着 `deleted_at`、`deleted_reason='event:upstream_purge'`，`stg_devices` 里已经没有它；而 `facts.device_fact_current` 里它的 7 个属性仍然 `valid_to IS NULL`。

**为什么静默**。两条代码叠在一起：

1. `plan_facts` 对「这一轮没给」的键只放进 `uncovered`、**不关**——这条设计本身是对的（上游少给一列不能当成清空）。
2. `consistency()` 只读 `stg_devices` 的活行，被删掉的设备在反向检查里只落进 `extra_in_facts` 一个**数字**，调用方不判红。

于是「当前设备清单」里永远有一台已经不存在的设备，而「两套真相一致」会报 35 项全过——因为它只比「两边都还在的键」，不比「该不该在」。

**修法**。删除的唯一合法来源是 L-1 的判定，不是「快照里没出现」：

- `sync` 从 `stg_device_state` 取 `deleted_at IS NOT NULL` 的实体，**并且要求它不在本轮 `stg_devices` 里**。只看「快照里没有」就关，等于把一次分页超时当成整厂设备报废。
- `plan_facts` 增加 `retire`：关而不开。这是唯一一种「关而不开」，必须与 `closes`（被新值取代）分开——下游对它们的反应完全不同。
- 关闭时写 `close_reason = 'deleted:<reason>'`，`valid_to` 取 L-1 判删的时刻，用 `GREATEST(..., valid_from)` 兜住「删除时刻早于这条值生效」的异常窗口（否则违反 `valid_window` CHECK）。
- `consistency` 新增第三维 `orphaned_entities`：实体还在不在。

**证据**。

```
删除传导     CX-105 判删 → 关 7 条、当前值残留 0 条、视图里 0 条；恢复后重开 7 条
```

反例（不传 `retire_entities`，即恢复原行为）：

```
问题：
  - 设备被判删后没有产生任何关闭（删除没传导到事实层）
  - CX-105 已被判删，但 facts 仍有 7 条当前值：camera_model, install_date, lens_model, light_model, line, maintenance_cycle_days, station
  - CX-105 已被判删，但仍出现在 device_fact_current（「当前设备清单」里还有它）
```

「恢复后重开 7 条」是顺手拿到的第二个证明：删除是可撤销的——与 L-1 的 `revive` 同一口径。

## 四、P0-2：多租户只做了列，没做读

**现象**。`read_current()` 返回 `{(entity_id, fact_key): ...}`，**没有 tenant**。两个客户都有 CX-101 时，后读的覆盖先读的，`plan_facts` 拿错的那条去比 hash，判成「改值」，于是 `closes` 按 id 关掉**另一个客户**的行。

**为什么没被发现**。唯一索引是 `(tenant, entity_id, fact_key)` 三列，跨租户不会冲突。所以它不会在普通单租户验收里暴露——只要库里只有一个租户，代码对不对长得完全一样。

**实测的形态和我预想的不一样**，这里必须写清：

我原本的判断是「静默改写另一个客户的当前值」。去掉过滤实测，脚本**崩了**：

```
psycopg.errors.UniqueViolation: 重复键违反唯一约束"device_fact_unique_current"
DETAIL:  键值"(tenant, entity_id, fact_key)=(fcheck, CX-101, line)" 已经存在
```

原因是：plan 认为 `(CX-101, line)` 的当前行是**另一个租户**的 id，于是 `UPDATE ... WHERE id = 别租户的 id` 关掉了错的行，而本租户自己的当前行没被关，随后 INSERT 撞上唯一索引。

所以这道错不是「静默地给出错结论」，是「**崩溃 + 关掉另一个客户的行**」。严重性不变（多客户部署直接不可用、且写坏别人的历史），但性质要写准：它被唯一索引兜住了，兜住的方式是报错，不是沉默。

**修法**。

- `read_current(prod, tenant)` 加 `WHERE tenant = ?`。
- `consistency`、`uniqueness_probe`、`version_chain`、`count_rows` 全部带租户。
- 第 `[10]` 步：在 `fcheck_b` 放一条同 ID 的当前值，改 `fcheck` 的值，断言 `fcheck_b` 的行数与值指纹**都没变**。
- `reset_tenant` 顺手做一件防呆：删本租户的行之前，先数「别的租户有多少行 `supersedes` 指向本租户的行」，这个数**就是**「读路径曾经漏过租户过滤」的证据；有就报红，然后只清引用、不动别的租户的行。

**证据**。

```
多租户隔离   fcheck_b 的 CX-101.line：1 → 1 行，值指纹 未变
```

反例（真的插一条跨租户引用）：

```
  - 发现 1 条跨租户 supersedes 引用（别的租户的行指向 fcheck 的行）：读路径曾经漏过租户过滤，版本链已经跨客户了
```

## 五、写判据时自己犯的错：算子少一个条件

跨租户判据第一版的 SQL 是：

```sql
SELECT count(*) FROM facts.device_fact
WHERE supersedes IN (SELECT id FROM facts.device_fact WHERE tenant = 'fcheck')
```

它把**本租户自己的历史自引用**也算进去了——fcheck 每轮改两次值，就有 2 条自己指向自己的行。于是每轮固定报「发现 2 条跨租户引用」，而直接查库是 0 条：

```sql
SELECT ... FROM facts.device_fact a JOIN facts.device_fact b ON a.supersedes = b.id
WHERE a.tenant <> b.tenant;   -- (0 rows)
```

判据和它对不上，才发现是算子错：缺 `AND tenant <> 'fcheck'`。

**教训**：新判据的第一个反例必须是「它说有问题、实际没问题」这种情况。否则一条永远报警的判据，会让人把报警本身当成背景噪声——比没有判据更坏。

## 六、一并堵上的两个小口子

- **`facts_issues` 里没接跨租户判据**。修完 `check_facts.py` 之后一度出现「脚本 exit 1、`data_health` 报 OK」——因为判据只加在了子脚本，没上移到汇总层。同一件事有两个结论，比一个错结论更糟。现在两处都有。
- **`reset_tenant` 被跨租户引用卡崩**。DELETE 撞自引用外键会直接抛异常，脚本死在半路、什么也没说。改成「先数、再清引用、再删」，把崩溃变成一个可读的数字。

## 七、这一轮之后，事实层的判据清单

| # | 判据 | 证明什么 | 反例方式 |
|---|---|---|---|
| 1 | 改值成对（1 关 1 开） | 旧值没被覆盖 | 注释掉 close |
| 2 | 重复同步 0 关 0 开 | 历史不被自己撑爆 | 去掉 hash 判断 |
| 3 | 唯一索引拒绝第二条 | 约束不是装饰 | DROP INDEX |
| 4 | `uncovered` 不关 | 少给 ≠ 清空 | 去掉 NULL 判断 |
| 5 | 沙箱重置后历史存活 | facts 在主库 | 把 facts 建到沙箱 |
| 6 | 生产租户前后行数相等 | 验收不碰生产 | 改 `reset_tenant` 目标 |
| 7 | 跨轮行数不降 / 最早一条不后移 | 上一轮攒的还在 | 手工清生产再跑 |
| 8 | 判删后关而不开、视图里 0 条 | 删除传导到 L1 | 不传 `retire_entities` |
| 9 | 另一租户行数与指纹不变 | 多租户读隔离 | 去掉 `WHERE tenant` |
| 10 | 跨租户 supersedes 引用为 0 | 版本链没跨客户 | 手工插一条跨租户引用 |

第 6、7 两条是这次补的，也是唯一两条「证的是一段时间里没发生的事」的判据——其它八条都只证「此刻对不对」。这一点值得记住：**只证此刻的判据集合，永远发现不了「昨天还在、今天没了」。**

## 八、仍然没修的（写清以免反复重提）

- **`valid_from` 只能记到货**：上游不给生效时间，这是已知限制不是缺陷；但「两次快照之间改了又改回」永远看不见。
- **空串仍是语义黑洞**：`rows_to_facts` 只跳 `None`，`''` 会被当成真值写进历史。DOC-45 记了 NULL，没记空串；改它要先定「空串到底是清空还是没给」，属于源端协议，不能在落地表里猜。
- **`FACT_KEYS` 与表结构漂移无判据**：`facts.py` 的注释声称「第 `[6]` 步会拿表结构核对」，第 `[6]` 步其实只比值。真加一列，那列永久无历史，没有任何检查会发现。
- **id 复用风险仍在**：`reset_tenant` 已改为 DELETE 保住序列，但生产租户若被人工 `TRUNCATE` 一次，历史里的 `supersedes` 会指错行。
- **跨轮台账只留 90 条**：够用一年（每天一次），但它是覆盖式截断，不是永久审计。
- **`facts` 没有 `snapshot_id`**：值存了，原始报文没存（`data/snapshots/` 仍不存在）。解析错了查不回来。
