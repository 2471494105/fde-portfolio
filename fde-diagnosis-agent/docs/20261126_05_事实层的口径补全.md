# 事实层的口径补全

> 2026-11-26 深夜 | 承接 `DOC-46`。那篇修掉三条 P0，第八节列了「仍然没修」的六条。
> 这篇处理其中三条 P1，外加一件之前一直悬着的事：`client_a` 那 35 行到底算什么。

## 一、为什么先补这三条

`DOC-46` 之后，事实层的判据从 7 条到 10 条，但有三处仍然没有任何机器判据：

| 编号 | 缺口 | 失败时会怎样 |
|---|---|---|
| P1-5 | 空串被当成值 | 上游用 `''` 表达「清空」，我们一直认为旧值有效 |
| P1-6 | `FACT_KEYS` 与表结构漂移 | 表加一列，那列永久不参与版本化，无人发现 |
| P1-4 | 判据全是「此刻对不对」 | 同步停摆，行数不变、一切照绿 |

三条的共同点：**都是「上游说了一句、我们没听见」**。不是错得离谱，是错得安静。

## 二、空串：定成「没给」，并把跳过留痕

原来 `rows_to_facts` 只跳过 `None`，`''` 会被当成真值写进历史——`fact_hash('')` 照算，历史里出现「设备型号是一个空字符串」。而同一个函数的注释写着：

> 要表达「真的清空」，必须改源端协议（空串、显式 tombstone）

注释说空串是清空信号，代码把空串存成值。两边一个字都没对上。

现在的口径：**`''` 一律当「没给」**。理由不是「空串不像清空」，是**这两种语义不能由同一个字符兼任**：

- Excel 导出、CSV 空单元格、接口空字段，给的都是 `''`；
- 一旦把 `''` 解释成清空，一次导出漏了空格子，整列设备的型号会被判成「已注销」。

真要表达清空，必须走显式 tombstone（`{"op":"clear"}` 之类）。协议没改之前，我们宁可「不清、但报数」。

所以拆成两个函数：

- `rows_to_facts()` —— 跳过空白串（`''`、纯空格、`\u3000` 都算）；
- `blank_cells()` —— 单独列出「这一轮给了个空白」的单元格。

第二个不是多余的：**跳过是对的，沉默不对**。如果上游真想清空，我们既不清也不报，那条旧值会一直有效下去。所以跳过要留痕，由巡检报数。

**反例（真跑）**：把跳过那一行 `if False and ...` 关掉，第 `[11]` 步立刻红两条：

```
空白串       CX-103.lens_model 写 '' → 记进 blanks、1 开 1 关，当前值仍 ''
问题：
  - 空白串改动了 CX-103.lens_model 的当前值（'' 被当成真值写进历史）
  - 空白串产生了 1 开 / 1 关（应为 0/0）
```

注意「当前值仍 `''`」——反例不只报了两个数，它把真实后果摆出来了：`16mm` 没了，历史里换成了空字符串。

## 三、列漂移：判据补上，顺手改掉一句假注释

`facts.py` 里 `FACT_KEYS` 上方原本写着：

> 这份清单必须与 `stg_devices` 的业务列一致；表里多一列而这里没跟，那一列就永久没有历史——`scripts/check_facts.py` 第 `[6]` 步会拿表结构核对。

第 `[6]` 步是 `consistency()`，它拿表里的**值**逐键比对，**从来不读列名**。这句话等于给了一个不存在的保证。

现在两件事都做了：

1. 注释改成实话（第 `[11]` 步核对）；
2. 真的加了那个核对。

`schema_drift(columns)` 的口径：

- 业务列 = 全部列 − `device_id`（实体键）− 以 `_` 开头（`_src`、`_loaded_at` 是装载元数据，描述「这行怎么来的」，不描述设备）；
- 表有、清单没有 → 那列永久没有历史（该修清单）；
- 清单有、表没有 → 清单过期（该修清单或表）。

判据只在 `check_facts` 里查` information_schema`，并且 `data_health` 也读这个结果——两处都判，不留「子脚本红、汇总层绿」的口子。

**反例（真跑）**：`ALTER TABLE stg_devices ADD COLUMN color TEXT` →

```
列漂移       stg_devices 11 列 vs FACT_KEYS 7 个；表多 color，清单多 无
问题：
  - stg_devices 有 1 列业务数据没纳入 FACT_KEYS：color（这些列永久没有历史）
```

EXIT=1。跑完 `DROP COLUMN` 复原。

## 四、时间跨度：单轮不判红，给跨轮留基线

这一条和前两条不一样，它**不能**在单轮里判。

「生产事实层跨度只有 0 小时」「只有 1 个入库批次」——这两句话在刚部署、刚切租户、只有一次夹具导入时都完全正常。如果单轮判红，它每天都红，而每天都红等于没红。

所以分成两半：

- **单轮只产证据**：`coverage` 段输出 `rows / first_valid_from / last_valid_from / span_hours / ingested_batches`，不产生 issue；
- **跨轮才判**：`data_health.facts_drift` 对着上一轮比，而且加了一个前提——**上轮批次数 ≥ 2 才启用**。

这个前提是关键：没有基线的时候判「批次倒退」没有意义；有基线之后批次倒退，只有两种解释——同步停摆，或者历史被清后重导。

台账 `eval/facts_ledger.json` 也同步加了两个字段（`prod_ingested_batches`、`prod_span_hours`）。理由和 `DOC-46` 一样：`data_health.json` 每轮被覆盖，能证明「一段时间里发生了什么」的只能是只增不减的文件。

现在的台账最后一条：

```json
{"checked_at":"2026-11-26 14:36:22","prod_tenant":"client_a","prod_rows":35,
 "prod_first_valid_from":"2026-11-26 14:15:35","prod_ingested_batches":1,
 "prod_span_hours":0.0,"selftest_tenant":"fcheck","selftest_rows":44}
```

`prod_ingested_batches=1` 就是现在的事实：只有一次夹具导入，历史还没被真实运行验证过。这句话现在写在数据里，不是写在文档里。

## 五、`client_a` 那 35 行：打上夹具标签

之前一直悬着的问题：生产租户 `client_a` 有 35 行，来源是 `--seed-prod` 从 `BASE` 夹具导的，`source='initial_load'`。这个标签分不出「夹具」和「客户首导」——将来真实数据进来，两批混在一张表里，谁也说不清哪条是真的。

三个入口，全部只能人手执行，不在 `data_health` 的调用路径里：

| 入口 | 做什么 | 已执行 |
|---|---|---|
| `--seed-prod` | 把 `BASE` 当生产租户首次导入，`source=fixture_seed` | 否（之前用旧标签导过） |
| `--mark-fixture` | 把历史遗留的 `initial_load` 补打成 `fixture_seed`，**只改 source 一列** | **是**，35 行 |
| `--purge-fixture` | 真实数据接入前，只删 `source=fixture_seed` 的行（先查跨租户引用再清再删） | 否 |

`--mark-fixture` 是一次**显式的人工写生产**——它不是巡检动作，巡检永远不写 `client_a`。这一点必须写清，否则下次看到「生产被改了」会以为 P0-1 复发。

现在的租户分布：

```
 tenant   |     source     | count
----------+----------------+-------
 client_a | fixture_seed   |    35
 fcheck   | facts_check    |    36
 fcheck   | blank_probe    |     1
 fcheck   | blank_restore  |     1
 fcheck   | delete_restore |     7
 fcheck   | tenant_probe   |     1
 fcheck_b | tenant_probe   |     1
```

`client_a` 只有一种 source，且是夹具标签。真实客户数据进来时，走 `source='upstream_sync'`；两种数据同时存在时，一个 `WHERE source='fixture_seed'` 就能把它们分开。

## 七、还是没修的

- **`valid_from` 只能记到货**：上游不给生效时间。这是已知限制，不是缺陷；但「两次快照之间改了又改回」永远看不见。
- **清空没有协议**：现在 `''` 和 `NULL` 都当「没给」，所以**没有任何方式**表达「这个属性被清空了」。要解决必须先改源端协议（显式 tombstone），不在落地表里猜。
- **`facts` 没有 `snapshot_id`**：值存了，原始报文没存。解析错了查不回来。
- **保留期与真删**：只作废不删，行数只会涨。
- **`client_a` 是夹具**：`--purge-fixture` 还没执行，真实数据还没进来。现在的事实层是「机制完整、数据是假的」。
