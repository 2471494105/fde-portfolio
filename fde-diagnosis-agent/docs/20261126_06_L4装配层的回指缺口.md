# L4 装配层的回指缺口

> 2026-11-26 夜 | L1（事实层）已经能答「当时是什么」，但它答的东西进不了结论。
> 这篇不改代码，只把「要不要动」摆清楚——因为这一步的成本是 53 分钟的全量基线。

## 一、六层现在各是什么状态

| 层 | 职责 | 状态 |
|---|---|---|
| L1 事实 | 设备属性带版本，答「当时是什么」 | **已落地**（`DOC-45` / `DOC-46` / `DOC-47`） |
| L2 推断 | 跨事实推断、把没说过的话记下来 | **刻意不做**（见第二节） |
| L3 衰减 | 没用的记忆变淡 | **不需要**（见第三节） |
| L4 装配 | 把事实装进结论，并让结论可回指 | **缺口在这里**（见第四节） |
| L5 会话 | 多轮上下文 | 已有一层（checkpointer），与 L1 无关 |
| L6 评测 | 判据与回归 | 已有（97.6% / 284/291） |

## 二、L2 为什么不做

不是没能力，是**做了会污染 L1**。

L2 的产物是「模型推断出来的事实」。一旦写回 `facts.device_fact`，下一轮同步读到它，就会当成上游给的事实继续用——推断变成事实，而且再也分不出来。这正好是记忆层那张卡片里 `derives` 那条边的反面：推断必须**能单独标出来、可人工复核**，不能和事实同表同列。

现状：结论里的推断只活在当轮 state 里，不进 L1。这是对的，不打算改。

## 三、L3 为什么不需要

`facts` 的过期只有一种形式：**被新版本关闭**（`valid_to` 有值）。没有「三天后自动变淡」这回事——设备状态不会因为没人看就变模糊。

衰减真正该用的地方是 Episodes（「昨天那次排查怎么做的」），本项目的诊断结论是交付物，属于「关键结论不许衰减」那一类。

## 四、L4 缺口的具体形态

现在一条结论长这样（示意）：

> CX-101 当前在 1号线B 的 1-3号工位，相机 In-Sight 2801，维护周期 90 天。

这句话的每个字都来自 `stg_devices` 的当前值。问题有两个：

1. **它不可回指**。结论里没有 `facts` 的 `id`，所以事后没法回答「这条结论依据的是哪一条事实记录、它什么时候生效、是不是后来又被改过」。
2. **它不可证伪**。`cite_hit 97.6%` 覆盖的是手册片段（`device_manual_chunks`），**设备事实根本不在引用范围里**。也就是说：手册部分的每一句都能溯源，设备部分的每一句都不能。

这是 L1 落地之后最刺眼的一处不对称：**我们花了一整天让事实有版本，却没让结论用上那个版本号。**

## 五、最小改造（如果要做）

三处改动，全部落在 `BEHAVIOR_FILES` 里：

| 文件 | 改什么 | 为什么必须改它 |
|---|---|---|
| `app/tools/diagnosis.py` | 查设备事实时带上 `facts.device_fact_current.id`，随结果返回 | 事实的来源在这一层 |
| `app/graph/state.py` | 新增 `fact_refs: [{entity_id, fact_key, fact_id}]` | 字段结构变了就是可观测输出变了 |
| `eval/run_eval.py` | 新增判据：设备类结论必须有 `fact_id`；没有就标灰 | 判据口径也在指纹里 |

再加一条不动的：`docs` 与 `data_health` 侧不需要改，`facts` 已经有 `id`。

**新判据应该长什么样**（这是关键，不然只是加了个字段）：

- 每条设备事实型 claim 必须带 `fact_id`；
- 该 `fact_id` 必须指向一条**当时有效**的行（`valid_from <= 结论时刻 < valid_to`）；
- 该行的 `value` 必须与 claim 里的值逐字相等；
- 三条任一不满足 → 标灰，不计入引用命中。

这三条合起来才是「可回指」，只加 id 不够——id 可能指向一条早已关闭的历史行。

## 六、成本，以及为什么必须先问

| 项 | 数字 |
|---|---|
| 改动文件 | 3 个（全在 `BEHAVIOR_FILES`） |
| `code_hash` | 会变（现在 `0909a28fbc1c`） |
| 全量基线 | **53 分钟** |
| 现有报告 | 126 份里大部分会对不上新指纹，需要标注「旧指纹」 |

这就是 `DOC-41` 第八节 B-1 那条：**当前工作区没有任何一份同指纹的全量报告**。动了 L4，等于把「代码 11-26、数字 11-23」这个状态再往后推一次，而且这次不是押后，是主动作废。

所以这一步不该由我单方面开工。

## 七、三个可选路径

| 路径 | 内容 | 代价 | 适合什么 |
|---|---|---|---|
| A. 先不动 | 保持现状，L4 缺口写进待做总表 | 0 | 还在做数据层、暂不需要答辩 |
| B. 只做 shadow | 改 `diagnosis.py` 让它**额外**返回 id，但结论不引用；不动 `state.py` | `code_hash` 变、仍需重跑 | 想先看「带 id 会不会拖慢/拖乱输出」 |
| C. 全做 | 三处都改 + 新判据 + 53 min 重跑 + 重新登记基线 | 半天 | 准备答辩或交付，需要「设备结论也可溯源」这句话 |

## 八、判断（如果要我给一个）

**选 C 的时间点，取决于「答辩要不要讲可溯源」。**

- 如果要讲，C 是唯一能让那句话成立的路径——现在讲 97.6% 只能说「手册可溯源」，设备部分一被追问就露。
- 如果不讲，A 是诚实的：把缺口写进文档，比留一个说了半句的指标好。

不建议 B：它付了 `code_hash` 变化的全部代价（必须重跑才能比），却拿不到「可回指」的收益——中间态既不能讲，也没省下什么。
