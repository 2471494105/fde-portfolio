## 一、一句话

设备档案的每个属性现在都带回 `facts.device_fact` 里那一行的 `id`、`valid_from`、`valid_to`、`value`；
结论里每一句设备事实，只要对不上这条行，`run_eval` 当场判红并拉低通过率。

改之前，「CX-101 在 1号线B」这句话在系统里只有两种状态：说对了、说错了。
改之后多出第三种，也是真正要的那种：**说对了，但说不出依据哪条记录**——这种现在能被机器抓到。

## 三、三个判断，都是「不这么做就会静默不可信」

### 1. 回指清单从完整返回里取，不从 `evidence` 里取

`evidence` 存的是 `_payload()` 压过的 `slim` 文本，`fact_refs` 这种嵌套结构一旦被裁掉，
判据会把「被压缩掉了」读成「没回指」——一个假红，而且只在长返回时才出现，最难复现。
两者同源（同一个 `res`），但一个是给人看的文本、一个是给机器核的结构，不该互相借。

### 2. 判据方向是「从 claim 出发」，不是「每条 ref 都要被用上」

工具会把 7 个属性全给回来，而一轮结论可能只用到 `line`——那是按题面取舍，不是缺陷。
要判的是反方向：**说出口的有没有出处**。写成「ref 使用率 < 100% 就红」，等于每轮都红。

### 3. `fact_refs` 要跨轮累积——第一版写成「本轮字段」，被全量实测推翻

第一版的理由是「回指的是这一轮结论的依据，跨轮累积会让第 1 轮的事实支撑第 3 轮没查设备的结论」。
听起来对，全量跑完就露了：

`W1` 是多轮用例（`turns=2`），第 1 轮查设备档案、第 2 轮建单时引用「CX-101 光源超额定寿命」。
每轮清空 → 第 2 轮判 `claim[10] query_device_profile#maintenance_cycle_days 在事实层找不到对应行`，
把一次**合法的跨轮引用**判成模型没写出处。而 `evidence` 本来就跨轮保留（它是整段会话「查过什么」），
一边说「隔壁证据还在」、一边说「依据没了」，自相矛盾。

改法：`fact_refs` 变累积字段（`Annotated[list, _add_list]`），每项带 `turn`，
判据对同一 `(entity, key)` 取**最近一轮**那条。栽赃（拿 A 台的记录支撑 B 台）不靠清空来防，
靠 `entity_id` 与 `value` 双重比对——清空防不住写错，比对才防得住。

改完重跑 `--only=W1,T2`：`设备事实回指 2/2`（清单 14 条），两条都过。

这不是设计时能想到的：它只在**多轮用例 + 跨轮引用设备事实**这一种组合下出现，
而单测夹具全是单轮。**判据的第一批真实反例来自全量，不来自单测。**

## 四、判据：三条一起判，缺一条都不叫「可回指」

```
1) 有 id    —— claim 能对上一条 ref（`query_device_profile#<字段>`）
2) 当时有效 —— ref 的 valid_to 必须为空
3) 值相等   —— claim 的值与 ref 的值逐字一致（只压成文本、去空白，不补零不改小数点）
```

为什么不是只判一条：

- 只判 1，会放过「指到一条早就关掉的历史行」——id 是真的，记录的却不是现在。
- 只判 3，会放过「值对但没出处」——模型自己写对也能过，等于没判。
- 只判 2，会放过「写了 id 但没人用」——约束存在，结论里还是裸数字。

判据只覆盖 `FACT_FIELDS`（7 个设备属性）。误判率、工单号、手册条款不归事实层管，
把它们算进来是用 L4 的判据去判 L2/L3 的事，红得不明不白。

## 五、反例：三次真跑，其中一次抓出了我自己的假绿

`--only=I6`（`cx-104 数据`，走 lookup 模板，2 秒一条，可反复跑）。

| 反例 | 手法 | 结果 |
|---|---|---|
| 缺 id | `fact_id` 置 `None` | `失败归因 fact_unref×1` ✅ |
| 值不等 | ref 的 `value` 改成 `"999"` | `设备事实回指 0/1`、`fact_unref×1` ✅ |
| 正例 | 还原 | `设备事实回指 1/1`（清单 7 条）、`剔除后正确率 100%` ✅ |

**第一次做「值不等」反例时暴露的问题**：判据红了（`fact_unref×1`），但 `剔除后正确率`
仍然是 `1/1 = 100%`。原因是 `fact_unref` 落在 soft severity，而 `semantic_ok` 是手写组合，
我没把它加进那个 `and` 链——于是「设备事实无法回指」只进报告、不进通过率。

这就是这个项目一路在清的那种假绿：**判据红了，数字还是绿的，读报告的人只会看数字。**
修法是两处联动：把 `_fact_audit()` 提到 `semantic_ok` 之前算，并在组合里加
`and not fact_problems`。修完再跑同一反例，`剔除后正确率 0/1 = 0.0%`。

留在这里是因为它是个可复用的坑：**任何新判据都要问一句「它进不进 semantic_ok」，
不进就等于只写了一条日志。**

## 六、回指的前提：facts 得先覆盖完整

开工时查出的事实：`facts.device_fact_current` 里 `client_a` 只有 **27 行 / 4 台**——
CX-101 缺 `line`、CX-105 整台没有。而 `devices` 表是 5 台 × 7 属性 = 35。

在这种状态下做 L4，`query_device_profile` 会给 CX-105 一个 `fact_missing: [7 个键全缺]` 的档案，
任何关于它的结论都**不可能**被回指——但 eval 只会看到「这条 claim 找不到对应行」，
判成模型没写出处。缺口在数据层，冤枉在模型身上。

两处补：

1. `--seed-prod --seed-from=devices`：从主库 `devices` 读行（不再用夹具 `BASE`），
   写沙箱再 `sync(client_a, source=initial_load)`。跑一次开 8 条（CX-101.line + CX-105×7），
   现 `client_a` = **35 条当前值 / 43 行历史**，与 `devices` 逐值一致。
2. 第 [12] 步 `source_coverage()`：`devices` 里**有值**的属性，`facts` 当前视图里必须有行，
   缺一个就红。实测 `devices 5 台应有 35 个属性，facts 当前缺 0 个`。
   空白值与 NULL 不算缺口——那是 P1-5 的口径（`''` = 没给），本来就不该有历史。

同时把它接进 `data_health.facts_issues()`：巡检每轮自己发现覆盖缺口，
不必等一次 53 分钟的全量跑才暴露。

## 八、全量跑了三遍，每一遍都改了一处

`code_hash` 变了三次，所以每变一次就得重跑一遍——不是返工，是**每一遍都逼出一个单测抓不到的错**。

| 轮 | `code_hash` | 语义正确率 | 明确出处率 | 可核验率 | 设备事实回指 | 失败归因 |
|---|---|---|---|---|---|---|
| 1 | `7bc10283f639` | 23/26 = 88.5% | 286/289 = 99.0% | — | 未统计（判据尚未进 `semantic_ok`） | `fact_unref×2`（W1、T2） |
| 2 | `7fda2a4c4bb6` | 23/26 = 88.5% | 267/275 = 97.1% | 274/275 = 99.6% | 15/16 | `fact_unref×1`（T2）、`回指缺失 1` |
| 3 | `602c99b29134` | **24/26 = 92.3%** | 262/269 = 97.4% | 265/269 = 98.5% | **13/14** | `fact_unref×1`（T2）、`回指缺失 0` |

三遍各自改了什么：

1. **第一遍 → 第二遍**：`W1`（多轮）被 `fact_refs` 每轮清空判红。这不是模型的错，是判据把
   一次合法的跨轮引用判成没写出处。改在 `state.py`（变累积字段）+ `_fact_audit` 取最近一轮。
   第二遍 `W1` 转绿。
2. **第二遍 → 第三遍**：`回指缺失 1/26` 是假报——`CX-106` 查无此设备，本来就没有行可回指，
   却被记成「工具侧没接上」。改成只统计**查到了**的那几次。第三遍 `回指缺失 0`。
3. **第三遍剩下的 `T2` 是真实缺陷，判据抓对了**：
   `claim[0] query_device_profile#station 值不等：claim=3 fact='1-3号工位'`。
   模型把「3号线」的 `3` 引到了 `station` 字段（`station` 真实值是「1-3号工位」）。
   这条**三遍都红**，说明是稳定行为而非抖动。

> **2026-11-26 傍晚更正（见 DOC-50）**：上面这一条对第三遍（`1519`）的定性是错的。
> 把 trace 里的 claims 原文挖出来看，第三遍的 `claim[0]` 是
> `{"text": "设备档案登记工位为「1-3号工位」", "ref": "query_device_profile#station"}`
> ——**没有 `value`**，正文与 `facts` 逐字一致。判据拿 `None` 去比，报「值不等：claim=None」，
> 把「没给」报成了「给错」。也就是说：第三遍的红是**判据自己制造的假红**，
> 只有前两遍（`value=3`）才是模型真的引了个不存在的值。
> 而这两种写法同时被判红，说明判据对 7 个字段里的 6 个文本型字段**不可满足**：
> 写 `value` 要逐字相等、不写 `value` 又永远不等。`DOC-50` 修的就是这条。

`T2` 值得单独说：它把 L4 的判据精度暴露了一遍。`3` 是 `'1-3号工位'` 的子串，
所以引用层（`path_ok`）判它「指到字段了」——宽松匹配会放过。逐字比对不放。
**「值能在字段里找到」和「值就是那个字段」是两件事**，这正是 `_norm_val` 只做去空白、
不做包含匹配的原因。

顺带记一个口径：`回指清单` 是 **147~154 条**而不是 26×7=182。因为它跨轮累积，
同一台设备查三次就留三份；这个数是「这段会话累计给出过多少条回指」，不是「本轮几条」。
所以报告里写「核的是条数」而不是「每台的 7 个键都齐」——两种口径不能混。

## 九、反例（第十二步）与这次没做的

`source_coverage` 的反例只能靠真关一行来做（造一份「源端有值、facts 没有」的缺口）：

```sql
-- 关掉 CX-105 的光源型号（不删行，只是让它不再是"当前"）
UPDATE facts.device_fact SET valid_to = now()
 WHERE tenant='client_a' AND entity_id='CX-105' AND fact_key='light_model' AND valid_to IS NULL;
```

结果：`源端覆盖 devices 5 台应有 35 个属性，facts 当前缺 1 个（CX-105.light_model）`，`EXIT=1`。

恢复时踩了一个坑：先写了 `SET valid_to = NULL WHERE ... valid_to IS NOT NULL`，
结果撞 `device_fact_unique_current` —— 这条键下面**有两行历史**（`fixture_seed` 的 id=292
与 `initial_load` 的 id=1370），一次 `UPDATE` 把两行都放开就等于两条当前值。
改成按 id 恢复（`WHERE id = 1370`）才对。这正好演示了「只保留一条当前值」这条约束是真的在拒。
恢复后 `缺 0 个`、`EXIT=0`。

**没做的**：

- **`T2` 的成因已在 `DOC-50` 修掉**（2026-11-26 傍晚）：不是"模型引错字段"，是判据对文本型
  字段不可满足（写 `value` 要逐字相等、不写又永远不等）。修法两条一起：判据给文本型字段
  开正文核对，提示词写明「文本型字段把整段原值写进 text，不要掰成数字」。
  修后同形状的 claim 在 `1547` 全量里通过。
- **L4 跨轮「还在不在用」**：`fact_refs` 已经跨轮保留（见第三节第 3 条），但「上一轮的结论
  这一轮还在不在被引用」仍然没有记录，那属于 episode（L3）。
- **epoch 级回指**：`fact_id` 指向一行，不是指向一个版本区间。
  若某个结论要覆盖「这一周里设备改过两次」，得引两条 ref——现在是两条 claim，没有合并表达。
- **`cite_hit` 分母没重算**：它从 99.0% 降到 97.4%，是三遍之间模型输出不同造成的分母波动，
  不是回指判据带来的。单独统计「设备事实的出处率」还没做。
