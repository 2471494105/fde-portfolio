# 判据分层与指纹预算：谁有裁判权、改动按什么编批

（2026-11-26 晚，接 `DOC-50`。`DOC-50` 解决"两条红是谁的错"；这篇解决"以后这类事归谁管、什么时候做"。）

## 一、一句话

**判据只有一个法庭（离线评测），运行时只有一道门岗（可确定性执行的规则）；改任何一个有裁判权的东西都要付一次全量，所以按指纹编批，不按心情排优先级。**

## 二、这篇为什么现在写

`DOC-50` 里那两条假红，一条是判据写错（文本字段不可满足），一条是归因缺口（建单失败记到模型头上）。
两条都不是模型的问题，但它们在报告上的形状和模型答错一模一样。今天的事不是"又修了两个 bug"，
而是暴露了一个结构问题：**同一个 claim 被两套规则各判一次，规则分居两处，口径已经开始漂。**

- `app/graph/nodes.py::_verify_claims` —— 在线：`ref` 能不能在证据里取到、值在不在那个字段里。
- `eval/run_eval.py::_fact_audit` —— 离线：`ref` 指向的 `facts` 行存不存在、值逐字等不等。

离线那条今天学会了"文本型字段按正文核对"，在线那条还不会；在线那条会判"ref 解不出路径"，
离线那条不判。**两边都在判"引用对不对"，但判的不是同一件事，而且没有一份文档说清楚谁说了算。**

## 三、四层，各自的裁判权

| 层 | 在哪 | 回答什么问题 | 有裁判权吗 | 判错的代价 |
|---|---|---|---|---|
| 事实层 | `facts.device_fact_current` + `fact_refs` | "当时这台设备的这个属性是什么" | **没有**，它只提供证据 | 缺键 → 结论不可能被回指（`N-16`） |
| 离线判据 | `eval/run_eval.py` | "这条结论算不算过、失败算谁的" | **唯一有** | 判错 → 假红/假绿（`DOC-50` 两条） |
| 在线护栏 | `app/graph/nodes.py::verify/check` | "这个数有没有出处、要不要退回去重写" | **有，但只限结构可判** | 判错 → 现场体验与成本（回环一次 = 一轮 token） |
| 运行前置 | `scripts/preflight.py` | "这 373 秒花下去算出来的数有没有意义" | **有，且是拒跑级** | 漏判 → 白跑一次，还把环境故障记到模型头上（`N-19`） |

这张表的用法：**出了红，先问"它归哪一层"，再问"这一层有没有权限判这件事"。**
`W3` 那次的错，是第三层没有"环境"这个输出口，第二层只好把它归给模型；
`T2` 那次的错，是第二层在判一件它自己没定义清楚的事（`value` 缺省时算什么）。

## 四、三条硬规则

1. **语义不归在线判。** 在线只能判"能不能取到"（结构），不能判"写得对不对"（语义）。
   `T2` 那种"值对、字段错位"属于语义，在线判不了——它不知道"3号线"和"1-3号工位"哪个才对。
   硬让它判，就只有两种结果：要么放行（等于没判），要么误伤。
   Anthropic《Building effective agents》里讲 guardrails 的那段说得更直接：
   一个模型处理用户请求、另一个模型做审查，比"同一次调用既生成又把关"效果更好；
   放到这里就是——**别让生成结论的那一方给自己打分**，要么用代码判，要么交给离线。
2. **可判性先于严格性。** 一条规则能不能上线，不看它"理想上该多严"，看它"在几个输入形状上被走过"。
   `N-18` 的教训：判据在 `maintenance_cycle_days` 上走了 31 次全绿，在文本字段上走了 2 次全红，
   而我按前者的表现给后者背书。新规则必须带**正反两侧**夹具，反向那条尤其要能红。
3. **凡是拒跑级判断，提前到场，且不写进指纹。** 前置条件（服务在听、库是种子态、事实层没缺口）
   应该在开跑前拦，而不是跑完之后解释。这类只读判断放在 `BEHAVIOR_FILES` 之外，
   加它不改变 `code_hash`，也就不会让既有基线作废。

## 五、三个悬着的事，今天裁定

### 5.1 `T2` 类缺陷（值对、结构化字段错位）——**不在 `verify` 拦，维持"提示词 + 离线判据"**

理由三条，按重要性排：

1. 在线判不了：错位意味着 claim 的 `value` 和 `ref` 指向的字段不是同一种写法，
   要判就得知道"这个字段的合法写法长什么样"，那是事实层的知识，在线只有一份被压缩过的 evidence。
2. 就算判得出，代价也不对：回环一次是整轮重写，而这类错的修复成本本来就该由提示词承担
   （`DOC-50` 已经写清"文本型字段整段写进 text、不要掰成数字"）。
3. Anthropic 那条 sectioning 的结论在这里反向适用：**在线环节里最该避免的，是让生成方兼任裁判。**

代价：这类错在演示里会直接出现在用户眼前，靠 prompt 兜。接受这个代价，因为它比"多一道误伤率未知的在线规则"便宜。

### 5.2 `fact_refs` 跨轮累积——**规则定死，执行冻结**

现状：`fact_refs` 是 `_add_list` 累积，`1547` 那份一共 154 条、**单条用例最多 14 条**（26 条里 20 条非空）。
上限不能简单按轮数切：`eval` 的 `_fact_audit` 是拿 `state.fact_refs` 去解析 claim 的 `ref` 的
（`run_eval.py` L238），**先裁后判，就会把"引到已裁掉的旧事实"读成"引了一条不存在的行"**——
又是一个判据造的假红，和 `DOC-50` 是同一个形状。

所以规则定成（写死在这里，等真需要时照做）：

- 先保住**本轮 claims 里出现过 ref** 的那些条目（它们是裁判要用的）；
- 再按轮次从近到远补，单轮上限 30 条、总量上限 90 条；
- 超出的从"最旧且未被引用"开始丢，丢了多少写进 `fact_refs_dropped`，进报告。
  最后这条是这次的教训：**裁剪必须是可数的**，静默丢数据等于给下一个人埋一个"为什么这条引不到了"。

**为什么执行冻结**：实测最大 14 条/用例，90 条的上限在评测里根本不会触发——
它服务的对象是演示之外的长会话（在线跑几十轮的那种），而演示是短的。
按"是否影响演示"这条尺子，它该冻结；但规则先写死，免得下次需要时又从零讨论。
真上线长会话之前，这条要从"设计"变成"代码"，并且仍然共用一次指纹预算。

### 5.3 `N-13`（`facts` 没有 `snapshot_id`）——**冻结到答辩后**

要动 schema、要回填、要改 `_fact_audit` 的口径（从"值逐字等"变成"值在这一版里逐字等"），
三件事都改 `code_hash`，且演示现场看不出差别。按"是否影响演示"这条尺子，冻结。

它不会消失：`claims` 落盘之后，裁决链上已经有"哪句话"，缺的只是"哪一版数据"。这条写进待做总表，等答辩后开。

## 六、指纹预算：改动按什么编批

`app/meta.py` 的 `BEHAVIOR_FILES` 里已经有 `eval/run_eval.py` 与 `app/graph/nodes.py`、`state.py`。
规则很简单：**改里面任何一份 = `code_hash` 变 = 磁盘上同指纹全量作废 = 一次 373 秒。**
所以排期不该按"哪件更重要"，该按"哪几件可以共用一次全量"。

| 改动 | 改指纹 | 该怎么做 |
|---|---|---|
| `scripts/preflight.py`（新增） | **否** | 立刻做，零成本（今天已做） |
| `tests/*`（新增） | 否 | 立刻做（今天已做） |
| `docs/*`、`eval/报告状态.md` | 否 | 随提交走 |
| `fact_refs` 裁剪（`state.py`） | 是 | **冻结**——评测里不会触发（5.2） |
| 把 preflight 接进 `run_eval` 入口（`run_eval.py`） | 是 | **冻结**——它要防的是一次白跑，靠纪律替代；等下一次必改指纹时顺带 |
| `snapshot_id`（`facts.py` + `run_eval.py` + DDL） | 是 | 答辩后 |

一句话：**现在没有任何必须付全量的改动。** 这不是拖延，是把 373 秒留给定要改的东西——
答辩前唯一值得为之重跑的，是"演示会当场穿帮"的那类问题。

## 七、今天落地了什么

`scripts/preflight.py`：端口（5432 / 11434 / 8010）、库态（`devices=5 / work_orders=1 / defect_logs=1000 / alarms=8`）、
事实层覆盖（`client_a` 应有 35 个键缺 0）、`code_hash` / `seed_hash` 一起打印。不过就拒跑，并给出去修的命令。

三条刻意的设计：

- **`seed_hash` 先判**：种子换过版本，行数期望就失效，先报"种子变了"，不能报成"上一轮没复位"——
  后者会让人去复位一个本来就不是旧版的库。
- **不在 `BEHAVIOR_FILES` 里**：单测里有一条断言这件事（`test_not_in_behavior_files`）。
  加完脚本实测 `code_hash=b5b70ab771e6`，与 `1547` 的 `meta` 一致——**基线没有被这次改动作废**。
- **判定逻辑与 IO 分开**（`seed_problems` / `coverage_problems` 是纯函数）：9 条单测不连库、不开端口
  就能把"该拒跑"的每种形状走一遍。一份自检自己坏掉的方式，和它要防的事一模一样：静默放过或静默永假。

实测：正常态 `EXIT=0`（六行输出全 OK）；把 8010 换成 9999 的端口表 → `EXIT=1`，并打印拒跑理由。
`1547` 仍对应当前代码，`1519` 仍作废。

## 八、下一批：现在没有

按上面那张表，能立刻做的（不碰指纹）今天都做完了；剩下的每一项都要付 373 秒，且演示现场看不出来。
所以这一段的结论是**不做**，而不是"排进下一批"——排进去就等于承认它比演示重要。

什么情况下这条会翻：

- 演示脚本里出现一段**长会话**（同一 `thread_id` 十几轮），`fact_refs` 或摘要开始吃 token → 5.2 从设计变代码。
- 演示当天要展示"这条结论引的是哪一版数据" → `snapshot_id` 解冻。
- 发现某条判据在**演示会用到的那条路径**上会误伤 → 那才值得重跑，而且重跑之前先看第四节第 2 条（可判性）。

## 九、没做的 / 风险

- **`snapshot_id` 冻结**（5.3）；**`fact_refs` 裁剪冻结**（5.2）。两者都写在待做总表里，带触发条件。
- **在线护栏的环境通道只覆盖建单**：`deduped_env` 覆盖幂等，`env_qms` 覆盖建单；
  其他工具将来若也会"整体不可达"，还得各配一条通道，否则同一类冤案会换个工具重演。
- **`preflight` 靠纪律，不靠机制**：没接进 `run_eval`，因为接进去要付一次全量。
  现在的纪律是"跑全量前先跑它"；纪律会失效，机制不会——这是这条风险将来的解法，不是现在的借口。
- **裁剪上限 90 条没有实测支撑**：单条用例实测最多 14 条，90 是给长会话留的量，没跑过。
