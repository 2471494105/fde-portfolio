# 源端登记与漂移（DOC-53）

> 2026-11-26。这是卡 2（源端变更）的判据落地。卡在 `90_生产骨架/20_结构与契约/源端变更：改字段的人不会通知你.md`。

## 一、问题不在判据，在观测面

我方已有两条漂移判据：

- `scripts/check_ds_delete.py` 的 `hash_columns_check()` 比 `CONTENT_COLS`；
- `scripts/check_facts.py` 的 `schema_drift()` 比 `FACT_KEYS`。

两条读的都是**我们的表**（`stg_*` / `facts`）。源端在自己的库/文件里加一列，我们的 staging 表永远不会有那一列——判据再严，它看不见；`app/ds/mapping.py` 第 8 行更是明写「源文件里多出来的列一律忽略」，于是「静默丢弃」本身是被设计出来的行为。

这不是配置问题，是**判据位置放错了**。要发现源端漂移，观测面必须在源端。

## 二、四条判据

| 判据 | 判什么 | 判红之后怎么办 |
|---|---|---|
| `S1` 源端漂移 | 登记的列 vs 现在的列：新增、消失、类型变、必填变 | 报出来，人工决定收不收 |
| `S2` 未消费列 | 源有、但映射没配的列 | **黄，不红**：要一句「有意识忽略」的理由 |
| `S3` 破坏性 | 主键/游标列消失；新增**必填**列 | **拒跑**（退出码 3） |
| `S4` 未声明改名 | 一加一减且 `renames` 里没有声明 | 拒，不猜「看着像」 |

退出码：`0` 干净、`1` 红（漂移但不破坏）、`3` 拒跑、`2` 脚本自身崩（此时任何结果都不能当结论）。

## 三、登记长什么样

`data/mapping/source_schema/<client>_<table>.json`：

```json
{
  "client": "client_a",
  "table": "devices",
  "observed_via": "csv_header",
  "observed_at": "2026-11-26",
  "source_path": "data/sandbox/from_client/equipment.csv",
  "key_columns": ["equip_no"],
  "renames": {},
  "columns": [{"name": "equip_no"}, ...],
  "limits": "CSV 表头只给列名，给不出类型与必填；这两维标记为未观测，不参与判定。"
}
```

已登记两份，都是**仓库里的真实样本**，不是手抄：

- `client_a_devices.json`（8 列，键 `equip_no`，源 `equipment.csv`）
- `client_a_defect_logs.json`（9 列，键 `rec_id`，源 `defect_records.csv`）

`renames` 是 `{"新名": "旧名"}`。**改名必须显式登记**：不登记的「一加一减」一律按嫌疑报出来。理由是 Avro 的教训——rename 只认 `aliases`，而 spec 里写的是 "may optionally"，实现不保证；靠列名相似度猜，猜错的代价是把一个语义无关的列当成同一列继续用。

## 四、四种可靠信号，实现了三种半

| 信号 | 实现 | 自证 |
|---|---|---|
| CSV/文件表头 | `observe_csv_header()`：读表头、去 BOM、拒绝空列名 | 两个真实样本各 8 / 9 列 |
| Odoo `fields.*` | `parse_odoo_fields()`：正则抽 `x = fields.Type(...)` + `required=True` | `07_外部样本/odoo-maintenance-model.py` → **47 个字段** |
| `information_schema` | `parse_information_schema()`：`IS_NULLABLE` 转 `required` | `stg_devices` → **10 列**，前六列 `device_id/line/station/camera_model/lens_model/light_model` 均为 `text`、可空 |
| 响应 JSON 键集合 | `parse_response_keys()`：**只取第一层**，嵌套对象当整体 | 单测：`{"id":1,"meta":{...}}` 只出 `id/meta` |

「半」是第四种：只取第一层，不递归猜结构。猜出来的 schema 比没有更危险——它会把「我们以为的嵌套形状」写进登记，之后每一次比对都是在自己跟自己比。

`commit` 消息不算信号，这条已被 G4 的样本证伪（那次真实提交是删死代码，字段没动）。

## 五、五个决定

1. **CSV 表头给不出类型，就标「未观测」，不标「无变化」。** `diff()` 把这种列放进 `type_unchecked`，单独一行打印数量。把「没看见」当成「没变」是最常见的假绿来源，和 `DOC-50` 的 `env_n=0` 是同一类错误。
2. **`S2` 是黄。** 源端有 20 列我们只用 8 列是正常的（`warranty_start` 这类我们确实不要）。判成红会逼人天天消警，最后整条判据被关掉。黄的用途是逼出一句理由，写进登记即可。
3. **新增必填列 = 拒跑。** Confluent 兼容矩阵里「加必填列」只有 FORWARD 允许，历史行拿不出值；我们的 staging 表列都可空，所以它不会报错，只会永远是 NULL——**静默的 NULL 比报错难查十倍**。
4. **不做列名相似度匹配。** 见第三节。
5. **不自动并表。** 新列不偷偷塞进 `CONTENT_COLS` / `FACT_KEYS`：一塞，历史指纹就跟着变，`check_ds_delete` 会开始报「内容哈希漂移」——那是我们自己的改动，不是源端的。

## 六、实测

判据跑真登记 vs 真文件：

```
[ok] client_a/defect_logs  via=csv_header(defect_records.csv)  登记于 2026-11-26
[ok] client_a/devices      via=csv_header(equipment.csv)       登记于 2026-11-26
```

四个反例（用 `--source=` 指向临时表头，**不动仓库里的样本**）：

| 反例 | 表头改动 | 结果 |
|---|---|---|
| 加一列 | 末尾加 `torque_limit` | `S1 新增列 ['torque_limit']` + `S2 未消费`，exit **1** |
| 删非键列 | 去掉 `lamp_type` | `S1 消失列 ['lamp_type']`，exit **1** |
| 删主键 | 去掉 `equip_no` | `S1 消失` + `S3 拒跑 主键/游标列消失：['equip_no']`，exit **3** |
| 改主键名 | `equip_no` → `equipment_no` | `S1 新增/消失` + `S3 拒跑`（两条：主键消失、疑似改名的正是主键）+ `S4 疑似改名`，exit **3** |

声明过 `renames` 的改名（`{"equipment_no": "equip_no"}`）走单测：`clean=True`、`renamed=[{from: equip_no, to: equipment_no}]`、`breaking=[]`。CLI 层没有为这条单独造一份带 `renames` 的登记——加一份假登记会让「登记都是真的」这条自证失效。

规模与代价：

- 新增 `tests/test_source_schema.py` **16 条**，全量单测 473 → **489 条** OK；
- `code_hash` 仍 `b5b70ab771e6`、`seed_hash` 仍 `9caa1322fbfc`：`app/ds/*`、`scripts/*`、`data/mapping/*` 都不在 `BEHAVIOR_FILES`，**没付 373 s 全量**；
- 快照 `eval/source_schema.json`（两份登记 + 四类差异 + 退出码）。

## 七、取舍与没做的事

- **`--db-table=` 能观测库，但登记口径不同。** 现在登记的是「客户端 CSV 表头」（`equip_no` 那一套），`stg_devices` 是标准列名（`device_id` 那一套）。拿 `--db-table=stg_devices` 去比必然全红——那是**映射的输入输出两侧**，不是漂移。什么时候用：等真的接了客户库（源就是库），登记改成 `observed_via=db` 再跑。适配器本身已验证可用（10 列、类型/可空都解析出来了），不算死代码。
- **只改数据不改 schema 的变更，这一层看不见。** 量纲从 mm 改成 cm、枚举多出一个值、时区从 +8 变 UTC——列名和类型都没动。卡 2 里把「同类型换量纲」列为真静默的一类，这一层抓不到，得上 `S5`（值域/量纲抽查）。**没做**，写在这里而不是假装覆盖了。
- **Airbyte 的 schema-change 管理没抄全。** 它有一套「检测到变更 → 暂停同步 → 人工批准/自动批准」的编排；这里只有判据，没有编排。演示路径上不需要编排，冻结。
- **`eval/data_health.json` 里没有这一层。** 巡检脚本要等下一轮才把它接进来（同 `DOC-52` 的 `policy` 快照情况）。
- **`renames` 的迁移语义没解决。** 声明改名只影响**判定**（不报红），不影响**数据**：改名那一列的历史行仍是旧列名，回填脚本没写。
