# 换源验收：八条判据指到第二家客户（DOC-55）

> 2026-11-26。`DOC-52`（A/B/C 口径登记）、`DOC-53`（S1–S4 源端登记与漂移）、`DOC-54`（S5 值域抽查）搭好了判据。这一篇是让它们第一次跑在**不是自己造**的源上。代码提交 `1fd6ae5`。

## 一、判据在自己造的库上全绿，说明不了什么

前九步的"验收"都是我造靶子、我射箭。靶子的形状与判据的形状出自同一份理解，所以全绿只能证明"我以为的危险我都想到了"，证明不了"换一家客户时它会不会跪"。

换源要验的不是"判据能不能跑"，是**换一家客户时，哪几处会先跪、跪在谁身上**。`client_mes` 与 `client_a` 的差别恰好落在判据最薄的几处：

| 维度 | `client_a`（旧） | `client_mes`（新） |
|---|---|---|
| 取数通道 | CSV 文件路径 | DSN 连接串（`source_path` 是一个 URL） |
| 列集合 | 8 / 9 列两份样本 | 三表 8 / 9 / 10 列，每表都多出一列本家没有的 |
| 类型与必填 | 登记里**没有**（CSV 表头给不出） | `information_schema` 给得出，登记里**应该有** |
| 映射 | `client_a.json` | 不存在，得新写一份 |

走 **A 方案**：`client_mes` 独立登记（`data/mapping/source_schema/client_mes_{md_device,biz_defect_record,biz_work_order}.json`），`client_a` 的两份样本一行没动。理由很实际：真跑坏了 `client_a`，事后分不清是判据坏了还是样本被我改坏了；回归面越小，结论越干净。

## 三、九条反例与档位

反例不拿 T8 的 `inject_faults` 去动客户真表。做法是建一个 `probe` schema，用 `create table probe.eN (like public.md_device)` 拿到结构再改一处；每条反例临时抄一份 `client_probe_<key>.json` 登记指向 `probe.eN`，跑完删登记、`DROP SCHEMA probe CASCADE`。

**为什么费这个劲**：判据的"拒跑"必须由"源结构真的变了"触发，不能由"我改了它的登记"触发。用客户表造景，跑绿的可能是运气，跑红的可能是手快；用同构影子表，"红"这个结论才归因得到判据。

| 反例 | 造法 | 期望 | 实得 |
|---|---|---|---|
| e1 新增列 | `probe.e1` 加 `torque_limit` | 1 | **1** ✅ S1 新增列 |
| e2 删非主键列 | 删 `lens_spec` | 1 | **1** ✅ S1 消失列 |
| e3 主键列消失 | 删 `equip_no` | 3 | **3** ✅ S3 拒跑 |
| e4 新增必填列 | 加 `batch_no NOT NULL` | 3 | **3** ✅ S3 拒跑 |
| e5 未声明改名（非空列） | `lens_spec → lens_model` | 3 | **3** ✅ S4 + S3 双报 |
| e5b 未声明改名（可空列） | `tmp_note → tmp_doc` | 1 | **1** ✅ S4 单独红 |
| e6 未声明改名（主键） | `equip_no → device_no` | 3 | **3** ✅ S3 拒跑 |
| e7 类型变 | `maint_cycle smallint → text` | 1 | **1** ✅ S1 类型变 |
| e8 量纲缩小 100 倍 | CSV 探针把 `conf_pct` 除以 100 | 3 | **3** ✅ S5 拒跑 |

`DOC-53`结尾记的"S3 与 S5 建好了但从未被真数据触发"，在这里补上了：S3 在 e3/e4/e5/e6 四条上真拒跑，S5 在 e8 上真判到「量纲疑似缩小 100 倍（百分制→小数）：声明 [0,100]，观测 min=0.61 max=0.92」。

## 四、六个真缺口：判据逻辑一条没改

这轮改的全是**取数与导出**——判据本身是对的，喂给它的东西是残的。

**1. 登记导出丢了两维（最要命的一条）**

`mock-mes/scripts/export_registry.py` 的 `build()` 只写 `{"name": col}`，而 `information_schema` 本来就给得出 `data_type` 与 `is_nullable`。后果不是报错，是**静默**：S1 每表都报"类型未观测 8/9/10 列"，看起来像"CSV 表头给不出类型"的合理妥协——可 `client_mes` 的来源是库，类型一直拿得到。真要有人把 `text→integer` 改了，它还是只会报"未观测"。补 `type` / `required: not is_nullable` 后归零，"未观测"这个词才恢复它本来的含义。

**2. 没有第二份映射，S2 就全亮**

`data/mapping/client_mes.json` 不存在 → `mapping_consumed()` 返回空 → 每张表的**所有列**都进"未消费"（9 / 10 / 10 列）。一条全靠亮的判据等于没有判据，第二个人看到就会把它关掉。补映射后降到 1 / 1 / 1，黄得有意义。

**3. S5 根本没有库通道**

`app/ds/value_domain.py` 的 `analyze()` 只用 `Path(reg["source_path"])` 读 CSV。`client_mes` 的 `source_path` 是 DSN 字符串，换客户后 S5 直接崩——不是判红，是崩。补 `observe_values_db()`（psycopg 取值）与 `--dsn`，按 `observed_via` 分流。

**4. 库里取到的值没按声明统一**

同一列，CSV 给的是 `2026-11-01 08:00`，库里 `str()` 出来的是 `2026-11-01 08:00:00+08:00`。按声明格式 `%Y-%m-%d %H:%M` 判，**每一行都"格式改了"**。补 `_text()` 按登记 `format` 归一，判据才在看格式而不是在看驱动怎么写 `datetime`。

**5. `limit 200` 不带 `ORDER BY`，脏行被跳过（本轮最像"假绿"的一条）**

首版库采样 `select * ... limit 200`，拿到的是物理末尾那 200 行（`rec_id 1001+`），`conf_pct=150/-10` 的 `rec_id 5/6` 根本没进样本 → 判据报 ok。**判据在跑、数据在库、脏值在第三行，三者都在，结论是绿的。** 改为按登记 `key_columns[0]` 排序后取前 N，"抽查了哪 200 行"从此可复述。

**6. 档位键名错，登记里写的"黄"被吞了**

`check_range` 读 `dom.get("range_severity")`，而导出写的是 `dom["severity"]`。登记里 `conf_pct` 明写 `severity: yellow`，却被判成红、exit 1。改成 `severity` 优先、兼容旧键。**口径由登记决定，不能由键名决定**——这是"声明了却没生效"的典型长相：不报错、也不按你说的办。

## 五、e5：期望错的是我，判据是对的

未声明改名，我预期 exit 1（S4 单独红），实得 **3**。原因是叠加：改名后新列对历史行而言就是"新增的必填列"，S3 先兜住了；S4 只是同时把它报出来。

所以又补了 e5b——对**可空**列（`tmp_note`）改名，新列没值也不算破坏，S4 才单独红（exit 1）。结论写进脚本注释：**多条规则叠加时取最严的那档，不做"第一条命中就停"**。前者会在客户最慌的时候给出最不清楚的状态。

## 六、e8 与它暴露的脆点：绕开了，没修好

量纲探针第一版被两件事同时污染：

1. `captured_at` 原样带秒带时区，先撞格式声明（就是缺口 4），红的原因不是量纲；
2. 库里既有的 `150 / -10` 缩放后变成 `1.5`，把"全部值都很小"这个量纲判据的必要条件顶掉了，只剩"超范围"黄。

改成取 `conf_pct between 0 and 100` 的干净子集、时间 `strftime("%Y-%m-%d %H:%M")` 之后，稳定命中拒跑。但这是**绕开**：

> S5 的量纲判定要求"每个值都 ≤ hi/100"。真实客户库里只要躺着一个历史脏值，一次真实的百分制→小数切换就会被它掩盖。改成看中位数/分位数能救，但那等于把判据语义从"每个值都小"改成"整体分布下移"，属于改口径，不是改 bug。

已记入待办，留答辩后按真实客户数据定——现在改，等于拿一家模拟客户去定一个给所有客户用的阈值。

```powershell

```

期望：末尾 `RESULT: ALL PASS`、退出码 0，且中段能看到 `e8 … 量纲疑似缩小 100 倍` 那一行。脚本自带造景与清理，**可以连跑**；排查时加 `--keep` 保留 `probe` schema 与临时登记。

单独跑判据（不造景，只看干净态）：

```powershell

venv\Scripts\python.exe -X utf8 scripts\check_source_values.py --client=client_mes --dsn=postgresql://postgres:postgres@localhost:5432/fde_client
venv\Scripts\python.exe -X utf8 scripts\check_data_contract.py --allow-quarantine
```

旧客户回归（不带参数即走 `client_a` 的两份 CSV 样本）：

```powershell

venv\Scripts\python.exe -X utf8 scripts\check_source_values.py
```

## 八、这一轮没覆盖的

1. **只有两家客户，而且一家是模拟库**。K-5（两家真实客户口径打架、登记成对方的 done/cancelled 之后折法对不对）仍未测——这轮只证明了"未登记会拒跑"，没证明"登记对了折法就对"。
2. **通道只覆盖了库直连与 CSV**。登记里 `observed_via` 有 `http` 分支，但没有一家客户走分页接口做换源验收（`mock-mes` 的 `/v1` 只是演示用的）。
3. **反例只造结构面与值域面**。权限（只读账号拿不到某张表）、字符集、时区差、编码（GBK 导出的 CSV）都没造——这些会让判据在"取数"阶段就错，而不在"判断"阶段。
4. **抽样仍是前 200 行**（已按主键序）。大表怎么抽样、抽样结论能不能代表全表，没定口径。
5. `check_source_values.py` 的 `--dsn` 只在 `observed_via` 为 db 类时必需；非 db 客户传了也无害（这条没写进脚本 help，容易让人以为必须传）。
6. S5 量纲的脆点（第六节），已知未修。
7. **复现只在本机验过**：第七节的四条命令逐条实跑并回读输出，但"新机器从 `bootstrap.ps1` 起能一路复现"这件事没有第二台环境可证。前置条件（PG 18.6、`fde_client`、venv 依赖）都写在第七节开头，缺一样就该在第一步报错，而不是跑到判据里报绿。
