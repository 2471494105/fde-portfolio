## 一、问题：一句话能骗过所有人

`DOC-57` 落完 K-5 之后，`status_policy.json` 里躺着这么一行：

```
"unsupported_checks": [
  "work_order_state_stage_conflict（我方『已完成但看板未关闭』）：Odoo 的 stage_id 是看板列不是终态……"
]
```

它写在文档里很好看：有 id、有理由、有代价说明。但它保证的只是「有人写下了不适用」，保证不了任何一件下面的事：

1. **id 根本匹配不上**。id 和散文塞在同一个字符串里，机器拿 `"work_order_state_stage_conflict"` 去比会失败——这行「声明」在机器眼里等于不存在，只对人有效。
2. **声明和执行没有连接**。判据照样跑，每天出一批假红；声明写得再对，也没人把它落到代码里。
3. **反过来也成立**。判据其实早被删了或早就不跑了，声明还挂着，于是文档说「已声明不适用」，读者以为有人管着，实际什么都没发生。

这三条同一个性质：**它不可证伪**。`DOC-53` 那句「判据在跑、观测面错了、结论纯装饰」，在声明这一层是「声明在写、没人执行、读者以为管着」。

## 二、决定

### 1. 声明改成 id → 理由

```json
"unsupported_checks": {
  "work_order_state_stage_conflict": "Odoo 的 stage_id 是看板列（可随手拖动），不是终态……"
}
```

id 必须能机器匹配，理由给人读。v2 的字符串数组**显式拒绝**（抛 `PolicyNotRegistered`），不做静默兼容——兼容等于把「只有声明」的旧状态再养一遍。

### 2. 顶层加 `checks` 登记表

每条判据登记 `what`（判什么）、`reads`（读哪些字段）、`board_closed_states` / `closed_labels`（判据用到的词表）、`enforced_where`（实现落点）、`counterpart`（外部对照，比如 mock-mes 页面里那条行内红标）。没有登记表的 id 一律 `UnknownCheck`，不是「大概没见过就这么叫吧」。

### 3. `run_check` 是唯一入口，返回里带 `ran`

`app/ds/checks.py` 的 `run_check()` 先问 `check_applies()`：

- 声明不适用 → 直接返回 `not_applicable`，`ran=False`、`checked=0`，**根本不读 rows**（连 `rows=None` 都不崩）；
- 未声明 → 调用实现，`ran=True`，返回 `checked` 与 `problems`。

`ran` 这个位是整件事的关键。「读了一遍然后忽略结果」和「根本没读」在报告里长得一样；只有把它写进返回值，判据才有东西可判。登记了却没人实现时**抛错**，不返回 `ok`——把「没跑」说成「通过」是最坏的一种绿。

### 4. 加一条对所有客户都适用的判据，作对照组

第一次跑 E 判据就红了，红得有价值：

```
[fail] E_unsupported_checks
        - client_b_odoo 把所有登记判据都声明不适用——这家客户身上没有任何一条判据在跑
```

当时登记表里只有一条判据，B 又正确地声明了它不适用——于是 B 身上**一条判据都没有**。这不是 B 的错，是我的登记表缺了一条「与版面无关」的判据：`status_vocabulary_coverage`（库里冒出既不闭环也不已知未闭环的词就红）。它只问「这个词我认识吗」，对谁都适用。

两种处理方式，我选了后者：前者是把判据降成黄（本项目已有教训——判红会被整条关掉），后者是补一条真适用的判据。前者会让这条判据永远黄、永远被略过；后者让「这条不适用」和「这家客户没人管」能分清。

## 三、E 判据：静对账 + 动验证

- **静**：`unsupported_checks` 的 id 都在 `checks` 登记表里；有理由；登记表里每条判据都有 what / reads / enforced_where 和实现；不许所有客户把同一条判据全关掉。
- **动**：对每个登记客户、每条登记判据真调一次 `run_check`（`rows=[]`）。声明不适用的必须 `ran=False` 且 `not_applicable`；没声明的必须 `ran=True`。

动的那一层是这条判据的全部意义：静态对账只能证明字对上了，证明不了「没跑」。

## 四、实测（数字来自真表）

数据是 `fde_client` 的 60 张工单——`state` 与 `stage_id` 刻意做成了交叉表（五词 × 四列），所以「已完成但看板停在别处」真的存在。

| 动作 | 结果 |
|---|---|
| `client_a` 适用 → 真跑 | `ran=True`、`checked=60`、红 **19 条**（已完成 10 + 已取消 9） |
| `client_b_odoo` 声明不适用 | `ran=False`、`checked=0`、`problems=[]`；`rows=None` 也不崩（真的没读） |
| 同一批 60 行，只把声明去掉 | 立刻红 **19 条**——「不适用」挡住的正是每天 19 条假红，不是装饰 |
| 声明一个登记表里不存在的 id（`stage_conflict_v1`） | E 报「声明了一个没人能兑现的判据」 |
| 声明了不写理由 / 所有客户全关掉 | E 都报 |
| 把入口换成「永远 `ran=True`」 | E 报「声明没落到代码里，每天会造一批假红」 |

最后一条是判据的自证：**注入一个假入口，E 必须红**。判据只能证明自己会红，才配说别人是绿的。

## 五、代价与未决

- **证明到入口层，不到「所有调用路径」层**。E 验证的是「`run_check` 在不适用的客户身上没跑」。将来若有人绕过入口直接调实现（`work_order_state_stage_conflict(rows, spec, ctx)`），E 看不见。现在生产侧只有脚本，没有第二个调用点；一旦有，得把「只许走 `run_check`」变成 lint 或单测，不能靠约定。
- **`counterpart` 只是文本**。mock-mes 页面上那条行内红标（`work_orders.flag`，`state === "已完成" && stage_id !== "已关闭"`）和这边 Python 实现是两套代码，判定是否逐字等价没有交叉验证。谁改了一边，另一边不会响。
- **看板词表只有一份**。`board_closed_states: ["已关闭"]` 现在是全局的；将来若某家客户的看板列叫别的名字，要按客户登记，这是下一格（与 K-5 的 `vocab_fold` 同类问题：**词表属于客户，不属于判据**）。
- **`reads` 没有机器校验**。声明「这条判据读 state 与 stage_id」，但没验它真的只读了这两个字段。
