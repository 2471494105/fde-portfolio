## 一、三条判据，三种「说得出但守不住」

`DOC-58` 把「声明不适用」做成了可证伪的：声明了就必须真的没跑，跑没跑由 `run_check` 返回的 `ran` 位说清。但那条判据的完备性架在三个隐含前提上，每一个都能单独塌：

| 前提 | 塌掉的样子 | 本轮的判据 |
| --- | --- | --- |
| 所有人都从 `run_check` 进 | 有人直接 `import` 实现函数，`ran` 位根本不会被写，E 判据看不见 | F：AST 扫全仓库 |
| 看板关闭词是全局常量 | 换一家客户，看板列叫别的名字，判据照跑、红得毫无意义 | 词表挪进 `client_a`，缺了抛 `CheckNotConfigured` |
| 状态之外没有别的列参与判定 | `priority`、班组按字面比——数字比数字永远「能跑」，只是判错 | G：`judged_fields` 二选一 |

三个都是同一类毛病：**约定写在了文档里，代码里没有对应的失败位**。

## 二、F：只许走入口，得能扫出来

`app/ds/checks.py::bypass_problems(root)` 用 AST 扫仓库里每个 `.py`，报三类：

1. `from app.ds.checks import <实现名>` —— 拿到实现就绕过了 `check_applies()`；
2. 直接调用实现名（`work_order_state_stage_conflict(rows, spec, ctx)`）；
3. 访问 `_RUNNERS` 私有表。

扫描跳过 `.git`、`__pycache__`、`venv`、`.venv`、`out`、`node_modules`、`.pytest_cache`；**解析失败的 .py 也要报**——扫不了不等于没绕过，静默跳过就是把洞留在原地。

## 三、看板关闭词：属于客户，不属于判据

原写法 `board_closed_states: ["已关闭"]` 挂在判据 spec 里。它错在归属：**「哪一列代表已关闭」是这家客户看板的叫法**，跟「关单但看板没关是问题」这条规则没关系。换一家客户，规则不变、词变了。

改法：

- `client_a.stage_board_closed = ["已关闭"]`；
- 判据 spec 去掉词表，改 `requires_client_words: ["stage_board_closed"]`；
- 实现从 `ctx` 读词，**缺词直接抛** `sp.CheckNotConfigured`，不猜。

空词表的危害值得单说：`stage not in []` 恒为真，等于「所有 stage 都还没关」，一批看着像真问题的假红就出来了。所以缺词必须抛，不能给默认值。

**第一次改出过一个真实漂移**：`closed_order_labels`（哪些闭环词算「关单」）最初从 `closed_states` 推，把「已合并」也算了进来，红从 19 变 28。显式登记成 `["已完成","已取消"]` 的理由写进 spec：合并后看板跟着合并到的那张单走，拿它判这张单是把别人的看板算到它头上。

实测：

```
把 client_a 看板关闭词改成 ["进行中"]      19 → 15 条
单测里改成 ["待排产"]                       W1/W2 红、W3 不红
清空                                       抛 CheckNotConfigured，且 E 静层同时报「适用却缺词表」
"已合并" + 看板未关                        0 条
```

## 四、字段面：`priority` 与班组，二选一

`vocab_fold` 管 `state`，`requires_client_words` 管 `stage_id`，剩下的两列没人管：`priority`（0–3）与 `maintenance_team_id`。它们会进比较和分组，一旦按字面比，**不报错，只是判错**。这类错误最难发现，因为数字比数字永远「能跑」。

一手样本给了硬事实（`07_外部样本/odoo-maintenance-model.py`）：

```python
# 第 291 行
priority = fields.Selection([('0','Very Low'),('1','Low'),('2','Normal'),('3','High')])
# 第 307 行
maintenance_team_id = fields.Many2one('maintenance.team', required=True)
```

- `priority`：Odoo 四档、数值同序，与我方 `smallint 0–3` 同构 → 登记**恒等折法**，并在 `field_fold_note` 写明「只做恒等，不声称标签语义等价——那要在真数据上对齐，目前没有」。
- `maintenance_team_id`：Odoo 是 `maintenance.team` 记录的**整数 id**（`required`，默认值由 `_compute_maintenance_team_id` 从设备反推），我方是文本名 `TEAM-n`。**没有对方的团队字典就没法映射**，猜一个 id 只会让「归给哪个班组」静默错 → 登记进 `unsupported_columns`，理由写进 `unsupported_columns_why`（跟 `unsupported_checks` 一个道理：没有理由的「不可用」和「忘了做」看不出区别）。

顶层新增 `judged_fields: ["priority","maintenance_team_id"]`，G 判据 `field_fold_problems` 报五类：

1. 登记客户对被判字段**既没折法也没声明不可用**；
2. 折法是空表（等于没折）；
3. 声明不可用但没写理由；
4. `field_fold` 的键不在 `judged_fields`（折了一张没人看的表）；
5. `unsupported_columns` 里的字段不在 `judged_fields`。

实测：

```
G 判据对现有策略        空
撤掉 client_b 的两条     priority / maintenance_team_id 各报一条
抹掉理由                 报「没写理由」
真库 priority 观测值     0/1/2/3 全在折法键里
真库 team 观测值         TEAM-1/2/3 全在折法键里，折法是恒等
```

最后两条是数据侧交叉：折法写对了不等于覆盖住了真数据，所以拿 `fde_client.public.biz_work_order` 的 `distinct` 结果去比折法键集合，两边必须相等。

## 五、代价与未决

- **F 是静态扫描，不是运行时拦截**。`eval`/`getattr`/动态拼出来的调用扫不到。它把「约定」变成了「可失败的检查」，但不等于是强制。
- **G 只查「有没有说法」，不查折法对不对**。恒等折法是当前唯一能自证的选项（真实语义需要对方数据对齐）；若将来折法开始做真映射，G 还得加一层「折过去的值落在目标词表里」。
- **`priority` 的标签语义没对齐**。Odoo 写的是 Very Low/Low/Normal/High，我方 0–3 的标签没在一手文档里确认。恒等折法的前提是「两边都只是四档有序」，这个前提目前只有我方一侧可证。
- **`counterpart` 仍只是文本**（`DOC-58` 第 2 条未决），且 `reads` 无机器校验（第 4 条）。
