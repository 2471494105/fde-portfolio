# 同一条规则写了四遍：counterpart 从一句文本变成一次对账

> meta：2026-11-26 · 范围 `data/mapping/status_policy.json`（v4→v5）、`app/ds/counterpart.py`（新）、`scripts/check_status_policy.py`（A–H）、`scripts/verify_unsupported.py`、`tests/test_status_policy.py`（37 条）、`mock-mes/api/static/flag.js`（新）、`mock-mes/api/static/index.html`、`mock-mes/scripts/verify_ui.py` · 指纹 `code_hash=b5b70ab771e6`、`seed_hash=9caa1322fbfc`（agent 侧 `app/ds/*`、`scripts/*`、`tests/*` 不在 `BEHAVIOR_FILES`；mock-mes 不进评测指纹）· 上游 `DOC-59`（第五节未决：`counterpart` 只是文本）

## 一、四个写点

「关单了但看板没关」这一条规则，在本仓库里被写了四遍：

| # | 在哪 | 形态 | 会不会跟着别人变 |
| --- | --- | --- | --- |
| 1 | `mock-mes/api/static/index.html` `VIEWS.work_orders.flag` | JS，词硬写 `"已完成"` / `"已关闭"` | 不会 |
| 2 | 同页 `refreshKpi` 计数 | JS，**再写一遍**同样的条件 | 不会 |
| 3 | `mock-mes/scripts/verify_ui.py::expect_wo` | Python 期望值，词也硬写 | 不会 |
| 4 | `app/ds/checks.py::work_order_state_stage_conflict` | 治理判据（读登记词表） | 会跟着登记变 |

1、2 在同一页里各写一遍，是漂移的起点；3、4 是**同一规则的两个独立实现**，谁改了谁都不会响——这正是 `DOC-59` 留下的那条未决。`counterpart` 原来只是一句文本：「mock-mes/api/static/index.html 的 work_orders.flag」。文本不执行，所以它证明不了任何事。

## 二、做法

**把 JS 收成一份**：新建 `mock-mes/api/static/flag.js`，导出 `rowFlag`（行标）、`counts`（KPI 计数）、`judge`（按工单号列表）。页面两处都改为调它，词收进 `MES_WORDS` 一处。行为不变（`verify_ui.py` 全 `[ok]`，截图里 KPI 仍是「两套状态对不上 25」）。

**把 counterpart 拆成结构**：

```json
"counterpart": {
  "file": "mock-mes/api/static/flag.js",
  "entries": ["rowFlag", "counts", "judge"],
  "words_client": "client_a",
  "expectations_in": ["mock-mes/scripts/verify_ui.py"],
  "expectation_func": "expect_wo",
  "allowed_tags": ["关单未关板", "关板未关单"],
  "compares": "red",
  "extra_rules": ["关板未关单（看板已关但关单时间为空）：页面判橙，Python 侧没有对应判据——登记为已知差异，不是悄悄漏判"]
}
```

**判据 H 做四件事**：

1. 静-1 入口真的存在：`entries` 里每个名字都得在文件里找得到 `function <name>(`；
2. 静-2 词逐字对齐：跑 `node` 读 `MES_WORDS`，与「判据 spec 的 `closed_order_labels` + 客户登记的 `stage_board_closed`」比——两套词表各写一份，就是漂移的入口；
3. 静-3 期望值不许自造词：从 `verify_ui.py::expect_wo` 里抓中文字符串字面量，必须 ⊆ 登记词 ∪ `allowed_tags`；
4. 动：同一批行喂两侧，**按工单号比集合**。不比条数——19 条红对 19 条红，可能是一换一。

`node` 不在 PATH 时 H 报「跑不了就是没验」，不当通过；`--skip-db` 时只跑静态三项，并在输出里写明「动态对账没跑」——同一个道理，跳过要留痕。

## 三、H 第一次跑就红了，红得对

第一次跑 H，红了两件事：

```
flag.js 的 closedOrderLabels = ['已完成']，登记的是 ['已完成','已取消']
verify_ui.py::expect_wo 里出现未登记的词 '已取消'
判据与页面对不上同一批工单：判据多 6 个号（后为 9 个，全貌见下）
```

真数据：`已完成` 且看板未关 10 张，`已取消` 且看板未关 9 张。T16 已经把「取消的单也算关单」写进判据（`closed_order_labels: ["已完成","已取消"]`），**但页面只认「已完成」**——所以页面上少标了 9 行红，KPI 也少算 9。这类差异过去没人能发现：页面看起来正常，判据也正常，只有把两侧摆到同一批工单上才看得见。

修法是让页面认同一套词（`MES_WORDS.closedOrderLabels` 加 `已取消`），期望值同步。修完：

```
页面 red 19 / amber 6；判据 red 19
两侧工单号集合相同（差集为空）
KPI：两套状态对不上 25 / 60（红 19 · 橙 6）
```

**顺带确认一条登记过的差异**：`关板未关单`（看板已关但 `closed_at` 为空）页面判橙 **6 张**，Python 侧没有任何判据管它。这条不是漏判吗？——它登记在 `extra_rules` 里，并且验收里钉住了「真数据上确实存在 6 张」。登记过的差异和没人管的差异，区别就在这里：前者说得出来、数得出来，后者只能等出事。

## 五、代价与未决

- **第三份仍是独立实现**。`verify_ui.py::expect_wo` 没被合并进 `flag.js`（它在 Python 侧、要给 DOM 当期望值），H 只能保证它的**词**与登记一致，保证不了它的**条件**一致。它有另一层保护：每次 `verify_ui.py` 跑完，它的期望值与页面逐行比过；而页面与判据由 H 对账——所以「期望值 ↔ 判据」是被这两步间接钉住的，不是直接。
- **H 依赖 node**。这是运行时依赖，不是构建依赖；缺了会红（不是跳过），但 CI 里若没装 node，这条判据就永远红着——届时要么装 node，要么把 `judge` 用纯 Python 重写（那就又回到两套实现，得靠 H 自己抓自己）。
- **只覆盖这一条规则**。`status_vocabulary_coverage` 的 counterpart 登记为 `why_text_only`（同仓两个取数路径，没有第二套代码可比），H 对这类只要求「说出为什么不对账」，不要求对账。
- **橙的那条（关板未关单）仍无 Python 判据**。它现在是登记过的差异；要变成判据，得先决定「看板已关但关单时间为空」算事故还是算进行中（这动摇 K-3 的时间轴口径）。
- **`reads` 仍无机器校验**（`DOC-58` 第 4 条）。H 只验「判据与页面同名」，不验「判据只读了它声明的字段」。
