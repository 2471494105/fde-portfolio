# 不兜底：工位契约、缺口认领、整改单闭环

> 一句话：**「把脏数据接上」不是治理，「说清谁没交、什么时候交、交完有没有真修好」才是。**
> 后端不做推导、不给默认值、不猜别名；给不出工位就判红退回产线补。
> 本篇记 T20（G4/G5/G6）的设计、实测数字和它拒绝掉的那条路。

## 一、被否掉的那条路：设备反推

现场三种写法：工单 `station_no` = 「1号工位」，缺陷 `work_station` 一列混着「产线A-01」和「4号线」，主数据是「产线A-01」。

最省事的接法是拿 `md_device.work_station` 反推：设备台账知道哪台设备在哪个工位，工单又有 `equip_no`。实测这条路的成绩：

| 检查 | 结果 |
|---|---|
| 工单写的工位号 = 该设备所属工位 `seq` | **20 / 60** |
| 与之矛盾 | **40 / 60** |
| 缺陷记录能由设备还原 | 97 / 302 |

WO-2026-0002 写「2号工位」，它那台 CX-102 却在 `产线A-01`（第 1 工位）。两边都不可信的时候，用一边去修另一边，再把结果写成事实——那不叫清洗，那叫替客户编数据。而且「1号工位」在 A/B/C/D 四条产线上都成立，任何一次选择都是无据的。

所以这条方案被否掉，理由不是「实现麻烦」，是**它会让结论静默错**：修完以后 60 行全绿，没人再知道其中 40 行是猜的。

## 二、id 进契约，不进映射表

- `md_station` 增加 `station_id`（`S-A01`…`S-D04`，16 行，唯一），`station_no` 仍是客户对外的名字。id 的作用是**改名不动外键**，不是拿来当展示字段。
- 明细侧（`biz_work_order` / `biz_defect_record`）增加 `station_id`、`prod_line`，**当前全为空**——这不是漏填，这就是契约违约的现场。
- 解析只有两条路，全部查字典，不推导：

| 输入 | 处理 |
|---|---|
| 给了 `station_id` | 在 `md_station` 里查得到 → 通过；查不到 → 红 |
| 给了 `prod_line` + 工位文本 | 文本正好是业务码（如「产线A-01」）→ 查字典，并核对产线是否说反，说反 → 红 |
| 同上 | 文本含「工位」且能取到数字 → 用 `(line_no, seq)` 唯一匹配，0 条或多条 → 红 |
| 同上 | 文本是「4号线」这类产线名（既不是业务码也没有「工位」二字）→ 红 |
| 只有工位号没有产线 | 红：同一工位号在四条产线上都成立 |

一个真跑出来的细节：最初版本对「4号线」取数字 4，会解析成 `产线A-04`——**错得还很像对的**。所以加了「文本必须像工位」这一条（业务码，或含「工位」二字），单测里钉死。

## 三、判据 I：违约要带单号

`scripts/check_station_contract.py` 输出的是可指认的东西，不是「数据质量不佳」：

```
I0_registry_selfcheck  ok
I_station_contract     fail
  - wo_station_identity: 违约 60/60，样例 WO-2026-0002, WO-2026-0004, WO-2026-0005…
  - defect_station_identity: 违约 302/302，样例 1001, 1002, 1003…
J_gap_claimed          warn
  - gap_wo_station_line [warn] 认领中：60 行违约，到期还有 7 天（2026-12-03）
```

判据 I 同时检查契约自己的完整性：`md_station` 没有 `station_id` 列、id 不合 `S-[A-D]\d\d`、id 重复、16 行变了——都先判红。**契约本身坏了，下游再对也没意义。**

## 四、判据 J：缺口要有主、有期

红出来的东西不能只活在终端里。`data/mapping/data_contract.json` 的 `field_gaps` 登记「缺什么、谁补、什么时候补、证据多不多」：

| 状态 | 条件 | 输出 |
|---|---|---|
| 红 | 没写责任方 / 没写到期日 / 已过期且违约行仍 > 0 | 计入 fail，exit 1 |
| 黄 | 有主、有期、未过期、违约行 > 0 | 不判死，但必须出现在输出里 |
| 闭合 | 违约行 = 0 | 自动闭合，**不需要人签字说修好了** |

「已认领」不等于容忍：它有责任人、有期限、有证据，到期自动转红。用 `--today=2026-12-10` 复跑，两条缺口都从黄转红——「暂时」不会变成永久，是因为判据不认「暂时」这个词。

## 五、整改单：纸面不能关闭数据问题

`gov_remediation_order`（`sql/012_remediation.sql`）：

```
rm_no / contract_id / table_name / field_name / violation_count / samples
owner / due_on / state(open|closed) / created_at / closed_at / close_evidence
```

- `raise`：违约 > 0 的契约开单；同一契约同一张表只允许一张 open（部分唯一索引），重复跑是更新数字，不是再印一张纸。
- `close`：**复跑违规归零才允许关闭**，并把「复跑时间 + 违规 0」写成关闭证据；还剩 60 / 302 行时直接拒绝。
- 已落库的两张单：`RM-20261126-01`（工单 60 行）、`RM-20261126-02`（缺陷 302 行），责任方「产线计划员」，到期 2026-12-03。

完整闭环在 `scripts/verify_station_governance.py` 里跑（七段，全真数）：

```
S1 前态        工单 60/60、缺陷 302/302；缺口黄（还剩 7 天）
S2 开单        两张；再跑是 updated 不是 created
S3 纸面关闭    还剩 60 / 302 行 → refused
S4 补 1 行     给 WO-2026-0001 补 prod_line='产线A' → 违约 59，该单解析为 S-A01；跑完撤回
S5 probe 闭环  3 行小表：2 行违约 → 开单 → 未修拒绝 → 补全归零 → closed，
               证据「2026-11-26 22:19:59 复跑 3 行，违约 0（判据 I），据此关闭」；schema 已清
S6 到期反例    以 2026-12-10 复跑，两条缺口转红
S7 收尾        真库回到 60/302，prod_line 非空 0 行；整改单数字刷新为 60/302
```

S7 顺带逮到一个真问题：S4 里跑过一次 close，它把单子上的 `violation_count` 写成 59，撤回数据后单子还写着 59——**存下来的数字会跟现场漂**。所以收尾必须先刷新再读。这和 T18「同一规则写四遍」是同一类毛病：任何被复制的事实都要有人盯着。

## 七、这次没做什么

- **后端不修数据**：不做设备反推写回，不做别名表擦屁股，不给 `station_id` 默认值。
- **302 行缺陷的其余脏值**仍零判据：`conf_pct` 越界 2、未来时间 1、`lot_no` NULL/空串各 1，页面只着色。它们属于「值域/时间轴」判据，不是工位契约。
- **报警 120 / 检验 80 / 维修 40** 没有接工位契约：目前没有「必须知道工位」的业务理由，硬接会造出一批假红。
- 门禁强度（不合格数据不许入库）仍不在本项目范围——现在做到的是「判红 + 退回 + 有单可追」，不是「拦在库门口」。

## 八、遗留

1. `station_id` 谁来写？真实项目里要产线系统改造或采集端补字段；本轮只证明契约和判据成立，写入侧留给产线配合。
2. `data_contract.json` 与 `sql/004`、`011` 是两处描述（登记表 + DDL）。判据查的是库，查不出两边文字漂移；要更严就得让 DDL 生成登记表，或者反过来。
3. 期限是人为定的（2026-12-03，7 天）。到期后会红，但「谁来延期、延期要不要审批」没有流程——那是变更管理，不在本轮。
