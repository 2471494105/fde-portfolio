# 可观测性：判据跑没跑、库新不新、接口快不快

> DOC-63 · 2026-11-26 · 治理线 T21
> 前一篇：`DOC-62`（不兜底）。本篇只做一件事：把「判据每天都在红」这件事本身变成可观测对象。

## 一、为什么现在做

到 T20 为止，治理线有 8 条判据（A–H）、1 条工位契约判据（I/J）和 1 张整改单表。它们的共同问题不是判得准不准，而是**没人知道它们跑没跑**：

- 判据要人开终端敲命令。今天跑了不等于明天跑了，跑失败了也不一定有人看输出。
- 判据的结果停在 stdout。上一轮红 362 行、这一轮红 362 行，中间有没有变化要靠记忆比。
- 库里的数据是不是新的，没有任何一页能回答。`biz_work_order` 最新一条是 `2026-01-18`，`biz_defect_record` 有一条 `2027-01-01` 的未来时间——这两件事在任何页面上都不显示。
- 接口慢不慢、错不错，只有人肉体感。

这四件事同一个性质：**结论在，证据不在**。可观测性补的正是证据，而不是再加一条判据。

## 二、判据运行台账（`gov_check_run`）

`mock-mes/sql/013_observability.sql` 建表：

| 列 | 说明 |
|---|---|
| `run_id` | `bigserial` 主键 |
| `check_id` | 判据/契约 id（`station_contract` / `status_policy`） |
| `ran_at` | 运行时刻（`timestamptz`） |
| `duration_ms` | 耗时 |
| `status` | `ok` / `warn` / `fail` / `error` 四态，白名单校验 |
| `red_count` | 红行数，**口径随 check**（见下） |
| `dataset` | 观测面（`fde_client @ fde_client` / `work_orders @ fde_rag`） |
| `code_hash` | 跑这次时的代码指纹，取 `app.meta.code_hash()`，失败降级 `NULL` |
| `details` | `jsonb`，含 `red_metric` 与判据自己的分解 |

索引 `ix_check_run_recent(check_id, ran_at desc)`。权限靠 003 里的 `ALTER DEFAULT PRIVILEGES` 自动给 `ro_reader` SELECT（已核验 12 行权限），页面才能用只读账号看到台账。

`fde-diagnosis-agent/app/ds/runlog.py` 提供三个函数：`record()`（写一行，返回 `run_id`）、`latest()`、`staleness_hours()`（**从未跑过返回 `None`，调用方必须当红**）。

两条判据脚本改成默认落台账、加 `--no-record`：

| 判据 | `red_count` 口径 | `details.red_metric` |
|---|---|---|
| `check_station_contract.py` | 违约行合计（工单 + 缺陷） | `violating_rows` |
| `check_status_policy.py` | 失败判据条数 | `failed_checks` |

两种口径不能统一成一个数，因为「一条判据失败」和「362 行违约」不是同一个量，混成一个数字以后趋势线没有意义。

实测前两行（第一轮）：

```
run_id=1  station_contract  fail  red=362   95 ms
run_id=2  status_policy     ok    red=0   1546 ms
```

验收时又各跑一次，台账变 4 行：`station_contract 362/88 ms`、`status_policy 0/1565 ms` 各两条。**同一判据跑两次就该有两行**——台账是只增不减的，`silent` 看的是最近一次（`latest`），不是「有没有过记录」。页面因此显示「共 4 条」。

### 一条硬规则：写台账失败要出声

`record()` 写不进去时打 `stderr`，不静默。理由很直接：观测少一条，不能让结论变绿。同理，`staleness_hours()` 返回 `None`（从未跑过）在页面上按「静默判据」计数，不按「0 小时前跑过」处理。

## 三、接口指标与数据新鲜度（`mock-mes/api/obs.py`）

**接口指标**：`WINDOW=300` 的 `deque` 采样 + `threading.Lock`（uvicorn 单进程多线程，采样是写共享结构，必须有锁）。`record()` 在中间件里调用，跳过 `/v1/obs*` 自身——否则读指标会污染指标。`api_snapshot()` 输出 `p50/p95/max`、`2xx/3xx/4xx/5xx`、最慢 5 条、`top_paths`。响应头带 `X-Resp-Ms`，单次请求也能眼看。

**数据新鲜度**：`FRESHNESS` 白名单 9 张表——业务 5 张（带事件时间列）、治理 2 张、主数据 2 张（**无时间列，显式标 `None`**，不误报）。`freshness(dsn)` 返回 `rows/latest/age_hours/stale/future`；`_STALE_HOURS=24`。

`future` 这个标记是刻意的：`age_hours < 0` 说明库里有未来时间，那不是「数据很新」，是脏数据。只看 `age` 会把 `2027-01-01` 读成「-849 小时，非常新鲜」，正好是反的。

**运行台账读数**：`runs(dsn, limit)` 返回最近若干次 + 每条判据的 `hours_since` / `silent`（`>24h` 未跑为真）。

## 四、接口与页面

`api/app.py`（version 3.0）新增：

| 路由 | 作用 |
|---|---|
| `GET /healthz` | 真连库（`select 1`），失败 `503`。不是进程活着就算健康 |
| `GET /v1/obs/summary` | 一次取全 `api + freshness + runs`，页面首屏只打这一枪 |
| `GET /v1/obs/api` | 仅接口指标 |
| `GET /v1/obs/freshness` | 仅新鲜度 |
| `GET /v1/obs/runs?limit=` | 仅运行台账 |

中间件 `observe()` 记样本；`/v1/obs` 路由**必须定义在 `/v1/{name}` 之前**，否则会被通用分页路由吞掉（已经如此）。`TABLES["check_runs"]` 复用通用分页，但走 `DESC`——台账页要看最新的在上面。

页面加第五页「判据运行」：7 列（运行时间 / 判据 / 结果 / 红 / 耗时 / 观测面 / 标记），结果着色 ok 绿 / warn 黄 / fail 红 / error 灰；KPI 一行读 `/v1/obs/summary`，输出：

```
运行 4 次 · 最近 1.1 分钟前 · p95 170.6 ms · 4xx/5xx 31（静默判据 0 · 陈旧表 4 · 未来时间 1）
```

`陈旧表 4 / 未来时间 1` 不是猜的：`biz_work_order` 最新 `2026-01-18`（7497.7 小时）、`biz_defect_record` 有 `2027-01-01`（-849.3 小时）。KPI 把它们变成一句能读的话，而不是埋在表里。

## 五、验收

`mock-mes/scripts/verify_obs.py` 六段（O1–O6），实测全过：

```
O1 /healthz 连库        82 ms
O2 请求计数在涨          1 → 6
O2 读指标不进样本        6 → 6
O2 p95 有值            84.7 ms
O3 工单表被标陈旧        2026-01-18 / 7497.7 h
O3 缺陷表被标未来时间     2027-01-01 / -849.3 h
O3 主数据无时间轴不误报   md_device 无时间列
O4 30 小时没跑 → silent  30.0 h / True
O4 刚跑过的不 silent     0.0 h
O5 --no-record 不写台账  2 → 2
[ALL OK]
```

`verify_ui.py` 从 9 组扩到 10 组，第五页逐行对账全过：行数 4、列数 `(7,7)`、页脚「第 1–4 条 / 共 4 条」、着色 `['row-red','row-green','row-green','row-red']`、标记 `[['红'],['绿'],['绿'],['红']]`、NaN 泄漏 False、控制台 0 报错；**期望值从 `/v1/check_runs` 现取，不写死**，所以台账多跑几次不会假红。侧栏五个计数 `48 302 60 2 4`。

### 顺带查出的一个真 bug：`text()` 被 `<b>` 截断

新加的断言「KPI 有 p95 与静默计数」一开始是红的，取到的 KPI 文本只有 `运行 2`。查下来不是页面没渲染，而是 `verify_ui.py` 的 `text()` 用非贪婪正则取 `id="kpi"` 的内容，遇到内层 `<b>…</b>` 就在第一个 `</b>` 前停住——**之前所有 KPI 断言比的都是被截断的字符串**（好在只判了非空/空，没造成假绿）。改为对整个 `<span id="kpi">…</span>` 段取内容再匹配，同时保住 KPI 的加粗排版。

这说明一件事：**验收脚本自己也是代码，也会截断证据**。断言能过不等于它读到了它以为读到的东西。

## 六、没做的与风险

1. **4xx 未拆路径**。当前 KPI 显示 `4xx/5xx 32`，但 `obs.py` 只统计总数和 `top_paths`（不带状态码），所以答不出「这 32 个是静态资源 404 还是参数错」。要看就得在样本里加状态码维度，本轮没加，记在这里而不是留在印象里。
2. **阈值 24 小时是拍的**。按表分别定（业务表 6 小时、主数据 7 天）更合理，但要先知道客户同步频率，本轮没定。
3. **指标只在内存**。进程重启归零；`total_since_start` 会说明这件事（`in_window` 与它不同），但跨重启趋势没有。写库要引入采样表，属另一个量级。
4. **`/healthz` 只证明库能连**，不证明判据在规定时间内跑过——后者靠 `runs` 的 `silent`，两者刻意分成两个信号，不合并成一个绿灯。
5. **没有告警通道**。静默判据为 1 时页面上是黄的，但没人看页面时等于没有。这一条与 `DOC-44` 的结论一致：先有告警而没有处理人，比没有更糟。

## 七、三条自答（答辩口径）

- **这东西和判据有什么不同？** 判据判断数据对不对，可观测性判断**判据自己有没有在工作**。前者红说明库有问题，后者黄说明**没人检查库**——后者更危险，因为它是静默的。
- **凭什么相信 KPI 里的数字？** 每个数都有一个可复跑的验收段：`verify_obs.py` 的 O1–O6 对应连库 / 计数 / p95 / 陈旧 / 未来时间 / 静默 / 不写台账。
- **为什么不干脆做成 Prometheus？** 这个 demo 的价值是「判据的运行台账」这一层业务语义，不是通用指标采集。通用采集器我接得起来，但它不知道 `station_contract` 的 362 行意味着什么。
