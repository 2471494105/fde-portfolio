# 页面染了色，判据却沉默：缺陷字段面补 K

> DOC-64 · 2026-11-26 · 治理线 T22
> 前一篇：`DOC-63`（可观测性）。这一篇补的是「页面上标红的 5 行，Python 侧一条判据都没有」。

## 一、问题：颜色是页面自己判的

缺陷页从 T10 起就把脏行染了色——红=置信度越界、橙=未来时间、灰=批次空。截图上一眼能看到第 4、5、6、8、10 行：

| rec_id | 现象 | 页面标签 |
|---|---|---|
| 4 | `captured_at` = `2027-01-01 08:00` | 橙 · 未来时间 |
| 5 | `conf_pct` = 150 | 红 · 超范围 |
| 6 | `conf_pct` = -10 | 红 · 超范围 |
| 8 | `lot_no` = 空串 | 灰 · 批次空串 |
| 10 | `lot_no` = NULL | 灰 · 批次 NULL |

这五行在页面上是「问题」，在治理结论里**什么都没发生**：`check_data_contract` 的 A3 只管状态词，`check_station_contract` 的 I 只管工位，`check_status_policy` 的 A–H 只管工单。缺陷字段面一条判据都没有。

这就是 `DOC-60` 的同一种病换了个页面：规则写在 JS 里，判据沉默。区别在于工单那边至少有个「页面 vs 判据」的 H 在对账，缺陷这边连对账对象都没有。

## 二、三条规则与它们的口径

登记在 `data/mapping/field_rules.json`，实现是 `app/ds/field_checks.py` 的三个纯函数。

**`conf_pct_range`（0–100，区间闭合）。** 边界值 0 与 100 合格，100.5 与 -0.5 越界——区间开闭是口径，不是手感，所以写进登记而不是写进比较式里。空值不按越界处理：那是「没给」不是「给错」，混一起会让人去改一个本来不存在的值。

**`captured_at_not_future`（判定时刻可注入）。** 未来时间不是「数据很新」：它会让增量水位跳到未来，之后每一条新数据都被判成「已灌过」而静默停摆（`DOC-40` 踩过这个坑）。这条判据要拿「现在」比，而页面取浏览器钟、判据取库钟，两个钟各走各自的，边界行就会随机红/绿——**随机在验收里等于假红**，比没有更坏。所以两侧都接受注入：`--now=2026-11-26 23:00:00`，对账时喂同一个字面值；默认用库里的 `now()`，因为「库里那一刻」才是数据该被判断的口径。

**`lot_no_blank_split`（NULL 与空串分开）。** 契约 R2 的「空串≠缺失≠0」在这里落地。两者都红，但修复动作不同：NULL 要去查映射与源端（源端压根没给这一列），空串要去查录入。合并成一个「空」就是把 R2 又抹平一次——所以判据返回里 `null_ids` 与 `empty_ids` 是两个列表，页面也是两个标签、两种灰。

## 三、为什么另起一族，不塞进 `checks.py`

`app/ds/checks.py` 的 `run_check` 是为状态词折法设计的：它的 ctx 是客户词表、看板关闭词这些**按客户不同**的东西，`check_applies()` 判的也是「这道判据对这家客户成不成立」。缺陷这三条没有客户差异——0–100 就是 0–100。硬塞进同一个 registry，E 判据会拿工单行去喂它们（字段根本不存在），判出来的东西没有意义。

所以分成第二族，但**不放松约束**：

- 同一份登记驱动（`field_rules.json`），同一个入口 `field_checks.run()`，返回值同样带 `ran`；
- 登记了没实现 → 抛 `UnknownCheck`，不返绿；
- F（入口绕过）的 AST 扫描范围扩到这一族——`impl_names` 现在同时收 `checks._RUNNERS` 与 `field_checks.RULES`，绕过哪一族都报。实测改完 F 仍 `ok`、真仓库 0 命中。

## 四、对账：按 rec_id 比集合，不比条数

`scripts/verify_defect_fields.py` 五段：

| 段 | 验什么 | 实测 |
|---|---|---|
| K1 | 登记↔实现（每条规则有实现、入口通、未登记必抛） | 4/4 ok |
| K2 | 阈值同源：`flag.js::DEFECT_LIMITS`（node 读出来）vs `field_rules.json` | `confMin 0 / confMax 100` 相等 |
| K3 | 同一批 302 行喂两侧，四类集合逐个比 | 页面 `conf=2 future=1 lot_null=1 lot_empty=1 violating=5`；判据同；编号 `['4','5','6','8','10']` 一致 |
| K4 | **反例**：把 conf 上界改成 200，K3 必须报 | 报「conf: 页面多 ['5']，判据多 []」 |
| K5 | 台账：真跑一次，`gov_check_run` 多一行 | `defect_fields / fail / red 5 / 109 ms`，`run_id=8` |

为什么比编号不比条数：5 对 5 可能是一换一（页面漏了 10、判据多判了 20）。判据要能说出「哪一行两侧说法不同」，才在评审席上被追问得住。

为什么 K4 是必需的：一段对账代码如果从来没红过，它跟 `assert True` 没区别。K4 用真实 302 行、把阈值改错一处，让「集合不等」这条路径真的跑一次。

## 五、顺带拆掉的第三份阈值

`mock-mes/scripts/verify_ui.py` 的 `expect_defect` 里原来写着 `100` 与 `0` 两个字面量——加上 `flag.js` 一份、`field_rules.json` 一份，同一条口径三个写点。现在 `expect_defect` 从 `field_rules.json` 读 min/max，写死的那份没了。

它仍然是一份独立实现（判定逻辑没共用），这一点与 `expect_wo` 同性质：`DOC-60` 记过「H 只保它的词、保不了它的条件」。现在它的条件是「阈值从登记读」，比原来强一档，但**规则结构仍是两份**，写在这里而不是留在印象里。

## 六、页面那一行 KPI

缺陷页原来只有图例、没有 KPI——脏行要一页页翻着数。现在顶部一行：

```
脏行 5 / 302（越界 2 · 未来 1 · 空批次 2）
```

和行标同一份实现（`MesFlag.defectCounts`），不是页面另算一遍。`verify_ui.py` 加两条断言：脏行数与三类计数都要与接口现算的值相等（**不是写死 5**——数据修好后它会自动变 0）。

## 八、没做的

1. **只覆盖页面已经染色的三类**。缺陷表其余字段（`is_ok` 与 `judge` 的语义关系、`work_station` 混「4号线」）没有新判据——前者属值域抽查（S5）的量，后者已由工位契约 I 判红（302/302）。
2. **`conf_pct` 换成 0–1 基准这条判据发现不了**：它只判「这个值在不在 0–100」，量纲整体挪位是 S5 的活（`DOC-56` 的中位数判据）。已知边界，不是遗漏。
3. **边界行仍可能两侧不一致**：注入 `now` 解决了「各自取钟」，但两侧的日期表示不同（Python `datetime` +08 vs JS 字符串比较）。数据离判定时刻远时无影响，将来若有秒级边界数据要加容差——那时再加，现在加等于给未知问题留一个调参口。
4. **没有接进每日巡检**（`data_health`）：本判据目前仍然要人跑。可观测性那边有 `silent > 24h` 能看出它多久没跑，但「自动跑」与告警不在本项目范围（与 `DOC-44` 一致）。

## 九、答辩口径

- **这条判据和页面是什么关系？** 页面是给人看的，判据是给结论看的；两边是同一条规则的两个实现，`verify_defect_fields.py` 按编号对账，改错一处立刻红。
- **凭什么相信这 5 行是真的？** 每行都能指到库里的具体值：`rec 5 conf_pct=150`、`rec 4 captured_at=2027-01-01`、`rec 10 lot_no IS NULL`，一条 SQL 可复现。
- **空批次为什么要分两种？** NULL 是源端没给（查映射），空串是给了但是空的（查录入）。合并成一个「空」，修复动作就分不清该找谁。
