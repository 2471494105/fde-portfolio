# DOC-65 · 中控台与推送：把「判据红了」变成「一件要人处理的活」

> T23 / 2026-11-26 / 入口 `http://127.0.0.1:8021/console`（同一个进程，不另开服务）

## 一、为什么要有这一屏

判据红了只证明「数据不对」，它回答不了客户的下一句：**「那谁来做、做到什么算完？」**

`DOC-63` 之前，答案是「没人知道」：判据结果停在 stdout，整改单要人手工开，页面是只读的作业视图。于是出现最坏的一种状态——**系统很诚实，但没人在听**。

中控台只补这一件事：把「红」变成一条有身份、有责任方、有轮次、能被认领、只能被复跑关掉的事件。它不是第二个判定系统，判据仍然是唯一裁判。

## 二、形态：同一进程里的第二张皮

- 地址 `/console`（HTML）与 `/v1/alerts`（JSON）都在 **8021** 的同一个 uvicorn 进程里，同一套 `ro_reader` 只读账号；
- 页面是深色（原 B 风格），作业页保持浅色 A 风格——**两套美术、一套数据**；
- 页面**只读**：没有关闭按钮、没有「标记已修复」。认领与关闭是脚本动作（`raise_alerts.py --ack/--close`）。

理由：按钮会让人以为点一下问题就解决了。修没修好只能由「同一道判据再跑一次、归零」证明。

## 三、事件不是告警：三个字段决定它能不能活

表 `gov_alert`（`mock-mes/sql/014_alerts.sql`）：

| 字段 | 作用 | 不这样会怎样 |
|---|---|---|
| `dedup_key` | 同一件事的身份：`<判据>:red` / `<判据>:silent` / `<整改单>:overdue` | 每次运行都插一条，362 行刷三周，最后所有人都静音 |
| `seen_count` | 这件事存在了几轮 | 和「推了几次」混成一个数，就看不出「没修」还是「没复跑」 |
| `state` | `open → acked → closed` | 一条 `closed` 里写「已修复」，等于把判定权交回给人 |

唯一索引 `(dedup_key) where state <> 'closed'`：同一件事同时只许一条活着；关掉之后同一 key 再出现，会新增一条——**「复发」本身变成可数的**。

## 四、三条克制规则（写在 `app/ds/alerts.py`，不在页面的 if 里）

1. **同一批红再跑一次不推。** 只有「从绿转红」或「红行里出现了新编号」才推；其余只涨 `seen_count`。
2. **变绿写「复跑归零」，不写「已修复」。** 关闭原因固定为 `复跑归零（0 行违约，未经人工声明）`。
3. **判据静默单独一类。** 它红的是「没人看」，不是数据；混进数据问题里，会让人去洗一批本来没错的数据。

行级变化按 **编号比集合**，不比条数：5 对 5 可能是一换一。老台账只有条数没有编号时（T22 之前），事件标 `baseline: true`，不假装「新增 0」。

## 五、页面上的数字从哪来（不重算）

| 页面元素 | 来源 |
|---|---|
| 未处理事件 / 事件流 | `/v1/alerts`（`gov_alert`，`state <> closed`） |
| 违约行构成（环形） | `/v1/obs/runs`：每道判据最近一次 `red_count` |
| 各判据红行趋势（三条） | 同上，各自最近 6 次；**不做「合计」**——各判据运行频率不同，合计是假线 |
| 整改单 | `/v1/remediation_orders` |
| p95 / 新鲜度 | `/v1/obs/summary` |

页面不许自己写条件、自己算判据：那是第二套口径，`DOC-60` 已经证明两套口径迟早对不上。

## 六、推送：先落投递箱，再谈通道

`raise_alerts.py` 的顺序是 **判据 → 台账 → 事件 → 通道**，任何一环可单独重跑。

- 默认不外发：事件落 `gov_alert`（页面就是投递箱），终端写明「未配置外部通道，N 条已落投递箱」；
- `--webhook=<url> --channel=feishu|dingtalk|json` 才外发；**外发失败不当作已推**，错误写进 `detail.delivery = {channel, ok:false, error}`，事件仍留着；
- 没有配飞书地址，所以现场演示走的是投递箱路径——这一点在页脚写清楚，不假装推过。

## 八、没做什么

- **没有真值班表/升级链**（谁 30 分钟没认领就找主管）——先有告警没有处理人，比没有更糟，这一条仍成立；
- **没有按客户/按表的阈值**：静默统一 24 h，是拍的；
- **没有实时推送**：靠人跑 `raise_alerts.py`（或接巡检），不监听数据库变更；
- **没有告警抑制窗口**（同一批行在 10 分钟内反复扫不会重复推，是因为 dedup，不是因为窗口）；
- **没有把事件写回作业页**：作业页仍只读原始数据，两个页面靠 `/v1/alerts` 关联（`check_id` 可回到台账）。

## 九、答辩三问

**问：为什么不用 Grafana / 现成监控？**
答：它们能画 `red_count`，画不出「这件事第几轮、谁认了、为什么关」。这里的核心不是图表，是**事件的状态机**和**关闭的举证责任**。

**问：为什么不直接把判据输出当告警？**
答：判据输出是「一次运行的快照」，告警是「一件持续存在的事」。两者混在一起，就会每次运行都推一遍——刷屏和没有告警是同一个结果。

**问：页面为什么不给关闭按钮？**
答：按钮会把「关掉」和「修好」变成同一个动作。这里的关闭只有一种合法理由：同一道判据复跑归零。
