# 收口演示：认领一次、补一行、看红数降一格、再复原

> DOC-67 ｜ 2026-11-27 ｜ 对应提交见文末

## 一、这一脚本回答的问题

T23/T24 证明了两件事：判据红了会变成事件、页面上的数字是「现在」的。没证明第三件——**有人动手之后，系统跟得上吗**。

「跟得上」拆成三条，缺一条演示就站不住：

1. 有人敢认领：事件从 `open` 变 `acked`，责任方落到具体人，而不是停在「待指派」；
2. 变化看得见：产线补一行，违约 362 → 361，页面上的合计 367 → 366，趋势那一条 `−1`；
3. 退得回去：这一行退回 NULL，362 回来，且整表与开始时**逐字一致**——演示不是改数据。

`scripts/demo_closeout.py` 一条命令把三段连起来，默认**全程可回放**。

| [3] 预演 | 拿 `md_station` 的「产线A」在内存里试算 | `(产线A, 第1工位)` 唯一命中 `S-A01` | `WO-2026-0001 1号工位 → S-A01`（查字典，不反推设备） |
| [4] 修复 | `UPDATE biz_work_order SET prod_line='产线A'` + 复跑判据（写台账） | 362 → 361，且只少这一条编号 | `361`，消失 `wo_station_identity#WO-2026-0001`，无新增；判据 `exit 1`（仍红） |
| [5] 复原 | `prod_line` 回 NULL + 复跑 | 362，指纹与 [1] 相同 | `362`，指纹 `df7c564b4185077b`，编号集合 362 条逐条一致 |

两处机器可读的证据：`--json=<path>` 落一份摘要（基线 / 修复 / 复原三段的行数、编号集合摘要、整表指纹），`--shot=<path>` 在「已修复」那一瞬间截一张中控台。

## 三、为什么必须跑真库，又必须复原

**真库**：中控台读的是运行台账（`gov_check_run`），不是内存里的判据结果。要让页面从 367 变成 366，只能真写那一行、真跑一次判据、真落一行台账。改一个假的 JSON 再截图，就是自欺。

**复原**：362 是全部文档、README、截图共用的基线。不复原，第二天所有人都在解释「为什么文档写 362、库里是 361」。

**复原怎么才算证明了**：不是「把数字改回去」，而是三样同时相等——

- 整表指纹：`biz_work_order` 全 60 行按 `wo_no` 排序、全列 JSON、sha256 前 16 位；
- 编号集合摘要：362 条违约编号排序后取 sha256（只比条数会漏掉「走一行、来一行」的一换一）；
- 复原后复跑的违约数。

`verify_demo_closeout.py` 的 V3 就是这三条。

## 四、那一行是假设，不是真相

`prod_line='产线A'` 是演示取值，不是这张工单的真实归属。脚本证明的只有一件事：**补上 `prod_line` 之后，判据按 `md_station` 字典认得出 `(产线A, 第1工位)`**。

不做反推的理由在 DOC-62：拿 `md_device.work_station` 反推只对 20/60，40 张与设备台账矛盾（WO-0002 写「2号工位」，它那台 CX-102 却在产线A-01）。用一条同样可疑的线去修另一条，再写成事实，就是替客户编数据。脚本在 `[3]` 那一步把这句打印出来，答辩照读，别说成「我们修好了数据」。

## 五、痕迹：台账两行、轮次 +1

彩排不是零成本，代价写在台账上：

- **每次彩排写两行 `station_contract`**：`361`（修复段）、`362`（复原段）。跑一次巡检再加四行（三判据 + 扫描自检）。不想留痕就 `--no-record`——但页面也不会动，那就不是「看得见的演示」。
- **事件 `seen_count` +1**（13 → 14）。`新增` 仍是 0，因为巡检顺序是「判据 → 扫描」：扫描比的是最新两行（362 vs 362），那一行「回来」被新的一轮盖住。**如果只跑扫描、不先跑判据，它会当成「新增 1 行」推一次**——这是台账先后的影响，不是 bug，也不是我们能「修掉」的：比的是轮次，不是真相。
- **文档不写死轮次**。`seen_count` 只会涨；「各 6 轮」「各 9 轮」这种写法两周后就是错的。DOC-65/DOC-66 与手卡已改成不写具体轮次的表述。

## 六、顺手补的洞：趋势线看不见「1 行」

彩排时发现的：页面合计从 367 掉到 366、数字变了，**趋势线还是平的**。

原因是纵轴从 0 起（`v / max`）：1 行 / 362 ≈ 0.3%，落在 34px 高的图里约 0.1px。要「看得见」，最省事的做法是把纵轴拉到 `min..max`——那是把噪音画成悬崖：1 行的变化会占满整张图，看的人会以为问题翻了倍。

所以不改纵轴，改写法：数字右侧加一列**「较上一次」**，`−1 / ±0 / +n`（相差 0 写 `±0`，只有一次运行写 `—`），副标题写明「纵轴从 0 起，所以 1 行的变化图上几乎看不见，看右端『较上一次』」。`verify_console.py` 加 C7c/C7d 两条锁住。

## 八、没做什么

- **没有无人值守**：仍是「有人敲一条命令」。定时调度不在本轮。
- **没有「客户补数据」的写入路径**：后端不写业务表，全仓库只有这一处写 `prod_line`，且必在 `finally` 复原；`--keep-ack` 只为演示存在，真环境认领后不该还原。
- **只演示了工单契约的一行**：缺陷表 302 行走同一判据、同一字典，演示一遍等于一样，重复没有信息量。
- **`--json` 摘要里的编号集合只存摘要**：362 条全写进去是 100 KB 垃圾，摘要够比对。

## 九、答辩三问

**Q：你们是不是改数据了？**
改了一行、跑了一次判据、又改回来。整表指纹前后一致（`df7c564b4185077b`），违约编号 362 条逐条一致。这一行是演示假设，不是这张工单的真实归属——真实归属要产线写，我们不反推。

**Q：那到底修好了吗？**
没有。362 一条没少，两条事件仍在。这一步只证明一件事：**补上字段，判据认得出；判据认得出，页面跟得上**。归零、复跑、事件自动关闭，才叫修好。

**Q：认领和关闭有什么区别？**
认领（`acked`）只是「有人接了」，数字不动、事件不关；关闭（`closed`）只认同一道判据复跑归零，且关闭原因不许写「已修复」——修复由复跑证明，不由人声明。

## 用法

```
python -X utf8 scripts/demo_closeout.py                 # 全流程，结束复原
python -X utf8 scripts/demo_closeout.py --dry-run        # 只打印计划
python -X utf8 scripts/demo_closeout.py --keep-ack       # 认领留在页面上（正式演示用）
python -X utf8 scripts/demo_closeout.py --shot=out/ui/console-fix-visible-1280.png
python -X utf8 scripts/verify_demo_closeout.py           # V1–V6，独立查库核对
```

退出码：`0` 每段都对得上且已复原 / `1` 有断言不符（已尽力复原）/ `2` 崩了或复原失败（先查 `prod_line`）。
