# 告警出站与飞书判决（DOC-71）

> 一句话：飞书**自建应用**这条路在「豆包账号」这个租户下被判死（`21001`），代码没有缺陷；改走**群自定义机器人 webhook** 把「判据红了」真的推到群里，实测红 6 → 推 1 条 → 复原 5，客户库指纹逐字不变。

## 一、这一篇答哪三个追问

1. **「飞书上次配到一半，现在什么情况？」** —— 代码停在 W2（能连上、只回执），后台配了机器人能力和发布，但换 `tenant_access_token` 一直 `21001`。
2. **「是不是我们哪一步没点对？」** —— 不是。三组对照实验把「凭据填错」这条路彻底排除；官方客服回复也确认是平台接入管控策略，不是误判。
3. **「那告警还能不能推到群里？」** —— 能，但只能单向：群自定义机器人 webhook 不经过应用凭据体系，不受这次管控限制。代价是不能收消息、不能点按钮。

## 二、判决过程（别再重跑一遍）

同一接口 `POST /open-apis/auth/v3/tenant_access_token/internal`，同一时刻，只换凭据：

| 用的凭据 | 返回 |
|---|---|
| `.env` 里真实的一对（`cli_…dd04`） | `21001 Access denied due to platform policy` |
| 同一个 app_id + 乱写的 32 位 secret | `10014 app secret invalid` |
| 乱写的 app_id + 乱写 secret | `10014 app id not exists` |
| 同一对凭据换 `app_access_token/internal` | 同样 `21001` |

读法：**app_id 真实存在、secret 与它一一匹配**，两关都过之后才命中 `21001`。所以问题不在填错，而在应用/租户层面被拒。

排除掉的四类常见原因：

- **网络不通**：不带 token 请求 `bot/v3/info` 能拿到网关的 `99991661`，请求到得了飞书。
- **IP 白名单**：官方定义该错误码是 `99991401`，并且明确写「IP 白名单对 access_token 相关接口不生效」。
- **版本没发布**：开发者后台顶部显示「当前修改均已发布」，应用状态「已启用」，机器人能力已添加。
- **权限不足**：权限不够报的是 `99991672`，不是 `21001`。

客服回复原文（2026-11-27 12:4x）：

> 您好，为更好地保障您账号下数据的安全与访问可控，平台近期升级了接入管控策略，给您带来的不便敬请谅解。本次升级不影响豆包产品功能的正常使用，如需进一步协助，欢迎随时联系我们。

翻译：这是**账号级的接入管控**，不会为单个应用放开；「不影响豆包产品功能」等于说，被限制的是第三方/自建应用通过 OpenAPI 取数。

结论三条，写在这里免得以后反复试：

1. 在这套账号（`@豆包账号`）下，**自建应用换不到 tenant token，发不出卡、收不到消息、点不了按钮**。
2. 权限、事件订阅、发布版本这些「配没配」都不再是变量，**配满也一样 `21001`**。
3. 换独立企业租户建自建应用是唯一恢复交互的路径，属于换账号，不是改配置；按「不影响演示就冻结」的口径押到答辩之后。

## 三、替代通道：为什么群机器人能过

群自定义机器人的入口是 `open.feishu.cn/open-apis/bot/v2/hook/<id>`（域名同 open.feishu.cn），一条 POST 就完事：**不需要 `tenant_access_token`、不校验应用权限、不受应用策略管控**。这就是它能在 `21001` 之下继续工作的原因。

能力边界必须说清楚，演示时别说过头：

| 能力 | 自建应用（被判死） | 群自定义机器人（在用） |
|---|---|---|
| 往群里发文本/卡片 | 要 token | **可以**，一条 POST |
| 收群消息（`im.message.receive_v1`） | 要 token + 订阅 | 不行 |
| 卡片按钮回调（`card.action.trigger`） | 要 token + 订阅 | 不行 |
| 私聊推送、按人发 | 要 token | 不行 |

所以它只承担一件事：**治理结论出站**——红了、有人该动了，群里响一声。原来飞书 W4–W10 想做的那套「收消息 → 回执卡 → 点按钮跑诊断 → 原地改卡」，在换租户之前没有地基。

## 四、两个坑：关键词 19024 与正文前缀

群机器人的安全设置选了「自定义关键词」（关键词＝`判据`），发消息时正文必须包含它，否则：

```
无关键词 -> code=19024 msg=Key Words Not Found
含关键词 -> code=0     msg=success
```

这两条是实测出来的，不是推的：先发一条含「判据」的自检消息（`success`），再故意发一条不含的（`19024`），两发对撞才敢确定关键词就是「判据」。

处理方式**没有**让他去群设置里改关键词，而是把关键词写进正文：`raise_alerts.py::deliver()` 的推送正文前缀从 `数据治理中控台` 改成 `数据治理中控台 · 判据告警`。理由：关键词是群侧配置、正文是代码侧产物，改动落在代码里能进 diff、能进单测视野；改群设置则是一次没人记得住的手工动作。

## 五、`.env` 注入：为什么加 `_load_dotenv`

原来 `raise_alerts.py` 只读 `os.environ`，`.env` 写了也不生效（`patrol_hourly.py` 的设计是「凭据从环境继承、仓库不存地址」）。这次补了一个最小读取：

```python
def _load_dotenv(path: Path) -> None:
    """把 .env 里尚未存在的键补进环境；显式导出的环境变量优先。"""
```

三条约束，缺一条就会出别的问题：

1. **只补缺**，不覆盖：显式 `$env:FDE_ALERT_WEBHOOK=...` 永远赢，方便临时切到别的群验证。
2. **不引第三方依赖**：手写十几行，不为了读 `.env` 引进 `python-dotenv`。
3. **地址只在本机 `.env`**：`.gitignore` 第 6 行覆盖 `.env`，仓库里永远没有 webhook 明文，`verify_schedule.py` 的 S5 也继续守着「仓库无地址」这条。

副作用一条，提前记下：计划任务 `FDE-Patrol` 每 30 分钟跑 `patrol_hourly.py` → `patrol.py` → 判据 → `raise_alerts.py`，现在 `raise_alerts` 自己会读 `.env`，所以**无人值守时新红也会进群**。这是能力不是 bug，但演示前要知道群里可能先出现一条非预期告警。

## 六、实测：红 6 → 推 1 条 → 复原 5

手法借 T25 的「造一次变更再复原」，但方向相反：**新增一行脏数据**逼判据多出一条，推到群里，再删掉复原。

| 步骤 | 结果 |
|---|---|
| 基线（插之前） | 302 行，`max(rec_id)=9001`，脏行 5 条 `[4,5,6,8,10]`，全表指纹 `52c0a26342c53a39b9df94c292c653fb` |
| 插一行 `rec_id=9002`，`conf_pct=120`（越界） | 302 → 303 行；指纹 `8bccfcde08c2adb4b01cbd492e648f7d` |
| `check_defect_fields.py` | 红 **6** 行，台账 `run_id=197`，exit 1 |
| `raise_alerts.py` | `[推] 缺陷记录字段越界或空批次：6 行（新增 1）` → `已外发 1 条 → feishu`；台账 `run_id=198`（`alert_sweep`，`channel=feishu`，`pushed_events=1`，无 errs） |
| 群侧 | 收到 `数据治理中控台 · 判据告警 / [1] 缺陷记录字段越界或空批次：6 行（新增 1）（质量工程师）`，用户已确认 |
| 删 `rec_id=9002` | 303 → 302 行，`max(rec_id)` 回 `9001`，指纹回 `52c0a26342c53a39b9df94c292c653fb`（**逐字相同**） |
| 复跑判据 | 红 **5** 行，台账 `run_id=199`，回基线 |
| 复跑中控台 | 三条全部 `[记]`，`新增 0`，不再推 |
| 违约行合计 | 362 + 5 + 40 = **407**，未变 |

两个细节值得记住：

- 推不推由**编号集合差**决定，不是由条数决定。`9002` 是新编号 → `新增 1` → 推。同一批红复跑只涨 `seen_count`，所以平时那三条一直是 `[记]`。这解释了为什么「不推」不代表「没红」。
- 复原验证用的是**全表指纹**，不是行数。行数回到 302 只能证明删掉了一行，指纹逐字相同才证明删的是那一行、且没碰别的行。

## 七、演示 60 秒话术

> 「前面九条判据跑出来的结果，不只是留在网页上。今天上午我做了一次：往缺陷表插一行置信度 120 的记录，判据当场从 5 行变 6 行，中控台按编号集合算出『新增 1』，把这条推到治理群里——群里的消息时间、这条数字、和页面上的 6 行是同一份数据。然后我把那行删掉，判据回 5 行，指纹和插入之前一字不差。这中间没有人工复制粘贴。」

三条禁说：别说「飞书机器人已经接好可以对话」；别说「点按钮就跑诊断」（没有按钮）；别说「告警会每天定时盯人」（计划任务只在已登录时跑、休眠不跑）。

## 八、没做什么（明确不算差一点）

- **自建应用那条线没有救活**：`21001` 是账号级策略，代码侧无解，等换租户。
- **没有实现签名校验**：群机器人安全设置用的是关键词，不是签名；要上签名得另算 HMAC，本机演示不需要。
- **没有做卡片样式**：现在推的是纯文本，因为文本最不容易踩关键词与格式的坑；带按钮的卡片本来也点不动（没有回调）。
- **没有给计划任务加工作时间开关**：现在 24 小时都可能在有新红时发群。
- **W4–W10 全冻结**：去重表进 schema、`iter_events` 接图、`operator_id`、表单签名、二次点击，一条都没动。

## 九、答辩三问

1. **「你怎么知道不是你们代码写错了？」** —— 三组对照：真凭据 `21001`、错 secret `10014 secret invalid`、错 app_id `10014 id not exists`。凭据校验通过后才被拒，说明是平台侧判定。
2. **「为什么不用飞书官方机器人？」** —— 用了，是群自定义机器人；不能用的是「自建应用 + OpenAPI」，因为该租户被策略管控。两者不是同一个东西。
3. **「这条通道的价值是什么？」** —— 它把「判据红了」这件事从页面搬到有人看的地方，而且**推的是编号集合的差**：新红才叫醒人，同一批红不重复刷屏。
