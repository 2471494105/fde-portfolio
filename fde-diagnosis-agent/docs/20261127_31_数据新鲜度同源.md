# 数据新鲜度同源：页面与判据读同一份登记（T32）

- 日期：2026-11-27
- 状态：已完成并实测（文档编号 `DOC-73`）
- 涉及：`data/mapping/freshness_map.json`（新）、`scripts/check_freshness.py`（新）、`scripts/patrol.py`（6 → 7 道）、`mock-mes/api/obs.py`（改读 json）、`scripts/verify_schedule.py`（S3 措辞）
- 一句话：**新鲜度从「KPI 上看得见」变成「判据在管、台账有记录、巡检每天跑」，而且页面与判据只有一份清单。**

## 一、这一轮要解决的问题

上一版的新鲜度只做到了「看得见」：

1. `mock-mes/api/obs.py` 里写死 9 张表的清单，中控台 KPI 显示「陈旧 4 表 / 未来 1 表」；
2. 没有任何判据脚本、没有 `gov_check_run` 记录、不在 `patrol.py` 里——**它不属于「判据体系」**；
3. 客户只要问一句「这 4 张哪天变 5 张，谁会告诉你」，只能答「我下次看页面」。

更麻烦的是：判据要管它，就得在 `fde-diagnosis-agent` 里再抄一份「表-时间列」清单。两份清单会各自漂移，最后出现「页面绿、判据红」——这正是上一轮花了很大力气消灭的第二套口径。

## 二、做法：一份登记 + static 标记 + F1/F2

**单一源**：`data/mapping/freshness_map.json` 只登记四件事——表名、事件时间列、`kind`（业务/治理/观测/主数据）、`static`（这份种子数据的时间轴会不会走）。页面和判据都读它：

- `mock-mes/api/obs.py::load_freshness_spec()` 读绝对路径 `../../fde-diagnosis-agent/data/mapping/freshness_map.json`（相对 `mock-mes/api/`），**读失败直接 `RuntimeError`**：不静默回落到内置副本，否则等于又开了一条口径；
- `scripts/check_freshness.py` 读同一份，阈值也取 `default_max_age_hours`（24），页面 KPI 的 `threshold_hours` 同源。

**static 标记是这一轮的判断核心**：客户库是 2026 时间轴的静态种子，任何 24 小时阈值都必然判陈旧——`biz_work_order` 最近一条 2026-01-18、「7512 小时前」，这不是客户数据在漂，是**样本的身份**。所以 8 张表标 `static:true`，只有 `gov_check_run.ran_at`（判据自己在跑）按实时判：

| 表 | 时间列 | static | 判定 |
|---|---|---|---|
| `biz_work_order` / `biz_defect_record` / `biz_inspection_lot` / `biz_alarm` / `biz_repair_order` | `opened_at` 等 | true | 跳过判红（页面仍显示 age，标 static） |
| `gov_remediation_order` | `created_at` | true | 同上 |
| `md_device` / `md_station` | 无 | true | 无时间列，连「最新」都没有 |
| `gov_check_run` | `ran_at` | **false** | 真判：>24h 未跑就是红 |

**判据 F1/F2**：`scripts/check_freshness.py` 两个失败模式分开记——F1 超阈值（陈旧）、F2 时间为未来（`-834.8 小时` 不是「很新」，是脏值）。落台账时 `check_id=freshness`、`red_metric=stale_or_future_tables`、`details` 带 `ids / stale / future / static_skipped / threshold_hours`；`--no-record` 只判不记；未知参数 `exit 2`，不许当红也不许当绿。

**进巡检**：`patrol.py` 的第 7 道。判据不进巡检，就等于中控台上不存在——这是 T29 已经付过一次学费的结论。

## 三、为什么进判据，却故意不进事件流

`app/ds/alerts.py::TITLES` 里没有 `freshness`，这是**刻意**的，不是漏了：

- 一开事件，5 个表级项（陈旧 4 + 未来 1）会立刻变成 5 条常红事件。事件 3 条 → 4 条（`station_contract` / `defect_fields` / `alarm_ack` + 新鲜度），**违约行 407 → 412**；
- 客户库「命中 3 / 6 类」这句口径随即作废，还要重新解释「为什么红的是我的样本而不是数据」；
- `verify_issues.py` 的 I4（`362+5+0+40`）、手卡里的 407、录屏稿里的环形，全部要跟着改。**这些都在答辩前几天，收益远小于代价。**

所以这一轮给它的是「判据 + 台账 + 巡检」三件，不给事件。要开的前提是先满足其一：

1. 样本换成时间轴会走的（例如定时灌入当日工单），阈值才有意义；
2. 按表拆事件（哪张表陈旧就报哪张），而不是合成一个 5 项的「新鲜度」事件。

这两条都没做，也没写在「已完成」里——写在第六节局限里。

## 六、局限（这一轮没解决的）

1. **静态种子让阈值失去意义**：除 `gov_check_run` 外 8 张表都标 `static`，等于「时限类判据在这个库里只有一张表在真判」。要变成真判据，需要样本能跟着时间走，或改成「相对上一批数据」的增量判据。
2. **不拆表级事件**：现在 5 个表级项合成一个 `freshness` 判据，`details.ids` 里能看到是哪几张，但中控台上不会出现「`biz_work_order` 陈旧」这样一行。客户要求「哪张表报哪张」时，当前答案是明细在 `details`，事件在目录里不单列。
3. **阈值只有全局 24 小时**：`default_max_age_hours` 是统一值。真实项目里报警表和工单表的新鲜度要求不一样，现在做不到按表配——json 结构里留了位置（`note` 字段），没做实现。
4. **没有历史趋势**：只有台账里的 `red_count` 与 `details` 快照，没有「这张表的 staleness 怎么变」的曲线。
5. **`static_skipped` 的口径要念准**：它只统计「有事件时间列且被 static 跳过」的 6 张；`md_device` / `md_station` 无时间列，不在这个字段里。答辩被问数字时别把 8 和 6 说混。

## 七、30 秒话术

> 「新鲜度这一项，上一版只是页面上一个数字。这一轮把清单抽成一份 json，页面和判据读同一份，判据落台账、进巡检第 7 道。客户库是 2026 时间轴的静态种子，所以 8 张表标了 static——**它们陈旧是样本的身份，不是数据在漂**，我不拿这个造红。真正在真判的是 `gov_check_run`：判据自己 24 小时没跑才算红。
> 我故意没把它接进事件流：一接就会常红 5 条，把『客户库命中 3 类』和 407 的演示数字一起污染。要接的前提是样本能跟着时间走，或者按表拆事件——这两件我都没做，也不假装做了。」

三条禁说：

- 不说「新鲜度判据全绿」——它只对 `gov_check_run` 真判；
- 不说「9 张表都在监控」——8 张是 static 跳过；
- 不说「客户数据陈旧」——陈旧的是种子时间轴。

## 八、客户会问的三句

1. **「陈旧 4 表你们不管？」** ——管，但管的方式是标 static + 讲清是样本身份；真管要样本跟着时间走，那是数据接入阶段的事。
2. **「这张表 24 小时没变化，你怎么知道？」** ——`gov_check_run` 是这么判的（唯一非 static 表）；业务表的时限判据要等真实数据流。
3. **「为什么事件里没有新鲜度？」** ——因为一开会常红、污染口径；明细在台账 `details.ids`，事件化需要按表拆，属于答辩后的事。
