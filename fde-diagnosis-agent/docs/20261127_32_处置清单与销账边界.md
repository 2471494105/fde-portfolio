# 处置清单与销账边界：把 407 行变成能派工的 CSV（T33）

- 日期：2026-11-27
- 状态：已完成并实测（文档编号 `DOC-74`）
- 涉及：`mock-mes/api/app.py`（新路由 `/v1/problem/{id}/export.csv`）、`mock-mes/api/static/problem.html`（按钮 + 不代填说明）、`scripts/export_actions.py`（新）、`scripts/verify_problem.py`（P6a–P6d）
- 一句话：**判据说「有多少行」，明细页说「是哪几行」，这一轮补上「拿得走」——但销账仍然只认判据复跑归零。**

## 一、这一轮要解决的问题

T27 已经做到「事件 → 台账编号 → 目标行 → 改哪一栏」，但三件事仍然缺一口：

1. 407 行只活在浏览器里。客户要的是能贴进排班表/工单系统的清单，不是一张截图；
2. 一条事件的行可能超过页面单页上限（工位归属 362 行，页面只截前 50），客户点「带走」时会少行；
3. 「谁去做、做了什么」没有任何落点——这既是客户下一问，也是最容易被讲成「点一下就关掉」的地方。

## 二、做法：接口先出 CSV，再配一个一键导出

**接口**：`GET /v1/problem/{alert_id}/export.csv`

- 复用 `problems.problem()` 的取数（同一个函数，不写第二套 SQL），按 200 行翻页取全，**362 行不会只给 200**；
- 14 列：事件编号 / 判据 / 类别 / 严重度 / 事件标题 / 负责人 / 先做这一步 / 目标表 / 定位键 / 定位值 / 改哪一栏 / 该行原值(JSON) / 台账 run / 判据跑的时间；
- `utf-8-sig`（带 BOM），Excel 双击不乱码；未知事件 `404`，不给空表让人误以为「没问题」。

**脚本**：`scripts/export_actions.py`

```powershell
# 三条活事件合并成一份（默认落到 out/actions/待处置清单_YYYYMMDD_HHMM.csv）
venv\Scripts\python.exe -X utf8 scripts\export_actions.py

# 只导一条；未知参数 exit 2
venv\Scripts\python.exe -X utf8 scripts\export_actions.py --alert=9 --out=out\actions\alarm.csv
```

**三条口径**（写进脚本头注释，也写进页面）：

1. **只导出，不代填**：清单只写「该改哪一栏」，不写回 `acked_by` / `cleared_at`。关闭仍只认判据复跑归零；
2. **数字来自接口，不重算**：行数取 `/v1/problem/{id}` 的 `ids_total`，脚本不查库、不数第二遍——页面上写 40，导出就是 40 行；
3. **空值照原样**：原值 JSON 里 `null` 就是库里空着，不补 0、不补空串。

## 三、为什么「认领」按钮没做

这是这一轮唯一一个「想做但不能做」的动作，理由不是工期：

- **它与已定的口径直接冲突**。T27 已经写过：页面不给关闭按钮，**关闭只认同一道判据复跑归零，不认人点一下**。一个「认领」按钮最容易被讲成「已处理」，而判据并不会因为有人认领就变绿。
- **写回客户库就是代填**。`biz_alarm.acked_by` / `cleared_at` 是客户的业务事实，后端替客户写进去，与之前否决的「别名表兜底」「设备反推工位」是同一个性质的问题：看起来修好了，实际是我们替客户编了一条记录。
- **8021 这个进程根本写不进去**：它用的是 `ro_reader`（只读账号），这一条本身就是「后端只读」的设计保证。要加写入口，就得再开一个账号、一条写入路径，等于把只读承诺拆掉一半。

所以这一轮只交付「拿得走」，不交付「点一下就关」。销账的路径仍是原来的那条：**客户改了行 → 判据复跑 → 归零 → 事件自动关闭**。

## 五、踩到的两个坑（都记下来，避免下次重复）

1. **`Decimal` 不是 JSON 可序列化对象**：工单表有 `Decimal` 列，`json.dumps` 直接 `TypeError: Object of type Decimal is not JSON serializable`，表现是整条导出 `500`，而 #2/#9 却是好的——因为那两张表没有 `Decimal`。修法 `default=str`，别去改表结构。
2. **页面模板里加的是「新变量」**：`render(await res.json())` 之后再引用 `r.ids_total`，而 `main()` 里根本没有 `r`，浏览器报 `r is not defined`，页面直接显示「取数失败」。改成 `const data = await res.json()`。**顺带的坑**：无头截图要加 `--virtual-time-budget=8000`，否则截到的是「读取中…」。

## 六、乙方案（认领台账）为什么这次不做

用户提到过「要不要加认领记录」。做得到的版本是：新增 `gov_action_log`（`alert_id / claimed_by / claimed_at / note`），由一条命令行写入，页面显示「已认领 by 张三 13:20，判据未归零 → 事件仍开」。

它确实比空着强，但这次没做的原因有三条，都跟答辩有关：

1. **要多一张表 + 一条写入口**。8021 只读，写只能走命令行；表一加，`gov_*` 的迁移脚本、`verify_*` 的断言都要跟着长，估 0.4d 而不是 0.1d；
2. **口径风险大于收益**。「已认领」在演示里很容易被读成「已处理」，而判据仍然红——这恰恰是我们最不该制造的那种误会；
3. **它不影响「判据能不能认出来」这条主线**。答辩展示的是识别与复核，不是配色更丰富的状态字段。

等答辩后要做，正确的顺序是：先加 `gov_action_log`（只记录、不改事件状态），再让明细页把它和判据状态并排显示，最后才讨论「超过 N 小时未认领」升级链。

## 七、局限

1. **CSV 是快照**：导出那一刻的行数与编号，之后可能变化；清单里带了台账 `run` 与时间，据此可以对上，但清单本身不会自动更新；
2. **一行一记录，原值塞在 JSON 列**：三种目标表的列不一样（工单、缺陷、报警），为了不出现「三份不同表头的 CSV」，统一成 14 列 + 原值 JSON。要按表拆列，得等按表导出；
3. **没有权限**：任何能打开 8021 的人都能下载清单。演示环境可接受，生产要加鉴权（与「该给谁看」这件事一起做）；
4. **不含外部自检三类**：`quarantine` / `source_schema` / `source_values` 是 `scope=external`，不进客户事件流，也就不在清单里。

## 八、30 秒话术与三问

> 「这三条事件，页面能看到 407 行不对。我把它们导成一份 CSV：每行告诉你改哪一栏、原值长什么样，362 行一条不少。**但这份表不代填**——没人点『知道了』就能关掉的按钮，关不关只看判据下一轮。有人问『那谁去做』，这表就是答案；有人问『做完了吗』，答案在判据的下一行台账里。」

三句要能接住：

1. **「客户想批量改，你这表能回灌吗？」** ——能，但要他们自己改、自己回灌；我们不替客户写业务事实。回灌后跑判据归零，事件自动关。
2. **「认领呢？谁在跟？」** ——现在是导出后在他们自己的排班里跟，页面上没有认领状态；这是刻意的，见第三节和第六节。
3. **「407 行导出来谁会看？」** ——按事件分：归属 362 行是一张工位对照表的事，缺陷 5 行是个别填写错，报警 40 行是值班表的事。三件事、三个负责人，清单里 `负责人` 那一列已经分开写了。
