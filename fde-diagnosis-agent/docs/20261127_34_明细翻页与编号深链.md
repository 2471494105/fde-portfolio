# 明细翻页与编号深链：把「带得走」补成能翻、能点（T35 / T36）

- 日期：2026-11-27
- 状态：已完成并实测（文档编号 `DOC-76`）
- 涉及：`mock-mes/api/static/problem.html`（翻页条 + 「打开 #x」改深链）、`scripts/verify_problem.py`（P7a–P7d、P8a–P8c）
- 一句话：**362 行不是只能看前 50 行；点「打开 #x」落到人看的客户端页，不再落到一坨 JSON。**

## 一、这一轮要解决的两件事

README 的限制 14 写着「明细页只截前 50 行，没有翻页按钮，362 行那种要自己调 size」。这是 T27 留下的口子，客户点一遍就会问「其余 312 行呢」。

另一件更小但更影响观感：明细页每行末尾的「打开 #x」跳的是 `/v1/...?q=` 的 JSON。技术上没错，但答辩现场点进去看到一屏 JSON，观感等于「没做完」。

## 二、翻页（T35）

后端 `/v1/problem/{id}` 早就支持 `page` / `size`（`size` 上限 200），一直没接上页面。这一轮只改页面：

- URL 参数：`?alert=N&page=P&size=S`（`S` 夹在 10–200，默认 50）；
- 底部翻页条：`← 上一页` / 页码（当前页高亮、两侧各留一页、超 7 页折叠成 `…`）/ `下一页 →`，另给一个「每页 200」；
- 明确写一句「**同一页号作用于每张表**」——因为一条事件可能跨两张表（工单 60 + 缺陷 302），页号统一才是可复述的；
- 越界页给空表，总数不变（`ids_total` 仍是 362）。

实测（`alert=1`）：第 1 页 50 行工单 + 50 行缺陷；第 2 页工单只剩 10 行、缺陷继续 50 行；拍 `problem-alert1-page2-1280.png`。`verify_problem` 新增 **P7a 60 行的表第 2 页 10 行 · P7b 两页不重复 · P7c size 生效（每表取 min(总数, size)）· P7d 越界给空且总数不变**。

## 三、编号深链（T36）

- 明细页链接改成 `/app/?q=<编号>#<视图>`（客户端那一页会过滤出那一行，搜索框回填、右上「共 1 条」），旁边留一个小的 `JSON` 链接给复核用；
- 只在客户端有对应视图时才走页面：`devices / defect_records / work_orders / remediation_orders / check_runs`。报警（`alarms`）客户端没有单独视图，仍走 `page_url` / JSON——**这一点没有藏起来**，因为「加一个报警页」属于答辩后被冻结的范围。

实测：`/app/?q=WO-2026-0001#work_orders` 直接定位到 1 条工单（截图 `app-deeplink-wo-1280.png`）；`/v1/work_orders?q=WO-2026-0001` 也是 `total=1`。`verify_problem` 新增 **P8a 页面里有 `/app/?q=` 模板 · P8b 深链 200 · P8c q 命中唯一一行**。

## 四、刻意没做的

1. **没有给客户端加「报警」页**：那要新增一个视图、一段列定义与 KPI，属于视觉与页面范围的新功能，不在「补口子」内；报警明细的双空列已经在明细页按原样显示（`problem-alarm-1280.png`）。
2. **没有做「跳转到第 N 行」**：翻页是页级，行级定位靠 `q` 深链。真要「翻到第 200 行」还得加 `offset`，但演示用不到。
3. **翻页不记忆**：换事件回到第 1 页。URL 可复述，因此不做本地状态。

## 五、局限

- 翻页是「服务端分页快照」：翻到第 2 页时若判据复跑改了编号，两页可能对不上同一次运行——所以每页都显示「编号来自台账 run N」，不一致时能被看见，而不是被抹平；
- 深链依赖客户端的 `q` 精确匹配（`ilike` 包含匹配）：编号有前缀撞车时可能命中多行（例如 `WO-2026-000` 会命中一批），此时页面显示的是「共 N 条」，不会假装只有一行。

## 六、30 秒话术
