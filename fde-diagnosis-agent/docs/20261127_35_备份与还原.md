# 备份与还原：能拿出一个文件，并且证明它真能还原（T37 / C1）

- 日期：2026-11-27
- 状态：已完成并实测（文档编号 `DOC-77`）
- 涉及：`scripts/backup_db.py`、`scripts/restore_db.py`、`scripts/verify_backup.py`、`tests/`（603 条）
- 一句话：**客户问「你们改坏了怎么退回去」时，池子里以前没有东西能答；现在有一份带 sha256、带行数、能还原到校核库对账的 dump。**

## 一、为什么这是治理问题，不是运维杂活

判据回答的是「这一遍跑的时候有没有违约行」。它回答不了「你昨天把某列改了，我今天的报表跟昨天对不上，能不能退回去」。这个问题以前没有任何东西能接——`scripts/` 里只有一个一次性 `migrate_idem_key.py`。

所以 C1 的目标不是「有个备份文件」，而是**能被证明的还原**：dump 旁边必须有校验值、pg_dump 版本、六张关键表的行数与整表指纹。没有这些，「文件存在」证明不了任何事。

## 二、三个脚本的分工

**1. `backup_db.py`（只读源库，产 dump + meta）**

- 输出 `out/backup/fde_client_YYYYMMDD_HHMMSS.dump`（`-Fc` 自定义格式）+ 同名 `.meta.json`；
- meta 里：`sha256`、字节数、`pg_dump` 版本（本机 18.6）、**六表行数**、**两表整表指纹**（工单 `df7c564b4185077b` 与演示基线同口径）；
- meta 的 `source` 只留 `host / port / db`——**不落密码、不落用户名**；
- `prune` 默认保留最近 10 份（dump 与 meta 成对删）；
- 找不到 `pg_dump` 直接 `exit 2`（PATH → `PG_DUMP` 环境变量 → `E:\POSTGRESQL\bin` / `C:\Program Files\PostgreSQL\*\bin` 探测），绝不「假装备份成功」。

**2. `restore_db.py`（只还原到校核库，两道硬拦）**

- 目标库必须以 `fde_client_restore` 开头（默认 `fde_client_restore_check`）；
- **没有 `--force` 之类的旁路**：`--target=fde_client` 直接拒绝，`exit 2`。理由是「一条命令覆盖客户库」的事故率远高于它省下的时间——回车按错一次就是数据没了。真要恢复生产，走「建新库 → 还原 → 人工切连接串」，脚本只负责前半段。
- 没有 `--yes` 也拒绝（这一步会 `DROP DATABASE ... WITH (FORCE)`）；
- 文件头必须是 `PGDMP`，拿 `.sql` 冒充直接拒；
- `pg_restore --exit-on-error`：半个库不算还原；**失败也收尾**——删掉半吊子校核库，不留一个「看起来存在但其实是残骸」的库；
- 还原后立刻用同一套 `snapshot()` 取六表行数 + 两表指纹，跟 meta 逐项比；不一致 `exit 1`（还原了但对不上，和「根本没还原」是两回事）。

**3. `verify_backup.py`（V1–V7，全部通过）**

## 三、刻意没做的

1. **不提供「还原到客户库」的入口**：见上，事故率问题。恢复生产是人工切连接串的事。
2. **不做增量 / WAL 归档 / PITR**：那是生产级备份（要 `archive_mode`、归档目录、恢复演练 SOP）。演示要的是「能退回去」，不是「能退到 14:03:27 那一刻」。
3. **不做异地 / 加密 / 上传对象存储**：dump 里有客户行原值，`out/backup/` 已进 `.gitignore`；加密与异地属于交付方案里的「客户环境」章节，不在这里伪造。
4. **不进计划任务**：定时备份要有保留策略、失败告警、存储配额，现在只做「手工一条命令 + 机器验收」。

## 四、局限（现场会被问到的）

- **一致性级别是 `pg_dump` 的**：它在导出瞬间取快照，但在业务系统持续写入时，跨表时间点严格说是「同一事务快照」而非「业务语义一致」。要业务一致得停写或上逻辑复制。
- **`--no-owner` 还原**：校核库里对象归还原操作的登录角色，不重建原 owner / 权限。所以它证明的是**数据与结构**能回去，不是**权限**能回去。
- **行数 ≠ 内容**：所以才有两张表的整表指纹。指纹只覆盖 `biz_work_order`（按 `wo_no`）与 `biz_defect_record`（按 `rec_id`），其余四表只对行数——这是刻意的成本取舍，不是漏做。
- **没有「备份可用性」的持续监控**：今天是手工跑 `verify_backup.py`。真要做，得让巡检每天跑一次还原校核——那会每 30 分钟建/拆一个库，成本比收益高，答辩后再说。

## 五、30 秒话术

> 「备份这件事，光有文件证明不了什么。我做的是能验证的还原：dump 旁边有 sha256、pg_dump 版本、六张表的行数和两张表的整表指纹；还原只许落在 `fde_client_restore_check` 这种校核库，客户库那条路我没给——一条命令覆盖客户库，省下来的时间不够赔一次误操作。还原完行数和指纹对不上，脚本退 1，不会说『还原成功』。」
