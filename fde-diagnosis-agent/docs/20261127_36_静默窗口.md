# 静默窗口：不打扰人，又不能把消息丢掉（T38 / C3）

- 日期：2026-11-27
- 状态：已完成并实测（文档编号 `DOC-78`）
- 涉及：`scripts/raise_alerts.py`（`parse_quiet` / `in_quiet` / `deliver` 的 deferred 路径 / 台账 `quiet` 字段）、`tests/test_quiet_hours.py`（9 条）、`scripts/verify_quiet.py`（Q1–Q5）
- 一句话：**凌晨报红不再往群里推；但「不推」必须留痕、下一轮补推——否则静默就是丢消息。**

## 一、问题

巡检每 30 分钟一次，24 小时都在跑。判据一旦变红，凌晨三点也可能往群里丢一条。观感上是「机器人半夜发疯」，业务上是「没人看，第二天微信群里全是红」。

但「不问时间直接不推」比这更糟：消息被吞掉，没人知道曾经红过。

## 二、做法

**配置**：`FDE_ALERT_QUIET=22:00-08:00`（也支持 `--quiet=22:00-08:00` / `--quiet-off`）。空串 = 不静默，默认行为与以前逐字一致。

**窗口判定**（`parse_quiet` / `in_quiet`）：

- 严格 `HH:MM`（正则卡死）：`time.fromisoformat` 太宽容，`2200`、`22.00` 都会被它收下——而「窗口写错了却看着跑通了」等于把消息悄悄吞掉，是最坏的一种失败；
- 半开区间 `[关, 开)`：`22:00` 在窗口内，`08:00` 不在——到点就该开始吵人；
- 跨午夜（关 > 开）是正常形态，不是特例；
- **零长度窗口（`10:00-10:00`）不算静默**：不能让人用一个看起来合法的配置做出「24 小时不打扰」。

**窗口内发生什么**：

1. 事件照建（`gov_alert` 里该有几条就几条，中控台照常显示，违约行数不变）；
2. **不推**，在事件 `detail.delivery` 上写 `{"deferred": "22:00-08:00", "ok": false}`；
3. 台账那一行 `alert_sweep` 的 `details.quiet` 记下窗口名，通道写 `inbox(静默)`——「这轮为什么没消息」在台账里查得到；
4. 下一轮**窗口外**的扫描会看到 `deferred`，把这条当成「欠推」补一次（成功则清掉标记，失败留 `ok:false` + 错误）。

这一步得改两处老逻辑，两处都是原来会静默丢消息的地方：

- `upsert` 原来每轮 `UPDATE ... detail = 新 detail`，会把上一轮的 `delivery` 整块擦掉——现在更新时把旧 `delivery` 并进来；
- `deliver` 原来在 `pushed` 为空时也会 POST 一个空包（然后失败、被记成「外发失败」）；现在没有要推的直接返回，不制造假失败。

## 三、实测（`verify_quiet.py`，全部 PASS）

| 项 | 条件 | 结果 |
|---|---|---|
| Q1 | 不设窗口 | 输出无「静默」字样，台账 `quiet` 为空——行为与以前一致 |
| Q2 | 窗口内、无待推事件 | 打印「静默窗口 22:00-08:00 · 现在在窗口内」，台账 `quiet` 记下窗口 |
| Q3a | 窗口内、**有**待推事件（探针：给 `station_contract:red` 打上 `deferred`） | 打印「1 条已建事件留在投递箱」，**没有**「外发失败」 |
| Q3b | 同上 | 事件 `delivery` 仍是 `{"ok": false, "deferred": "22:00-08:00"}` |
| Q4a | 窗口外（`--now=10:00`）同一条件、死端口 | 真的尝试外发 → `外发失败` + exit 2 |
| Q4b | 同上 | `deferred` 被清掉、`ok: false` 与错误留下——**静默不等于丢消息** |
| Q5 / Q5b | `--quiet=2200` / `22.00-08.00` | exit 2 +「配置错」，不当「今天没事」 |

配套单测 `tests/test_quiet_hours.py` 9 条钉边界（含 `08:00` 该开始吵人、零长度窗口不静默）；全仓单测 603 条通过。事件仍是 3 条、违约行仍是 407——静默不改变判据结论。

## 四、刻意没做的

1. **没做失败重试 N 次 + 升级到二级接收人**：那是「通道升级链」（C2）。要一张投递状态表、重试计数、升级规则，收益在演示里讲不出一屏；答辩后单独做。现在只做「压一次、下一轮补一次」。
2. **没做按事件级别静默**（例如只静默黄色）：多一个维度就多一套配置口径，现在没需求。
3. **没做节假日 / 排班日历**：`22:00-08:00` 这种每天固定的窗口够用；真客户那套要接人力系统。

## 五、局限

- **补推只在下一轮扫描时发生**：如果事件在窗口内被复跑归零关闭，`deferred` 不会被推出去（也不需要推——它已经不红了）。要说清：静默窗口里「关掉的」不会补一条「已恢复」，这是判断而非遗漏。
- **窗口是进程本地时间**：服务器时区与客户时区不一致时，窗口按服务器走。演示单机无所谓，交付要写进部署清单。
- **不是「静默」而是「不打扰」**：事件、台账、中控台、明细页、处置清单全都在，只是群里不出声。

## 六、30 秒话术

> 「巡检 24 小时跑，但群里不该半夜响。所以我加了静默窗口：窗口内事件照建、台账照记，就是不推——并且在事件上留一个 `deferred`，窗口结束后下一轮补推一次。这样既不打扰人，也不会把消息悄悄吞掉。窗口写错（`2200` 这种）我直接退 2，因为一个看起来跑通的错误配置，代价就是消息静默消失。」
