# 判据规矩登记与「确定违约行」：把 407 拆成 5 + 402

> T41｜2026-11-27｜改动：`fde-diagnosis-agent/data/mapping/check_rules.json`（新）、`mock-mes/api/rules.py`（新）、`obs.py`、`problems.py`、`console.html`、`problem.html`、`verify_check_rules.py`（新）、`verify_console.py`
>
> 一句话：**判据有两种，混在一个数字里就说不清——一种是数据本身错，一种是我们自己推的规矩。**

## 一、为什么动这一刀

今天之前，中控台 KPI 写「违约行 407」。这 407 由四道行类判据的红行相加：工位归属 362、缺陷字段 5、状态口径 0、报警闭环 40。

问题是这 362 和 40 不是同一种东西：

- 缺陷字段那 5 行是**数据本身错**（置信度 150/−10、批次空串与缺失没分开、采集时间在未来）；
- 工位 362 行是**我方推断的业务规矩**——「一个工位号应唯一对应一条产线的工位」，客户从来没答过；
- 报警 40 行同理——「三级报警也要有人认领」，客户也没答过。

把 402 行挂在我们自己推的规矩上，却和 5 行真错混成一个 407 交出去，客户第一眼会说「你判得不对」。这不是数字错了，是**说法错了**：它应该说「5 行确定、402 行在等你回答两道题」。

## 二、三种状态 + 一个不算数的字段

`check_rules.json` 给每条判据登记四个关键字段：

| 字段 | 取值 | 作用 |
|---|---|---|
| `status` | `hard` / `assumed` / `registered` | hard = 数据本身错；assumed = 我方推断、客户未答；registered = 客户认过（**必须**带 `decided_by` 与 `decided_at`） |
| `counts_in_total` | true / false | 决定这条判据的红行算不算进「确定违约」；`assumed` 必须为 false |
| `row_kpi` | true / false | 决定进不进「行数」这一类 KPI 与环图。契约按「件」、值域按「列」、结构按「项」、新鲜度按「表」，一律 false——**混进去是换单位，不是加严** |
| `effect` | 文字 | 客户答了之后数字往哪走（工位答「只到几号工位」→ 362 不计，407→45） |

`row_kpi` 取代了 `console.html` 里原来写死的 `ROW_CHECKS` 数组。原来那份名单是第二份源：页面一份、脚本一份，第三次改一定对不上。现在页面从接口拿 `row_kpi` 过滤，名单只活在 JSON 里。

## 三、单一源怎么落地（同 `freshness_map.json` 那套）

```
fde-diagnosis-agent/data/mapping/check_rules.json     ← 只有这一份
        ↑                      ↑
mock-mes/api/rules.py     fde-diagnosis-agent/scripts/verify_check_rules.py
        ↑                      （覆盖 + 不变量 + 数字复算）
mock-mes/api/obs.py  → /v1/obs/runs（每行带 rule_status / counts_in_total / row_kpi）
mock-mes/api/problems.py → /v1/problem/{id}（多一个 rule 字段）
→ console.html（KPI 拆分、环图虚线、目录标签、事件标签）
→ problem.html（顶部横幅）
```

两条守卫：

1. **读不到就抛**，不内置兜底清单。兜底会悄悄变回第二套口径（与 `load_freshness_spec` 同一规矩）。
2. **未登记的判据不隐藏**：`status_of()` 对没登记的 `check_id` 返回 `unregistered` 且 `counts_in_total=True`——宁可多报一行红，也不让一条新判据的红在总数里静默消失。缺登记由 `verify_check_rules.py` 的 R2/R3 拦在合并前。

| 位置 | 之前 | 现在 |
|---|---|---|
| 中控台 KPI | 违约行 `407` | **确定违约行 `5`**，备注写「待口径 402：工单 362 · 报警 40」 |

明细页的横幅是这次最值钱的一处：客户从「362 行」点进来，第一句看到的是「这 362 行在等你回答工位那一题」，而不是「你们错 362 处」。

## 六、限制（写清，不藏）

1. **`registered` 一次都还没发生**。客户还没答任何一题，所以这道三态里第三态是空跑；`decided_by/decided_at` 的校验只有形式意义。
2. **数字是快照**。R4 里的 5 / 402 / 407 是 2026-11-27 客户库的数；重灌种子或客户修了数据，verifier 会红——那时改预期，不是改实现。
3. **`effect` 是手抄的**。DOC-80 里写的「407→45 / 407→367」抄进 JSON，没有程序复算；等第三层真发生了一次改动，才谈得上「复跑数字等于承诺」。
4. **`alert_sweep` 不是判据**。它是「判据有没有按时跑」的自检，登记里 `unit=checks`、`row_kpi=false`，别把它当第 11 道判据数。
5. **`unregistered` 只保护不丢红，不保证正确**。它把新判据按「计入」处理，这是保守选择；正确性仍靠 R2/R3。
6. **页面仍不重算判据**。所有数字来自 `/v1/obs/runs` 的台账 `red_count`，登记只决定"怎么显示、算不算"，不改任何一个数。

## 七、与骨架的关系

这张卡是骨架 [[对接客户的四层：业务分析·治理与v1·对齐口径·优化后交付]] 第五节 `rules.json` 草案的落地版：草案里那四个字段（`status`/`counts_in_total`/`effect`/`source`）全部用上，另加了一个草案没想到的 `row_kpi`——因为「单位不是行」这件事在草案阶段被漏了，而它是 407 与 409 的分界线。

到此第二层的出门判据补齐了最后一条：**假设与结论在页面上分开**。剩下没做的仍是那三件（客户回执、9 条倒置落不落判据、`remediation` 无样本），按「是否影响演示」继续冻结。
