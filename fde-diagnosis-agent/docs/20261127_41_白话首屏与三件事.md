# 白话首屏：把 407 收成「3 件事 / 5 行 / 2 道题」

> T42｜2026-11-27｜改：`mock-mes/api/static/console.html`（首屏重构）、`mock-mes/api/obs.py`（下发 `rule_ask`）、`fde-diagnosis-agent/data/mapping/check_rules.json`（两条 assumed 补 `ask`）、`fde-diagnosis-agent/app/ds/issues.py`（9 条首步动作改白话）+ `scripts/seed_issues.py` 同步、`mock-mes/scripts/verify_console.py`（新增 C13）、`fde-diagnosis-agent/scripts/verify_check_rules.py`（R7a 改口径）
>
> 一句话：**页面原来是给工程师看的密度，不是给老板看的。**

## 一、起点是一句质疑

「界面够不够简洁，学历不高的老板能不能轻松用」——这一条以前没有任何证据。已知的验收（`verify_console.py` 的 C 系列、`verify_check_rules.py` 的 R7）验的是「文案在不在、数字对不对」，没有一条验「不懂技术的人卡不卡」。

先把现状量出来，而不是凭感觉：`console.html` 里「判据」出现 23 次、「口径」10 次，还有契约、值域、隔离区、外部自检、事件流、台账；判据名直接上屏（`station_contract`、`alarm_ack`）；七张 KPI 里有「接口 p95 141 ms」「事件扫描 0 分钟前」「整改单未关 2 张」。这不是「稍微密」，是**读者选错了**。

## 二、先定三条能被验的判据

术语是可以穷举的，所以「看不懂」这件事能被机器挡住一部分，剩下的只能靠人。

| 判据 | 能不能自动验 | 怎么验 |
|---|---|---|
| 三秒题：首屏看出「有几件事要人动手」 | 半自动 | 首屏只允许 3 张数字卡（C13b） |
| 一句话题：知道「第一句该跟谁说」 | 不能 | 只能真人 30 秒测试，见第六节 |
| 无术语：首屏不出现工程词 | 能 | 首屏黑名单（C13a） |

「首屏」按页面结构切：目录表格以上。术语不是删掉，是**下沉**——目录灰字、明细页、折叠区都还在，专业的人点得到。这一条决定了后面所有改法：老板看到的是结论，工程师看到的是过程，同一页两种读法。

## 三、改了什么

**首屏三张卡，只回答三个问题**

- 「没人接的事」3 条（红 3 · 黄 0 · 已认领 0）
- 「真错了多少行」5 行（另有 402 行在等客户回答：工单 362 · 报警 40）
- 「卡在客户一句话上」2 道题（答完这 2 题，402 行才有结论）

原来七张里的问题类别、事件扫描、整改单、p95、新鲜度收进底部一个 `<details>` 折叠区：「给工程师的部分：判据跑没跑、接口快不快、数据新不新、整改单几张（点开）」。**指标一个没少，只是不在首屏。**

**新增「今天要客户点头的几件事」**

把 Q1 / Q2 直接摆到首屏，每题三行：问什么 → 可选哪两个答案 → 答完会怎样（362 行不算违约 / 407→45）。这道题原来只藏在备注小字里，而 402 行全卡在它后面。

题面不是页面写的，是 `check_rules.json` 里两条 `assumed` 判据新增的 `ask` 字段（`question` / `options` / `after`），由 `/v1/obs/runs` 下发。**页面不许再抄一份文案**——文案挂两份，第三次改必有一份是旧的。

**目录的第一动作改成「谁去做、做完会怎样」**

原来写「在工单里补 `prod_line`（与 `md_station` 的产线名一致），再复跑判据 J」，现在写「让产线计划员把每条记录的「产线」和「工位」填全（产线A–D 之一，工位号写数字）」，下面一行灰字补后果：「做完这一步，这 5 行就不再算错」。

9 条文案改在 Python 源头 `app/ds/issues.py`（页面读表，不读 Python），用 `seed_issues.py` 同步进 `gov_issue_catalog`——**没有在页面上另写一份**。

判据名与边界没删，改成灰字前缀「给工程师：判据 station_contract · 最大的那一类……」

## 五、取舍

- **不删术语，只下沉**。删了术语，面试官那一层就没了；下沉之后同一页能同时喂两种人。
- **不做两套页面**。两套页面意味着两套截图、两套验收、两份会过期的文案；这一版是「一页两种读法」。
- **不动任何数字**。5 / 402 / 407 的算法一行没碰，改的只有「先说什么、后说什么」。
- **KPI 从 7 张减到 3 张，代价是首屏信息量变小**：想看类别命中率、接口延迟的人必须点开折叠区。这是有意的——首屏只答「今天要不要动手」。
- **题面进 JSON 而不是页面**，代价是 `ask.options` 与 DOC-80 的正式选择题成了**两处措辞**（见限制 2）。

## 六、限制（写清，不藏）

1. **真人没测**。三秒题、一句话题只能靠一个不懂技术的人做 30 秒实测，脚本永远验不了。现在只有「无术语 + 结构」两条机器证据，**不能对外说「已验证老板能用」**。
2. **题面与 DOC-80 是两份措辞**。`ask.question/options/after` 是精简版，正式 6 道选择题在 `DOC-80`（含后果矩阵）。客户答法若与 `options` 不一致，要同时改这两处；现在没有交叉校验，只靠人。
3. **黑名单是穷举的**。新出现一个术语（比如以后加「幂等」「水位」）不会自动被拦，得回 C13a 的列表里补。
4. **明细页仍然技术密度高**，有意为之：它是「点进去看哪几行」的钻取层，不是首屏。若客户老板也会点进去，那一页还得再做一轮白话（未做）。
5. **白话不解决「信不信」**。说得再直白，客户仍会问「你凭什么说这 362 行不对」——那句只能靠口径确认单和横幅里的「依据」回答。
6. **「做完这一步，这 5 行就不再算错」是话术，不是承诺**。页面不会自动验客户改数据后归零；归零只认复跑台账。

## 七、和骨架的关系

这一版把 [[对接客户的四层：业务分析·治理与v1·对齐口径·优化后交付]] 里「v1 是提问的道具，不是交付物」落到具体页面上：首屏三件事里有一件就是「要客户点头」，而不是把 407 摆出来当成绩。

同时补了第二层最后一个缺口：**假设与结论分开**（T41）之后，这一版做的是**结论与过程分开**——老板看结论，工程师看过程。
