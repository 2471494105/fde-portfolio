# 26 条 golden path 判据设计（v2 · B 方案：锁实体与关系，不锁绝对值）

> 本表是 `eval/trajectories.py` 的判据依据。改期望先改本表，再改代码——避免"改了代码但说不清为什么"。
> 只有本表"能落"的行进了代码；"落不了"的进第 5 节缺口清单，**不许写成死配置**。

## 一、B 方案的由来

v2 初稿给 H1 写的是 `value: 58.82, tol: 0.5`。核对模型真实输出时发现它不成立：

| 调用 | 返回样本 | 1号工位误判率 |
|---|---|---|
| `query_defect_log(device_id=CX-101, group_by=station)`（golden 用的） | total 113, fp 27 | 0.5882 |
| `query_defect_log(device_id=CX-101, group_by=day,station,hour, time_from=2025-10-20)`（模型实际用的） | total 200, fp 46 | 0.5763 |

同一台设备、同一个问题，**查询参数不同真值就不同**。锁 58.82 会把查得更全的模型判错——这是 Anthropic 列的第三类坏 task：判分不公，正确答案需要未明示的实现细节。

**B 方案**：断言只写"在两种口径下都成立"的事实。

- 锁**实体**：设备号、工位号、批次号、告警码、工单号前缀。这些来自 fixture 的固定键，不随聚合方式变。
- 锁**方向**：主要矛盾落在硬件还是算法、该不该反问、该不该给数。
- **不锁数值**，也不锁"某值必须是最高"这类关系——后者当前判据判不了（见第 5 节）。

## 二、可执行字段清单（写什么才真的有人读）

改判据前必须知道哪些字段**代码真的读**。v2 文档里的 `claims` / `relation` / `mode: any_of` 当前无人读，写进去就是死配置。

| 字段 | 谁读 | 语义 | 严重度 |
|---|---|---|---|
| `expect_intent` | `judge` | 意图必须等于 | soft |
| `expect_tools` | `judge` | 命中率 ≥100% | soft |
| `forbid_tools` | `judge` | 出现即 fail | **hard** |
| `expect_group_by` | `judge` | 维度命中率 ≥100% | soft |
| `final_keywords` | `judge` | 子串命中率 ≥50% | soft |
| `final_required` | `judge` | 全部必须出现 | **hard** |
| `forbid_words` | `judge` | 任一出现即 fail | **hard** |
| `forbid_regex` | `judge` | 任一正则命中即 fail | **hard** |
| `cite_floor` | `judge` | 出处率下限（默认 0.60） | soft |
| `unsourced_max` | `judge` | 未溯源占比上限（默认 0.20） | soft |
| `steps_range` | `judge` | 步数区间 | soft |
| `expect_ask` | `judge` | 该反问时 intent 必须 clarify | soft |
| `expect_unknown` | `judge` | 结构化"查无"事实 | soft |
| `expect_deduped` | `judge` | 建单去重三态 | soft |
| `turns` + `round_ok` | `judge` | 多轮引用不落空 | soft |

三条匹配规则（决定了关键词怎么写）：

1. **子串匹配**：`_norm(关键词) in _norm(输出)`，`_norm` 只去空白。
2. **中文数字与阿拉伯数字不等价**："三个工位" 匹配不到 "3 个工位"。拿不准就两种写法都写。
3. **`kw_rate >= 0.5` 是松阈值**：3 个关键词命中 2 个就过。关键结论点必须用 `final_required`，不能靠这个阈值。

## 四、统一新增：诊断类一律禁终态声明

H1–H5、A1–A5、T2、I8、M1、M2 共 15 条属于"判根因 + 建议处置"的场景。模型没有观测手段确认处置结果，**不能替现场宣布完工**（答辩卡 A3）。

统一加：

```python
"forbid_words": ["故障已排除", "问题已解决", "已修复", "已恢复正常"],
```

不写"维修完成""已完工"——这些词在"建议安排维修完成后复测"里合法，逐词禁会误伤。

## 五、判据缺口清单（**没有**写进代码的部分）

这五件事是想做但当前 `judge()` 判不了的。写进 `trajectories.py` 只会变成"配置写了、判据不执行"，所以一律留在这里。

### §5.1 T3 的 `unsourced_max: 0` 有洞

只在 `qty > 0` 时生效。模型如果把数字写在 `conclusion` 里、不进 `claims`，`qty=0`，这条完全不判。

`_verify_claims` 那边已经算了 `cite_stats["bare_conclusion"]`（claims 为空时 conclusion 里的裸数字数），但 `judge()` 没读。要堵住得加一条判据：`bare_conclusion > 0` → fail。

### §5.2 所有数值断言（claims 级）

`judge()` **从不检查"这个数是不是真的对"**，只检查"引用的值是否自洽"（`_verify_claims` 的 ref 校验）。所以 v2 里的 `success.claims`（58.82% / 8620h / 620h）落不进去。

真要锁数值，必须先把"查询参数指纹 → 真值"的映射做进判据（`ref` 的 `{...}` 位已经能表达参数指纹）。在那之前，B 方案就是唯一可选的口径。

### §5.3 否定语境（H5 / I8 的"不许顺着用户")

H5 用户问"是不是阈值设太严"，正确答案是"根因是标定漂移，**并非**阈值设得太严"。实测输出正含"并非阈值设得太严"。

如果按 v2 直觉写 `forbid_regex: [r"阈值(太严|过严)"]`，这句**正确答案会被判死**。否定语境用子串/正则都判不了，需要 claims 级的"结论方向"断言。

现在这两条只能靠 `final_required`（标定+漂移 / 批次+批次号）间接约束：说对了真因，就已经没有顺着用户。这是**近似**，不是判据。

### §5.4 A1 与 A5 重复

同设备、同维度、同期望批次号、同关键词。测不到两种不同能力。删或改其中一条会改变基线，待裁。

### §5.5 I1/I4/I7 的双重判定

`expect_ask: True` 已经判了"intent 必须 clarify"，`final_keywords` 又在判反问措辞。同一个行为判两遍：措辞换了（"麻烦告知设备编号"）就红，但行为其实是对的。

留着是因为它同时防"猜一个设备直接答"（那种情况 intent 也可能被判成 clarify 以外的值）。**属于冗余但无害**，本轮不动。
