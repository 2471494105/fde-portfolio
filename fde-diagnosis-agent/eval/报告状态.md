## 新格式（2026-11-16 起）

从这一份开始，报告从"一个裸数组"变成三段结构：`meta` / `summary` / `results`。
文件名同时带上时间戳与 commit：`report_YYYYMMDD_HHMM_<commit7>.json`。

`meta` 里四个字段决定两份报告能不能比：

| 字段 | 含义 | 不同就意味着 |
|---|---|---|
| `model` | 实际模型名 | 换过模型，旧分数不可比 |
| `commit` | 产生这份报告时的代码版本 | 代码不同，行为可能已变 |
| `code_hash` | `nodes.py` / `llm.py` / `schemas.py` / `workorder.py` 的内容指纹 | prompt 或枚举被改过 |
| `cases_hash` | 用例集的指纹 | 期望值被改过，分数不再同义 |

**判定规则：四个字段全同、且 `meta.evaluated` 相同，两份报告才可比。**少任何一个都只能当历史记录。

`meta.evaluated` 还顺手解决了一个老问题：以前用 `--only=` 跑子集，结果整份覆盖
`report_eval.json`，事后没人分得清那是全量还是残缺。现在报告自己写明跑了几条。

## 为什么前 7 份作废

**1. 判定器是旧的。** 这三处缺陷当时都还在：

- 没有 `_norm()`，关键词/必含项/禁用词比对时空白差异会误判
- 没有 `final_required` 严格判据，只有 H4 一条设过
- 语义正确率靠关键词命中算，否定语境会误判（"不是镜头问题"也算命中"镜头"）

**2. 没有结论正文，无法离线复核。** 每条只存了 `final_head`（结论开头一段），
想在新判定器下重算也做不到——必须重跑，而重跑就是新数据，不是"修正旧数据"。

**3. 端点不同。** 前 7 份跑在官方 `deepseek-chat`，现在主链路走中转站
（`deepseek-v4.1-flash-1017`）。同一条问题谷时 24.9 s、峰时 160.3 s，
模型换了、排队也变了，旧数字不具备可比性。

## 这些数字还能不能用

能，但只能当**历史记录**引用，不能当**当前基线**：

- README 里"8 轮 91.7%、区间 83.3%–91.7%"是 `report_round*.json` 时期的结论，
  引用时必须带上"当时 24 条、旧判定器、官方端点"三个限定
- 任何"当前通过率"的说法，只能引用 `eval/history.jsonl` 里新判定器下的记录

## 什么时候补全量

```
python eval\run_eval.py --workers=3 --only=A3,A4,A5,I1,I2,I3,I4,W1,W2,W3,T1,T2,T3,I5,I6,I7,I8,I9
```

补跑完成后 `eval/history.jsonl` 才有 25 条完整序列，那时 `report_eval.json`
会重新写成 25 条，本文件的状态表也要跟着改。

## 注意

`report_eval.json` 是 `run_eval.py` 的输出文件，**每跑一次就整份覆盖**。
别把它当累积记录——累积记录在 `eval/history.jsonl`，那是逐次追加的。
