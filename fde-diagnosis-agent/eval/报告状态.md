### `1227` → `1230`：同一行为，两次跑出 25% 与 100%

这两份唯一差别是 `_verify_claims` 里 `path_miss` 的报错文案（多印了编号和工具名），
不影响任何判定逻辑，`code_hash` 变了但行为没变。结果：

- `1227`：`path_miss=15`，15 条全部报"字段不存在"
- `1230`：`path_miss=0`，22/22 全对

15 条失败的字段名逐条核过——`cumulative_hours` / `rated_life_hours` /
`over_life_hours` / `brightness_set` / `brightness_history[1].value` /
`degradation_estimate` 在 `query_light_usage` 的返回里全都有，
`records[0].drift_px` 在 `query_calibration` 有，`conflicts[0].value` 在
`check_doc_conflict` 有，`chunks[2].text` 在 `search_manual` 有。
`_slim_result` 只截数组、不改键名。**所以不是字段名错，是证据序号 `k` 错位。**

结论：**单条锚点不能证明这片区域稳**。同一机制下一次 25%、一次 100%，
说明"模型自己数第几条工具返回"本身是随机失效源。要看真实水位必须连跑多次或跑全量，
单次 OK 是另一形式的假绿灯。

### `1238` / `1242`：证据编号改成程序印、模型抄

改动：`_payload(res, ev_no=N)` 在每条 tool 返回最前面写 `[证据 N] `，
`_load_obj` 剥掉前缀，`_verify_claims` 按证据自带的 `ev_no` 查，不再用 `ev[k-1]` 下标；
`act` 的编号从 state 已有的条数续（原来按本轮增量列表算，第二轮会从 1 重数）。

两份都是 `code_hash=03aa9d2f16ee`，连续两次 `path_miss=0`、`ref_bad=0`。

**已被证明的**：前缀没有破坏结构——`_load_obj` 不剥前缀的话会全线 `ref_bad`，
这个数归零说明剥的逻辑在工作。单测 `EvidenceNumberingTest` 6 条覆盖乱序编号、
非零起始、前缀预算、缺编号不兜底。

**没证明的**：单轮场景下证据编号恰好等于列表位置，所以这两次通过**不能证明
模型真的在抄编号**，只能证明改造没引入破坏。唯一有区分力的场景是多轮——
第二轮编号从 10 开始，模型若仍按位置数就会写 `1#`，那会被判"不在可见范围"。
**多轮端到端未验证。**

另注：`1227` / `1230` / `1238` / `1242` 四份的 `meta.commit` 都写着 `df94a36`，
但它们跑的时候工作区有未提交改动，`commit` 字段并不能代表实际代码。
判断行为只能看 `code_hash`——这正是当初加这个字段的原因：
git 只能指向已提交的边界，工作区状态得靠内容指纹。

## 新格式（2026-11-16 起）

从这一份开始，报告从"一个裸数组"变成三段结构：`meta` / `summary` / `results`。
文件名同时带上时间戳与 commit：`report_YYYYMMDD_HHMM_<commit7>.json`。

`meta` 里四个字段决定两份报告能不能比：

| 字段 | 含义 | 不同就意味着 |
|---|---|---|
| `model` | 实际模型名 | 换过模型，旧分数不可比 |
| `commit` | 产生这份报告时的代码版本 | 代码不同，行为可能已变 |
| `code_hash` | `nodes.py` / `llm.py` / `schemas.py` / `workorder.py` 的内容指纹 | prompt 或枚举被改过 |
| `cases_hash` | 用例集的指纹 | 期望值被改过，分数不再同义 |

**判定规则：四个字段全同、且 `meta.evaluated` 相同，两份报告才可比。**少任何一个都只能当历史记录。

`meta.evaluated` 还顺手解决了一个老问题：以前用 `--only=` 跑子集，结果整份覆盖
`report_eval.json`，事后没人分得清那是全量还是残缺。现在报告自己写明跑了几条。

## 为什么前 7 份作废

**1. 判定器是旧的。** 这三处缺陷当时都还在：

- 没有 `_norm()`，关键词/必含项/禁用词比对时空白差异会误判
- 没有 `final_required` 严格判据，只有 H4 一条设过
- 语义正确率靠关键词命中算，否定语境会误判（"不是镜头问题"也算命中"镜头"）

**2. 没有结论正文，无法离线复核。** 每条只存了 `final_head`（结论开头一段），
想在新判定器下重算也做不到——必须重跑，而重跑就是新数据，不是"修正旧数据"。

**3. 端点不同。** 前 7 份跑在官方 `deepseek-chat`，现在主链路走中转站
（`deepseek-v4.1-flash-1017`）。同一条问题谷时 24.9 s、峰时 160.3 s，
模型换了、排队也变了，旧数字不具备可比性。

## 这些数字还能不能用

能，但只能当**历史记录**引用，不能当**当前基线**：

- README 里"8 轮 91.7%、区间 83.3%–91.7%"是 `report_round*.json` 时期的结论，
  引用时必须带上"当时 24 条、旧判定器、官方端点"三个限定
- 任何"当前通过率"的说法，只能引用 `eval/history.jsonl` 里新判定器下的记录

会重新写成 25 条，本文件的状态表也要跟着改。

## 注意

`report_eval.json` 是 `run_eval.py` 的输出文件，**每跑一次就整份覆盖**。
别把它当累积记录——累积记录在 `eval/history.jsonl`，那是逐次追加的。
