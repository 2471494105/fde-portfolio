# eval/ 报告状态说明

这个目录里的 `report_*.json` 不是同一批条件下的产物，混用会得出错误结论。下表写明每一份能不能引用。

## 为什么这些 json 不在 git 里

根 `.gitignore` 第 39 行 `fde-diagnosis-agent/eval/report_*.json` 把整个目录的报告排除在外。11-19 及之前那些还在版本库里，是因为规则加上之前就已跟踪；**11-20 之后一份都没进过**。

这条策略要写清，否则接手的人会以为是漏提交：

| 进版本库 | 不进版本库 |
|---|---|
| 本文件（每份报告能不能引用的判断） | `report_*.json` 本体 |
| `docs/` 里的设计与结论 | `runs/` 轨迹、`eval/health_daily.log` |
| 脚本与断言（怎么算出来的） | 算出来的数字（跑一次就有一份新的） |

三个理由：

1. 报告是**现场产物**。同一 commit 在不同时段跑出的数不同（中转站排队、模型抽样），入库等于承诺「某个 commit 对应某个分数」，而那个承诺兑现不了。
2. 体积：单份 26 条的报告几百 KB，日积月累。
3. 可比性由 `meta` 的四个指纹决定，不由「文件在不在库里」决定。

代价：**换一台机器就看不到任何历史报告**，只能重跑。这也是每次引用旧数字必须同时写 `code_hash` / `cases_hash` 的原因——那两个值是判断可信的唯一依据，而这个判断本身是入库的。

### 14:05 那次撞出的两个 bug（都不是编号问题）

**一、`final_text` 跨轮污染**
第 3 轮走 diagnose，`diagnose` 不产 `final_text`，而 `verify` 里
`final_text = preset_text or _render_claims(doc)` 优先取已有值 → **UI 上显示的是
第 2 轮 knowledge 的"手册未收录"，claims 却是本轮诊断的、校验全绿。**
指标看不出来，只有人读文本才知道答的不是同一题。
修法：`intake` 清 `final_text`（和 `stop_reason` 同一个道理）。

**二、`bare_conclusion` 第一次真实触发就误伤**
第 2 轮结论是"手册中未收录。所给片段中没有 **CX-104** 的条目"——
`104` 是型号编号，被判成"写了数字却不给 claims"。
修法：判前先用 `_IDENT_RE` 剥掉 `CX-104` / `E-101` / `WO-20261116-004` /
`2026-11-14 23:14:56` / `11-07` 这类标识符，再数数字。
这和 verify 早先定的口径必须一致：**标识符不是量。**

`check_notes` / `check_retry` / `misquoted` / `cite_stats` 也一并进 `intake` 清空——
`check_notes` 会被 `verify` 并进 `misquoted`，不清就会让上一轮的回环问题在这一轮再判一次失败。

这是判据该拦的编数，不是"结构装不下多值"。

claim 形状是照数据定的，不是拍脑袋定的：

    brightness_history  [{ts, value}]
    calibrations.records[{ts, drift_px, drift_mm, result, operator}]
    defect_log.groups   [{key, count, false_positive, rate}]

共同点都是"一个标识 + 若干数值"的对象数组，所以一条 claim 装 N 对：

    {"text": "...", "ref": "query_light_usage#brightness_history",
     "items": [{"key": "2025-03-12", "field": "value", "value": 85}, ...]}

判据要求**配对成立**，不是"值在数组里出现过"。差别在 H1 上很具体：
85/80/65 可能都在数组里，但把 85 配到 09-15 就说明没在读数据，只是在凑数字。

明确没做的：**"ref 指数组时值只要出现过就放过"的宽松兜底**。
那属于关掉检查——模型能把三个数随手配三条记录，判据一律放行。
代价是模型不写 items 仍会 FAIL，但旧结构下多值本来就没有表达能力，不写是能力缺口。

## 为什么前 7 份作废

## 2026-11-19 夜（续）：引用覆盖门槛 —— 少引用不再免罚

### 为什么加

18:28 那份基线暴露了一处不一致：

| 用例 | 未溯源 | 出处率 | 裁决 |
|---|---|---|---|
| H1 | 4 条 | 78% | **失败** |
| H5 | 4 条 | 74% | **通过** |

两条的未溯源条数与出处率几乎一样，差别只在于 H1 的 4 条是**回环之后从 2 条涨上来的**，
H5 的一开始就是 4 条。触发它的是 `nodes.py` 的趋势判据（回环后变多 → 记进 misquoted）。

**"有没有发生过回环"是一个和质量无关的元事实，不该决定裁决。**

更根本的一层：`明确出处率` 早就算出来了（`run_eval.py` 的 cite_hit/cite_qty），
但它只是打印给人看的数字，**不参与 `semantic_ok`**。于是模型的处境是：

| 行为 | 结果 |
|---|---|
| 写了数字、给了可核的 ref | 通过 |
| 写了数字、没给 ref（unsourced） | **通过（只标灰）** |
| 写了数字、ref 取不到（path_missing） | 失败 |

**"少引"与"引对"在通过率上等价。** 这和 OpenAI 那篇 Nature 论文
（Kalai et al., 2026, 评分规则奖励猜测而非承认不确定）说的是同一个结构：
免罚的那一侧，模型必然往那边倒。

### 改了什么

`eval/run_eval.py` 新增两个门槛，一起进 `semantic_ok`：

- `CITE_RATE_FLOOR = 0.60`：单条用例的**可核验率**低于六成 → `cite_floor` 失败
- `UNSOURCED_RATE_MAX = 0.20`：未溯源占比高于两成 → `cite_floor` 失败
- `qty == 0` 时不判（0/0 不是 0 分，是没有样本）

**可核验率 = (cited_ok + derived_ok) / qty**，不是 `cited_ok/qty`。
算式算对的数也是可核验的（值能从算式复算，比"指到某个字段"更强）。
这一点是加门槛时踩出来的坑：第一版只认 `cited_ok`，把 35 条合法算式算成"没出处"，
实测 A5 因此被误伤——10/20 看着是 50%，加上 8 条 derived 其实是 90%。
报告汇总现在两条都印：`明确出处率`（只认 ref）和 `可核验率`（判据用的那个）。

**第二个用比例、不用绝对条数**：条数会和 qty 耦合——qty=22 里 4 条（18%）
和 qty=10 里 4 条（40%）质量差一倍，用同一条线会误伤前者
（实测 I2 出处率 89%、只因 2 条未溯源就被判失败）。

**趋势判据保留**：它抓的是"回环把 2 条变 4 条"的真退化，和绝对门槛不重叠。

`app/graph/nodes.py` 的 `SYSTEM_PROMPT` 同步改了四处：

1. 删掉 **「ref 写错比写 null 更糟：拿不准就不写字段路径，写 null」** ——
   这是 H1 弃引的**直接指令来源**，prompt 明确教过它这么做。
2. 字段路径必须来自本轮实际看到过的返回（`query_defect_log` 有 `groups`，没有 `samples`）
3. `items` 的 ref 必须指数组本身，不能指装着数组的对象
4. `expr` 只支持数字 + 四则运算 + 括号，禁 `count()/sum()/avg()`
