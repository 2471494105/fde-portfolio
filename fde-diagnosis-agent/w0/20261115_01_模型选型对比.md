# 模型选型对比：qwen2.5:7b（本地）vs DeepSeek（API）

日期：2026-11-15
实验：同一套 5 条轨迹 × 3 轮 = 15 次，同一套判据，同一套护栏。

---

| 项 | 本地 | API |
|---|---|---|
| 模型 | qwen2.5:7b（Ollama） | deepseek-chat |
| 硬件 | RTX 3060 Laptop 6GB / 16GB | — |
| 上下文 | num_ctx=4096 | 默认 |
| 温度 | 0 | 0 |
| 工具数 | 3 | 3 |
| 护栏 | 归属校验 + 存在性校验 + 时间窗校验 + 结论溯源 + 熔断 | 同 |

## 二、对比结果

| 指标 | qwen2.5:7b | deepseek-chat | 差异 |
|---|---|---|---|
| 路径命中率 | 100% | 100% | 持平 |
| 参数命中率 | **100%** | **80%** | 7b 领先 |
| 终局命中率 | **100%** | **93.3%** | 7b 领先 |
| **语义正确率** | **100%** | **73.3%** | 7b 领先 |
| 编造设备号 | 3 / 15 | 3 / 15 | 持平（都被护栏拦住） |
| fc 解析失败 | 0 / 23 | 0 / 81 | 均无格式问题 |
| 平均步数 | **0.9** | **1.5** | DS 取证更多 |
| 护栏拦截次数 | 14 | 12 | — |
| 修正重试次数 | 2 | 4 | — |
| 总耗时（15 次） | 140 s | **99 s** | DS 快 29% |
| 单次均耗时 | 9.3 s | **6.6 s** | — |

**第一个反直觉的结论：6GB 显存跑本地 7b，比调用 API 还慢。** 本地每次 9.3 秒，API 每次 6.6 秒。原因是 6GB 显存装不下 7b 全量权重（4.36GB 模型 + 4096 上下文的 KV cache），必然有部分层走 CPU。

---

## 三、7b 的 100% 要打折看

7b 拿满分，靠的是**平均 0.9 步**——几乎每条轨迹只调 1 次工具就下结论。

它为什么能过？
- H1 它一次就切 `group_by=station`，正好命中判据
- A1 一次切 `batch`
- A5 一次切 `defect_type`

**是"第一次猜对了维度"，不是"系统性地验证了维度"。**

判据只要求"期望维度在过程中出现过"，不要求"用多个维度交叉验证"。这个标准下，7b 的"一击命中"和 DeepSeek 的"多维度取证"得分相同，谁猜得准谁赢。

**7b 的高分来自取证少 + 猜得准，不是来自诊断扎实。**

---

## 四、DeepSeek 的 73.3% 要拆开看

4 次失败 = H1 三次 + I2 一次。

### H1 的三次失败：证据链不全，但结论对

- DeepSeek 的调用序列：`device_profile → defect_log(hour) → defect_log(defect_type) → defect_log(batch) → light_usage`
- **它查了时间、缺陷类型、批次，唯独没查工位分布**
- 它的结论靠 `light_usage`（8620h 超额定 8000h、亮度从 80 下调到 65）单点支撑
- 结论是对的（光源衰减），但**缺了"误判集中在 1 号工位"这个佐证**

这是**比"答错"更隐蔽的失败**：答案对、依据不硬、用户无法验证。工业场景里，一个"结论正确但证据单薄"的诊断，和"结论错误"在验收时同样过不了。

### I2 的一次失败：自动补了默认时间窗，但表述没落到"追问"上

这一次它自己按默认时间查了日志并给结论，判据期望是追问或明确说明补全逻辑。

---

## 五、两种失败模式，风险不同

| | 7b | DeepSeek |
|---|---|---|
| 主要失败形态 | 编数字、编设备号 | 取证不全、漏维度 |
| 可发现性 | 难（数字看起来合理） | 易（调用序列里能看出缺了哪一步） |
| 可修复性 | 难（模型能力上限） | 易（提示词/工具描述引导） |
| 对工业场景的威胁 | 高（输出错误信息） | 中（输出未证实的结论） |

**这一条决定了选型方向**：宁可要一个"取证多但偶尔漏维度、漏了能看出来"的模型，也不要一个"取证少、编造隐蔽"的模型。

---

## 六、判据的已知局限（诚实声明）

1. **参数判据不区分"猜对"和"验证过"**：只要期望维度出现过就给分。7b 的 100% 因此被高估。
2. **没有独立的"证据充分性"指标**：结论引用的事实是否来自 ≥2 个独立维度，目前没测。
3. **H1 的判据要求切 station，是严格标准**：DeepSeek 走的"光源用量直查"路径也能得出正确结论，但属于单点证据。判据判它失败是**符合本意的**，不是误判。
4. **轨迹只有 5 条**，每条 3 轮，样本量小，结论只能作方向性判断。

**后续要补的指标**：证据维度覆盖数（结论前用过几个独立维度）、工具选择准确率（选了该选的工具 / 全部工具）、失败归因分类。

## 七、结论与建议

### 主力模型：DeepSeek

理由：
1. **取证步数 1.5 vs 0.9**——它会主动多查，这是 Agent 该有的行为
2. **更快**：6.6 s/次 vs 9.3 s/次，本地 6GB 反而是瓶颈
3. **失败可发现**：漏维度在 trace 里看得见，可以补
4. **格式稳定**：81 次调用 0 失败

### 本地 7b：保留为离线兜底

不追求效果对等，只保证"断网也能演示完整链路"。对外表述要诚实：离线档是降级模式。

### 护栏：两个模型都必须带

DeepSeek 同样在 I1 编设备号（3/15），比例和 7b 一样。**编造不是小模型特有的毛病，是"用户没给关键参数时模型倾向于自己补"的普遍行为。**

### W1 要做的针对性改进

1. **工具描述里写死取证要求**：在 `query_defect_log` 的描述里加"判断硬件类问题方向时，必须先按工位聚合"
2. **加证据覆盖度指标**：结论前必须用过 ≥2 个独立维度，否则判证据不足
3. **把"漏维度"做成显式检查**：硬件类问题（涉及光源/镜头/标定）必须查过 `station` 聚合，否则拦截或标注
