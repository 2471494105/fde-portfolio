# W0 可行性验证报告

日期：2026-11-14
项目：fde-diagnosis-agent（视觉检测设备故障诊断 Agent）
目的：在投入 7 工具全量开发前，确认模型能力与护栏的必要性。

---

## 一、实验设计

| 项 | 设置 |
|---|---|
| 模型 | `qwen2.5:7b`（本地 Ollama，RTX 3060 6GB，num_ctx=4096，temperature=0） |
| 工具数 | 3（设备档案 / 误判日志聚合 / 光源使用） |
| 轨迹数 | 5（H1 光源衰减、A1 新物料批次、A5 单一缺陷、I1 无设备号、I2 无时间窗） |
| 编排 | 原生 tool-calling 循环，**不用 LangGraph**（避免框架掩盖模型本身的问题） |

三组对照：

- **A 组**：无护栏，基线提示词（5 次样本）
- **B 组**：无护栏，追加 2 条硬约束（"数字必须原样来自工具返回""至少核对两个维度"）（5 次样本）
- **C 组**：带护栏，基线提示词（15 次样本 = 5 轨迹 × 3 轮）

### 判据

不看"跑通"，四个维度交叉，全过才算语义正确：

- **路径**：调用序列是否为 golden path 的子序列
- **参数**：`group_by` 是否选对（station / batch / defect_type 是方向判断的入口）
- **终局**：结论是否命中期望标签
- **溯源**：结论里的百分比、设备号能否在工具返回里原样找到

## 二、结果对比

| 指标 | A 组（无护栏） | B 组（加约束·无护栏） | C 组（带护栏） |
|---|---|---|---|
| 路径命中率 | 100% | 100% | 100% |
| 参数命中率 | 100% | 80% | 100% |
| 终局命中率 | 80% | 80% | 100% |
| **语义正确率** | **40%** | **20%** | **100%** |
| 编造设备号（次） | 1 | 1 | 3 |
| fc 解析失败 | 0 / 7 | 0 / 9 | 0 / 23 |
| 平均步数 | 1.0 | 1.4 | 0.9 |
| 样本量 | 5 | 5 | 15 |

**C 组的 100% 必须带一句说明**：15 次里有 3 次（都是 I1）是模型**试图**编造设备号 CX-101，被护栏拦下后熔断转成追问，才拿到合格输出。没有护栏，这 3 次就是错误交付。

**所以真实的表述是：7b 的自主可靠性约 80%，剩下 20% 靠护栏兜。护栏不是优化项，是必需组件。**

## 三、护栏的四个坑（这部分比结论更值钱）

护栏第一版只做了"参数存在性校验 + 结论溯源"，上线后连续暴露四个问题，逐个修：

### 坑 1：存在性校验拦不住"编一个清单里存在的设备"

- **现象**：I1 用户没说是哪台设备，模型自己挑了 `CX-101` 去查。CX-101 是真设备，存在性校验直接放行。
- **根因**：校验只问"这个值合不合法"，没问"这个值该不该由模型来定"。
- **修法**：加**归属校验** —— 用户消息里没出现过任何设备号时，禁止模型自行指定 `device_id`。
- **教训**：校验要查"来源"，不只是"合法性"。

### 坑 2：用户自己输入的设备号被判成编造

- **现象**：A1 用户说了 `CX-102`，结论里提到 CX-102 却被判"无据"——因为该次工具调用被护栏拦了，返回 payload 里没有这个号。
- **根因**：溯源只在"工具返回"里找，忘了"用户输入"也是合法来源。
- **修法**：`check_traceability` 增加 `user_msg` 参数，用户输入过的设备号放行。

### 坑 3：拦住之后模型原地打转

- **现象**：I1 被拦后不追问，而是换个工具继续调，连续被拦 **6 次**，把 6 步预算烧光，最后没给结论。
- **根因**：护栏只说了"不许"，没说"那你该怎么办"。模型手上没有"向用户提问"这个动作可以选。
- **修法**：加**熔断** —— 连续 2 次被拦截即终止循环，由程序生成追问文案（"请问是哪一台？请提供设备编号"）。
- **教训**：拒绝一个动作时，必须同时给出替代路径，否则 Agent 会空转。

### 坑 4：判据把"护栏的正确行为"判成失败

- **现象**：熔断后输出的是合格的追问，但语义正确率只报 80%。
- **根因**：判据里写了 `只有模型想过编造 → 不算正确`，等于惩罚护栏救回来的那次。
- **修法**：区分"编造**尝试**"（观测模型倾向）与"编造**被执行**"（真正的交付失败），前者记指标不进失败判定。

**这一条是自测脚本自己出的 bug。教训：评测口径和护栏口径必须是同一个真源，否则两边各算一套，结果自相矛盾。**（当时 `run_w0.py` 里还留着一份重复的正则实现，已改为直接调用 `guard.check_traceability`）

## 四、结论

1. **tool calling 格式从来不是问题**：23 次调用 0 次解析失败，7b 的参数结构生成是可靠的。
2. **7b 的真实故障是"说假话"，不是"调不动"**：编设备号、编百分比、一次取证就下结论。
3. **提示词约束解决不了这个问题，反而有害**：B 组加了两条硬约束，编造照旧，参数准确率反而从 100% 掉到 80%，步数从 1.0 涨到 1.4。指令越多，7b 越容易顾此失彼。
4. **护栏能把交付正确率从 40% 拉到 100%**，代价是要接受它承担 20% 的兜底工作。
5. **护栏本身会引入新故障**（死循环、误判），必须把这些也当功能来设计和测试。

**可写进简历的一句话**：模型选型的依据不是"能不能调用工具"，而是"编造倾向有多强、需要几层护栏才兜得住"。

## 五、对后续的影响

### 7 工具场景的风险

C 组是 3 工具跑出来的 100%。工具数从 3 扩到 7（增加工单创建、文档冲突核查、物料批次、转人工），意味着：
- 工具选择空间变大，选错的概率上升
- 参数更多（工单字段、审批人、幂等键），归属校验要覆盖的字段更多
- 步数预算可能不够

**不能把 3 工具的成绩直接外推到 7 工具**。W1 上全量后必须重跑同一套判据。

### B（API 主力）还需要什么

本地 7b 带护栏已经能跑，但有两个没验证的点：
- 长上下文下的表现（7 工具 schema 全塞进 4096 ctx 会更挤）
- 复杂岔口的决策质量（工具选对率，而不只是路径合法）

API 模型（DeepSeek / 豆包 / GLM）接入需要用户提供 key，拿到后可以做同轨迹对比：**同一套 15 条轨迹，7b+护栏 vs API**，直接产出模型选型数据。
